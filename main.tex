\title{\textsc{CoEP}: Amortizing Recurring Repairs in Programming Assignments with LLM-Synthesized Repair Tools}

\author{Anonymous Author(s)}
\affiliation{\institution{Anonymous Institution}\country{Anonymous}}

% [번역] 우리는 대형 언어 모델(LLM)이 제출물마다 패치를 만드는 대신 과제 전용 수리 도구를 합성하게 하여 학생의 프로그래밍 과제를 수리하는 비용 효율적인 접근 CoEP를 제시한다. 최근 LLM 기반 프로그램 수리는 자동으로 수리할 수 있는 학생 제출물의 비율을 크게 높였다. 그러나 이 기법들은 버기 제출물마다 모델에 한 번씩 질의하므로, 많은 제출물이 "반복 수리"—같은 과제의 다른 제출물도 필요로 하는 편집—를 필요로 함에도 지출이 수강 인원과 함께 늘고 매 학기 되풀이된다. 이 논문은 커버리지를 희생하지 않고 반복 수리를 과제 단위에서 상각하는 것을 목표로 한다. 주요 도전과제는 반복 수리가 글자 그대로 반복되는 일이 드물어, 하나의 수리를 그것이 나온 프로그램 너머로 일반화하기 어렵다는 점이다. 이를 해결하기 위해 CoEP는 학급의 편집 스크립트를 군집화해 작업 쌍을 선택하고, 과제의 테스트 케이스로 검증한 오개념 이름 AST 재작성 규칙을 합성하며, 학급의 정답 프로그램과의 차분 테스트로 그 테스트 케이스를 증폭하고, 그 규칙과 hunk 단위 참조 이식으로 모든 제출물을 로컬에서 수리하며, 제출물당 질의로 넘긴 소수의 제출물에서 새 규칙을 학습한다. CoEP가 반환하는 모든 수리는 LLM이 무엇을 쓰든 증폭된 테스트를 통과한다. 11개 과제의 버기 프로그램 2,970개에 대한 실험 결과, CoEP는 그중 99.4%를 수리해 제출물당 LLM 수리의 98.9%와 참조 유도 수리의 85.9%에 대등하거나 앞섰고, 패치는 33% 작았으며, 두 LLM에서 지출은 21.3배와 27.3배 적었다. 또한 1학년 과제에서 CoEP 수리의 99.4%가 held-out 테스트 케이스도 통과해, 제출물당 수리의 97.9%보다 높았다.
\begin{abstract}
We present \tool, a cost-effective approach that repairs students' programming assignments by having a large language model (LLM) synthesize an assignment-specific repair tool rather than a patch for every submission. Recently, LLM-based program repair has substantially improved the share of student submissions that can be repaired automatically. However, these techniques query the model once per buggy submission, so their spending grows with enrollment and recurs every term, even though many submissions need ``recurring repairs''---edits that other submissions to the same assignment also need. This paper aims to amortize recurring repairs at the level of the assignment without sacrificing coverage. One major challenge is that recurring repairs rarely recur verbatim, making it difficult to generalize a repair beyond the program it came from. To address this, \tool selects worked pairs by clustering the class's edit scripts, synthesizes misconception-named rewrite rules validated against the assignment's test cases, amplifies those test cases by differential testing against the class's correct programs, repairs every submission locally with the rules and a hunk-level reference transplant, and learns new rules from the few submissions it escalates to a per-submission query. Every repair \tool returns passes the amplified tests, whatever the LLM writes. Experimental results on 2{,}970 buggy programs from 11 assignments show that \tool repairs 99.4\% of them, compared with 98.9\% for per-submission LLM repair and 85.9\% for reference-guided repair, while producing 33\% smaller patches and spending 21.3 and 27.3 times less on two LLMs; on a first-year course, 99.4\% of its repairs also pass held-out test cases, against 97.9\% of per-submission repairs.
\end{abstract}

\section{Introduction}
%=============================================================================

% [번역] 프로그래밍 과제를 위한 자동 프로그램 수리(APR)는 학생의 잘못된 제출물을 자동으로 고쳐 강의의 모든 학생이 즉각적이고 개인화된 피드백을 받게 한다. 과제의 문제 설명, 테스트 케이스, 버기 제출물이 주어지면 이 기법은 모든 테스트 케이스를 통과하는 수정 프로그램을 만들고, 그로부터 힌트나 패치를 학생에게 제시한다. 실제로 한 강의에서는 수백 명의 학생이 같은 과제를 풀고, 온라인 저지에는 같은 문제에 대한 제출물이 수천 건씩 쌓인다. 특히 이미 모든 테스트 케이스를 통과한 제출물은 수리가 활용할 수 있는 참조 프로그램 풀을 이룬다.
Automated program repair (APR) for programming assignments~\cite{gulwani2018automated,wang2018search,hu2019re,ahmed2022verifix,zhang2024pydex} automatically fixes students' incorrect submissions, so that every student in a course receives immediate and personalized feedback~\cite{yi2017feasibility}. Given an assignment's problem description, its test cases, and a buggy submission, the technique produces a fixed program that passes every test case, from which a hint or a patch is presented to the student. In practice, hundreds of students attempt the same assignment in a course, and online judges accumulate thousands of submissions to the same problem~\cite{penedo2025codeforces}. In particular, the submissions that already pass every test case form a pool of reference programs on which repair can draw.

% [번역] 이 과제를 위해 두 계열의 기법이 개발되어 왔다. 참조 유도 기법은 버기 프로그램을 구조적으로 맞는 참조 프로그램에 정렬하고 어긋나는 영역을 옮겨 심는다. 이 기법은 모델이 필요 없고 제출물당 추가 비용 없이 수리한다. LLM 기반 기법은 대신 버기 프로그램으로 대형 언어 모델(LLM)에 질의하므로, 맞는 참조가 필요 없고 더 어려운 문제까지 수리를 넓힌다. 그 결과 자동으로 수리할 수 있는 제출물의 비율이 눈에 띄게 향상되었다.
Two lines of techniques have been developed for this task. Reference-guided techniques~\cite{gulwani2018automated,wang2018search,hu2019re,ahmed2022verifix} align a buggy program with a structurally matching reference program and transplant the regions in which they differ; they need no model and repair each submission at no marginal cost. LLM-based techniques~\cite{zhang2024pydex,xia2024automated,yang2024cref,liu2024fastfixer,orvalho2025counterexample,orvalho2025mentor,yang2026morepair,dai2026learner} instead query a large language model (LLM) with the buggy program, which removes the need for a matching reference and extends repair to harder problems. As a result, the share of submissions that can be repaired automatically has seen marked improvement~\cite{zhang2024pydex,orvalho2025mentor}.

% [번역] 그러나 우리의 관찰은 제출물당 수리가 같은 수리를 거듭 다시 유도한다는 것이다. 이 연구에서 우리는 같은 과제의 다른 버기 제출물이 가장 가까운 참조 프로그램에 이르기 위해 동일한 편집을 필요로 하면 그 수리를 반복 수리라고 정의한다. 3.2절에서 보이듯 11개 과제의 버기 프로그램 2,970개 중 36.6%가 반복 수리를 필요로 하고, 1학년 강의 과제에서는 49.9%에 이른다. 하나의 오개념을 공유하는 두 제출물이 편집 전체까지 공유하는 일은 드물므로 이는 하한이다. 그런데도 LLM 기반 수리기 PyDex는 제출물마다 질의 하나를 지불해 claude-sonnet-5에서 이 프로그램들에 292.77달러를 쓰며, 프롬프트 캐싱은 그 지출의 10.2%만 덜어 준다. 참조 유도 수리는 그 지출을 피하지만, Refactory는 풀에 구조적으로 맞는 프로그램이 없는 1200 이상 등급 온라인 저지 문제에서 버기 프로그램의 54.5%만 수리한다. 결국 강의는 커버리지와, 수강 인원과 함께 늘고 매 학기 되풀이되는 모델 지출 사이에서 선택해야 한다.
However, our observation is that per-submission repair re-derives the same repairs over and over. In this work, we define a repair as \emph{recurring} if another buggy submission to the same assignment needs the identical edit to reach its nearest reference program. As shown in Section~\ref{sec:limit}, 36.6\% of 2{,}970 buggy programs from 11 assignments need a recurring repair, and 49.9\% on first-year course assignments; this is a lower bound, since two submissions that share one misconception rarely share an entire edit. Yet the LLM-based repairer PyDex~\cite{zhang2024pydex} pays one query for every submission, \$292.77 over these programs on \cs, and prompt caching removes only 10.2\% of that spend. Reference-guided repair avoids the spend, but Refactory~\cite{hu2019re} repairs only 54.5\% of the buggy programs on online-judge problems rated 1200 and above, where the pool seldom holds a structurally matching program. Consequently, a course must choose between coverage and a model spend that grows with enrollment and recurs every term.

% [번역] 이 논문에서 우리는 LLM이 제출물마다 패치를 한 번씩 만드는 대신 과제마다 과제 전용 수리 도구를 한 번 합성하게 하여 반복 수리를 상각하는 CoEP(Cost-Effective Program repair)를 제시한다. 출발점은 학급이 저지르는 실수를 담은 재작성 규칙 집합, 즉 작은 error model이 과제의 잘못된 시도 대부분을 고친다는 Singh 등의 관찰이다. 다만 그 error model은 과제마다 손으로 써야 한다. CoEP의 핵심 통찰은 error model 자체를 합성할 수 있다는 것이다. 반복 수리는 하나의 변환이고, 변환은 자신이 고치는 오개념의 이름을 단 AST 재작성 규칙으로 한 번 적어 둘 수 있으며, 빌더 LLM은 소수의 (버기, 참조) 작업 쌍으로부터 그런 규칙을 쓸 수 있다. 그러면 배포된 도구는 대부분의 제출물을 모델 없이 수리하고, 고치지 못한 것만 관례적인 제출물당 질의로 넘긴다.
In this paper, we present \tool (\underline{Co}st-\underline{E}ffective \underline{P}rogram repair), which amortizes recurring repairs by having an LLM synthesize an assignment-specific repair tool once per assignment, rather than a patch once per submission. Our starting point is the observation of Singh et al.~\cite{singh2013automated} that a small \emph{error model}---a set of rewrite rules capturing the mistakes a class makes---corrects most incorrect attempts at an assignment; their error models, however, are written by hand for each assignment. The key insight of \tool is that the error model can itself be synthesized: a recurring repair is a transformation, a transformation can be written down once as an abstract syntax tree (AST) rewrite rule named after the misconception it repairs, and a builder LLM can write such rules from a handful of worked (buggy, reference) pairs. The deployed tool then repairs most submissions with no model at all, and only what it cannot repair is sent to a conventional per-submission query.

% [번역] 그러나 핵심 도전과제는 반복 수리가 글자 그대로 반복되는 일이 드물다는 점이다. 3.2절에서 보고하듯 버기 프로그램 2,970개는 서로 다른 편집 스크립트 2,228개를 필요로 한다. 규칙 하나가 버기 프로그램 560개 중 108개를 수리하는 cAPS lOCK에서조차, 동일한 편집 스크립트를 공유하는 가장 큰 프로그램 묶음은 31개뿐이다. 따라서 빌더는 각 수리를 자신이 본 프로그램 너머로 일반화해야 하고, 빌더가 쓴 코드는 그 코드에 대한 빌더 자신의 주장을 믿지 않고도 신뢰할 수 있어야 한다. 두 번째 장애물은 강사의 테스트가 빈약하다는 것이다. 1학년 강의에서 과제당 7.4개이므로 이를 통과한 후보도 틀릴 수 있으며, 많은 후보를 탐색하는 도구일수록 문제가 아니라 테스트에 맞는 후보를 찾기 쉽다.
However, a key challenge is that recurring repairs rarely recur verbatim. As reported in Section~\ref{sec:limit}, the 2{,}970 buggy programs need 2{,}228 distinct edit scripts. Even on cAPS lOCK, where a single rule repairs 108 of the 560 buggy programs, the largest group of programs sharing an identical edit script holds only 31. Thus, a builder must generalize each repair beyond the program it was shown, and the code it writes must be trusted without trusting its own claims about that code. A second obstacle is that the instructor's tests are thin, 7.4 per assignment on the first-year course, so a candidate that passes them may still be wrong, and a tool that searches many candidates is precisely the repairer most likely to find one that fits the tests rather than the problem.

% [번역] 이 도전과제들을 해결하기 위해 CoEP는 LLM을 신뢰하지 않는 합성기로 다루고 그것이 만드는 모든 것을 실행으로 검증한다. CoEP는 네 단계를 수행한다. (1) Select는 각 버기 프로그램을 최소 편집 참조 프로그램과 짝짓고 그 결과 편집 스크립트로 학급을 군집화해 군집마다 작업 쌍 하나를 고른다. (2) Synthesize는 빌더가 오개념 이름 재작성 규칙을 쓰고 규칙이 아직 수리하지 못한 작업 쌍을 돌려받는 반례 유도 루프이며, 빌더는 입력 생성기도 써서 학급의 정답 프로그램이 다수결로 라벨링한 입력으로 강사의 테스트 T를 T⁺로 증폭한다. (3) Repair는 프리즈된 규칙 조합에 대한 너비 우선 탐색과 hunk 단위 참조 이식으로 모든 제출물을 수리하고, 기권과 과대 패치에서만 제출물당 질의로 에스컬레이션한다. (4) Learn은 에스컬레이션된 수리를 새 규칙으로 증류한다. 우리는 CoEP가 반환하는 모든 수리가 빌더가 무엇을 쓰든 T⁺를 통과하고, 규칙 탐색이 가장 얕은 조합을 반환하며, 에스컬레이션이 커버리지를 잃거나 패치를 키우지 않고, 수리가 종료함을 증명한다(4.7절).
To address these challenges, \tool treats the LLM as an untrusted synthesizer and validates everything it produces by execution. It performs four stages: (1) \emph{Select}, which pairs each buggy program with its minimum-edit reference program and clusters the class by the resulting edit scripts, choosing one worked pair per cluster; (2) \emph{Synthesize}, a counterexample-guided loop in which the builder writes misconception-named rewrite rules and is shown the worked pairs they still fail to repair, and in which it also writes an input generator whose inputs the class's correct programs label by majority vote, amplifying the instructor's tests $T$ into a suite $T^{+}$; (3) \emph{Repair}, which repairs every submission by a breadth-first search over compositions of the frozen rules and a hunk-level reference transplant, escalating to a per-submission query only on abstentions and oversized patches; and (4) \emph{Learn}, which distills the escalated repairs into new rules. We prove that every repair \tool returns passes $T^{+}$ whatever the builder writes, that the rule search returns a shallowest composition, that escalation never loses coverage or enlarges a patch, and that repair terminates (Section~\ref{sec:props}).

% [번역] 실험 결과는 CoEP가 커버리지를 희생하지 않고 LLM 기반 수리의 비용을 크게 줄임을 보여 준다. 우리는 두 빌더 claude-sonnet-5와 gpt-5.4-mini로 CoEP를 11개 과제의 버기 프로그램 2,970개에서 평가했으며, 다섯 개는 1학년 프로그래밍 강의, 여섯 개는 800~2000 등급의 Codeforces 문제이고, 참조 유도 Refactory 및 LLM 기반 PyDex와 비교했다. 수리율 측면에서 CoEP는 프로그램의 99.4%를 수리했으며 Refactory는 85.9%, PyDex는 98.9%를 수리했고, CoEP의 프리즈된 도구만으로도 모델 호출 없이 98.4%를 수리했다. 패치 크기에서 CoEP의 패치는 PyDex보다 33% 작았다. 비용에서 CoEP는 두 모델에서 벤치마크 전체에 13.74달러와 1.04달러를 써서 PyDex보다 21.3배와 27.3배 적었고, 과제당 제출물 11건과 7건 만에 일회성 빌드를 회수했다. 강사 테스트 너머의 정확성에서, 1학년 과제에 대한 CoEP 수리의 99.4%가 과제당 held-out 테스트 케이스 100개도 통과했으며 PyDex는 97.9%였다. 나아가 ablation으로 각 단계의 효능을, 뒤의 제출물로 일반성을 보인다. 학급의 처음 10%로 만든 도구는 두 코퍼스에서 마지막 4분의 1의 버기 프로그램 중 99.4%와 98.2%를 수리했다.
Experimental results demonstrate that \tool markedly reduces the cost of LLM-based repair without sacrificing coverage. We evaluated \tool with two builders, \cs and \gm, on 2{,}970 buggy programs from 11 assignments, five from a first-year programming course~\cite{hu2019re} and six Codeforces problems rated 800 to 2000~\cite{penedo2025codeforces}, against the reference-guided Refactory~\cite{hu2019re} and the LLM-based PyDex~\cite{zhang2024pydex}. In terms of repair rate, \tool repaired 99.4\% of the programs, where Refactory repaired 85.9\% and PyDex 98.9\%, and \tool's frozen tool alone repaired 98.4\% without a model call. Regarding patch size, \tool's patches were 33\% smaller than PyDex's. Regarding cost, \tool spent \$13.74 and \$1.04 over the benchmark on the two models, 21.3 and 27.3 times less than PyDex, and repaid its one-off build after 11 and 7 submissions per assignment. Regarding correctness beyond the instructor's tests, 99.4\% of \tool's repairs on the first-year course also passed 100 held-out test cases per assignment, against 97.9\% of PyDex's. We further demonstrate the efficacy of each stage through ablation, and the generality of \tool on later submissions: a tool built from the first 10\% of a class repaired 99.4\% and 98.2\% of the last quarter's buggy programs on the two corpora.

\textbf{Contributions.} We summarize our contributions below:
\begin{itemize}
  \item \textbf{Formulation:} We formulate repair for programming assignments as the synthesis of an assignment-specific repair tool---a set of AST rewrite rules together with an amplified acceptance suite---with an LLM as an untrusted synthesizer, generalizing the hand-written error models of prior work~\cite{singh2013automated} (Sections~\ref{sec:prelim} and~\ref{sec:approach}).
  \item \textbf{Technique and guarantees:} We present \tool, an algorithm that selects worked pairs by clustering edit scripts, synthesizes misconception-named rules in a counterexample-guided loop, amplifies the tests by differential testing, repairs every submission locally by searching rule compositions and transplanting reference hunks behind a gated fallback, and learns new rules from escalated repairs; we prove its soundness relative to $T^{+}$ and three further properties (Section~\ref{sec:approach}).
  \item \textbf{Evaluation:} We evaluate \tool against reference-guided and LLM-based repair on 2{,}970 buggy programs from 11 assignments, including the prevalence of recurring repairs, held-out test cases, and splits by submission order. We make \tool, the 22 synthesized tools, the 10 input generators, every prompt, and every per-submission log publicly available (Data-Availability Statement).
\end{itemize}

    tree = ast.parse(source)

\textbf{A recurring misconception.} cAPS lOCK (Codeforces 131A) asks whether a word was typed with the caps lock on, i.e., whether all its letters, or all but the first, are uppercase. Suppose a student tests the tail of the word with \texttt{s[1:].isupper()} at line~4 of Figure~\ref{fig:example}-(a). The program then fails on a one-letter word such as \texttt{"z"}, since the tail is empty and an empty string is not uppercase in Python. 108 of the 560 buggy programs submitted to this problem share this misconception. Per-submission LLM repair queries the model 108 times to rediscover the same fix, and a reference transplant must import a length guard together with the structure around it. Nor do the 108 programs share one edit: they differ elsewhere, so their edits to the nearest correct program differ too.

% [번역] 도구 합성. CoEP는 첫 수리 전에 도구를 만든다. Select는 버기 프로그램 560개 각각을 편집이 가장 적게 드는 정답 프로그램과 짝짓고 그 편집 스크립트로 프로그램을 군집화해 작업 쌍 353개를 고른다. Synthesize는 이를 빌더 LLM에 보여 주고, 빌더는 재작성 규칙의 Python 모듈로 답한다. CoEP는 규칙을 작업 쌍에 실행해 아직 수리하지 못한 쌍을 돌려주며 이를 세 라운드 반복한다. cAPS lOCK에서 claude-sonnet-5는 1.23달러로 규칙 10개를 썼다. Figure 1-(b)가 그중 하나인 slice_case_check_to_equality다. 이 규칙은 슬라이스에 대한 대소문자 검사를 찾아 빈 슬라이스에서도 성립하는 등식으로 바꿔 끼운다. 규칙은 작업 쌍 하나에서 쓰였지만 AST 위에서 진술되므로 그 패턴이 나타나는 곳이면 어디든 적용된다.
\textbf{Synthesizing the tool.} \tool builds the tool before the first repair. Select pairs each of the 560 buggy programs with the correct program it is fewest edits from and clusters the programs by these edit scripts, yielding 353 worked pairs. Synthesize shows them to a builder LLM, which answers with a Python module of rewrite rules; \tool runs the rules on the worked pairs and returns the pairs they still fail to repair, for three rounds. On cAPS lOCK, \cs wrote 10 rules for \$1.23. Figure~\ref{fig:example}-(b) shows one, \rn{slice_case_check_to_equality}: it locates a case test on a slice and splices in an equality that also holds for the empty slice. The rule was written from one worked pair but is stated over the AST, so it applies wherever the pattern occurs.

\textbf{Escalation and learning.} When both local strategies abstain, or the local patch is at least as large as the program it repairs, \tool issues one query that attaches the minimum-edit reference program; on our benchmark, this happened for 12.5\% of the submissions (Section~\ref{sec:rq-cost}). The Learn stage generalizes such repairs into new rules, which the tool keeps only if they reproduce the repair. Whichever path a repair takes, it passes $T^{+}$ (Section~\ref{sec:props}).

\subsection{Program Repair for Programming Assignments}
\label{sec:prelim-apr}

% [번역] 프로그래밍 과제 수리의 주된 목적은 각 버기 제출물을 과제의 테스트 케이스를 통과하는 수정 프로그램으로 바꾸는 것이다. 이를 위해 수리기는 모든 제출물에 대해 후보 프로그램을 반복적으로 생성하고, 검증하고, 선택한다. 우리는 과제를 사중쌍 (d, T, B, R)로 정의하며, d는 자연어 문제 설명, T = {t_1, ..., t_n}는 교수자의 테스트 케이스, B는 버기 프로그램, R은 참조 프로그램을 나타낸다. 프로그램 p가 T의 모든 테스트 케이스를 통과할 때 p ⊨ T로 쓰면 제출물은 B = {p | p ⊭ T}와 R = {p | p ⊨ T}로 나뉜다. b ∈ B를 수리한다는 것은 f ⊨ T인 수정 프로그램 f를 만드는 것이며, 테스트 케이스 일부만 통과하는 후보는 수리가 아니다.
The main aim of program repair for programming assignments is to turn each buggy submission into a fixed program that passes the assignment's test cases. To do so, a repairer iteratively generates, validates, and selects candidate programs for every submission. We define an assignment as a quadruple $(d, T, B, R)$, where $d$ represents the natural-language problem description, $T = \{t_1, \dots, t_n\}$ denotes the instructor's test cases, $B$ indicates the buggy programs, and $R$ the reference programs. Writing $p \models T$ when a program $p$ passes every test case in $T$, the submissions divide into $B = \{p \mid p \not\models T\}$ and $R = \{p \mid p \models T\}$. To repair $b \in B$ is to produce a fixed program $f$ with $f \models T$; a candidate that passes only some test cases is not a repair.

\begin{algorithm}[t]
\caption{Repairing an Assignment}\label{alg:generic}
\footnotesize
\begin{algorithmic}
\Require Description ($d$), tests ($T$), buggy programs ($B$), reference programs ($R$), local repair tool ($L$).
\Ensure Fixed programs ($F$).
\end{algorithmic}
\begin{minipage}[t]{0.5\textwidth}
\begin{algorithmic}[1]
\Procedure{RepairAssignment}{$d, T, B, R, L$}
  \State $F \gets \emptyset$
  \For{\textbf{each} $b \in B$}
    \State $f \gets \V{fail}$
    \If{$L \neq \emptyset$}
      \State $f \gets \Fn{LocalRepair}(L, b, R, T)$
    \EndIf
\algstore{generic}
\end{algorithmic}
\end{minipage}\hfill
\begin{minipage}[t]{0.48\textwidth}
\begin{algorithmic}[1]
\algrestore{generic}
    \If{$f = \V{fail}$}
      \For{\textbf{each} $c \in \Fn{Generate}(d, T, b, R)$}
        \State \textbf{if} $c \models T$ \textbf{then} $f \gets c$; \textbf{break}
      \EndFor
    \EndIf
    \State $F \gets F \cup \{(b, f)\}$
  \EndFor
  \State \Return $F$
\EndProcedure
\end{algorithmic}
\end{minipage}
\end{algorithm}

% [번역] Algorithm 1은 과제를 수리하는 일반 알고리즘을 기술한다. 이 알고리즘은 다섯 입력, 즉 설명(d), 테스트 케이스(T), 버기 프로그램(B), 참조 프로그램(R), 로컬 수리 도구(L)를 받는다. 지금은 마지막 입력 L과 관련 함수 LocalRepair를 잠시 미뤄 두자. 그 역할은 4장에서 설명한다. 기존 기법은 도구 없이(즉 L = ∅) Algorithm 1을 실행한다. 2행에서 알고리즘은 수정 프로그램 집합 F를 공집합으로 초기화한다. 그런 다음 각 버기 프로그램 b에 대해 3–10행의 루프를 반복한다. 8행에서 Generate 함수가 b로부터 후보 프로그램을 만들고, 9행은 모든 테스트 케이스를 통과하는 후보 c를 남긴다. 어떤 통과 후보를 남기는지는 기법마다 다르다(예: b에 가장 가까운 것). 마지막으로 Algorithm 1은 버기 프로그램과 그 수정 프로그램의 쌍 집합 F를 반환하며, f = fail은 수리되지 않은 프로그램을 표시한다.
Algorithm~\ref{alg:generic} describes a generic algorithm that repairs an assignment. It takes five inputs: the description ($d$), the test cases ($T$), the buggy programs ($B$), the reference programs ($R$), and a local repair tool ($L$). For now, let us set aside the last input, $L$, and the associated function, \Fn{LocalRepair}; their roles will be explained in Section~\ref{sec:approach}. Existing techniques run Algorithm~\ref{alg:generic} without a tool (i.e., $L = \emptyset$). At line 2, the algorithm initializes the set $F$ of fixed programs as an empty set. It then repeats the loop at lines 3--10 for each buggy program $b$. At line 8, the \Fn{Generate} function produces candidate programs from $b$, and line 9 keeps a candidate $c$ that passes every test case; techniques differ in which passing candidate they keep (e.g., the one closest to $b$~\cite{zhang2024pydex}). Finally, Algorithm~\ref{alg:generic} returns the set $F$ of pairs of a buggy program and its fixed program, where $f = \V{fail}$ marks a program that was not repaired.

% [번역] 프로그래밍 과제를 위한 기존 기법은 8행의 Generate 함수를 구현하는 방식에서 갈린다. 참조 유도 기법은 b를 구조적으로 맞는 참조 프로그램 r ∈ R에 정렬하고 둘이 어긋나는 영역을 옮겨 심는다. CLARA와 Sarfgen은 b를 가장 가까운 참조 프로그램에 정렬하고, Verifix는 그 정렬을 형식 검증으로 뒷받침하며, Refactory는 참조 프로그램을 리팩터링해 정렬 가능한 범위를 넓힌다. 이들은 추가 비용 없이 오프라인으로 돌지만, R에 b와 구조가 맞는 프로그램이 없으면 Generate는 후보를 내지 못한다. LLM 기반 기법은 Generate를 모델 질의로 구현한다. PyDex는 d, b, 그리고 학급에서 검색한 (버기, 정답) 예시 세 쌍으로 모델에 프롬프트하고 후보 열 개를 샘플링하며, 다른 기법들은 대화, 튜터링, 미세조정, 결함 위치 추정을 더한다. 이 기법들은 어떤 참조와도 맞지 않는 제출물을 수리하지만, 3행 루프의 매 반복이 자기 질의를 발행하므로 질의 수가 |B|와 함께 늘어난다.
Existing techniques for programming assignments differ in how they implement the \Fn{Generate} function at line 8. Reference-guided techniques align $b$ with a structurally matching reference program $r \in R$ and transplant the regions in which they differ: CLARA~\cite{gulwani2018automated} and Sarfgen~\cite{wang2018search} align $b$ with its nearest reference program, Verifix~\cite{ahmed2022verifix} backs the alignment with formal verification, and Refactory~\cite{hu2019re} refactors the reference programs to widen the range of alignable programs. They run offline at no marginal cost, but \Fn{Generate} returns no candidate when $R$ holds no program whose structure matches $b$. LLM-based techniques implement \Fn{Generate} as a model query: PyDex~\cite{zhang2024pydex} prompts the model with $d$, $b$, and three (buggy, correct) exemplars retrieved from the class and samples ten candidates, while others add conversation~\cite{xia2024automated}, tutoring~\cite{yang2024cref}, fine-tuning~\cite{liu2024fastfixer,yang2026morepair}, or fault localization~\cite{orvalho2025counterexample,orvalho2025mentor}. These techniques repair submissions that no reference matches, but each iteration of the loop at line 3 issues its own query, so the number of queries grows with $|B|$.

\subsection{Limitation of Per-Submission Repair}
\label{sec:limit}

% [번역] 우리의 핵심 관찰은 한 과제의 많은 제출물이 같은 수리를 필요로 하는데도 Algorithm 1은 그 각각을 독립적으로 유도한다는 것이다. 이 연구에서 우리는 같은 과제의 다른 버기 제출물도 필요로 하는 편집을 가진 수리를 반복 수리로 새로 정의한다. 더 정확히는, π(b)를 b로부터 AST 편집 연산이 가장 적게 드는 참조 프로그램, ε(b)를 b를 π(b)로 옮기는 편집 연산의 다중집합이라 하자(둘 다 4.3절에서 정의한다). 다른 b' ∈ B에 대해 ε(b) = ε(b')이면 b의 수리는 반복 수리다.
Our key observation is that many submissions to one assignment need the same repair, yet Algorithm~\ref{alg:generic} derives each of them independently. In this work, we newly define a \emph{recurring repair} as a repair whose edit another buggy submission to the same assignment also needs. More precisely, let $\pi(b)$ be the reference program that takes the fewest AST edit operations from $b$, and $\varepsilon(b)$ the multiset of edit operations that takes $b$ to $\pi(b)$ (both defined in Section~\ref{sec:select}); the repair of $b$ is recurring if $\varepsilon(b) = \varepsilon(b')$ for some other $b' \in B$.

Table~\ref{tab:limit} shows that 1{,}087 of the 2{,}970 buggy programs (36.6\%) across the 11 assignments of our benchmark (Section~\ref{sec:settings}) need a recurring repair, and 49.9\% on the five first-year assignments. Nevertheless, the per-submission repairer PyDex~\cite{zhang2024pydex} spent \$292.77 on \cs querying for each of them, so that a single misconception is paid for once per student who makes it. Surprisingly, the share of recurring repairs falls to 2.7\% on Codeforces problems rated 1200 to 2000, precisely where the reference-guided Refactory~\cite{hu2019re} repairs only 54.5\% of the programs. This might stem from the larger number of solution strategies that harder problems admit: each buggy program needs an edit of its own, and the pool seldom holds a program of the same structure.

One alternative is to make each query cheaper. However, this naive approach proved unsatisfactory. Prompt caching~\cite{anthropiccaching,openaicaching}, which bills a repeated prompt prefix at a tenth of the input rate, reduced PyDex's spend by only 10.2\% on \cs and 17.3\% on \gm, since output tokens account for 76.6\% of the former's spend and the variable buggy program precedes any shared content. Memoizing patches by submission text helps even less: only 8.6\% of the buggy programs are textual duplicates of another.

\subsection{Goal}
\label{sec:goal}

% [번역] 이 논문의 목표는 모델 질의를 제출물이 아니라 과제 단위로 쓰면서 과제의 모든 버기 프로그램을 수리하는 것이다. 형식적으로, 우리는 빌더 질의 수가 |B|와 함께 늘지 않는 방식으로 로컬 수리 도구 L을 합성해 아래 집합을 최대화하는 것을 목표로 한다. 여기서 LocalRepair는 Algorithm 1의 6행에 있는 훅이며, 나머지 프로그램은 8행의 Generate로 넘어간다. 그러나 이는 실제로 결코 간단하지 않다. 우리 벤치마크에서 버기 프로그램 2,970개는 서로 다른 편집 스크립트 2,228개를 필요로 하고, 반복 수리로 범위를 좁혀도 편집 스크립트 하나를 공유하는 가장 큰 묶음은 프로그램 48개(R4)에 그친다. 이러한 관찰이 우리의 접근을 동기 짓는다. 따라서 우리 연구는 두 가지 핵심 도전과제를 다룬다. (1) 수천 개의 서로 다른 편집 중에서, 빌더가 자신이 본 프로그램 너머로 수리를 일반화할 수 있는 작업 예시를 고르는 것, (2) 빌더가 쓴 코드를 그 코드에 대한 빌더의 주장을 믿지 않고 신뢰하는 것.
The goal of this paper is to repair every buggy program of an assignment while spending model queries per assignment rather than per submission. Formally, we aim to synthesize a local repair tool $L$, with a number of builder queries that does not grow with $|B|$, such that the set
\[
\{\, b \in B \mid \Fn{LocalRepair}(L, b, R, T) \neq \V{fail} \,\}
\]
is maximized, where \Fn{LocalRepair} is the hook at line 6 of Algorithm~\ref{alg:generic}; the remaining programs fall through to \Fn{Generate} at line 8. However, this is far from straightforward in practice. Across our benchmark, the 2{,}970 buggy programs need 2{,}228 distinct edit scripts, and even among recurring repairs, the largest group sharing one edit script holds only 48 programs (R4). These observations motivate our approach. Our work thus tackles two key challenges: (1) selecting, from thousands of distinct edits, the worked examples from which a builder can generalize a repair beyond the program it saw, and (2) trusting the code a builder writes without trusting its claims about that code.

Synthesize에서 빌더 LLM은 작업 쌍을 오개념 이름 AST 재작성 규칙의 Python 모듈로 바꾸고, CoEP는 테스트 케이스를 실행해 규칙이 여전히 실패하는 쌍을 돌려주며 라운드 예산까지 반복한다. 빌더는 입력 생성기도 쓰며, CoEP는 그 입력을 참조 프로그램들의 다수결로 라벨링해 T를 T⁺로 증폭한다. 뒤의 두 단계는 모든 제출물에서 돈다. Repair에서 프리즈된 도구는 규칙과 hunk 단위 이식을 시도하고 T⁺를 통과하는 후보만 받아들이며, 둘 다 기권하거나 로컬 패치가 프로그램보다 클 때만 제출물당 질의를 발행한다. Learn에서 모델은 그런 질의의 수리를 새 이름 붙은 규칙으로 일반화하고, 도구는 그 규칙이 수리를 재현할 때만 유지한다.
Figure~\ref{fig:overview} illustrates how \tool synthesizes and deploys an assignment-specific repair tool while interacting with an LLM. The first two stages run once per assignment and build the tool. Select pairs each buggy program with its minimum-edit reference program and chooses one worked pair per cluster of edit scripts, without querying a model. In Synthesize, a builder LLM turns the worked pairs into a Python module of AST rewrite rules, each named after the misconception it repairs, and \tool executes the test cases to return the pairs on which the rules still fail, up to a round budget. The builder also writes a generator of test inputs, which \tool labels by the majority output of the reference programs to amplify $T$ into $T^{+}$. The last two stages run on every submission. In Repair, the frozen tool tries its rules and then a hunk-level transplant, accepting a candidate only if it passes $T^{+}$, and issues a per-submission query only when both abstain or the local patch is larger than the program it repairs. In Learn, the model generalizes each repair obtained from such a query into a new named rule, which the tool keeps only if the rule reproduces the repair.

% [번역] CoEP의 핵심 신규성은 모델을 각 제출물의 수리에서, 오프라인으로 돌고 감사할 수 있는 평범한 코드인 도구의 구축으로 옮기는 데 있다. PyDex처럼 대신 모든 제출물마다 모델에 질의하면 비슷한 수리율에 21.3배를 더 쓴다(5.3절).
The key novelty of \tool lies in moving the model from the repair of each submission to the construction of the tool, which is ordinary code that runs offline and can be audited. Querying a model for every submission instead, as PyDex does, spends 21.3 times more for a comparable repair rate (Section~\ref{sec:rq-cost}).

\subsection{\textsc{CoEP}}

\begin{algorithm}[t]
\caption{\textsc{CoEP}}\label{alg:coep}
\footnotesize
\begin{algorithmic}
\Require Description ($d$), tests ($T$), buggy programs ($B$), reference programs ($R$), builder LLM ($M$).
\Ensure Fixed programs ($F$), repair tool ($L'$).
\end{algorithmic}
\begin{minipage}[t]{0.5\textwidth}
\begin{algorithmic}[1]
\Procedure{CoEP}{$d, T, B, R, M$}
  \State \textbf{/* Step 1. Select */}
  \State $S \gets \aux{Select}(B, R)$ \Comment{$(b^{\star}, \pi(b^{\star})) \in S$}
  \State \textbf{/* Step 2. Synthesize */}
  \State $\langle U, j \rangle \gets \langle S, 0 \rangle$ \Comment{$\eta_{\V{round}} = 3$}
  \Repeat
    \State $j \gets j + 1$
    \State $L_j \gets \aux{Synthesize}(M, d, T, S, U)$
    \State $U \gets \{(b, \WC) \in S \mid \aux{Search}(L_j, b, T) = \V{fail}\}$
  \Until{$U = \emptyset$ \textbf{or} $j = \eta_{\V{round}}$}
\algstore{coep}
\end{algorithmic}
\end{minipage}\hfill
\begin{minipage}[t]{0.48\textwidth}
\begin{algorithmic}[1]
\algrestore{coep}
  \State $L \gets \argmax_{i \le j} \aux{cov}(L_i)$
  \State $T^{+} \gets T \cup \aux{Amplify}(M, d, T, R)$
  \State \textbf{/* Step 3. Repair */}
  \State $F \gets \Fn{RepairAssignment}(d, T^{+}, B, R, L)$
  \State \textbf{/* Step 4. Learn */}
  \State $L' \gets L$
  \For{\textbf{each} $(b, f) \in F$ repaired by \Fn{Generate}}
    \State $\rho' \gets \aux{Learn}(M, b, f)$
    \State \textbf{if} $\aux{Search}(L \cup \{\rho'\}, b, T^{+}) \neq \V{fail}$ \textbf{then} $L' \gets L' \cup \{\rho'\}$
  \EndFor
  \State \Return $F, L'$
\EndProcedure
\end{algorithmic}
\end{minipage}
\end{algorithm}

% [번역] Algorithm 2는 CoEP가 과제의 수리 도구를 합성하고 제출물을 수리하는 방법을 자세히 보여 준다. CoEP는 과제 (d, T, B, R)와 빌더 LLM(M)을 받아 수정 프로그램(F)과 도구를 반환한다. 3행에서 Select 함수가 빌드 집합 S를 고른다(4.3절). 5–11행에서 CoEP는 최대 η_round 라운드로 도구를 합성한다. 각 라운드는 빌더에게 모듈 L_j를 요청하고(8행) 그 모듈이 여전히 수리하지 못하는 작업 쌍 U를 모아(9행) 다음 라운드에 돌려주며, 커버리지가 가장 높은 라운드를 남긴다(11행). 12행에서 Amplify 함수는 수용 테스트 집합 T⁺를 만든다(4.4절). 14행에서 CoEP는 프리즈된 도구 L과 T⁺로 Algorithm 1을 호출해 모든 버기 프로그램을 수리하고, 16–19행에서 모델 질의로 얻은 수리로부터 새 규칙을 학습한다. 실험에서 η_round는 3으로 두었고, 아래의 다른 모든 상수도 모든 과제에 걸쳐 고정했다.
Algorithm~\ref{alg:coep} details how \tool synthesizes a repair tool for an assignment and repairs its submissions. \tool accepts the assignment $(d, T, B, R)$ and a builder LLM ($M$), and returns the fixed programs ($F$) together with the tool. At line 3, the \aux{Select} function chooses the build set $S$ (Section~\ref{sec:select}). At lines 5--11, \tool synthesizes the tool in at most $\eta_{\V{round}}$ rounds: each round asks the builder for a module $L_j$ (line 8), collects the worked pairs $U$ it still fails to repair (line 9) for the next round, and the round with the highest coverage is kept (line 11). At line 12, the \aux{Amplify} function builds the acceptance suite $T^{+}$ (Section~\ref{sec:synth}). At line 14, \tool repairs every buggy program by calling Algorithm~\ref{alg:generic} with the frozen tool $L$ and $T^{+}$, and at lines 16--19, it learns new rules from the repairs obtained from a model query. In our experiments, $\eta_{\V{round}}$ was set to 3, and every other constant below is fixed across all assignments.

\subsection{Select}
\label{sec:select}

% [번역] Select 단계의 목표는 빌더가 학급의 반복 수리를 일반화할 수 있는 작업 쌍 집합을 고르는 것이다(3행). 이 단계는 로컬이며 모델 질의를 하지 않는다. 프로그램을 짝짓기 위해 CoEP는 AST를 비교한다. σ(p)를 p의 AST 노드 타입을 너비 우선으로 읽은 수열로 두되 최상위 문장마다 수열 σ_i(p) 하나로 나눈다. lev를 두 수열 사이 레벤슈타인 거리라 할 때, 버기 프로그램 b와 참조 프로그램 r 사이 거리를 두 수열들 사이의 가장 싼 일대일 대응 M의 비용으로 정의한다.
The goal of the Select stage is to choose a set of worked pairs from which the builder can generalize the recurring repairs of the class (line 3). This stage is local and issues no model query. To pair programs, \tool compares their ASTs. Let $\sigma(p)$ be the sequence of node types of $p$'s AST read in breadth-first order, split into one sequence $\sigma_i(p)$ per top-level statement. With $\mathrm{lev}$ the Levenshtein distance between two such sequences, we define the distance between a buggy program $b$ and a reference program $r$ as the cost of the cheapest one-to-one matching $\mathcal{M}$ between their sequences:
\[
\delta(b, r) = \min_{\mathcal{M}} \Big[ \sum_{(i, j) \in \mathcal{M}} \mathrm{lev}(\sigma_i(b), \sigma_j(r)) + \sum_{i \notin \mathcal{M}} |\sigma_i(b)| + \sum_{j \notin \mathcal{M}} |\sigma_j(r)| \Big]
\]
% [번역] 여기서 대응되지 않은 수열은 길이 전체를 비용으로 치르므로 빠지거나 남는 정의는 제값을 낸다. 그런 다음 각 버기 프로그램은 편집이 가장 적게 드는 참조 프로그램 π(b) = argmin_{r∈R} δ(b, r)을 짝으로 삼고, ε(b)는 b를 π(b)로 옮기는 편집 연산의 다중집합이다. 직관적으로 π(b)는 그저 가장 비슷해 보이는 프로그램이 아니라 b가 시도한 방식대로 문제를 푸는 참조 프로그램이다. 노드 타입 정렬이 편집을 내지 못하면 ε(b)는 식별자와 리터럴 수준의 정렬로 세분화되는데, 잘못된 변수나 상수는 노드 타입만으로는 보이지 않기 때문이다.
where an unmatched sequence costs its full length, so a missing or surplus definition costs what it is. Each buggy program then takes as partner the reference program it is fewest edits from, $\pi(b) = \argmin_{r \in R} \delta(b, r)$, and $\varepsilon(b)$ denotes the multiset of edit operations that takes $b$ to $\pi(b)$. Intuitively, $\pi(b)$ is the reference program that solves the problem the way $b$ tries to, rather than the one that merely looks closest. When the node-type alignment yields no edit, $\varepsilon(b)$ is refined to an alignment over identifiers and literals, since a wrong variable or constant is invisible to node types alone.

% [번역] 다음으로 CoEP는 편집 스크립트 ε(b)의 TF-IDF 벡터 사이 코사인 거리에 대한 평균 연결 응집 군집화로 B를 군집 C_1 ⊎ ... ⊎ C_k로 나누며, k는 평균 실루엣 계수를 최대화하도록 고른다. 군집화 특징으로 편집 스크립트를 선택한 이유는 한 원소에서 쓴 규칙이 같은 편집을 필요로 하는 원소들에서만 값어치를 하기 때문이다. 프로그램 자신의 AST 경로로 군집화하면 가장 큰 군집이 서로 닮았을 뿐인 프로그램들로 채워졌다. SemCluster는 문법이 프로그램을 과분할한다며 의미 특징으로 군집화하지만, 그 논거는 편집에는 이어지지 않는다. 편집 스크립트는 b가 π(b)와 공유하는 문법을 상쇄하고, 군집을 소비하는 재작성 규칙은 문법에 매칭되기 때문이다. 예를 들어 R1에서 gpt-5.4-mini의 규칙 strict_lt_to_lte는 enumerate(seq)를 도는 두 줄짜리 루프와 range(len(seq)-1)을 도는 루프를 감싼 네 갈래 분기를 모두 수리한다. 두 프로그램이 공유하는 것은 프로그램이 아니라 편집이다. 각 군집은 군집이 가장 많이 동의하는 편집을 가진 최빈 원소 b*_i를 내놓는다. 우리는 메도이드와 편집이 가장 작은 원소도 고려했다. 그러나 메도이드는 대개 여러 결함이 뒤엉켜 있고, 편집이 가장 작은 원소는 정답에 가장 가까웠던 이상치다. 메도이드는 편집이 한 번도 반복되지 않는 군집의 대비책으로만 쓴다. 빌드 집합은 δ가 증가하는 순서로 놓인 S = {(b*_i, π(b*_i))}이므로, 약한 빌더도 각 버기 프로그램을 그것을 수리하는 참조 프로그램과 함께 보고 변환을 일반화하기만 하면 된다. 실험적으로 Select는 11개 과제에서 작업 쌍 1,524개를 골랐으며 과제당 2개에서 353개다.
\tool then partitions $B$ into clusters $C_1 \uplus \dots \uplus C_k$ by average-linkage agglomerative clustering over the cosine distance between TF-IDF vectors of the edit scripts $\varepsilon(b)$, choosing $k$ to maximize the mean silhouette coefficient~\cite{rousseeuw1987silhouettes}. We selected edit scripts as the clustering feature because a rule written from one member pays off only on the members needing the same edit; clustering on the programs' own AST paths instead filled the largest clusters with programs that merely look alike. SemCluster~\cite{perry2019semcluster} clusters programs by semantic features because syntax over-partitions them, but the argument does not carry over to edits: an edit script cancels the syntax $b$ shares with $\pi(b)$, and the consumer of a cluster, a rewrite rule, matches syntax. On R1, for instance, \gm's rule \texttt{strict\_lt\_to\_lte} repairs both a two-line loop over \texttt{enumerate(seq)} and a four-way branch around a loop over \texttt{range(len(seq)-1)}; what the two share is the edit, not the program. Each cluster contributes its modal member,
\[
b^{\star}_i = \argmax_{b \in C_i} \big|\{ b' \in C_i \mid \varepsilon(b') = \varepsilon(b) \}\big|,
\]
whose edit the cluster most agrees on. We also considered the medoid and the member with the smallest edit. However, the medoid is usually a tangle of several faults, and the smallest edit belongs to an outlier that came closest to correct; the medoid serves only as the fallback for a cluster whose edits never repeat. The build set is $S = \{(b^{\star}_i, \pi(b^{\star}_i))\}_{i=1}^{k}$, ordered by increasing $\delta$, so a weak builder is shown each buggy program with a reference program that repairs it and need only generalize the transformation. Empirically, Select chose 1{,}524 worked pairs over our 11 assignments, from 2 to 353 per assignment.

\subsection{Synthesize}
\label{sec:synth}

% [번역] Synthesize 단계의 목표는 빌드 집합을 과제 전용 수리 도구와 그 수용 테스트 집합으로 바꾸는 것이다(5–12행). 8행에서 Synthesize 함수는 설명 d, 예시로 쓰는 T의 테스트 케이스 최대 η_test = 8개, S의 작업 쌍으로 빌더 M에 프롬프트한다. 빌더는 AST 재작성 규칙들로 된 Python 모듈 L_j로 답하며, 각 규칙은 자신이 겨냥하는 오개념의 이름을 달고 자신이 다루는 실패 증상(예: 오답, TypeError)으로 태그된다. 형식적으로 규칙은 프로그램 p를 후보 프로그램 집합 ρ(p)로 보내는 후보 생성기 ρ다. Figure 1-(b)가 그런 규칙 하나를 보여 준다. 규칙의 계약은 엄격하다. 규칙은 AST에서 편집 위치를 찾아 소스 구간 치환으로 이어 붙이며, 손대지 않은 줄까지 다시 서식화하는 모듈 재렌더링을 하지 않는다. 함수 전체를 다시 쓰지 않으며, 수정을 주장하지 않고 후보를 제안한다. 표적 편집을 표현할 수 없거나, 예외를 던지거나, η_alarm = 2초 알람을 넘기는 규칙은 ρ(p) = ∅을 내므로 그 제출물은 다음 전략으로 넘어간다.
The goal of the Synthesize stage is to turn the build set into an assignment-specific repair tool and the suite that accepts its repairs (lines 5--12). At line 8, the \aux{Synthesize} function prompts the builder $M$ with the description $d$, up to $\eta_{\V{test}} = 8$ test cases of $T$ as examples, and the worked pairs of $S$. The builder answers with a Python module $L_j$ of AST rewrite rules, each named after the misconception it targets and tagged with the failure symptoms it addresses (e.g., a wrong answer or a \texttt{TypeError}). Formally, a rule is a candidate generator $\rho$ that maps a program $p$ to a set $\rho(p)$ of candidate programs. Figure~\ref{fig:example}-(b) shows one such rule. The contract on a rule is strict. A rule locates its edit on the AST and splices it in as a source-span replacement rather than re-rendering the module, which would reformat untouched lines; it never rewrites a whole function; and it proposes candidates rather than claiming a fix. A rule that cannot express a targeted edit, raises an exception, or runs beyond an $\eta_{\V{alarm}} = 2$-second alarm yields $\rho(p) = \emptyset$, so its submission falls through to the next strategy.

% [번역] 한 번에 쓴 모듈은 자체 결함을 가질 수 있으므로, CoEP는 반례 유도 귀납 합성과 실행 피드백 기반 자기 정제의 방식으로 빌드 집합 자체에서 루프를 닫는다. 규칙이 아직 실패하는 작업 쌍이 반례다. 우리는 모듈의 커버리지를 그 규칙이 버기 쪽을 수리하는 빌드 집합의 비율로 정의한다. 여기서 Search는 4.5절의 규칙 탐색이다. 커버리지는 모듈 자신의 주장이 아니라 T를 실행해 측정하며, 참조 이식을 제외하므로 각 라운드는 그 아래 기반이 아니라 빌더가 쓴 규칙으로 채점된다. cov(L_j) < 1인 동안 9행은 여전히 실패하는 쌍 U를 수정용으로 빌더에게 돌려준다. 프리즈된 도구 L은 커버리지가 가장 높은 라운드이며(11행) 동점이면 가장 이른 라운드를 택한다. 직관적으로 정제는 빌더가 구체적 실패로부터 자기 규칙을 고치게 하고, argmax는 수정본이 더 나은 모듈을 대체하는 일이 없게 한다.
Since a module written in one shot can contain its own defects, \tool closes the loop on the build set itself, in the manner of counterexample-guided inductive synthesis~\cite{solar2006combinatorial} and of self-refinement from execution feedback~\cite{madaan2023self,shinn2023reflexion}: the worked pairs the rules still fail are the counterexamples. We define the coverage of a module as the fraction of the build set whose buggy half its rules repair:
\[
\aux{cov}(L_j) = \frac{|\{ (b, \WC) \in S \mid \aux{Search}(L_j, b, T) \neq \V{fail} \}|}{|S|}
\]
where \aux{Search} is the rule search of Section~\ref{sec:repair}. Coverage is measured by executing $T$, never from the module's own claim, and it excludes the reference transplant, so a round is scored on the rules the builder wrote rather than on the substrate beneath them. While $\aux{cov}(L_j) < 1$, line 9 returns the still-failing pairs $U$ to the builder for revision. The frozen tool $L$ is the round with the highest coverage (line 11), ties going to the earliest. Intuitively, the refinement lets a builder repair its own rules from concrete failures, while the $\argmax$ ensures that a revision never replaces a better module.

% [번역] 증폭된 수용 테스트. 강사의 테스트 케이스는 적다. R1–R5는 과제당 평균 7.4개이며, Repair 단계의 모든 전략은 c ⊨ T인 후보를 받아들이므로 빈약한 T는 테스트에만 맞춘 패치를 통과시킨다. 그래서 12행의 Amplify 함수는 과제당 한 번, 참조 프로그램과의 차분 테스트로 수용 테스트 집합을 키운다. 빌더 M은 d, T, 강사의 참조 해답을 받아 유효한 무작위 입력의 생성기를 작성하고, CoEP는 규칙을 검증하듯 생성기를 검증한다. 생성기가 예외를 던지거나, 형식이 틀린 입력을 내거나, 참조 해답이 입력의 10% 넘게를 거부하면 그 라운드는 실패하며, 실패 이유가 최대 η_round 라운드 동안 빌더에게 돌아간다. 그런 다음 CoEP는 새 입력 η_draw = 300개를 뽑아, R에서 표본으로 뽑은 프로그램 η_vote = 40개와 참조 해답의 다수 출력으로 각 입력을 라벨링하고, 그중 90% 이상이 일치하는 입력만 남긴다. 따라서 정답 프로그램끼리 엇갈리는 명세 밖의 입력은 테스트가 되지 않는다. 그렇게 남은 처음 η_amp = 100개가 T_amp를 이루고 T⁺ = T ∪ T_amp이다. Repair와 Learn 단계의 모든 수용 검사에서 T⁺가 T를 대신하며, 규칙의 커버리지는 계속 T로 잰다. 이는 학급을 오라클로 삼은 차분 테스트이며, 과적합된 패치에 맞선 테스트 생성의 취지를 따른다. 증폭은 과제당 빌더 질의를 하나 더할 뿐 제출물당 질의는 더하지 않는다.
\textbf{Amplified acceptance.} The instructor's test cases are few, 7.4 per assignment on R1--R5, and every strategy of the Repair stage accepts any candidate $c \models T$, so a thin $T$ admits patches that fit the tests rather than the problem. At line 12, the \aux{Amplify} function therefore enlarges the acceptance suite once per assignment, by differential testing against the reference programs. The builder $M$ is prompted with $d$, $T$, and the instructor's reference solution, and writes a generator of random valid inputs, which \tool validates as it validates rules: a round fails if the generator raises, returns a malformed input, or yields inputs of which the reference solution rejects more than 10\%, and the failure is returned to the builder for at most $\eta_{\V{round}}$ rounds. \tool then draws $\eta_{\V{draw}} = 300$ fresh inputs and labels each with the majority output of $\eta_{\V{vote}} = 40$ programs sampled from $R$ together with the reference solution, keeping an input only if at least 90\% of them agree, so an input outside the specification, on which correct programs disagree, never becomes a test. The first $\eta_{\V{amp}} = 100$ such inputs form $T_{\V{amp}}$, and $T^{+} = T \cup T_{\V{amp}}$. $T^{+}$ replaces $T$ in every acceptance check of the Repair and Learn stages, whereas the coverage of the rules is still measured on $T$. This is differential testing~\cite{mckeeman1998differential} with the class as the oracle, in the spirit of test generation against overfitted patches~\cite{smith2015cure,xin2017identifying}; it adds one builder query per assignment and none per submission.

\subsection{Repair}
\label{sec:repair}

% [번역] Repair 단계의 목표는 프리즈된 도구로 각 버기 프로그램 b를 수리하고, 도구가 못 하는 곳에서만 모델 질의를 쓰는 것이다(14행). CoEP는 Algorithm 1의 LocalRepair 훅(6행)을 비용이 낮은 순서의 두 전략으로, Generate 함수(8행)를 관례적인 모델 질의로 구현한다. c ⊨ T⁺인 후보를 먼저 내놓는 쪽이 f를 공급한다.
The goal of the Repair stage is to repair each buggy program $b$ with the frozen tool, and to spend a model query only where the tool cannot (line 14). \tool implements the \Fn{LocalRepair} hook of Algorithm~\ref{alg:generic} (line 6) with two strategies in increasing order of cost, and the \Fn{Generate} function (line 8) with a conventional model query; whichever first yields a candidate $c$ with $c \models T^{+}$ supplies $f$.

% [번역] 규칙 기반 수리. Search 함수는 재작성된 프로그램 층에 대한 너비 우선 탐색으로 규칙을 조합한다. Λ_0 = {b}이고 Λ_{j+1}은 Λ_j의 각 프로그램에 모든 규칙을 적용한 결과에서 이전 층을 뺀 것이며, b의 실패 테스트 서명이 선언 증상이 일치하는 규칙들의 순서를 정한다. Λ_{j+2}를 열거하기 전에 Λ_{j+1}의 모든 후보를 검증하므로 반환되는 수리는 c ⊨ T⁺인 가장 얕은 후보다. 탐색은 η_search = 3초가 지나면 더 깊은 층을 열거하지 않는다. 빌더의 규칙과 나란히, 모든 도구는 어느 학급이든 범하는 실수, 예컨대 비교 연산 뒤집기와 range·인덱스의 하나 차이 이동을 위한 항상 켜진 규칙 몇 개를 지니며, 이는 고전적 변이 연산자를 거꾸로 한 것이다. 규칙이 만든 모든 수리는 그 뒤에 있는 규칙들의 이름을 순서대로 지닌다.
\textbf{Rule-based repair.} The \aux{Search} function composes the rules by a breadth-first search over layers of rewritten programs, $\Lambda_0 = \{b\}$ and $\Lambda_{j+1} = (\bigcup_{p \in \Lambda_j} \bigcup_{\rho \in L} \rho(p)) \setminus \bigcup_{i \le j} \Lambda_i$, where the failing-test signature of $b$ orders the rules whose declared symptoms match it. Every candidate in $\Lambda_{j+1}$ is validated before $\Lambda_{j+2}$ is enumerated, so the returned repair is the shallowest candidate $c$ with $c \models T^{+}$. The search enumerates no further layer once $\eta_{\V{search}} = 3$ seconds have elapsed. Alongside the builder's rules, every tool carries a handful of always-on rules for the slips any class makes, such as flipped comparisons and off-by-one range and index shifts, which invert classical mutation operators~\cite{just2014mutants,kim2013automatic,liu2019tbar}. Every repair the rules produce carries the ordered names of the rules behind it.

% [번역] 참조 기반 수리. 대부분의 학생 버그는 토큰 수준 규칙이 표현하지 못하는 구조적 편집을 필요로 하며 R이 그것을 공급한다. δ로 b에 가장 가까운 참조 프로그램 η_ref = 8개 각각에 대해 CoEP는 b와 r이 어긋나는 줄 hunk의 집합 H(b, r)를 계산하며, r 그대로와 r의 변수를 b의 것으로 바꾼 사본(매개변수는 위치로, 지역 변수는 첫 바인딩 순서로) 양쪽에 대해 계산한다. b ⊕ h를 hunk h ⊆ H(b, r)를 적용한 b라 하자. CoEP는 1 ≤ |h| ≤ 3이면서 바뀌는 줄 수가 가장 적은 부분집합 η_cand = 300개를 검증하고, 처음 통과하는 부분집합 η_pass = 5개 P에 대해 RPS를 최소화하는 것을 반환하며, 하나도 통과하지 않으면 기권한다. 여기서 상대 패치 크기 RPS(b, f)는 b와 f의 AST 사이 트리 편집 거리를 b의 AST 크기로 나눈 값이다. 이는 CLARA, Sarfgen, Refactory 계보의 참조 재사용이지만 블록 전체가 아니라 줄 hunk 입도이므로, 학생의 전략이 다른 곳에서 참조 프로그램과 달라도 hunk는 여전히 적용 가능하다.
\textbf{Reference-based repair.} Most student bugs need a structural edit that no token-level rule expresses, and $R$ supplies it. For each of the $\eta_{\V{ref}} = 8$ reference programs nearest to $b$ under $\delta$, \tool computes the set $H(b, r)$ of line hunks in which $b$ and $r$ differ, both for $r$ as written and for $r$ with its variables renamed to $b$'s (parameters by position, locals by first binding). Let $b \oplus h$ denote $b$ with the hunks $h \subseteq H(b, r)$ applied. \tool validates the $\eta_{\V{cand}} = 300$ subsets $h$ with $1 \le |h| \le 3$ that change the fewest lines, and returns $\argmin_{h \in P} \RPS(b, b \oplus h)$ over the first $\eta_{\V{pass}} = 5$ passing subsets $P$, abstaining when none passes. Here, the relative patch size $\RPS(b, f)$ is the tree-edit distance~\cite{zhang1989simple} between the ASTs of $b$ and $f$ divided by the size of $b$'s AST~\cite{hu2019re}. This is reference reuse in the lineage of CLARA, Sarfgen, and Refactory~\cite{gulwani2018automated,wang2018search,hu2019re}, but at the granularity of line hunks rather than whole blocks: a hunk remains applicable when the student's strategy differs from the reference program's elsewhere.

% [번역] LLM 기반 수리. 두 로컬 전략이 모두 기권하면 CoEP는 Select 단계의 최소 편집 참조 프로그램을 붙인 질의 LLM(d, T, b, π(b)) 하나를 발행해, 모델이 학생 자신의 전략 쪽으로 b를 수리하게 한다. CoEP는 또한 로컬 전략이 RPS(b, f_loc) > η_rps = 1로 성공할 때, 즉 통과 패치가 고치려는 프로그램만큼 클 때도 에스컬레이션한다. 그 이유는 수용 검사 c ⊨ T⁺가 패치 크기에 대해 아무 말도 하지 않기 때문이다. 이식은 학생 프로그램의 대부분을 대체해서도 T⁺를 통과할 수 있는 반면, 규칙은 표적 편집을 표현할 수 없으면 언제나 기권해야 한다. CoEP는 둘 중 T⁺를 통과하면서 RPS가 가장 작은 것을 남기므로, 에스컬레이션은 질의 하나를 쓸 수는 있어도 커버리지나 패치 크기를 잃을 수는 없다. 임계값은 적합된 값이 아니라 정의다.
\textbf{LLM-based repair.} When both local strategies abstain, \tool attaches the minimum-edit reference program from the Select stage and issues a single query $\mathrm{LLM}(d, T, b, \pi(b))$, so that the model repairs $b$ toward the student's own strategy. \tool also escalates when the local strategies succeed with $\RPS(b, f_{\V{loc}}) > \eta_{\V{rps}} = 1$, i.e., with a passing patch at least as large as the program it repairs. The reason is that the acceptance test, $c \models T^{+}$, says nothing about patch size: a transplant can pass $T^{+}$ by replacing most of a student's program, whereas a rule must abstain whenever it cannot express a targeted edit. \tool keeps
\[
\argmin_{f \in \{f_{\V{loc}},\, \mathrm{LLM}(d, T, b, \pi(b))\},\ f \models T^{+}} \RPS(b, f),
\]
so an escalation can cost a query but never coverage or patch size. The threshold is a definition rather than a fitted value.

\subsection{Learn}
\label{sec:learn}

% [번역] Learn 단계의 목표는 도구가 하지 못한 수리를 도구 자체에 흡수하는 것이다(16–19행). Algorithm 1이 모델 질의로 수리한 각 쌍 (b, f)에 대해 Learn 함수는 M에게 b에서 f로의 편집을 새 이름 붙은 규칙 ρ'으로 일반화하게 한다. CoEP는 ρ'으로 확장한 도구가 b를 스스로 수리할 때, 즉 Search(L ∪ {ρ'}, b, T⁺) ≠ fail일 때만 ρ'을 유지한다. 학습된 규칙은 현재 패스가 참조하지 않는 스테이징 사본 L'에 기록되므로 어떤 제출물의 결과도 그 앞의 제출물에 의존하지 않으며, L'은 도구가 다시 프리즈될 때에만 L을 대체한다. Learn은 이미 에스컬레이션된 제출물에서만 모델에 질의하므로, 도구가 수리하는 제출물에는 질의를 더하지 않는다.
The goal of the Learn stage is to absorb the repairs the tool could not make into the tool itself (lines 16--19). For each pair $(b, f)$ that Algorithm~\ref{alg:generic} repaired with a model query, the \aux{Learn} function asks $M$ to generalize the edit from $b$ to $f$ into a new named rule $\rho'$. \tool keeps $\rho'$ only if the tool extended with it repairs $b$ by itself, i.e., $\aux{Search}(L \cup \{\rho'\}, b, T^{+}) \neq \V{fail}$. Learned rules are written to a staging copy $L'$ that the current pass never consults, so no submission's outcome depends on which submissions preceded it, and $L'$ replaces $L$ only when the tool is frozen again. Since Learn queries the model only for submissions that already escalated, it adds no query for a submission the tool repairs.

% [번역] 배포된 도구 자체는 모델에 질의하지 않는다. 로컬 전략은 제출물당 2~3초 안에 CPU에서 돌므로(5.3절) 학생 코드는 에스컬레이션될 때만 기관을 떠나며, 모든 후보가 반환되기 전에 T⁺로 검증되므로 결함 있는 규칙은 실패하는 수리가 아니라 기권으로 퇴화한다.
The deployed tool itself never queries a model. Its local strategies run on a CPU in about three seconds per submission (Section~\ref{sec:rq-cost}), so student code leaves the institution only on escalation, and a defective rule degrades into abstention rather than a failing repair, because every candidate is validated against $T^{+}$ before it is returned.

\subsection{Properties}
\label{sec:props}

% [번역] 성질. 이 절은 빌더가 무엇을 쓰든 CoEP가 보장하는 것을 진술한다. 이하에서 c ⊨ T는 후보 c가 T의 모든 테스트 케이스를 시간 제한 안에 통과한다는 뜻이므로, 충돌하거나 시간을 넘긴 후보는 통과하지 않는다. CoEP_L은 Algorithm 1을 Generate 없이(에스컬레이션 없이) 돌린 것이고 CoEP_LF는 Generate와 관문을 포함한 것이다.
We now state what \tool guarantees whatever the builder writes. Throughout, $c \models T$ means that the candidate $c$ passes every test case of $T$ within its time limit, so a candidate that crashes or times out does not pass; \coepL runs Algorithm~\ref{alg:generic} without \Fn{Generate}, and \coepLF with \Fn{Generate} and the gate of Section~\ref{sec:repair}.

% [번역] 명제 1(T⁺ 기준 건전성). 모든 빌더 M과 모든 b ∈ B에 대해, CoEP가 b에 대해 f ≠ fail을 반환하면 f ⊨ T⁺이고, 따라서 f ⊨ T이다.
\begin{proposition}[Soundness relative to $T^{+}$]\label{prop:sound}
For every builder $M$ and every $b \in B$, if \tool returns $f \neq \V{fail}$ for $b$, then $f \models T^{+}$, and hence $f \models T$.
\end{proposition}
% [번역] 증명. 수리는 세 경로 중 하나로 F에 들어가며, 각 경로는 후보를 반환하기 전에 T⁺에 대해 검증한다. Search는 층의 후보를 T⁺로 검증한 뒤에만 반환하고, 이식은 통과하는 부분집합 P에 대한 argmin을 반환한다. Generate의 후보는 c ⊨ T⁺일 때만 남으며(Algorithm 1의 9행에서 T 대신 T⁺), 관문은 f ⊨ T⁺인 후보에 대한 argmin을 남긴다. 학습된 규칙은 Search를 통해서만 들어온다. 빌더의 규칙과 생성기, 생성된 입력, 모델의 답은 후보와 테스트를 제안할 뿐이며 그 무엇도 T⁺에 대해 실행되지 않고는 반환되지 않는다. 마지막으로 T ⊆ T⁺이므로 f ⊨ T⁺이면 f ⊨ T이다.
\begin{proof}
A repair enters $F$ through one of three paths, and each validates its candidate against $T^{+}$ before returning it. \aux{Search} returns a candidate only after validating it against $T^{+}$, and the transplant returns the $\argmin$ over the passing subsets $P$; a candidate of \Fn{Generate} is kept only if $c \models T^{+}$ (line~9 of Algorithm~\ref{alg:generic}, called with $T^{+}$ for $T$); and the gate keeps an $\argmin$ over candidates $f \models T^{+}$. Learned rules enter only through \aux{Search}. The builder's rules and generator, the generated inputs, and the model's answers only propose candidates and tests; none of them is returned without being executed against $T^{+}$. Finally, $f \models T^{+}$ implies $f \models T$ because $T \subseteq T^{+}$.
\end{proof}

% [번역] 명제 1은 증폭이 수락 집합을 줄일 수만 있다는 것을 함의한다. T 아래의 수리는 T⁺ 아래에서 기권이 되거나 다른 수리로 바뀔 수 있지만, T가 거부하는 후보가 받아들여지는 일은 없다. 5.6절은 이 교환의 실제 값, 즉 T에서의 수리율 0.6포인트와 held-out 테스트에서의 8.4–10.2포인트를 측정한다.
Proposition~\ref{prop:sound} implies that amplification can only shrink the set of accepted candidates: a repair under $T$ may become an abstention or a different repair under $T^{+}$, but no candidate that $T$ rejects is accepted. Section~\ref{sec:rq-heldout} measures what this exchange is worth: 0.6 points of repair rate on $T$ for 8.4 to 10.2 points on held-out tests.

% [번역] 명제 2(가장 얕은 규칙 조합). Search가 층 Λ_j에서 후보 c를 반환하면, Λ_0 ∪ … ∪ Λ_{j−1}의 모든 후보는 T⁺를 통과하지 못한다. 즉 c는 열거된 층 중에서 통과하는 가장 적은 규칙 적용의 조합이다.
\begin{proposition}[Shallowest composition]\label{prop:shallow}
If \aux{Search} returns a candidate $c \in \Lambda_j$ for $b$, then no candidate in $\Lambda_0 \cup \dots \cup \Lambda_{j-1}$ passes $T^{+}$; that is, $c$ composes the fewest rule applications among the passing candidates of the enumerated layers.
\end{proposition}
% [번역] 증명. Search는 Λ_{j+1}을 열거하기 전에 Λ_j의 모든 후보를 검증하고 통과하는 첫 후보에서 멈춘다. 따라서 c가 Λ_j에서 반환되었다면 Λ_0, …, Λ_{j−1}은 모두 끝까지 검증되었고 통과한 후보가 없었다. 층은 이전 층에 나온 프로그램을 빼므로 Λ_i의 원소는 정확히 i번의 규칙 적용으로 처음 도달한 프로그램이다.
\begin{proof}
\aux{Search} validates every candidate of $\Lambda_j$ before it enumerates $\Lambda_{j+1}$, and stops at the first passing candidate. If $c$ is returned from $\Lambda_j$, the layers $\Lambda_0, \dots, \Lambda_{j-1}$ were therefore validated completely and held no passing candidate. Since each layer excludes the programs of earlier layers, an element of $\Lambda_i$ is a program first reached by exactly $i$ rule applications.
\end{proof}
% [번역] 가장 얕다는 것은 패치 크기가 가장 작다는 것과 같지 않다. 규칙 적용 하나가 큰 편집일 수 있기 때문이다. 우리는 규칙의 계약(4.4절)으로 그 차이를 줄인다. 규칙은 표적 편집을 소스 구간 치환으로 끼워 넣을 뿐 함수 전체를 다시 쓰지 않는다.
Shallowest is not smallest, since one rule application may be a large edit; the contract on rules (Section~\ref{sec:synth}) narrows the gap, as a rule splices a targeted edit as a source-span replacement and never rewrites a whole function.

% [번역] 명제 3(에스컬레이션의 단조성). 모든 b에 대해, CoEP_L이 b를 f_L로 수리하면 CoEP_LF도 b를 RPS(b, f_LF) ≤ RPS(b, f_L)인 f_LF로 수리한다.
\begin{proposition}[Monotone escalation]\label{prop:gate}
For every $b$, if \coepL repairs $b$ with $f_L$, then \coepLF repairs $b$ with some $f_{LF}$ such that $\RPS(b, f_{LF}) \le \RPS(b, f_L)$.
\end{proposition}
% [번역] 증명. CoEP_LF는 같은 로컬 수리 f_loc = f_L을 계산한다. RPS(b, f_L) ≤ η_rps이면 에스컬레이션하지 않으므로 f_LF = f_L이다. 그렇지 않으면 f_LF는 {f_L, LLM(d, T, b, π(b))} 중 T⁺를 통과하는 것들에 대한 RPS의 argmin이며, 명제 1에 의해 f_L ⊨ T⁺이므로 이 집합은 f_L을 포함하고 공집합이 아니다.
\begin{proof}
\coepLF computes the same local repair $f_{\V{loc}} = f_L$. If $\RPS(b, f_L) \le \eta_{\V{rps}}$, it does not escalate and $f_{LF} = f_L$. Otherwise, $f_{LF}$ is the $\argmin$ of $\RPS(b, \cdot)$ over the candidates in $\{f_L, \mathrm{LLM}(d, T, b, \pi(b))\}$ that pass $T^{+}$, a set that contains $f_L$ by Proposition~\ref{prop:sound} and is therefore nonempty.
\end{proof}

% [번역] 명제 4(종료). 모든 b에 대해 Repair 단계는 종료한다.
\begin{proposition}[Termination]\label{prop:term}
For every $b$, the Repair stage terminates.
\end{proposition}
% [번역] 증명. 규칙 호출 하나는 η_alarm에서 끊기고, 후보 검증 하나는 테스트마다 시간 제한이 있으며, 규칙 집합과 각 층은 유한하다. Search는 η_search가 지나면 더 깊은 층을 열거하지 않으므로 유한한 수의 층에서 멈춘다. 이식은 η_ref개 참조 각각에 대해 최대 η_cand개 부분집합을 검증한다. 마지막으로 Generate는 질의 하나를 발행한다.
\begin{proof}
Each rule call is cut off after $\eta_{\V{alarm}}$, each validation runs under a per-test time limit, and the rule set and every layer are finite. \aux{Search} enumerates no further layer once $\eta_{\V{search}}$ has elapsed, so it stops after finitely many layers. The transplant validates at most $\eta_{\V{cand}}$ subsets for each of the $\eta_{\V{ref}}$ reference programs, and \Fn{Generate} issues one query.
\end{proof}
% [번역] 탐색 예산이 벽시계 시간이므로 어떤 층이 열거되는지, 따라서 반환되는 수리는 기계의 부하에 따라 달라질 수 있다. 실제로 R5에서 claude-sonnet-5의 프리즈된 도구를 다시 실행했을 때 패치 108개가 모두 그대로 재현되었다.
Because the search budget is wall-clock time, which layers are enumerated, and hence which repair is returned, can depend on machine load; in practice, re-running the frozen \cs tool on R5 reproduced all 108 of its patches.

% [번역] 보장하지 않는 것. CoEP는 완전하지 않다. 이식은 최대 300개 부분집합에서 hunk를 최대 세 개까지 시도하고 탐색은 예산에서 멈추므로, 수리 가능한 프로그램도 에스컬레이션으로 넘어가거나 수리되지 않은 채 남을 수 있다. 또한 수리는 T⁺ 너머에서 올바르다고 보장되지 않는다. 명제 1은 CoEP가 받아들이는 것을 명세가 아니라 T⁺로 묶으며, 5.6절은 held-out 테스트에서 그 간극을 측정한다.
\textbf{What is not guaranteed.} \tool is not complete: the transplant tries at most three hunks over at most 300 subsets and the search stops at its budget, so a repairable program may fall through to escalation or remain unrepaired. Nor is a repair correct beyond $T^{+}$: Proposition~\ref{prop:sound} bounds what \tool accepts by $T^{+}$, not by the specification, and Section~\ref{sec:rq-heldout} measures the gap on held-out tests.

\section{Experiments}
\label{sec:exp}

% [번역] 이 장에서는 다음 연구 질문에 답하기 위해 CoEP를 평가한다.
% [번역] (1) 효과: CoEP는 수리율과 패치 크기 측면에서 참조 유도 및 LLM 기반 수리와 비교해 버기 프로그램을 얼마나 효과적으로 수리하는가?
% [번역] (2) 효율: 과제당 한 번 도구를 합성하는 것은 제출물마다 LLM에 질의하는 것에 비해 모델 지출과 소요 시간을 얼마나 절약하는가?
% [번역] (3) 각 단계의 효능: Synthesize, Repair, Learn 단계는 CoEP의 성능에 각각 어떻게 기여하는가?
% [번역] (4) 일반성: 학급의 앞선 제출물로 만든 도구가 뒤의 제출물을 수리하는가, 그리고 빌드는 학급 규모에 따라 어떻게 늘어나는가?
% [번역] (5) 테스트 너머의 정확성: 수리 결과는 어떤 팔도 탐색에 쓰지 않은 테스트 케이스에서도 올바른가?
In this section, we evaluate \tool to answer the following research questions:
\begin{enumerate}
  \item[(1)] \textbf{Effectiveness:} How effectively does \tool repair buggy programs compared to reference-guided and LLM-based repair, in terms of repair rate and patch size?
  \item[(2)] \textbf{Efficiency:} How much model spend and turnaround does synthesizing a tool once per assignment save, compared to querying an LLM per submission?
  \item[(3)] \textbf{Efficacy of Each Stage:} How do the Synthesize, Repair, and Learn stages contribute to the performance of \tool?
  \item[(4)] \textbf{Generality:} Does a tool built from a class's earlier submissions repair its later ones, and how does its build scale with the class?
  \item[(5)] \textbf{Correctness beyond the Tests:} Do the repairs remain correct on test cases that no arm searched against?
\end{enumerate}
% [번역] 우리는 CoEP를 Python의 표준 ast 모듈 위에 Python으로 구현했으며, 합성된 각 도구는 오프라인으로 도는 평범한 Python 모듈로 출력된다. 트리 편집 거리는 Zhang–Shasha 알고리즘으로, 군집화는 scikit-learn으로 계산한다. 모든 로컬 계산은 Mac Studio(Apple M1 Ultra, 20코어, 64 GB RAM, macOS 26.7)에서 수행했다.
We implemented \tool in Python on top of the standard \texttt{ast} module, and each synthesized tool is emitted as an ordinary Python module that runs offline. Tree-edit distance is computed with the Zhang--Shasha algorithm~\cite{zhang1989simple} and clustering with scikit-learn. All local computation ran on a Mac Studio (Apple M1 Ultra, 20 cores, 64 GB RAM, macOS 26.7).

\subsection{Experimental Settings}
\label{sec:settings}

% [번역] 베이스라인. 우리는 CoEP를 프로그래밍 과제 수리의 두 주류 계열을 대표하는 두 베이스라인과 비교했다. (1) 참조 유도 수리(Refactory)와 (2) LLM 기반 수리(PyDex)이며, 다른 기법이 베이스라인이 될 수 없었던 이유는 6장에서 설명한다. Refactory는 학급의 참조 프로그램을 각 버기 프로그램의 구조에 맞게 리팩터링하고 어긋나는 블록을 옮겨 심으며, 우리의 Python 코퍼스에서 도는 가장 강한 참조 유도 수리기다. PyDex는 각 버기 프로그램과 학급에서 검색한 가장 유사한 (버기, 정답) 예시 세 쌍으로 모델에 프롬프트하고, 후보 열 개를 샘플링해 T로 거른 뒤 학생 프로그램에 가장 가까운 생존자를 반환한다. 우리는 그 few-shot 의미 수리 단계를 재구현했고 열 개의 샘플 모두에 비용을 청구했다. 또한 동일한 프롬프트 열 개 중 첫 번째만 정가로, 나머지는 공급자의 캐시 읽기 요율로 모델링해 프롬프트 캐싱 하의 PyDex(PyDex_PC)를 가격 매겼으며, 이는 이 질의들에서 캐싱이 아낄 수 있는 상한이다. CoEP는 두 구성으로 평가했다. 수리 시점에 모델 없이 프리즈된 도구만 돌리는 CoEP_L, 그리고 에스컬레이션 시 제출물당 질의를 더하는 CoEP_LF다. 각 단계의 효능을 위해 Synthesize 단계(Algorithm 2의 4–11행)를 빼고 항상 켜진 규칙과 참조 이식만 남긴 CoEP_L−Syn, 학습된 규칙을 미리 합쳐 프리즈한 뒤 CoEP_L을 다시 돌리는 CoEP_L+Learn, 그리고 CoEP_LF의 질의 LLM(d, T, b, π(b))를 모든 버기 프로그램에 보내는 LLM_Direct를 추가로 평가했다. LLM_Direct는 같은 프롬프트, 같은 모델, 같은 최소 편집 참조 프로그램, 같은 수용 검사를 쓰므로, CoEP_LF와는 프리즈된 도구가 처리하지 못하는 곳에서만 모델에 질의한다는 설계 하나만 다르다.
\textbf{Baselines.} We compared \tool with two baselines representing the two mainstream lines of repair for programming assignments: (1) reference-guided repair (Refactory~\cite{hu2019re}) and (2) LLM-based repair (PyDex~\cite{zhang2024pydex}); Section~\ref{sec:related} explains why the other techniques could not serve as baselines. Refactory~\cite{hu2019re} refactors the class's reference programs to match each buggy program's structure and transplants the divergent blocks; it is the strongest reference-guided repairer that runs on our Python corpora. PyDex~\cite{zhang2024pydex} prompts a model with each buggy program and the three most similar (buggy, correct) exemplars retrieved from the class, samples ten candidates, filters them with $T$, and returns the survivor closest to the student's program; we re-implemented its few-shot semantic phase and billed all ten samples. We also priced PyDex under prompt caching (\pydexPC), modeling the first of its ten identical prompts at full price and the rest at the providers' cache-read rate~\cite{anthropiccaching,openaicaching}, which upper-bounds what caching can save on these queries. We evaluated \tool in two configurations: \coepL, which runs the frozen tool alone with no model at repair time, and \coepLF, which adds the per-submission query on escalation. For the efficacy of each stage, we further evaluated \coepNS, which omits the Synthesize stage (lines 4--11 of Algorithm~\ref{alg:coep}) and keeps only the always-on rules and the reference transplant; \coepLL, which re-runs \coepL with the learned rules merged and frozen beforehand; and \direct, which issues \coepLF's query $\mathrm{LLM}(d, T, b, \pi(b))$ for every buggy program. Since \direct uses the same prompt, model, minimum-edit reference program, and acceptance test, it differs from \coepLF in one design choice alone: querying the model only where the frozen tool cannot serve.

% [번역] 벤치마크. 우리는 Table 2에 요약한 두 코퍼스의 11개 과제에서 버기 프로그램 2,970개를 사용했다. 처음 다섯 과제(R1–R5)는 대학 1학년 프로그래밍 강의의 과제로, 학생들이 쓴 모든 제출물을 담고 있으며 Refactory의 저자들이 공개했다. 나머지 여섯(C1–C6)은 open-r1 릴리스가 제출물을 반영하는 Codeforces 문제다. 입문 연습 이상으로 난이도가 올라가도록 800, 1000, 1200, 1400, 1600, 2000 등급에서 한 문제씩 골랐으며, Newbie부터 Candidate Master까지 다섯 공식 등급 밴드를 포괄한다. 각 코퍼스의 레이블을 그대로 유지했으므로 모든 팔의 분모는 같은 프로그램 2,970개다.
\textbf{Benchmarks.} We used 2{,}970 buggy programs from 11 assignments in two corpora, summarized in Table~\ref{tab:effect}. The first five assignments (R1--R5) are those of a first-year university programming course, with every submission its students wrote, released by the authors of Refactory~\cite{hu2019re}. The other six (C1--C6) are Codeforces problems whose submissions the open-r1 release mirrors~\cite{penedo2025codeforces}. So that difficulty extends beyond introductory exercises, we selected one problem at each of the ratings 800, 1000, 1200, 1400, 1600, and 2000, covering five official rating bands from Newbie to Candidate Master~\cite{cfratings}. We kept each corpus's own labels, so the denominator of every arm is the same 2{,}970 programs.

% [번역] 기타 설정. 모든 LLM 팔은 공급자당 하나씩 두 모델에서 돌았다. gpt-5.4-mini(입력/출력 백만 토큰당 0.75/4.50달러)와 claude-sonnet-5(2/10달러)다. 캐싱 베이스라인에 최선의 조건을 주기 위해 각 공급자에서 이 프롬프트들에 캐싱이 동작하는 가장 값싼 티어를 골랐다. 각 모델은 CoEP의 빌더이자 fallback이면서 PyDex의 수리 모델로 쓰였다. CoEP는 R1–R5에서 증폭된 테스트 집합 T⁺로 수리를 받아들였고, 테스트 케이스가 채점기의 공식 전체 테스트 집합(문제당 22–56개)인 C1–C6에서는 T⁺ = T로 두었다. 우리는 네 지표를 측정했다. 수리율(RR)은 팔이 수리한 버기 프로그램의 비율이며, 수정 프로그램이 T의 모든 테스트 케이스를 통과할 때만 수리로 센다. 따라서 R1–R5에서 CoEP의 수용 기준은 베이스라인보다 엄격하다. 상대 패치 크기(RPS, 4.5절)는 팔이 수리한 프로그램에 대해 평균한다. 소요 시간(ATT)은 제출물당 평균 벽시계 초로, 로컬 계산(ATT_cpu)과 모델 지연(ATT_api)으로 나눈다. 모델 비용 C_tot = C_build + C_api는 정확한 토큰 수로 가격을 매긴 벤치마크 전체의 미국 달러로, C_build는 일회성 합성(증폭 포함), C_api는 제출물당 질의다. R1–R5에서 Refactory는 저자들이 발표한 수리율과 패치 크기를 보고하며, 이는 우리가 도구를 잘못 설정했다는 반론의 여지를 없앤다. C1–C6에서는 공개 도구를 직접 돌리고 다른 모든 팔처럼 학생의 원래 프로그램에 대해 RPS를 측정했다. 효과는 두 빌더를 합쳐(팔–제출물 쌍 5,940개) 보고하고 비용은 빌더별로 보고한다. 수리율은 짝지은 결과에 대한 정확 McNemar 검정으로, 패치 크기는 Wilcoxon 부호 순위 검정으로 비교했으며 기준은 둘 다 p < 0.05다.
\textbf{Other Settings.} Every LLM arm ran on two models, one per provider: \gm (\$0.75/\$4.50 per million input/output tokens) and \cs (\$2/\$10). We selected each provider's cheapest tier at which prompt caching works on these prompts, to give the caching baseline its best case. Each model served both as \tool's builder and fallback and as PyDex's repairer. On R1--R5, \tool accepted repairs against the amplified suite $T^{+}$; on C1--C6, whose test cases are the judge's full official test sets (22 to 56 per problem), $T^{+} = T$. We measured four metrics. The \emph{repair rate} (RR) is the percentage of buggy programs an arm repairs, counting a repair only when the fixed program passes all test cases of $T$; on R1--R5, \tool's acceptance is therefore stricter than the baselines'. The \emph{relative patch size} (RPS, Section~\ref{sec:repair}) is averaged over the programs an arm repairs. The \emph{turnaround} (ATT) is the mean wall-clock seconds per submission, split into local computation ($\mathrm{ATT}_{\V{cpu}}$) and model latency ($\mathrm{ATT}_{\V{api}}$). The \emph{model cost} $C_{\V{tot}} = C_{\V{build}} + C_{\V{api}}$ is the US dollars spent over the benchmark, priced from exact token counts, where $C_{\V{build}}$ is the one-off synthesis, amplification included, and $C_{\V{api}}$ the per-submission queries. For Refactory on R1--R5, we report the repair rates and patch sizes its authors published, which leaves no room to argue that we misconfigured it; on C1--C6, we ran the released tool and measured RPS on the student's original program, as for every other arm. Effectiveness is pooled over the two builders (5{,}940 arm--submission pairs), and cost is reported per builder. We compared repair rates with the exact McNemar test on paired outcomes and patch sizes with the Wilcoxon signed-rank test, both at $p < 0.05$.

% [번역] Table 2는 CoEP_LF가 가장 강한 베이스라인만큼 많은 프로그램을 수리하면서 가장 작은 패치를 만들었음을 보여 준다. 전체적으로 CoEP_LF는 프로그램 2,970개의 99.4%를 수리했으며, Refactory는 85.9%, PyDex는 98.9%였다. CoEP_LF는 11개 과제 중 여덟 과제에서 100%에 도달했다. 패치 크기 측면에서 CoEP_LF의 평균 RPS 0.428은 PyDex의 0.634보다 32.5% 작고 Refactory의 0.500보다도 작다. RPS는 각 팔이 수리한 것에 대해 평균하므로 모든 팔이 공통으로 수리한 프로그램에서도 비교했다. CoEP_LF와 PyDex가 모두 수리한 5,841쌍에서 RPS는 0.426 대 0.634였고, 세 팔이 모두 수리한 5,023쌍에서는 CoEP_LF가 0.413으로 Refactory의 0.479와 PyDex의 0.626보다 작았다(Figure 4-(b), 곡선이 왼쪽에 있을수록 패치가 작다).
Table~\ref{tab:effect} shows that \coepLF repaired as many programs as the strongest baseline while making the smallest patches. Overall, \coepLF repaired 99.4\% of the 2{,}970 programs, against 85.9\% for Refactory and 98.9\% for PyDex, and reached 100\% on eight of the eleven assignments. In terms of patch size, \coepLF's mean RPS of 0.428 is 32.5\% smaller than PyDex's 0.634 and also smaller than Refactory's 0.500. Since RPS is averaged over what each arm repairs, we also compared it on the programs both arms repaired: on the 5{,}841 pairs \coepLF and PyDex both repaired, their RPS was 0.426 against 0.634, and on the 5{,}023 pairs all three arms repaired, \coepLF's 0.413 was below Refactory's 0.479 and PyDex's 0.626 (Figure~\ref{fig:effect}-(b), where a curve further to the left means smaller patches).

% [번역] 특히 난이도가 오를수록 Refactory와의 격차가 벌어진다. CS1 과제, Codeforces 800–1000, Codeforces 1200–2000으로 묶으면 Refactory의 수리율은 90.8%에서 83.1%, 54.5%로 떨어지는 반면 CoEP_LF는 98.9%, 100.0%, 100.0%를 유지한다(Figure 4-(a)). 빈약한 풀만으로는 이 붕괴가 설명되지 않는다. C5와 C6는 모든 팔에 참조 프로그램 두 개만 주지만 두 CoEP 팔은 모두 완전히 수리하기 때문이다. 차이는 재사용의 입도에 있다. Refactory는 어긋나는 블록을 채택하므로 다른 방식으로 문제를 푸는 풀에서는 채택할 것이 남지 않지만, CoEP는 이름을 바꾼 뒤 줄 hunk를 채택한다.
Notably, the gap to Refactory widens with difficulty. Grouped into the CS1 assignments, Codeforces 800--1000, and Codeforces 1200--2000, Refactory's repair rate falls from 90.8\% to 83.1\% and 54.5\%, whereas \coepLF holds 98.9\%, 100.0\%, and 100.0\% (Figure~\ref{fig:effect}-(a)). Thin pools alone do not explain this collapse, since C5 and C6 give every arm only two reference programs and both \tool arms repair them completely. The difference lies in the granularity of reuse: Refactory adopts divergent blocks, so a pool that solves the problem another way leaves nothing to adopt, whereas \tool adopts line hunks after renaming.

% [번역] 흥미롭게도 프리즈된 도구만 쓰는 CoEP_L은 모델 호출 없이 98.4%를 수리해 PyDex의 98.9%보다 조금 적었다. 차이는 대부분 CoEP의 수용이 더 엄격한 R2와 R3에 있다. 후보는 증폭된 테스트 케이스 100개도 통과해야 한다. CoEP_LF의 에스컬레이션이 그 대부분을 되살려 R2를 97.1%로 올렸고, 5.6절은 이 엄격한 수용이 T 너머에서 수리를 올바르게 유지함을 보인다. 도구가 모든 오개념을 덮을 필요는 없다.
Interestingly, the frozen tool alone, \coepL, repaired 98.4\%, slightly fewer than PyDex's 98.9\%, without a single model call. Most of the gap lies on R2 and R3, where \tool's acceptance is stricter: a candidate must also pass the 100 amplified test cases. The escalation of \coepLF recovered most of these programs, raising R2 to 97.1\%, and Section~\ref{sec:rq-heldout} shows that the stricter acceptance is what keeps \tool's repairs correct beyond $T$; the tool need not cover every misconception.

% [번역] 이 결과들은 Refactory 대비 통계적으로 유의했다(정확 McNemar, 두 빌더 모두 p < 0.001). PyDex 대비로는 CoEP_LF가 두 빌더를 합쳤을 때 더 많은 프로그램을 수리했지만(p = 0.014) 각 빌더만으로는 유의하지 않았고(p = 0.14, 0.065), CoEP_L은 합쳤을 때 조금 적게 수리했다(p = 0.018, 빌더별 p = 0.15, 0.075). 두 CoEP 팔 모두 공통 쌍에서 두 베이스라인보다 작은 패치를 만들었다(Wilcoxon 부호 순위, p < 0.001). 이 결과들은 과제당 한 번 합성한 도구가 제출물마다 질의하는 모델만큼 많은 프로그램을 수리하면서 3분의 1 작은 패치를 만든다는 것을 보여 준다.
These results were statistically significant against Refactory (exact McNemar, $p < 0.001$ on both builders). Against PyDex, \coepLF repaired more programs with the builders pooled ($p = 0.014$) but not significantly on either builder alone ($p = 0.14$ and $0.065$), and \coepL repaired slightly fewer when pooled ($p = 0.018$; $p = 0.15$ and $0.075$ per builder). Both \tool arms made smaller patches than both baselines on the common pairs (Wilcoxon signed-rank, $p < 0.001$). These results indicate that a tool synthesized once per assignment repairs as many programs as a model queried per submission, with patches a third smaller.

We evaluated the contribution of each stage with the variants of Section~\ref{sec:settings}. Since the Select stage only feeds the Synthesize stage, we assess the two together by removing the builder's rules (\coepNS).

% [번역] Synthesize. Table 4는 합성된 규칙이 참조 풀이 빈약할 때 커버리지를, 그리고 언제나 더 작은 패치를 기여함을 보여 준다. 전체 벤치마크에서 CoEP_L−Syn은 98.25%를 RPS 0.509로 수리했고 CoEP_L은 98.43%를 0.481로 수리했다. 11쌍의 차이는 claude-sonnet-5에서는 유의했지만(정확 McNemar, p = 0.004) gpt-5.4-mini에서는 유의하지 않았으며(p = 0.50), CoEP_L−Syn만 수리한 프로그램은 없었다. 커버리지 이득이 작은 것은 맞는 풀이 있으면 참조 이식이 규칙이 수리하는 거의 모든 것을 수리하기 때문이다. 규칙이 수리한 1,293쌍 중 99.1%는 CoEP_L−Syn도 수리했다. 풀이 빈약할 때는 규칙이 중요하다. 빌더가 보지 않은 프로그램에서 참조 프로그램이 하나도 없으면 규칙은 수리율을 8.2%에서 30.1%로 올렸고, 참조 프로그램이 하나나 둘이면 RPS를 0.10–0.15 줄였다. 이름도 규칙이 하는 일을 말한다. 세 평가자가 규칙 191개를 코드와 그 규칙이 만든 수리 하나에 비추어 독립적으로 판정했으며(Fleiss' κ = 0.890), 규칙이 만든 수리의 99.2%가 규칙이 한 일과 일치하는 이름을 지녔다. 틀린 이름 16개는 모두 gpt-5.4-mini가 썼고 그중 14개는 한 번도 발동하지 않았다.
\textbf{Synthesize.} Table~\ref{tab:ablation} shows that the synthesized rules contribute coverage when the reference pool is thin, and smaller patches throughout. Over the full benchmark, \coepNS repaired 98.25\% at RPS 0.509, against \coepL's 98.43\% at 0.481; the difference of 11 pairs was significant on \cs (exact McNemar, $p = 0.004$) but not on \gm ($p = 0.50$), and no program was repaired by \coepNS alone. The gain in coverage is small because the reference transplant repairs nearly everything a rule repairs when a matching pool exists: of the 1{,}293 pairs the rules repaired, \coepNS also repaired 99.1\%. When the pool is thin, the rules matter: on programs the builder never saw, they raised the repair rate from 8.2\% to 30.1\% with no reference program, and cut RPS by 0.10 to 0.15 with one or two. The names also say what the rules do: three raters independently judged 191 rules against their code and a repair each produced (Fleiss' $\kappa = 0.890$), and 99.2\% of the rule-produced repairs carry a name consistent with what the rule did; all 16 names judged wrong were written by \gm, and 14 of them never fired.

% [번역] Repair. Repair 단계 안에서는 참조 이식이 폭을, 규칙이 정밀도를 맡았다. CoEP_L이 수리한 5,847쌍 중 이식이 77.9%를 평균 RPS 0.587로, 규칙이 22.1%를 시스템에서 가장 작은 패치인 0.109로 만들었다. 규칙의 몫은 C5의 9.1%에서 C4의 44.7%까지였고 0인 과제는 없었다(Figure 6-(a)는 CoEP_LF의 분할이다). 규칙 수리는 단일 재작성이 아니었다. 1,293개 중 460개(35.6%)가 규칙 적용 둘에서 다섯을 조합했으며(Figure 6-(b)), 너비 우선 탐색은 더 얕은 조합이 모두 실패한 뒤에야 이들에 도달했다(명제 2). 에스컬레이션은 약간의 지출로 패치 크기를 줄였다. CoEP_LF는 수리율을 0.93 포인트 올리고 RPS를 0.481에서 0.428로 낮췄다.
\textbf{Repair.} Within the Repair stage, the reference transplant carried the breadth and the rules carried the precision. Of the 5{,}847 pairs \coepL repaired, the transplant produced 77.9\% at mean RPS 0.587, and the rules 22.1\% at 0.109, the smallest patches in the system; the rules' share ranged from 9.1\% on C5 to 44.7\% on C4 and was never zero (Figure~\ref{fig:source}-(a) gives the split under \coepLF). The rule repairs were not single rewrites: 460 of the 1{,}293 (35.6\%) composed two to five rule applications (Figure~\ref{fig:source}-(b)), which the breadth-first search reached only after every shallower composition had failed (Proposition~\ref{prop:shallow}). The escalation trades a little spend for patch size: \coepLF raised the repair rate by 0.93 points and lowered RPS from 0.481 to 0.428.

% [번역] 일치하는 제어 흐름 없이. 참조 이식은 버기 프로그램과 제어 흐름이 같은 정답 프로그램을 요구하지 않는다. CLARA는 이를 자기 접근의 유일한 근본적 문제라 했고 Sarfgen은 정확한 일치를 요구한다. CoEP_LF가 수리한 5,902쌍 중 154개(2.6%)는 학급의 어떤 정답 프로그램과도 루프 구조가 달라 CLARA가 맞출 프로그램이 없고, 1,446개(24.5%)는 루프와 조건문의 중첩이 어떤 정답 프로그램과도 달라 Sarfgen이 정렬할 프로그램이 없다. 그중 1,260개는 모델 질의 없이 도구의 규칙과 이식이 수리했다. 반대로 이식 수리 4,108개 중 2,171개(52.8%)는 버기 프로그램의 루프와 조건문 중첩을 바꾸었다.
\textbf{Beyond a matching control flow.} The transplant needs no correct program with the buggy program's control flow, the requirement CLARA calls the only fundamental problem of its approach~\cite{gulwani2018automated} and Sarfgen imposes exactly~\cite{wang2018search}. Of the 5{,}902 pairs \coepLF repaired, 154 (2.6\%) have a loop structure that no correct program of the class shares, leaving CLARA nothing to match, and 1{,}446 (24.5\%) a nesting of loops and conditionals that none shares, leaving Sarfgen nothing to align; the tool's rules and transplant repaired 1{,}260 of these without a model query. Conversely, 2{,}171 of the 4{,}108 transplant repairs (52.8\%) changed the buggy program's nesting of loops and conditionals.

% [번역] Local-first 구조. 같은 질의를 모든 프로그램에 보내는 LLM_Direct와 CoEP_LF를 가르는 것은 local-first 구조다. CoEP_LF는 99.4%를 수리했고 LLM_Direct는 82.5%였으며(두 빌더 모두 정확 McNemar p < 0.001), LLM_Direct만 수리한 프로그램은 3개뿐이었다. 질의 하나는 패치가 실패하면 두 번째 후보가 없지만, 도구는 에스컬레이션 전에 규칙과 최대 300개의 hunk 부분집합을 탐색한다. 그러나 둘 다 수리한 4,896쌍에서는 LLM_Direct의 패치가 더 작았다(RPS 0.330 대 0.391). 따라서 패치를 작게 만드는 것은 구조가 아니라 두 팔이 모두 붙이는 최소 편집 참조 프로그램 π(b)이며, 구조가 기여하는 것은 커버리지와 비용이다(5.3절).
\textbf{Local-first architecture.} The local-first architecture is what separates \coepLF from \direct, which sends the same query for every program. \coepLF repaired 99.4\% against \direct's 82.5\% (exact McNemar, $p < 0.001$ on both builders), and \direct repaired only 3 programs that \coepLF did not: a single query has no second candidate when its patch fails, whereas the tool searches its rules and up to 300 hunk subsets before escalating. On the 4{,}896 pairs both repaired, however, \direct's patches were smaller (RPS 0.330 against 0.391). It is therefore the minimum-edit reference program $\pi(b)$, which both arms attach, rather than the architecture that makes the patches small; the architecture contributes coverage and cost (Section~\ref{sec:rq-cost}).

% [번역] Learn. Learn 단계는 도구가 실패하는 곳에서만 동작하며 그런 경우는 드물다. 두 빌더에 걸쳐 CoEP_L은 R1, R2, R3, C3에서 93쌍에 실패했다. fallback이 그중 55쌍을 수리했고, Learn 단계는 이 수리들로부터 재현 검사를 통과한 규칙 11개를 0.89달러에 유도했다. CoEP_L+Learn은 이 규칙들로 회귀 없이 프로그램 32개를 되살렸다(정확 McNemar, 두 빌더에서 p < 0.001과 p = 0.002). 학습된 규칙은 같은 과제 안에서 재사용된다는 증거이며, 과제를 건너 일반화된다는 증거는 아니다. CoEP_LF가 끝내 수리하지 못한 38쌍은 모두 R1–R3에 있고 모두 fallback까지 갔다. 그중 25쌍은 같은 팔이 T만으로 받아들이면 수리되므로 증폭된 테스트만이 거부한 것이고, 나머지 13쌍(R2)은 T 자체를 통과하는 후보가 없었다.
\textbf{Learn.} The Learn stage fires only where the tool fails, which is rare. Over both builders, \coepL failed on 93 pairs, on R1, R2, R3, and C3; the fallback repaired 55 of them, and the Learn stage generalized these repairs into 11 rules that passed the reproduction check, for \$0.89. \coepLL recovered 32 programs with these rules without a single regression (exact McNemar, $p < 0.001$ and $p = 0.002$ for the two builders). The learned rules are evidence of reuse within an assignment, not of transfer across assignments. The 38 pairs \coepLF left unrepaired all lie on R1--R3 and all reached the fallback: 25 are repaired by the same arm accepting against $T$ alone, so only the amplified test cases rejected them, and for the other 13, all on R2, no candidate passed $T$ itself.

% [번역] 우리는 학급의 앞선 제출물로 만든 도구가 뒤의 제출물을 수리하는지 살폈다. 제출 id가 제출 시간을 따르는 Codeforces에서는 C1–C5의 제출물을 id 순으로, 시간도 학생도 기록하지 않는 CS1에서는 시드를 고정한 무작위 순서 세 개로 놓았다(C6는 제출물이 다섯 개다). 처음 f ∈ {10, 25, 50, 75}%의 제출물로 도구를 만들고(버기 프로그램은 Select에, 정답 프로그램은 R에), 마지막 4분의 1의 버기 프로그램(CS1은 순서마다 439개, Codeforces는 313개)을 수리했으며, 기준으로 학급 전체로 만든 5.2절의 도구로도 같은 프로그램을 수리했다(Figure 7-(a)의 all).
We examined whether a tool built from a class's earlier submissions repairs its later ones. We ordered the submissions of C1--C5 by id, which follows submission time, and those of CS1, which records neither time nor student, in three seeded random orders (C6 has five submissions). We built a tool from the first $f \in \{10, 25, 50, 75\}\%$ of each order, its buggy programs feeding Select and its correct programs forming $R$, and repaired the buggy programs of the last quarter, 439 per order on CS1 and 313 on Codeforces, also with the tools of Section~\ref{sec:rq-effect}, built from the whole class, as a reference (``all'' in Figure~\ref{fig:general}-(a)).

% [번역] Figure 7-(a)는 학급의 처음 10%로 만든 도구가 전체 학급으로 만든 도구만큼 뒤의 제출물을 잘 수리했음을 보여 준다. CS1에서 CoEP_LF는 10% 빌드로 떼어 둔 프로그램의 99.4%를 수리했으며, 전체 제출물로 만든 도구는 99.1%였다. Codeforces에서는 98.2% 대 100.0%였고 학급 절반부터 99.2%로 올랐다. 프리즈된 도구만으로는 Codeforces에서 더 많은 이력이 필요했다. CoEP_L은 10%에서 94.4%, 50%에서 98.4%를 수리했고 전체 풀 도구는 100.0%였다. 빈약한 풀은 이식할 참조 프로그램이 적기 때문이며, fallback이 그 차이 대부분을 되살렸다. 따라서 새 과제를 맡은 강사는 첫 제출물 몇십 개로 도구를 만들고 학기가 진행되며 다시 만들 수 있다.
Figure~\ref{fig:general}-(a) shows that a tool built from the first 10\% of a class repaired its later submissions about as well as one built from the whole class. On CS1, \coepLF repaired 99.4\% of the held-out programs from a 10\% build, against 99.1\% for the tool built from all submissions; on Codeforces, 98.2\% against 100.0\%, rising to 99.2\% from half the class. The frozen tool alone needed more history on Codeforces: \coepL repaired 94.4\% from 10\% and 98.4\% from 50\%, against 100.0\% for the full-pool tool, since a thin pool offers fewer reference programs to transplant from, and the fallback recovered most of the difference. An instructor facing a new assignment can therefore build a tool from its first few dozen submissions and rebuild it as the term proceeds.

% [번역] 특히 빌드 비용은 학급보다 훨씬 느리게 늘었다(Figure 7-(b)). CS1에서 10%에서 75%로 가는 동안 빌드 집합은 과제당 작업 쌍 15.6개에서 143.1개로 9.2배 커졌지만, claude-sonnet-5의 빌드 비용은 0.88달러에서 1.66달러로 1.9배 늘었다(gpt-5.4-mini: 0.027달러에서 0.069달러). 빌더의 입력은 작업 쌍과 함께 7.8배 늘었지만, 가격을 지배하는 출력, 즉 규칙 모듈은 1.6배만 늘었다. 학급이 커지면 새 쌍은 대부분 도구가 이미 이름을 붙인 오개념에 속하기 때문이다.
Notably, the build cost grew far more slowly than the class (Figure~\ref{fig:general}-(b)). From 10\% to 75\% of CS1, the build set grew 9.2-fold, from 15.6 to 143.1 worked pairs per assignment, whereas the build cost on \cs grew 1.9-fold, from \$0.88 to \$1.66 (\gm: \$0.027 to \$0.069). The builder's input grew with the pairs, 7.8-fold, but its output, the module of rules that dominates the price, grew only 1.6-fold, since most new pairs fall into misconceptions the tool has already named.

% [번역] CoEP는 빌더가 바뀌어도 유지되었다. 두 빌더의 빌드 비용은 18배 차이 나지만(12.24달러 대 0.69달러), 그 도구들은 프로그램의 98.52%와 98.35%를 수리했고, CoEP_LF는 99.33%와 99.39%를 RPS 0.420과 0.435로 수리해 같은 모델의 PyDex(0.598과 0.669)보다 작았다. 따라서 커버리지는 최신 빌더에 달려 있지 않으며, 더 강한 빌더의 이점은 패치 크기와 오개념 이름에서 나타난다.
\tool also held across builders. The two builders differ 18-fold in build cost (\$12.24 against \$0.69), yet their tools repaired 98.52\% and 98.35\% of the programs, and \coepLF repaired 99.33\% and 99.39\% at RPS 0.420 and 0.435, below PyDex's 0.598 and 0.669 on the same models. Coverage therefore does not hinge on a frontier builder, and a stronger builder pays off in patch size and in the misconception names.

\subsection{Correctness beyond the Tests}
\label{sec:rq-heldout}

\begin{figure}[t]
\centering
\includegraphics[width=\textwidth]{figures/fig_heldout}
\caption{Repair rates on R1--R5 under the instructor's test cases and a held-out suite. \coepLF accepting $T$: \coepLF accepting against $T$ alone.}
\label{fig:heldout}
\end{figure}

% [번역] R1–R5는 과제당 강사 테스트 케이스 7.4개를 제공하며, 5.2절에서 모든 팔은 이 테스트로 탐색하고 이 테스트로 채점받았다. 수리가 그 너머에서도 올바른지 확인하기 위해 우리는 어떤 팔도 탐색에 쓰지 않은 held-out 테스트 집합을 과제마다 만들었다. 우리가 손으로 쓴 생성기에서 다른 시드로 뽑은 입력 100개이며, 빌더의 생성기와는 독립이다. 각 입력은 정답 프로그램의 다른 표본 40개와 참조 해답의 다수 출력으로 90% 이상 일치할 때만 라벨링했고, T⁺와 겹치지 않는다. 그런 다음 모든 팔의 수리를 T와 held-out 집합에서 다시 실행했다. C1–C6는 이미 채점기의 공식 전체 테스트 집합을 쓴다.
R1--R5 ship 7.4 instructor test cases per assignment, and in Section~\ref{sec:rq-effect} every arm both searched against them and was judged by them. To check whether the repairs remain correct beyond them, we built a held-out suite per assignment that no arm searched against: 100 inputs drawn with a different seed from a generator we wrote by hand, independently of the builders' generators, each labelled by the majority output of a different sample of 40 correct programs and the reference solution at 90\% agreement, and none in $T^{+}$. We then re-ran every arm's repairs on $T$ and the held-out suite; C1--C6 already use the judge's full official test sets.

% [번역] Figure 8은 증폭된 수용이 CoEP의 수리를 모든 팔 중 가장 견고하게 만들었음을 보여 준다. CoEP_LF가 수리한 프로그램의 99.7%와 99.2%가 held-out 집합도 통과했으며 PyDex는 97.8%와 98.0%였다. 그 결과 held-out 집합에서 CoEP_LF는 프로그램의 98.5%와 98.1%를, PyDex는 96.4%와 97.2%를 수리했다(정확 McNemar, 두 빌더를 합쳐 p < 0.001, 빌더별 p < 0.001과 p = 0.075). 증폭 없이 T만으로 받아들인 같은 도구는 T에만 맞는 패치를 받아들였다. 수리의 90.7%와 88.4%만 살아남았고 held-out 수리율은 90.2%와 88.0%로 떨어졌다. 증폭은 T에서의 수리율 0.6 포인트를 held-out 집합에서의 8.4와 10.2 포인트와 맞바꾼 것이다. 모델 질의 없이 프리즈된 도구만으로도 held-out 수리율은 97.3%와 96.5%로 PyDex와 비슷했다.
Figure~\ref{fig:heldout} shows that the amplified acceptance made \tool's repairs the most robust of all arms. Of the programs \coepLF repaired, 99.7\% and 99.2\% also passed the held-out suite, against 97.8\% and 98.0\% for PyDex, so on the held-out suite \coepLF repaired 98.5\% and 98.1\% of the programs against PyDex's 96.4\% and 97.2\% (exact McNemar, $p < 0.001$ pooled; $p < 0.001$ and $p = 0.075$ per builder). Without amplification, the same tool accepted patches that fit $T$ alone: only 90.7\% and 88.4\% of its repairs survived, and its held-out repair rate fell to 90.2\% and 88.0\%. Amplification thus traded 0.6 points of repair rate on $T$ for 8.4 and 10.2 points on the held-out suite. Even the frozen tool, with no model call, reached 97.3\% and 96.5\% on the held-out suite, on par with PyDex.

% [번역] 흥미롭게도 같은 증폭이 제출물당 팔에는 해가 되었다. LLM_Direct는 T⁺로 받아들이면 held-out 집합에서 87.8%와 82.1%를, T만으로 받아들이면 90.2%와 83.8%를 수리했다. 질의 하나는 두 번째 후보가 없으므로, T가 다루지 않는 입력(예: R1에서 원소가 반복되는 정렬된 수열)에서 학급과 다르게 행동하는 패치는 탈락하고 끝나지만, CoEP의 규칙과 이식은 통과하는 다른 후보를 찾는다. 더 엄격한 수용은 탐색할 수 있는 수리기에서만 값을 하며, 과제당 한 번 만드는 도구는 그 탐색을 감당할 수 있다.
Interestingly, the same amplification hurt the per-submission arm: \direct repaired 87.8\% and 82.1\% on the held-out suite when accepting against $T^{+}$, but 90.2\% and 83.8\% against $T$ alone. A single query has no second candidate, so a patch that departs from the class's behavior on inputs $T$ never exercises, such as sorted sequences with repeated elements on R1, is simply lost, whereas \tool's rules and transplant search for another that passes. A stricter acceptance pays off only under a repairer that can search, and a tool built once per assignment can afford the search.

% [번역] 남은 실패는 적고 설명 가능하다. R5의 여섯 개는 모두 유일한 빈 입력 top_k([], 0)에서 실패하는데 두 집합을 겹치지 않게 하면서 이 입력이 T⁺에서 빠졌고, gpt-5.4-mini의 R3 생성기는 −2에서 3 사이 값만 뽑아 더 큰 값에서만 실패하는 패치 아홉 개를 놓쳤다. 이 결과들은 CoEP의 수리가 제출물당 수리보다 강사의 테스트 너머에서 더 자주 올바름을 보여 준다.
The remaining failures are few and explicable: the six on R5 all fail \texttt{top\_k([], 0)}, the only empty input, which keeping the suites disjoint removed from $T^{+}$, and \gm's generator for R3 drew values only from $-2$ to $3$, missing nine patches that fail on larger ones. These results indicate that \tool's repairs are correct beyond the instructor's tests more often than per-submission repairs.

\subsection{Threats to Validity}
\label{sec:threats}

% [번역] (1) 학급 분할: CS1 코퍼스는 시간도 학생도 기록하지 않으므로 5.5절의 CS1 분할은 무작위 순서이며, 학기 단위로 나누면 수리율이 낮을 수 있다. (2) 테스트 적정성: 수리는 T를 통과할 때 센다. R1–R5에서 CoEP는 T⁺도 요구하고 5.6절은 held-out 테스트로 검사하지만 두 집합 모두 학급의 정답 프로그램으로 라벨링되므로 학급 전체가 똑같이 틀리는 동작은 드러나지 않으며, C1–C6에서는 채점기의 공식 테스트에 의존한다. (3) 빌더: 두 빌더 모두 닫힌 상용 모델이므로 다시 빌드하면 같은 규칙이 나오지 않을 수 있다. 우리는 오프라인으로 도는 도구 22개와 생성기 10개를 공개한다. (4) 벤치마크: 과제 11개는 Python 문제이고 C6는 버기 프로그램 세 개만 기여하므로 다른 언어나 큰 프로젝트로 이어지지 않을 수 있다.
(1) \textbf{Class splits:} The CS1 corpus records neither time nor student, so its splits in Section~\ref{sec:rq-general} are random orders; a split by term may yield lower rates. (2) \textbf{Test adequacy:} A repair counts when it passes $T$. On R1--R5, \tool also requires $T^{+}$ and Section~\ref{sec:rq-heldout} checks held-out tests, but both suites are labelled by the class's correct programs, so a behavior the whole class gets wrong goes undetected; on C1--C6, we rely on the judge's official tests. (3) \textbf{Builders:} Both builders are closed commodity models, so a rebuild may not reproduce the same rules; we release the 22 tools and 10 input generators, which run offline. (4) \textbf{Benchmarks:} Our 11 assignments are Python problems, and C6 contributes three buggy programs; the results may not carry over to other languages or to large projects.

\section{Related Work}
\label{sec:related}
%=============================================================================

% [번역] 프로그래밍 과제 수리. 우리 연구는 학생의 프로그래밍 과제를 수리하는 기법들과 공통 목표를 공유한다. Singh 등은 강사가 쓴 error model, 즉 Sketch 기반 탐색이 최소 수정을 찾아 조합하는 재작성 규칙 집합으로 시도를 수리한다. CoEP는 그 error model을 과제마다 합성하고, T⁺로 검증하는 열거로 탐색한다. 참조 유도 기법은 학급의 정답 프로그램을 재사용한다. CLARA와 Sarfgen은 버기 프로그램을 루프 구조나 제어문 순서가 같은 정답 프로그램에 정렬하는데 우리 수리의 4분의 1은 그런 프로그램이 없으며(5.4절), Verifix는 그 정렬을 형식 검증으로 뒷받침하며, Refactory는 풀을 리팩터링해 정렬 가능한 범위를 넓히고, MENTORED는 정답과 오답 프로그램을 유전 프로그래밍으로 재조합한다. LLM 기반 기법은 제출물마다 모델에 질의하며, 검색한 예시(PyDex), 튜터링 대화(CREF), 미세 조정(FastFixer, MORepair), 선호 학습 기반 위치 추정(AdaPatcher), MaxSAT 기반 결함 위치 추정과 반례 유도 합성, 또는 다른 학생의 (오답, 수정) 쌍 검색(LSGen)을 쓴다. 이들과 달리 CoEP는 모델 노력을 과제당 한 번 만드는 도구에 쓰고 배포된 수리기에는 모델을 남기지 않는다. 이들 중 어느 것이든 그 도구 뒤의 Generate 함수가 될 수 있다.
\textbf{Program Repair for Programming Assignments.} Our work shares a common goal with techniques that repair students' programming assignments~\cite{gulwani2018automated,wang2018search,hu2019re,ahmed2022verifix,choi2025automated,zhang2024pydex,yang2024cref,liu2024fastfixer,orvalho2025counterexample,orvalho2025mentor,yang2026morepair,dai2025less,dai2026learner}. Singh et al.~\cite{singh2013automated} repair an attempt with an instructor-written \emph{error model}, a set of rewrite rules whose combinations a Sketch-based search explores for a minimal correction; \tool synthesizes that error model per assignment and searches it by enumeration validated against $T^{+}$. Reference-guided techniques reuse the class's correct programs: CLARA~\cite{gulwani2018automated} and Sarfgen~\cite{wang2018search} align a buggy program with a correct one of the same loop structure or the same sequence of control statements, which a quarter of our repairs lack (Section~\ref{sec:rq-stage}), Verifix~\cite{ahmed2022verifix} backs the alignment with formal verification, Refactory~\cite{hu2019re} refactors the pool to widen what aligns, and MENTORED~\cite{choi2025automated} recombines correct and incorrect programs by genetic programming. LLM-based techniques query a model per submission, with retrieved exemplars (PyDex~\cite{zhang2024pydex}), tutoring conversation (CREF~\cite{yang2024cref}), fine-tuning (FastFixer~\cite{liu2024fastfixer}, MORepair~\cite{yang2026morepair}), preference-trained localization (AdaPatcher~\cite{dai2025less}), MaxSAT-based localization with counterexample-guided synthesis~\cite{orvalho2025counterexample,orvalho2025mentor}, or retrieval of other students' (incorrect, corrected) pairs (LSGen~\cite{dai2026learner}). Unlike these techniques, \tool spends its model effort on a tool built once per assignment and leaves no model in the deployed repairer; any of them can serve as the \Fn{Generate} function behind its tool.

% [번역] 제출물의 군집화와 변환. OverCode는 정규화한 문장이 일치하는 정답 프로그램을, CLARA는 제어 흐름과 변수 추적이 일치하는 프로그램을, SemCluster는 경로별 입력 수와 값 변화 빈도가 비슷한 프로그램을, InvAASTCluster는 불변식과 익명화한 AST가 일치하는 프로그램을 묶으며, 모두 수리기가 정렬할 참조 프로그램을 고르는 데 쓴다. CoEP는 대신 버기 프로그램을 그것을 수리하는 편집으로 묶는데, 군집이 빌더가 일반화할 수리를 정하기 때문이다. Head 등은 오답을 그것을 고치는 변환으로 묶어 강사가 묶음마다 피드백을 한 번 쓰게 한다. CoEP처럼 Refazer도 (전, 후) 쌍에서 과제 전용 변환을 유도하지만, 학생 자신의 수정으로부터 DSL에서 예제 기반 프로그래밍으로 합성하는 반면 CoEP는 LLM이 이름 붙고 테스트로 검증되는 규칙을 범용 코드로 쓰게 한다. 템플릿 기반 수리와 Reyes 등은 마이닝하거나 LLM이 만든 AST 변환을 학급이 아닌 소프트웨어 프로젝트에 적용한다.
\textbf{Clustering and Transforming Submissions.} OverCode~\cite{glassman2015overcode} groups correct programs whose normalized statements coincide, CLARA~\cite{gulwani2018automated} those with the same control flow and variable traces, SemCluster~\cite{perry2019semcluster} those with similar per-path input counts and value-change frequencies, and InvAASTCluster~\cite{orvalho2025invaastcluster} those with matching invariants and anonymized ASTs, each to choose the reference program a repairer aligns with. \tool instead clusters buggy programs by the edit that repairs them, since its clusters decide which repairs a builder generalizes. Head et al.~\cite{head2017writing} group incorrect submissions by the transformations that fix them, so that a teacher writes feedback once per group. Like \tool, Refazer~\cite{rolim2017learning} induces assignment-specific transformations from (before, after) pairs, but synthesizes them by programming-by-example in a domain-specific language from students' own fixes, whereas \tool has an LLM write named, test-validated rules as general-purpose code. Template-based repair~\cite{kim2013automatic,liu2019tbar} and Reyes et al.~\cite{reyes2026agentic} apply mined or LLM-generated AST transformations to software projects rather than to a class.

% [번역] 도구 제작자로서의 LLM. 우리 접근은 LLM이 과제를 직접 풀지 않고 재사용 가능한 도구를 쓰는 연구 흐름에 속한다. LATM은 강한 모델이 쓴 유틸리티를 약한 모델이 재사용하고, CRAFT는 과제 특화 도구 모음을 만들고 검색하며, TroVE와 ReGAL은 검증 가능한 함수 라이브러리를 유도하고, Voyager는 기술을 축적하며, FunSearch는 점수에 맞춰 프로그램을 진화시키고, ReaComp는 모델 추론을 기호 해결기로 컴파일한다. 그러나 앞의 다섯은 추론 시 도구를 부르는 모델을 루프에 남기는 반면, CoEP는 뒤에 모델이 없는 도구를 배포한다. 프로그램 수리가 더하는 것은 도구 자체에 대한 실행 가능한 오라클이다. PL에 더 가까운 연구로, 타입 제약 디코딩은 각 접두사를 타입 시스템에 비추어 검사함으로써 LLM 출력이 타입 검사를 통과함을 보장한다. CoEP는 대신 LLM이 쓴 모든 것을 T⁺에 대해 실행함으로써 보장을 얻는다(명제 1).
\textbf{LLMs as Tool Makers.} Our approach belongs to a line of research in which LLMs write reusable tools instead of solving each task directly~\cite{cai2024large,yuan2024craft,wang2024trove,stengel2024regal,wang2023voyager,romera2024mathematical,naik2026reacomp}: LATM~\cite{cai2024large} has a strong model write utilities that a weaker one reuses, CRAFT~\cite{yuan2024craft} creates and retrieves task-specialized toolsets, TroVE~\cite{wang2024trove} and ReGAL~\cite{stengel2024regal} induce verifiable function libraries, Voyager~\cite{wang2023voyager} accumulates skills, FunSearch~\cite{romera2024mathematical} evolves programs against a score, and ReaComp~\cite{naik2026reacomp} compiles model reasoning into symbolic solvers. However, the first five keep a model in the loop that calls the tools at inference, whereas \tool deploys its tool with no model behind it. What program repair adds is an executable oracle for the tool itself. Closer to programming languages, type-constrained decoding guarantees well-typed LLM output by checking each prefix against the type system~\cite{mundler2025type}; \tool obtains its guarantee instead by executing everything the LLM writes against $T^{+}$ (Proposition~\ref{prop:sound}).

% [번역] 베이스라인 선정. 우리는 위 기법들 중에서 기법이 (1) 군집이나 다른 과제용 도구가 아니라 수리를 내놓고, (2) Python 프로그램을 수리하며, (3) 학생의 연속된 시도 사이의 연결, 루프 안의 튜터, 이 과제를 위해 학습한 모델처럼 우리 벤치마크에 없는 입력을 요구하지 않고, (4) CS1 코퍼스에서 자기 계열을 대표한다는 네 기준으로 베이스라인을 골랐다. Refactory와 PyDex만 네 기준을 모두 만족한다. 군집화, 강사가 개입하는 피드백, 도구 제작 접근은 기준 (1)을, Verifix, SemCluster, InvAASTCluster, 반례 유도 수리기(C), Sarfgen(C#), 템플릿·변환 기반 수리(소프트웨어 프로젝트)는 (2)를, 학생의 연속된 시도에서 배우거나 검색하는 Refazer와 LSGen, 과제마다 강사가 쓴 error model이 필요한 Singh 등, 튜터를 두는 CREF, 모델을 미세 조정하는 FastFixer, AdaPatcher, MORepair는 (3)을 만족하지 못한다. 남은 CLARA와 MENTORED는 Refactory처럼 학급의 제출물을 재사용하며, 우리는 CS1 코퍼스를 공개하고 그 위에서 CLARA와 비교한 Refactory를 이 계열의 대표로 삼는다. PyDex는 ChatRepair 같은 범용 수리기와 달리 입문 Python 과제를 위해 설계되었고 프롬프트를 전부 공개한다.
\textbf{Selection of Baselines.} We selected the baselines of Section~\ref{sec:settings} by four criteria: a technique must (1) produce repairs rather than clusters or tools for other tasks, (2) repair Python programs, (3) require no input our benchmark lacks, such as the link between a student's successive attempts, a tutor in the loop, or a model trained for the task, and (4) represent its line of repair on the CS1 corpus. Only Refactory and PyDex satisfy all four. Clustering, teacher-in-the-loop feedback, and tool-making approaches~\cite{glassman2015overcode,perry2019semcluster,orvalho2025invaastcluster,head2017writing,cai2024large,yuan2024craft,wang2024trove,stengel2024regal} fail (1); Verifix~\cite{ahmed2022verifix}, SemCluster, InvAASTCluster, and the counterexample-guided repairers~\cite{orvalho2025counterexample,orvalho2025mentor} (C), Sarfgen~\cite{wang2018search} (C\#), and template- and transformation-based repair~\cite{kim2013automatic,liu2019tbar,reyes2026agentic} (software projects) fail (2); and Refazer~\cite{rolim2017learning} and LSGen~\cite{dai2026learner}, which learn from or retrieve a student's successive attempts, Singh et al.~\cite{singh2013automated}, which needs an instructor-written error model per assignment, CREF~\cite{yang2024cref}, which keeps a tutor in the loop, and FastFixer~\cite{liu2024fastfixer}, AdaPatcher~\cite{dai2025less}, and MORepair~\cite{yang2026morepair}, which fine-tune a model, fail (3). Of the remaining techniques, CLARA~\cite{gulwani2018automated} and MENTORED~\cite{choi2025automated} reuse the class's submissions as Refactory does, and we take Refactory, whose authors released the CS1 corpus and evaluated it against CLARA there~\cite{hu2019re}, as the representative of that line; PyDex, unlike general-purpose repairers such as ChatRepair~\cite{xia2024automated}, is designed for introductory Python assignments and publishes its prompts in full~\cite{zhang2024pydex}.

\section{Conclusion}
%=============================================================================

% [번역] 최근 LLM 기반 프로그램 수리는 자동으로 수리할 수 있는 학생 제출물의 비율을 크게 높였다. 그러나 이 기법들은 버기 제출물마다 모델에 한 번씩 질의하므로, 학급은 반복 수리마다 값을 다시 치른다. 이 논문은 LLM이 제출물마다 패치를 쓰는 대신 과제마다 수리 도구를 한 번 합성하게 함으로써 반복 수리를 상각하는 CoEP를 제시한다. CoEP는 학급의 편집 스크립트를 군집화해 작업 쌍을 고르고, 오개념 이름이 붙은 재작성 규칙을 합성하고, 학급의 정답 프로그램과의 차분 테스트로 테스트 케이스를 증폭하고, 모든 제출물을 로컬에서 수리하며, 에스컬레이션한 소수에서 새 규칙을 학습한다. 실험 결과는 CoEP가 수리율에서 제출물당 LLM 수리와 대등하면서 더 작은 패치를 만들고, 그 수리가 held-out 테스트에서 더 자주 올바르며, 모델 지출은 그 일부에 그침을 보여 준다. 우리는 학급의 첫 제출물로 만든 도구가 나머지 학급을 수리하므로 CoEP가 큰 학급에서도 자동 수리를 감당할 수 있게 하리라 기대한다.
Recently, LLM-based program repair has substantially improved the share of student submissions that can be repaired automatically. However, these techniques query the model once per buggy submission, so a class pays again for every recurring repair. This paper presents \tool, which amortizes recurring repairs by having an LLM synthesize a repair tool once per assignment rather than a patch for every submission. \tool selects worked pairs by clustering the class's edit scripts, synthesizes misconception-named rewrite rules, amplifies the test cases by differential testing against the class's correct programs, repairs every submission locally, and learns new rules from the few it escalates. Experimental results demonstrate that \tool matches per-submission LLM repair in repair rate while producing smaller patches, repairs that hold on held-out tests more often, and a fraction of the model spend. We expect \tool to make automated repair affordable for large classes, since a tool built from a class's first submissions repairs the rest.
