\title{Use LLMs to Build Repair Tools, Not Patch Generation: Cost-Effective Automated Program Repair}
\author{Anonymous submission}

\begin{abstract}
Large language models (LLMs) repair buggy submissions to programming assignments well, but they are deployed \emph{one query per submission}: every buggy program triggers a fresh model call, so cost, latency, and external dependence scale with enrollment and recur every term, while the specification-level reasoning being purchased is identical across a class --- and caching or cheaper models shrink only the constant, not the structure. We propose \textsc{CoEP}, which moves the LLM from the marginal-cost to the fixed-cost column: \emph{spend the model once per assignment, not once per submission}. An LLM agent reads the assignment and a clustered sample of worked (buggy $\to$ fixed) pairs and authors the assignment-specific layer of a local repair tool --- AST rewrite rules named after the misconceptions they fix --- atop a shared symbolic substrate of generic edits and reference-guided minimal-hunk transplant from the class's own correct solutions. Every candidate patch is validated against the instructor's tests before it is kept; the tool can never self-report success, and submissions it abstains on escalate to a conventional per-submission call, so coverage is never sacrificed. On the standard benchmark of this literature, the synthesized tool repairs \emph{more} submissions with \emph{smaller} patches than the strongest hand-built symbolic tool, on that tool's own corpus and metric --- with the entire model spend collapsed into a one-off synthesis plus a small escalation tail, so everything repaired locally costs no model call at all, offline and deterministically. A price-invariant break-even analysis shows when amortization wins and why cheaper models and caching do not change the answer, and the artifact yields what a per-query API cannot: reproducible minimal patches and a per-class misconception profile.
\end{abstract}

\section{Introduction}

Timely, individualized feedback is the scarcest resource in programming education: introductory courses enroll hundreds of students on campus and tens of thousands online, each producing buggy submissions no instructor can examine one by one. Automated program repair (APR) has therefore long been proposed as a feedback engine for programming assignments: given a buggy submission and the assignment's test suite, produce a small patch that makes it correct while preserving the student's own approach \citep{itsp2017,clara2018,sarfgen2018,refactory2019,verifix2022}.

Three generations of systems have pursued this goal. The first established the setting: test-driven repair of introductory assignments, with the requirement that a patch stay close to the student's program, since a correct but unrelated rewrite passes the tests and teaches nothing \citep{itsp2017}. The second exploited the structure of a \emph{class}, mining the assignment's own solution space: CLARA clusters correct submissions, Sarfgen searches aligned examples, Refactory refactors correct solutions into a per-problem search space, and Verifix aligns the student's program to a reference under verified equivalence \citep{clara2018,sarfgen2018,refactory2019,verifix2022}. These repair each submission cheaply, at two prices: an assignment must first accumulate a large pool of correct solutions, and repair proceeds by matching the student's control flow against one of them, so a submission whose structure diverges from every reference is out of reach \citep{orvalho2025}. Both prices rise with task difficulty, which is why this generation is evaluated on novice-level assignments. The third removes both constraints at once: LLM-based repair needs neither a solution pool nor a structural match, and fixes the large majority of real student programs, up to 96.5\% of buggy submissions in PyDex \citep{pydex2024}, at modest per-bug prices \citep{chatrepair2024,alpharepair2022,fastfixer2024,cref2024}.

What the third generation fixed in coverage, however, it broke in \emph{cost structure}. Its deployment default is one model query per buggy submission, so spending scales linearly with enrollment and restarts every term --- while the queries themselves are massively redundant. Assignment repair is a \emph{many-instances, one-specification} regime: one handout is attempted by hundreds or thousands of students whose failures cluster into a handful of recurring misconceptions \citep{clara2018,refactory2019}; on the corpus we study, 77\% of a repair prompt is byte-identical across submissions to the same assignment. Paying a model to rediscover the same off-by-one for the three-hundredth time is not intelligence at work; it is a billing artifact. The standard remedies do not change this shape: cheaper models and provider caching \citep{anthropiccaching,openaicaching} shrink the \emph{constant}, retrieval enriches the query \citep{lsgen2026}, but every submission still triggers a frozen-model round trip, with the attendant marginal cost, latency, rate limits, nondeterminism, and shipping of student code to an external service. The question worth asking is not how much a call costs, but \emph{where in the pipeline the LLM is invoked}.

Our answer moves the LLM from the marginal-cost column to the fixed-cost column: \textbf{spend the LLM once per assignment, not once per submission}. Agent research has shown that LLMs can author reusable code once and amortize it across many uses \citep{toolmakers2024,voyager2024}; classical program synthesis has even learned per-assignment fix rules from examples \citep{refazer2017}. We instantiate this idea for assignment repair, under the discipline the setting demands --- every patch validated against the instructor's tests, never trusted from generation. In \textsc{CoEP} (\underline{Co}st-\underline{E}ffective \underline{P}rogram repair), an LLM agent reads the specification, tests, and a clustered sample of worked (buggy $\to$ fixed) pairs, and authors the assignment-specific layer of a local repair tool: AST rewrite rules named after the misconceptions they fix. That layer runs on a shared symbolic substrate --- a generic small-edit library and a reference-guided \emph{minimal-hunk transplant} engine that adopts the smallest differing hunks from the structurally nearest correct solution, in the lineage of reference-reuse repair \citep{clara2018,sarfgen2018,refactory2019}. Every candidate is executed against the visible tests before it is kept, and the builder loop refines the module against harness feedback; a tool can never self-report success. The frozen tool then repairs submissions locally, in about a second on a CPU, at \emph{zero} marginal LLM cost, and the few it abstains on escalate to a conventional per-submission call, so the hybrid never sacrifices coverage.

The resulting artifact does not merely approximate the hand-built state of the art --- it beats it on its own benchmark and its own metric. Against Refactory \citep{refactory2019}, \textsc{CoEP}'s local repair covers more submissions at smaller patch size (\LocalRR\% vs.\ 90.8\% repair rate, \LocalRPS{} vs.\ 0.40 mean relative patch size over 1{,}686 real student programs). We are explicit about attribution: the rule layer produces ${\sim}13\%$ of local fixes at near-minimal patch size (RPS ${\approx}0.03$), the transplant engine the rest --- and a framework-only ablation shows the symbolic substrate alone already carries the coverage, so the LLM layer's measured contribution on this corpus is the \emph{diagnosis} (misconception-labeled repairs) and the strategy-matched escalation path, not the headline number. The claim is therefore not that an LLM wrote a SOTA repairer; it is that the \emph{invocation structure} --- one cheap build plus a ${\sim}2\%$ fallback tail instead of an inference per submission --- removes the per-submission model call for everything repaired locally, while the artifact it feeds exceeds the hand-built state of the art.

The stakes scale with where repair is deployed. In one CS1 offering the per-submission bill is dollars; on an online judge it is not: CodeNet aggregates 13.9M submissions to 4{,}053 problems, 46.4\% of them failing their tests \citep{codenet2021}. At a representative frontier tier, one repair pass over that backlog is on the order of \$18K of inference, re-paid as every new submission arrives --- where the amortized route pays a fixed ${\sim}\$1$K of one-off builds plus a ${\sim}2\%$ escalation tail, and the gap \emph{widens} with every further submission. The comparison is also robust to pricing. If building a tool costs $C_{\text{build}}$ and it locally resolves a fraction $(1{-}f)$ of submissions that would each have cost $\Delta$, amortization wins once enrollment exceeds $N^{*} = C_{\text{build}} / (\Delta(1{-}f))$ --- and when build and per-query spending are priced on the same token schedule, $N^{*}$ is \emph{invariant to token price}: ``just use a cheaper model'' shrinks both sides of the ledger and leaves the crossover untouched. Meanwhile the fixed-cost artifact carries properties per-submission inference cannot offer at any price, scoped to the locally repaired fraction: it assembles patches on the AST, so it cannot emit syntactically invalid code and splices minimal spans rather than regenerating files; it is deterministic and reproducible; it runs offline, so student code never leaves the institution and repair latency does not grow with enrollment; and its rule-fired repairs aggregate into a per-class misconception profile an API call never returns.

This paper makes the following contributions:
\begin{itemize}
\item \textbf{A cost-structure reformulation of assignment repair.} We move the LLM from per-submission marginal cost to per-assignment fixed cost, with a break-even analysis $N^{*} = C_{\text{build}}/(\Delta(1{-}f))$ that is price-invariant under a stated pricing assumption --- amortization is a structural advantage, not a constant-factor one that cheaper models erase.
\item \textbf{The \textsc{CoEP} system.} A builder agent synthesizes misconception-named AST rewrite rules through a generate--validate--refine loop \citep{selfrefine2023,reflexion2023}, atop a shared substrate of generic edit rules and reference-guided minimal-hunk transplant with variable renaming; every patch is independently test-validated, so a tool can never self-report success, and abstentions escalate to a strategy-matched LLM fallback.
\item \textbf{An empirical result on the baseline's own corpus and metric.} \textsc{CoEP}'s local repair exceeds Refactory on both coverage and patch size at negligible one-off build cost, deterministic and offline at 1--2\,s per submission, with an honest mechanism attribution (rule layer ${\sim}13\%$, transplant ${\sim}87\%$), a framework-only ablation isolating the LLM layer's contribution, and per-builder analyses across two commodity models.
\item \textbf{Artifacts.} We release the harness, dataset-import pipeline, prompts, synthesized repairers, and all raw model outputs.\footnote{Anonymized repository submitted as supplementary material.}
\end{itemize}

\section{The Cost Anatomy of Per-Submission Repair}
\label{sec:anatomy}

Decomposing the per-submission prompt of our PyDex reproduction (and, mutatis mutandis, of ChatRepair-style systems \citep{pydex2024,chatrepair2024}) shows where the money goes. Averaged over the Refactory corpus, a query consumes \BaseInTok{} input and \BaseOutTok{} output tokens: a preamble with the assignment description and visible tests (241 tokens, 55\%), the buggy-submission section (99 tokens, 23\%), which is the \emph{only} part that varies within an assignment, and fixed instructions (99 tokens, 23\%). Only the contiguous \PrefixFrac\% prefix ahead of the code is even cacheable, and richer prompt styles widen the gap: the PyDex-style few-shot variant re-transmits 1{,}493 identical tokens per query, 88\% of its input.

Two consequences follow. (1)~\emph{Caching is a discount, not a fix; here, not even a discount.} Prompt caching bills a shared prefix at $0.1\times$ after a $1.25\times$ write \citep{anthropiccaching}; with no minimum it would cut per-submission cost \CacheSavingFrac\%, but CS1 repair prompts (\BaseInTok{} tokens) fall below the provider's 1{,}024-token cacheable minimum, so even that bound is unreachable; caching does engage on the bloated few-shot prompt (1{,}705 tokens; \$6.5 to \$2.9$\times10^{-3}$): the redundancy is real, but provider caching serves it at the wrong granularity. (2)~\emph{The redundancy is exactly the amortizable part.} What is constant per assignment, namely understanding the specification, the tests, and the space of likely mistakes, can be reified \emph{once} into an executable artifact. That is the move \textsc{CoEP} makes, and the rest of the paper quantifies what it buys.

\subsection{Problem Formulation}
An \emph{assignment} is a triple $A = (d, T, R)$: a natural-language description $d$, a test suite $T = \{(x_i, y_i)\}$ (function-entry or judge-style stdin/stdout), and the pool $R$ of correct student solutions, which the setting assumes is available at feedback time --- as every per-assignment system from CLARA to Refactory assumes \citep{clara2018,refactory2019}. A \emph{repair} of a buggy submission $b$ is a program $p$ that passes all of $T$. Patch quality is measured, never gated: RPS, the tree-edit distance between the ASTs of $b$ and $p$ normalized by the size of $b$ (computed with Refactory's reference implementation \citep{refactory2019}), is reported for every repair, since a small patch is feedback on the \emph{student's} program while a rewrite passes tests but teaches nothing \citep{itsp2017}.

Conventional LLM-based APR maps each $b$ to a query $\mathrm{LLM}(d, T, b)$. \textsc{CoEP} instead synthesizes, once per assignment, a \emph{repairer} $\rho_A : b \mapsto p \,\cup\, \{\bot\}$, an ordinary module with no model access, and deploys the hybrid: $\mathrm{repair}(b) = \rho_A(b)$ if $\rho_A(b) \ne \bot$ (local, ${\approx}0$ marginal cost), else $\mathrm{LLM}(d, T, b, r)$ --- the conventional call, strengthened with one reference $r$ chosen to match the student's strategy (cluster $R$ on program structure; draw $r$ from the cluster nearest $b$).

\subsection{Repairer Synthesis (once per assignment)}
\textbf{Build-set selection (local, no LLM cost).} The builder does not see the whole pool; it sees a \emph{chosen} sample. We cluster the buggy pool on a structural view (TF-IDF over normalized-AST paths, identifiers folded) and, walking clusters largest-first, take from each the member with the smallest tree-edit distance to its nearest correct solution --- a clean, single-misconception exemplar rather than the medoid's typical-but-tangled program --- paired with that nearest correct program. The result is a set of worked (buggy $\to$ fixed) pairs: frequent misconceptions first, each shown \emph{with} its minimal fix, so a weak builder needs only to generalize a transformation it is shown, not infer it.

\textbf{Rule authoring.} The builder LLM receives $d$, $T$, reference solutions (structural-cluster medoids of $R$), and the worked pairs, and emits the assignment-specific rule module: AST rewrite rules, each named after the misconception it targets and tagged with the failure symptoms it addresses. The contract is strict: locate the edit on the AST, splice it as a source-span replacement (never re-render the module, which reformats untouched lines), emit \emph{candidates} rather than claimed fixes, and never rewrite a whole function --- a rule that cannot express a targeted edit must abstain so the submission escalates.

\textbf{Generate--validate--refine.} A single-shot module can contain its own defects, so the harness closes the loop: it loads the module, runs it on the sample bugs, \emph{independently} validates every candidate patch by executing the full suite (the repairer's own claims are never trusted), and, while any sample remains unrepaired, returns the module with per-bug outcomes and the still-failing sources for revision, up to $R_{\max}{=}3$ builder calls. The best-validated round is kept. Build cost is exactly the token count of these $\le R_{\max}$ exchanges, measured from the raw strings --- \$0.004--\$0.05 per assignment at the cheapest tiers.

\subsection{Local Repair (every submission)}
The frozen tool repairs in three stages, cheapest and smallest-patch first, validating every candidate against the full suite before it is kept:

\textbf{(1) Named rules + generic search.} Rules are \emph{candidate generators}, composed by a symptom-ordered combination search: the submission's failing-test signature ranks rules whose declared symptoms match, then single rules, then pairs, under an explicit candidate budget. A shared generic library (comparison flips, off-by-one range and index shifts, Boolean-operator flips --- the inversion of the classical mutation-operator space \citep{mutants2014,par2013,tbar2019}) is always on, so common slips are covered regardless of what the builder wrote. Every patch that survives carries the ordered list of rule names that produced it --- provenance that aggregates into a per-class \emph{misconception profile}.

\textbf{(2) Reference-guided minimal-hunk transplant.} Most student bugs need a structural edit no token-level rule expresses; the correct pool supplies it. We diff $b$ against its structurally nearest correct solutions, rename the reference's variables to the student's (parameters by position, locals by first-appearance order), and adopt the \emph{smallest} set of differing line-hunks that passes the tests, candidates ordered smallest-first and batch-validated, returning the minimum-RPS passer. This is reference reuse in the lineage of CLARA, Sarfgen, and Refactory \citep{clara2018,sarfgen2018,refactory2019}, at hunk granularity rather than block granularity --- which is what keeps patches smaller than the hand-built tool's.

\textbf{(3) Escalation and self-learning.} A submission both stages abstain on takes the fallback $\mathrm{LLM}(d,T,b,r)$, its cost counted against \textsc{CoEP} in every comparison. Each successful fallback fix can be generalized by the LLM into a new named rule, appended only if the augmented tool then repairs that miss on its own (else rolled back) --- so the tool accumulates coverage across a term. Self-learning spends model calls only on submissions that already escalated, so the once-per-assignment build claim is untouched; still, to keep the accounting unambiguous we evaluate two configurations: \textsc{CoEP} (frozen tool, no rule additions --- every headline number in this paper) and \textsc{CoEP-SL} (absorption enabled, its calls priced), reported separately.

The local path runs on a CPU in ${\sim}1$--$2$\,s per submission, deterministically and offline; a defective tool degrades to $\bot$ (escalation), never to a wrong ``repair'', because the grading harness re-validates every patch before a student sees it.

\section{Experimental Setup}
\label{sec:setup}

We compare six approaches --- Refactory, PyDex, PyDex+cache, and three \textsc{CoEP} configurations forming an ablation ladder: \textbf{\textsc{CoEP}\textsubscript{L}} (the frozen \underline{l}ocal tool alone; zero LLM at deployment), \textbf{\textsc{CoEP}\textsubscript{LF}} (\textsc{CoEP}\textsubscript{L} plus per-submission LLM \underline{f}allback on abstentions), and \textbf{\textsc{CoEP}\textsubscript{LFSL}} (\textsc{CoEP}\textsubscript{LF} plus \underline{s}elf-\underline{l}earning: absorption of successful fallback fixes into new rules) --- and ask three research questions.
\textbf{RQ1 (Repair effectiveness):} per-problem and overall RR and RPS across the six approaches --- does the synthesized local tool beat the hand-built symbolic SOTA, and what do fallback and self-learning add on top?
\textbf{RQ2 (Cost):} what does each approach cost --- turnaround time decomposed into $\mathrm{ATT}_{\mathrm{cpu}}$/$\mathrm{ATT}_{\mathrm{api}}$/$\mathrm{ATT}_{\mathrm{all}}$ plus \textsc{CoEP}'s one-off $\mathrm{ATT}_{\mathrm{build}}$, tokens In/OuT, and LLM cost --- and when does the one-off build amortize ($N^{*}$)?
\textbf{RQ3 (Rule analysis \& attribution):} which rules does the builder author and which does self-learning add, which rules recur across problems, which fire most --- and what does the LLM layer add over the shared framework (framework-only ablation)?

\subsection{Dataset}
We evaluate on 11 problems from two real-student corpora (Table~\ref{tab:data}), 2{,}970 buggy submissions in all, covering the two execution models an assignment-repair harness must support. \textbf{Refactory} \citep{refactory2019} gives five CS1 assignments by 361 NUS students, the standard corpus of this literature \citep{verifix2022,pydex2024,orvalho2025}; their tests call named functions (one assignment needs three), so they run in \emph{function-entry} mode. \textbf{Codeforces} gives six competitive-programming problems from the open-r1 release \citep{penedo2025codeforces}, which read stdin/stdout (\emph{judge} mode) and reach beyond CS1. We select the latter by construction: from the \emph{verifiable} subset, we keep problems with $\ge$1 wrong and $\ge$1 accepted Python\,3 submission, \emph{complete} official tests (Codeforces truncates tests over 400 characters; we require none were dropped, so the oracle is the full judged suite), and no special-output checker; to span difficulty we take one representative per rating band \citep{cfratings}, the problem with the most wrong submissions.

\textbf{Oracle fidelity.} A weak suite would let a wrong program pass, inflating every arm's repair rate, so we validate the imported oracles rather than trust the labels: running every Codeforces submission against the full official suite, 1 of 1{,}187 wrong programs passes and 2 of 698 accepted programs fail (0.16\%), the three anomalies excluded. The check also surfaced two runner gaps we fixed---file-mode I/O (\texttt{input.txt}/\texttt{output.txt}) and the fast-I/O idiom (\texttt{sys.stdin.buffer}).

Both corpora are plausibly in every current LLM's training data; we use them \emph{deliberately}, since memorization inflates every LLM arm symmetrically (baselines and builder share a model) while leaving the non-LLM tool and generic search untouched, and cannot pass our harness on the builder's behalf. The same label audit applied to Refactory finds 97 of its 1{,}783 ``wrong'' submissions already pass the full suite; the remaining 1{,}686 truly-buggy programs are the repair targets in every Refactory-corpus figure we report.

\subsection{Baselines}
We compare four systems: one non-LLM tool (Refactory) and, at each of two LLM models, two per-submission baselines (PyDex, PyDex+cache) and \textsc{CoEP}. \textbf{Refactory} \citep{refactory2019} is the classical non-LLM per-assignment tool. On its own corpus we take its published numbers verbatim (RR, RPS, and per-submission time from the paper's strongest configuration). On the Codeforces problems we run the tool itself in its strongest configuration (online refactoring, structure mutation, block repair, 100\% sampling of correct solutions), through a data adapter that feeds the judge-style submissions to its function-based executor under the same test oracle as every other approach. \textbf{PyDex} \citep{pydex2024} is the per-submission LLM paradigm: we reproduce its pipeline --- a multi-modal prompt (handout, visible tests, buggy program, and execution feedback), candidate generation with test-based selection, and iterative feedback refinement --- and drive it with the same model as \textsc{CoEP}, so every difference is attributable to the deployment paradigm, not the model. \textbf{PyDex+cache} re-prices the same queries under provider prompt caching (shared prefix written once at $1.25\times$, read at $0.1\times$) \citep{anthropiccaching}. \textbf{\textsc{CoEP}} (ours) synthesizes one repairer per (assignment, model) once, then repairs locally: problem-specific rules and a shared generic edit library first, reference-guided minimal-hunk transplant for the structural remainder, and per-submission LLM fallback only for what abstains.

We run every LLM arm at the cheapest tier of each provider --- \textbf{GPT-5.4-nano} (\$0.05/\$0.40 per Mtok) and \textbf{Claude Haiku 4.5} (\$1/\$5 per Mtok) --- for two reasons: the cheapest tier is the natural deployment for a cost-driven method, and it makes every measured dollar gap a conservative \emph{floor}, since frontier tiers multiply all per-submission figures by one to two orders of magnitude while the break-even $N^{*}$ is unchanged (RQ2). The non-LLM Refactory is model-independent. This yields the setting grid of Table~\ref{tab:main}.

\subsection{Metrics}
\textbf{Repair rate (RR)}: percentage of buggy submissions for which the system produces a program passing the full test suite. \textbf{Relative patch size (RPS)}: tree-edit distance between buggy and repaired ASTs normalized by buggy program size, computed with the Refactory reference implementation \citep{refactory2019}; smaller patches preserve the student's approach and are pedagogically preferable, and RPS is \emph{reported}, never used to gate a repair. \textbf{Average turnaround time (ATT)}: mean wall-clock seconds to repair one submission end to end, decomposed into $\mathrm{ATT}_{\mathrm{cpu}}$ (local search on the CPU), $\mathrm{ATT}_{\mathrm{api}}$ (model-call latency), and their sum $\mathrm{ATT}_{\mathrm{all}}$; \textsc{CoEP}'s one-off build wall-clock is reported separately as $\mathrm{ATT}_{\mathrm{build}}$ per assignment --- like $C_{\text{build}}$, an intercept rather than a per-submission term. \textbf{Input/output tokens (InT/OuT)}: mean prompt and response tokens per repaired submission. \textbf{LLM cost}: USD spent on model inference per repaired submission and per assignment (including a system's one-off build cost), priced at the tier above from exact prompt/response token counts --- named precisely because monetary inference spend is only one of the costs this paper argues about (latency, determinism, and data egress are carried by ATT and the protocol).

Three derived quantities tie the metrics to the claims. The \textbf{repair-source split} attributes every fix to the mechanism that produced it (synthesized rule, generic rule, reference transplant, or LLM fallback), grounding RQ3's attribution. The \textbf{abstention rate} $f$ --- the fraction of submissions the local tool escalates --- is what the break-even $N^{*}=C_{\text{build}}/(\Delta(1-f))$ consumes. \textbf{Diagnosis coverage} is the fraction of repaired submissions whose patch carries a misconception label (rule-fired repairs), quantifying how much of the instructor-facing profile the tool actually delivers rather than leaving it implicit. Repair rates carry 95\% Wilson intervals; paired comparisons use exact McNemar tests at the submission level, with per-assignment directions reported alongside pooled tests.

\subsection{Protocol}
\textbf{No train/test split.} Every arm sees the same data and is evaluated on \emph{all} \NumEval{} buggy submissions. This is not an advantage granted to any one system but the shared regime of the setting: Refactory consumes all correct solutions before repairing, PyDex draws its in-context example fixes from the submission pool, and \textsc{CoEP} builds from a small sample of it. Since the baselines already exploit the whole pool of buggy and reference programs, \textsc{CoEP} using the same pool is the \emph{identical} experiment, and building a repairer from programs drawn from the evaluation pool is temporally sound because the pool exists in full at feedback time. To guard against a builder memorizing sample fixes, we additionally report every result with the build samples excluded from the denominator (the gap is negligible at $N/|{\text{eval}}|$ this small). The three \textsc{CoEP} variants are derived from a \emph{single} pass over the submission stream, with no duplicated LLM calls: every submission first runs the frozen local tool (that is \textsc{CoEP}\textsubscript{L}'s outcome, and the other variants' whenever it repairs); only on a frozen miss do we retry with the self-learning tool's accumulated rules (an \textsubscript{LFSL}-only local hit), make the one fallback call \textsc{CoEP}\textsubscript{LF} needs anyway (shared with \textsubscript{LFSL}'s accounting unless its retry already repaired), and absorb a successful fallback fix into the \textsc{CoEP}\textsubscript{LFSL} tool (validate-or-rollback; priced to it alone). Headline local numbers are therefore the frozen tool's --- self-learning never inflates them. All LLM interactions --- per-submission repairs and builder/refinement calls alike --- are single-shot prompt$\to$response \emph{exchanges} with no code execution or test access at generation time: PyDex's iterative refinement is realized as a sequence of such exchanges, each round one call ($n{=}1$) whose execution feedback our harness computes and inlines into the next prompt, and every arm's calls are metered identically. All validation is performed by our harness; local search is deterministic. Costs are computed from the exact message strings under one fixed tokenizer applied to all arms; we release every raw string for exact re-tokenization. Refactory ran in the strongest published configuration described above, ported to Python\,3.11, on the same submissions; experiments ran on CPU only.

\subsection{RQ2: Cost and Break-Even}

The three systems differ in \emph{cost structure}, not just constant. A per-submission LLM arm (PyDex) pays an inference on every submission, so its cost grows linearly with enrollment and recurs every term; prompt caching (PyDex+cache) discounts the shared prefix but leaves the linear structure intact. \textsc{CoEP} pays a one-off synthesis cost $C_{\text{build}}$ per assignment, then repairs the covered fraction at \emph{zero} marginal LLM cost locally and pays a per-submission inference only on the abstaining tail.

Let $\Delta$ be the marginal per-submission saving of \textsc{CoEP} over a competitor and $f$ the abstention (fallback) rate; synthesis wins once the enrollment exceeds $N^{*}=C_{\text{build}}/(\Delta(1-f))$. The expression is invariant to token price under the stated assumption that build and per-query tokens are billed on the same schedule: $C_{\text{build}}$ and $\Delta$ then scale together, so a cheaper model or provider caching shrinks both sides equally and does not change $N^{*}$ --- the claim is about \emph{how many model calls per specification} ($N\!\to\!1$), not the price of a call, which is why running every arm at the cheapest tier does not blunt it. On the Refactory corpus the abstention rate is $f \approx 2.2\%$ (local RR \LocalRR\%). \emph{[Table~\ref{tab:main}'s LLM-cost column, per-assignment $f$, and per-assignment $N^{*}$ are populated from the full run.]} Synthesis is cheap: a repairer costs \$0.004--\$0.05 per assignment (\$0.05 with Claude Haiku 4.5, \$0.004 with GPT-5.4-nano on the Refactory assignments), the price of a handful of baseline repairs, paid once. Because every arm runs at the cheapest tier, the measured dollar gaps are a \emph{floor} on the effect, not its size. Projected with our measured prompt sizes onto a representative frontier tier (\$3/\$15 per Mtok --- the class of GPT-5.4-pro or Claude Fable 5 deployments) and judge-scale volume, the structure dominates: repairing CodeNet's 6.5M failing submissions once costs on the order of \$18K per pass and recurs with every cohort, while the amortized route pays ${\sim}\$1$K of one-off builds for its 4{,}053 problems plus a ${\sim}2\%$ escalation tail (${\sim}\$0.4$K) --- an order-of-magnitude gap that grows linearly with every further submission.

Beyond dollars, the covered fraction is repaired in about a second on a CPU with no network dependency, rate limits, or nondeterminism --- properties a hosted per-query API does not offer, and that matter most at deadline-night submission spikes.

\smallskip
\noindent\fbox{\parbox{0.965\columnwidth}{\textbf{RQ2.} \textsc{CoEP} replaces a per-submission inference with a one-off \$0.004--\$0.05 synthesis plus a fallback-only tail, breaking even at $N^{*}=C_{\text{build}}/(\Delta(1-f))$; the bound is price-invariant, so cheaper models and caching shrink both sides without changing when amortization wins.}}

\subsection{RQ3: Rule Analysis and Mechanism Attribution}

\textbf{Two complementary local mechanisms.} \textsc{CoEP}'s local repair combines named rules (problem-specific plus the shared generic library) with reference-guided transplant, and the two carry different loads. The rules make small, \emph{labelled} edits --- a relaxed comparison, an off-by-one bound, a wrong return --- for the common misconceptions, at very small patch size (mean RPS ${\approx}0.03$). But most student bugs are not single-token slips; they need a medium, structural edit no token-level rule expresses, and there the reference-guided transplant supplies it by adopting the smallest set of differing hunks from a structurally-matched correct program, variable-renamed to fit. Across the Refactory corpus the rule layer fixes ${\sim}13\%$ of repaired submissions (220/1{,}648) and the transplant the rest; the transplant is what lifts a rule-only tool (which caps near 18\%) to competitive coverage, while the rules keep the common cases at near-minimal patch size and carry the diagnosis below. A \emph{framework-only} ablation --- the identical tool with the LLM-authored rules removed --- isolates the LLM layer: on this corpus it adds nothing to coverage and almost nothing to patch size (RR 97.75\% vs.\ 97.75\%; mean RPS 0.326 vs.\ 0.329), because the transplant absorbs the cases the rules handled, and the always-on generic library accounts for two-thirds of the rule-layer firings (143 of 220). What the \$0.004--\$0.05 build measurably buys here is therefore not coverage but \emph{diagnosis} --- the misconception-labeled repairs --- and the strategy-matched escalation path; whether LLM-authored rules buy coverage where correct pools are sparse is precisely what the harder Codeforces half of our benchmark tests \emph{[Codeforces cells from the full run]}.

\textbf{Diagnosis for free.} Every rule-produced patch carries the ordered rule names that produced it, so aggregated over a class the tool yields a misconception profile --- how often each named mistake occurred, on which programs --- a report an instructor gets at no extra cost and a per-submission API never emits. Diagnosis coverage --- the fraction of local repairs carrying a misconception label --- is ${\sim}13\%$ on this corpus, concentrated on the most frequent slips. This is a property of the artifact, not the coverage number: it is why a local, auditable repairer is worth synthesizing even where a hosted model would pass the same tests.

\textbf{What is authored, what is learned, what recurs.} Every repair event logs the ordered rule names that produced it, split by origin (builder-authored vs.\ self-learned vs.\ generic), so we can report which misconceptions the builder anticipated, which only surfaced as fallback fixes that self-learning absorbed, which rules recur across problems (the generic comparison/bound slips), and which fire most often per assignment. \emph{[Rule-provenance tables from the full run's event logs.]}

\textbf{Builder capability.} Synthesis is run at the cheapest tier of each provider (GPT-5.4-nano, Claude Haiku 4.5). Showing the builder \emph{worked (buggy $\to$ fixed) pairs} rather than raw buggy samples turns ``infer the fix, then generalize'' into ``generalize this shown repair,'' which the weak models do well (build-sample coverage rises from single digits to 75\% at these tiers), and the shared generic library plus the reference engine make the local path robust to a weak builder --- on the cheapest model the generic and reference mechanisms carry the majority of repairs. Capability is bought once per assignment, not once per submission; that is the entire point.

\smallskip
\noindent\fbox{\parbox{0.965\columnwidth}{\textbf{RQ3.} Named rules (RPS ${\approx}0.03$, with a misconception label) cover the common slips; reference-guided transplant supplies the structural edits that lift coverage from a rule-only ${\approx}18\%$ to Refactory-beating, and the rule provenance yields a per-class diagnosis a hosted API cannot.}}


\section{Related Work}
\label{sec:related}

\textbf{APR for programming assignments.} The pre-LLM systems surveyed in the introduction \citep{itsp2017,clara2018,sarfgen2018,refactory2019,verifix2022} exploit per-assignment structure but need many prior solutions; our transplant stage stands openly in their reference-reuse lineage, at hunk rather than block granularity, and our head-to-head run shows the composed artifact exceeding the strongest of them on both coverage and patch size. Closest to our synthesis layer, Refazer learns per-assignment syntactic transformations from (buggy, fixed) student pairs with PROSE \citep{refazer2017}; \textsc{CoEP} replaces the example-driven synthesizer with a cheapest-tier LLM that \emph{names} the misconception behind each rule, and surrounds the learned layer with generic search, reference transplant, and harness-gated escalation. At AAAI the setting stays active from the per-submission side: counterexample-guided and preference-tuned minimal repair at AAAI-25 \citep{orvalho2025,adapr2025}, and AAAI-26's learner-tailored repair, which retrieves per-assignment example fixes to guide each query \citep{lsgen2026}, amortizing \emph{data} into a retrieval index while every repair still pays for an LLM call (our PyDex arm bounds this design's economics). \textsc{CoEP} instead removes the per-submission call for everything its artifact covers and pays only on escalation.

\textbf{LLM-based repair.} AlphaRepair recast repair as generation \citep{alpharepair2022}; ChatRepair adds conversational test feedback and per-bug cost accounting \citep{chatrepair2024}; PyDex/MMAPR target student programs \citep{pydex2024,mmapr2022}; FastFixer accelerates per-query inference \citep{fastfixer2024}; CREF adds a tutor in the loop \citep{cref2024}. All are per-submission; \textsc{CoEP} is complementary (any can serve as its fallback) but shifts the primary cost to the assignment.

\textbf{Templates, cost-efficient inference, and tool synthesis.} PAR and TBar showed a fixed library of human-curated fix templates repairs a surprising share of real bugs \citep{par2013,tbar2019}; \textsc{CoEP}'s generic layer is a mutation-inversion instance \citep{mutants2014}, and its novelty is the \emph{synthesized, assignment-specific} template layer, authored per specification by an LLM. FrugalGPT cascades, SRepair's cheap pipelines, and provider caching \citep{frugalgpt2024,srepair2024,anthropiccaching,openaicaching} all optimize \emph{within} the pay-per-query paradigm and compose with \textsc{CoEP}, which instead removes queries. Voyager and LLMs-as-tool-makers amortize agent-written code across episodes \citep{voyager2024,toolmakers2024}, self-refinement improving one-shot generations \citep{selfrefine2023,reflexion2023}; \textsc{CoEP} adds what education forces: verifiability (never-trust-self-reports) and minimal, measured patches, because its output is feedback to a learner.

\section*{Ethical Statement}
\textsc{CoEP} automates feedback, not grading, under instructor oversight; unhandled students get full-LLM treatment; repairs are auditable; data are public.
