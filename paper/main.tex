\title{Use LLMs to Build Repair Tools, Not Patch Generation: Cost-Effective Automated Program Repair}
\author{Anonymous submission}
\affiliations{}

\begin{document}
\maketitle

\begin{abstract}
Large language models (LLMs) repair buggy submissions to programming assignments well, but they are deployed \emph{one query per submission}: every buggy program triggers a fresh model call, so cost, latency, and external dependence scale with enrollment and recur every term, while the specification-level reasoning being purchased is identical across a class. Caching and cheaper models shrink only the constant, not the structure. We propose \textsc{CoEP}, which moves the LLM from the marginal-cost to the fixed-cost column: \emph{spend the model once per assignment, not once per submission}. An LLM agent reads the assignment and a clustered sample of worked (buggy $\to$ fixed) pairs and authors the assignment-specific layer of a local repair tool: AST rewrite rules named after the misconceptions they fix, atop a shared symbolic substrate of generic edits and reference-guided minimal-hunk transplant from the class's own correct solutions. Every candidate patch is validated against the instructor's tests before it is kept; the tool can never self-report success, and submissions it abstains on escalate to a conventional per-submission call, so coverage is never sacrificed. On the standard benchmark of this literature, the synthesized tool repairs \emph{more} submissions with \emph{smaller} patches than the strongest hand-built symbolic tool, on that tool's own corpus and metric, with the entire model spend collapsed into a one-off synthesis plus a small escalation tail, so everything repaired locally costs no model call at all, offline and deterministically. A price-invariant break-even analysis shows when amortization wins and why cheaper models and caching do not change the answer, and the artifact yields what a per-query API cannot: reproducible minimal patches and a per-class misconception profile.
\end{abstract}

\section{Introduction}

Timely, individualized feedback is the scarcest resource in programming education: introductory courses enroll hundreds of students on campus and tens of thousands online, each producing buggy submissions no instructor can examine one by one. Automated program repair (APR) has therefore long been proposed as a feedback engine for programming assignments: given a buggy submission and the assignment's test suite, produce a small patch that makes it correct while preserving the student's own approach \citep{itsp2017,clara2018,sarfgen2018,refactory2019,verifix2022}.

Three generations of systems have pursued this goal. Early systems established the setting: test-driven repair whose patch must stay close to the student's program, because an unrelated rewrite passes the tests but teaches nothing \citep{itsp2017}. A second generation mined the class's own solution space, matching each buggy program against previously accepted solutions \citep{clara2018,sarfgen2018,refactory2019,verifix2022}. This repairs cheaply, but it requires a large solution pool and fails whenever a submission matches no reference \citep{orvalho2025}. LLM-based repair removed both constraints and now fixes most real student programs at modest per-bug prices \citep{pydex2024,mmapr2022,chatrepair2024,fastfixer2024}.

What the third generation fixed in coverage, it broke in cost structure. The deployment default is one model query per buggy submission, so spending grows with enrollment and restarts every term. The queries themselves are massively redundant. A single assignment is attempted by hundreds of students whose failures cluster into a few recurring misconceptions \citep{clara2018,refactory2019}, and on the corpus we study, about two thirds of a repair prompt is byte-identical across submissions to the same assignment. Paying a model to rediscover the same off-by-one for the three-hundredth time is not intelligence at work; it is a billing artifact. The standard remedies do not change this shape. Cheaper models and provider caching shrink the constant \citep{anthropiccaching,openaicaching}, and retrieval enriches each query \citep{lsgen2026}, but every submission still triggers a model round trip with its marginal cost, latency, and data egress. The question is not how much a call costs, but where in the pipeline the LLM is invoked.

Our answer is to spend the LLM once per assignment, not once per submission. Agent research has shown that LLMs can author reusable code and amortize it across many uses \citep{toolmakers2024,voyager2024}, and classical synthesis has learned per-assignment fix rules from examples \citep{refazer2017}. \textsc{CoEP} (\underline{Co}st-\underline{E}ffective \underline{P}rogram repair) instantiates this idea for assignment repair. An LLM agent reads the assignment once and authors its problem-specific layer: AST rewrite rules named after the misconceptions they fix. These rules run on a shared symbolic substrate, a generic edit library plus reference-guided transplant from the class's correct pool. Every candidate patch must pass the instructor's tests before it is kept, so a tool can never self-report success. The frozen tool then repairs submissions locally in about a second at zero marginal LLM cost, and the few it abstains on escalate to a conventional per-submission call.

The resulting artifact beats the hand-built state of the art on its own benchmark and metric: \LocalRR\% repair rate at \LocalRPS{} mean relative patch size, against Refactory's 90.8\% at 0.40, over 1{,}686 real student programs. We are explicit about attribution. The rule layer produces about 13\% of local fixes, at near-minimal patch size and with a misconception label each; the transplant engine produces the rest, and an ablation shows the symbolic substrate alone already carries the coverage. The claim is therefore not that an LLM wrote a state-of-the-art repairer. The claim is the invocation structure: one cheap build plus a small fallback tail replaces an inference per submission, and the artifact it feeds exceeds the hand-built tool.

The stakes scale with deployment. In one course the per-submission bill is dollars; on an online judge it is not. The public Codeforces dump our benchmark draws from aggregates 12.6M submissions to over 10{,}000 problems \citep{penedo2025codeforces}, At the standard \$3/\$15 per Mtok rate of the models we run, our measured per-submission repair costs about \$125 per thousand submissions, re-paid as every new submission arrives. The comparison is also robust to pricing. If a build costs $C_{\text{build}}$ and locally resolves a fraction $(1{-}f)$ of submissions that would each have cost $\Delta$, amortization wins past $N^{*} = C_{\text{build}} / (\Delta(1{-}f))$, and $N^{*}$ is invariant to token price when build and query spending follow the same schedule. The artifact also offers what per-submission inference cannot at any price. Every patch is re-executed against the instructor's tests before it is emitted, so it can never be invalid or unverified code, and the rule layer edits by AST-located source-span splice rather than re-rendering the module. It is deterministic and runs offline, so student code never leaves the institution. Its rule-fired repairs aggregate into a per-class misconception profile that no API call returns.

This paper makes the following contributions:
\begin{itemize}
\item \textbf{A cost-structure reformulation of assignment repair.} We move the LLM from per-submission marginal cost to per-assignment fixed cost, with a price-invariant break-even analysis $N^{*} = C_{\text{build}}/(\Delta(1{-}f))$: amortization is a structural advantage, not a constant-factor one that cheaper models erase.
\item \textbf{The \textsc{CoEP} system.} A builder agent synthesizes misconception-named AST rewrite rules through a generate--validate--refine loop \citep{selfrefine2023,reflexion2023}, atop a shared substrate of generic edits and reference-guided minimal-hunk transplant. Every patch is independently test-validated, and abstentions escalate to a strategy-matched LLM fallback.
\item \textbf{An empirical result on the baseline's own corpus and metric.} \textsc{CoEP}'s local repair exceeds Refactory on both coverage and patch size at negligible one-off build cost, with an honest mechanism attribution, a framework-only ablation isolating the LLM layer's contribution, and per-builder analyses across two commodity models.
\item \textbf{Artifacts.} We release the harness, dataset-import pipeline, prompts, synthesized repairers, and all raw model outputs.\footnote{Anonymized repository submitted as supplementary material.}
\end{itemize}

\section{The Cost Anatomy of Per-Submission Repair}
\label{sec:anatomy}

Decomposing the per-submission prompt of our PyDex reproduction shows where the money goes \citep{pydex2024,chatrepair2024}. Averaged over the Refactory corpus, about two thirds of a query's input tokens are byte-identical across every submission to the same assignment: the instructions, the visible tests, and, in the zero-shot layout, the description. Only the buggy program and the retrieved exemplars vary. Provider caching cannot reach that redundancy, because it discounts a leading shared \emph{prefix} rather than shared content. PyDex's layouts place the variable material first, so the longest identical prefix across submissions is about ten tokens, a few percent of the prompt. The remaining reuse is within a submission, across the $K$ sampled candidates, and even that is gated by cacheable minimums of 1{,}024 to 4{,}096 tokens that these 1{,}300-token prompts meet only at the smaller end.

Two consequences follow. First, caching is a discount, not a fix, and here not even a discount: the redundancy is real, but provider caching serves it at the wrong granularity. Second, the redundancy is exactly the amortizable part. What is constant per assignment, namely understanding the specification, the tests, and the space of likely mistakes, can be reified once into an executable artifact. That is the move \textsc{CoEP} makes, and the rest of the paper quantifies what it buys.

\subsection{Problem Formulation}
An \emph{assignment} is a triple $A = (d, T, R)$: a natural-language description $d$, a test suite $T = \{(x_i, y_i)\}$ (function-entry or judge-style stdin/stdout), and the pool $R$ of correct student solutions, which the setting assumes is available at feedback time, as every per-assignment system from CLARA to Refactory does \citep{clara2018,refactory2019}. A \emph{repair} of a buggy submission $b$ is a program $p$ that passes all of $T$. Patch quality is measured, never gated: RPS, the tree-edit distance between the ASTs of $b$ and $p$ normalized by the size of $b$, following Refactory's definition \citep{refactory2019}, is reported for every repair, since a small patch is feedback on the \emph{student's} program while a rewrite passes tests but teaches nothing \citep{itsp2017}.

Conventional LLM-based APR maps each $b$ to a query $\mathrm{LLM}(d, T, b)$. \textsc{CoEP} instead synthesizes, once per assignment, a \emph{repairer} $\rho_A : b \mapsto p \,\cup\, \{\bot\}$, an ordinary module with no model access, and deploys the hybrid: $\mathrm{repair}(b) = \rho_A(b)$ if $\rho_A(b) \ne \bot$ (local, ${\approx}0$ marginal cost), else $\mathrm{LLM}(d, T, b, r)$: the conventional call, strengthened with one reference $r$ chosen to match the student's strategy by clustering $R$ on program structure and drawing $r$ from the cluster nearest $b$.

\subsection{Repairer Synthesis (once per assignment)}
\textbf{Build-set selection (local, no LLM cost).} The builder does not see the whole pool; it sees a \emph{chosen} sample. We cluster the buggy pool on a structural view (TF-IDF over normalized-AST paths, identifiers folded) and, walking clusters largest-first, take from each the member with the smallest tree-edit distance to its nearest correct solution, a clean single-misconception exemplar rather than the medoid's typical but tangled program, paired with that nearest correct program. The result is a set of worked (buggy $\to$ fixed) pairs: frequent misconceptions first, each shown \emph{with} its minimal fix, so a weak builder needs only to generalize a transformation it is shown, not infer it.

\textbf{Rule authoring.} The builder LLM receives $d$, $T$, reference solutions (structural-cluster medoids of $R$), and the worked pairs, and emits the assignment-specific rule module: AST rewrite rules, each named after the misconception it targets and tagged with the failure symptoms it addresses. The contract is strict. A rule locates its edit on the AST and splices it as a source-span replacement, never re-rendering the module, which would reformat untouched lines. It emits candidates rather than claimed fixes, and it never rewrites a whole function: a rule that cannot express a targeted edit must abstain so the submission escalates.

\textbf{Generate--validate--refine.} A single-shot module can contain its own defects, so the harness closes the loop: it loads the module, runs it on the sample bugs, \emph{independently} validates every candidate patch by executing the full suite (the repairer's own claims are never trusted), and, while any sample remains unrepaired, returns the module with per-bug outcomes and the still-failing sources for revision, up to $R_{\max}{=}3$ builder calls. The best-validated round is kept, and build cost is exactly the token count of these exchanges, measured from the raw strings.

\subsection{Local Repair (every submission)}
The frozen tool repairs in three stages, cheapest and smallest-patch first, validating every candidate against the full suite before it is kept:

\textbf{(1) Named rules + generic search.} Rules are \emph{candidate generators}, composed by a symptom-ordered combination search: the submission's failing-test signature ranks rules whose declared symptoms match, then single rules, then pairs, under an explicit candidate budget. A shared generic library of comparison flips, off-by-one range and index shifts, and Boolean-operator flips is always on, so common slips are covered regardless of what the builder wrote; it is the inversion of the classical mutation-operator space \citep{mutants2014,par2013,tbar2019}. Every patch that survives carries the ordered list of rule names that produced it, provenance that aggregates into a per-class \emph{misconception profile}.

\textbf{(2) Reference-guided minimal-hunk transplant.} Most student bugs need a structural edit no token-level rule expresses; the correct pool supplies it. We diff $b$ against its structurally nearest correct solutions, rename the reference's variables to the student's (parameters by position, locals by first-appearance order), and adopt the \emph{smallest} set of differing line-hunks that passes the tests, candidates ordered smallest-first and batch-validated, returning the minimum-RPS passer. This is reference reuse in the lineage of CLARA, Sarfgen, and Refactory \citep{clara2018,sarfgen2018,refactory2019}, at hunk granularity rather than block granularity, which is what keeps patches smaller than the hand-built tool's.

\textbf{(3) Escalation.} A submission both stages abstain on takes the fallback $\mathrm{LLM}(d,T,b,r)$, its cost counted against \textsc{CoEP} in every comparison. Abstention is not the only trigger. Local repair's acceptance test is the instructor's suite, which says nothing about patch size, so transplant can return a patch larger than the student's whole program while the rule layer must abstain whenever it cannot express a targeted edit. We give transplant the same contract by escalating any passing local patch whose $\mathrm{RPS}$ exceeds $1$: a patch at least as large as the program it repairs is a rewrite, not a repair, under any assignment's standards. The smaller of the local and model patches is kept, so escalating can cost a call but never coverage or patch size.

The threshold is a constant, not a calibrated quantity, and that is a finding rather than a simplification. We swept it over 38 settings --- relative rules anchored on the median or mean with MAD, standard-deviation or interquartile spread, bare quantiles, multiples of the assignment's median, and fixed constants --- and every one of them leaves repair rate unchanged and every one of them beats all three baselines on repair rate, patch size, turnaround and dollars simultaneously (RQ5). Within that family, making the threshold relative to the assignment does not pay: a single corpus-wide cutoff sits on the same cost-quality frontier or better, because $\mathrm{RPS}$ is already normalized by program size and a second per-assignment normalization spends calls where the tool is doing well rather than where it is doing badly. Since no setting is measurably best, we take the only one whose value is a definition rather than a fitted constant, and report the rest as a sensitivity band.

\textbf{(4) Self-learning.} Each successful fallback fix can be generalized by the LLM into a new named rule, kept only if the augmented tool then repairs that miss on its own and rolled back otherwise. Absorption writes to a staging copy the evaluated pass never consults, so no submission's outcome depends on which submissions preceded it and both deployment configurations remain reproducible from the frozen artifact alone. The accumulated rules are a separate artifact, evaluated by a second frozen pass and priced to themselves rather than to the configuration they were gathered alongside (Section~\ref{sec:setup}). Self-learning spends model calls only on submissions that already escalated, so it too leaves the build claim untouched.

The local path runs on a CPU in ${\sim}1$--$2$\,s per submission, deterministically and offline; a defective tool degrades to $\bot$ (escalation), never to a wrong ``repair'', because the grading harness re-validates every patch before a student sees it.

\section{Experiments}

\subsubsection{Research Questions.}
The primary research questions (RQs) addressed by our evaluation are as follows:
\begin{itemize}
\item \textbf{RQ1} (\emph{repair effectiveness}): Assignment by assignment, how many submissions does \textsc{CoEP} repair and how much of each program does it edit, against a state-of-the-art symbolic tool and a per-submission LLM repairer?
\item \textbf{RQ2} (\emph{cost effectiveness}): How much does the once-per-assignment invocation structure reduce turnaround time and dollars, past what submission volume does the one-off build pay off, and can provider prompt caching or cheaper model tiers close the gap?
\item \textbf{RQ3} (\emph{where the repairs come from}): How do the LLM-authored rules, the shared symbolic substrate, the reference transplant, and the fallback each contribute to the repairs and to the misconception labels the tool reports?
\item \textbf{RQ4} (\emph{learning from its own escalations}): Do the rules \textsc{CoEP} induces from its own fallback fixes improve the frozen tool on submissions they were not induced from?
\item \textbf{RQ5} (\emph{what the conclusion survives}): Does the advantage hold across assignment difficulty, from CS1 to Codeforces problems rated 800 to 2000, across both LLM providers, and across the choice of escalation threshold?
\end{itemize}

\subsubsection{Baselines.}
\label{sec:setup}
\textbf{Refactory} \citep{refactory2019} is the classical symbolic per-assignment tool: it refactors the class's correct solutions to match each buggy program's structure and transplants the divergent blocks. On its own corpus we use its published results; on Codeforces we run the released tool in its strongest configuration. \textbf{PyDex} \citep{pydex2024} is per-submission LLM repair: each buggy submission is sent to the model in its few-shot layout, which prepends the three most similar (buggy, correct) exemplars retrieved from the class pool, sampled candidates are filtered by the test oracle, and the surviving candidate closest to the student's program is returned. \textbf{PyDex\textsubscript{PC}} re-prices the same queries under provider prompt caching, as an upper bound that assumes a cache hit wherever the provider's rules allow one. \textbf{\textsc{CoEP}} is ours: a repairer synthesized once per assignment and model, evaluated in two deployment configurations plus one that measures what a term of use adds. \textbf{\textsc{CoEP}\textsubscript{L}} runs the frozen local tool alone, with zero LLM use at deployment, and accepts any patch its test oracle passes. That is deliberately the same acceptance rule Refactory uses, so the comparison between them is about repair, not about a size filter one of them applies. \textbf{\textsc{CoEP}\textsubscript{LF}} adds the per-submission fallback, which it spends both on abstentions and on passing local patches above $\mathrm{RPS}=1$; a gate is only meaningful where there is somewhere to escalate to, which is why it lives here rather than in the frozen configuration. \textbf{\textsc{CoEP}\textsubscript{L+SL}} is \textsc{CoEP}\textsubscript{L} re-run with the rules self-learning accumulated, merged and frozen before evaluation so the arm is order-independent; the induction calls are priced to it rather than to \textsc{CoEP}\textsubscript{LF}, which never loads those rules. The submissions a rule was induced from are the only ones for which it is not a test of generalization, and are reported separately.

\subsubsection{Datasets.}
We evaluate on 11 problems and 2{,}970 buggy submissions drawn from two real-student corpora (Table~\ref{tab:data}). Refactory contributes five CS1-level assignments \citep{refactory2019}, the standard corpus of this literature \citep{verifix2022,pydex2024,orvalho2025}. Codeforces contributes six competitive-programming problems from the open-r1 release \citep{penedo2025codeforces}, spanning difficulty ratings from 800 to 2000, which cover five official rating bands from Newbie to Candidate Master \citep{cfratings}; we keep only problems whose complete official test suites are released, so the oracle is the judge's own. Every submission each corpus labels buggy is a repair target for every arm, so the denominator is the pool as published and is identical across arms. No train/test split is used, as prior per-assignment systems assume, and all results additionally hold with \textsc{CoEP}'s build samples excluded from the denominator.

\subsubsection{LLM Configuration.}
Every LLM arm runs on two models, one per provider: \textbf{GPT-5.4-mini} (\$0.75/\$4.50 per Mtok) and \textbf{Claude Sonnet 5} (\$2/\$10 per Mtok). We select each provider's cheapest tier at which prompt caching is functional, for two reasons. First, fairness to the caching baseline: PyDex\textsubscript{PC} only competes if caching can engage, and the absolute cheapest tiers rule it out. We verified empirically that Claude Haiku 4.5 refuses to cache prompts below its 4{,}096-token minimum, above these repair prompts, and that GPT-5.4-nano's automatic caching did not engage even on identical 1{,}200-token prompts, whereas both selected models cache at their documented 1{,}024-token minimums. Second, cheap tiers keep every measured dollar gap a conservative floor, and the break-even $N^{*}$ is price-invariant regardless (RQ3).

\subsubsection{Evaluation Metrics.}
Metrics are grouped by the research question they serve.

\textbf{RQ1 and RQ5 (repair effectiveness).} \textbf{Repair rate (RR)}: percentage of buggy submissions for which the system produces a program passing the full test suite. \textbf{Relative patch size (RPS)}: tree-edit distance between buggy and repaired ASTs normalized by buggy program size, reimplemented from Refactory's definition \citep{refactory2019}; smaller patches preserve the student's approach and are pedagogically preferable. RPS is never used to \emph{claim} a repair the tests do not support; it enters the pipeline only in \textsc{CoEP}\textsubscript{LF}, where a value above 1 routes a submission to the fallback and the smaller of the two patches is kept, so the gate can add a model call but cannot manufacture a repair or enlarge a patch. Repair rates carry 95\% Wilson intervals. Comparisons between arms we ran ourselves are paired at the submission level and tested with exact McNemar, the exact form rather than the chi-square approximation because the discordant counts are often single-digit. That covers every pairing on Codeforces and every pairing against PyDex. It does not cover Refactory on its own corpus, where we quote its published per-assignment results and therefore have no per-submission outcomes to pair against; that one comparison is reported as unpaired rates with intervals, and we mark it as such wherever it appears.

\textbf{RQ2 (cost).} \textbf{Average turnaround time (ATT)}: mean wall-clock seconds to repair one submission end to end, decomposed into $\mathrm{ATT}_{\mathrm{cpu}}$ (local search on the CPU), $\mathrm{ATT}_{\mathrm{api}}$ (model-call latency), and their sum $\mathrm{ATT}_{\mathrm{all}}$; \textsc{CoEP}'s one-off build wall-clock is reported separately as $\mathrm{ATT}_{\mathrm{build}}$ per assignment, an intercept like $C_{\text{build}}$ rather than a per-submission term. \textbf{API cost}: USD spent on model inference per repaired submission and per assignment (including a system's one-off build cost), priced at the tiers above from exact prompt and response token counts. Naming it for the API is deliberate: monetary inference spend is only one of the costs this paper argues about, and latency, determinism, and data egress are carried by ATT and the setup. The \textbf{abstention rate} $f$, the fraction of submissions the local tool escalates, is what the break-even $N^{*}=C_{\text{build}}/(\Delta(1-f))$ consumes. For RQ5 we additionally report the \textbf{gate rate}, the fraction of \emph{repaired} submissions the threshold routes to the fallback, and sweep that threshold over the family of Section~\ref{sec:approach} to show the resulting patch-size/spend frontier.

\textbf{RQ3 and RQ4 (component contributions).} The \textbf{repair-source split} attributes every fix to the mechanism that produced it (synthesized rule, generic rule, reference transplant, or LLM fallback). \textbf{Rule provenance} counts the rules the builder authored, the rules self-learning added, and the rules that actually fired at deployment, and tracks which recur across problems. For RQ4 the comparison is \textsc{CoEP}\textsubscript{L} against \textsc{CoEP}\textsubscript{L+SL} on identical submissions, reported with and without the few each rule was induced from. \textbf{Diagnosis coverage} is the fraction of repaired submissions whose patch carries a misconception label (rule-fired repairs), quantifying how much of the instructor-facing profile the tool actually delivers rather than leaving it implicit.

\subsubsection{Setup.}
All experiments run on a single Apple M1 Ultra workstation (64\,GB RAM, macOS) under Python\,3.13, CPU only for everything but the API calls. PyDex uses $K{=}10$ sampled candidates per submission, issued in parallel, with every call billed and timed. The three \textsc{CoEP} configurations are derived from a single pass over the submission stream with no duplicated LLM calls, so the reported local numbers are always the frozen tool's. Refactory runs with its original algorithm unchanged, ported to Python\,3. We release the code, prompts, raw model outputs, and per-submission logs.

The central finding concerns \textsc{CoEP}'s local repair against the strongest non-LLM tool. On the Refactory corpus of \NumEvalRefac{} buggy submissions, \textsc{CoEP}'s local path of named rules, the shared generic library, and reference-guided transplant repairs \textbf{\LocalRR\%} of submissions at mean \textbf{\LocalRPS} RPS, against Refactory's own reported \textbf{\RefacRR\%} at \textbf{\RefacRPS}: higher coverage and a patch a quarter smaller, at zero marginal LLM cost. This comparison is unpaired, since Refactory's results on its own corpus are published per-assignment aggregates. Where we run Refactory ourselves, on Codeforces, the gap widens and the comparison is paired: \LocalRRCF\% against \RefacRRCF\%, exact McNemar $b{=}406$, $c{=}17$, $p{<}10^{-97}$. This is the result that makes a local tool worth synthesizing. It is not merely cheaper than a symbolic tool that consumes every correct solution; it repairs more.

Against the per-submission LLM baseline the separation is not in coverage. Over the whole benchmark \textsc{CoEP}\textsubscript{L} reaches \LocalRRAll\% and PyDex \PydexRRAll\%, and the paired test finds no difference ($b{=}28$, $c{=}25$, $p{=}0.78$): on CS1-scale programs coverage is near-saturated for any competent repairer \citep{pydex2024}. The separation is in \emph{patch size}. \textsc{CoEP}\textsubscript{L} edits \LocalRPSAll{} of a program against PyDex's \PydexRPSAll, and adding the escalation tail takes \textsc{CoEP}\textsubscript{LF} to \textbf{\HybridRRAll\%} at \textbf{\HybridRPSAll} --- now significantly ahead of PyDex on coverage as well ($b{=}28$, $c{=}7$, $p{=}5.1{\times}10^{-4}$), with 95\% Wilson intervals of $[99.38, 99.82]$ against $[98.52, 99.26]$. Because \textsc{CoEP}'s patches are test-validated before a student sees them, its only local failure mode is abstention ($\bot$), never a wrong repair; abstentions take the per-submission LLM path, so the hybrid never sacrifices coverage. What this costs is RQ2.

Reading Table~\ref{tab:effect} by row rather than by column is what the per-assignment form is for. Refactory's rate swings from 40.3\% to 100\% across the eleven assignments while neither LLM arm drops below 93.8\%, and the swing does not track difficulty: it repairs all three of the hardest problem's submissions (rating 2000) and four in ten of a rating-1600 problem's. What predicts its collapse is whether the correct pool holds a structurally matching reference, which RQ5 takes up. The rows also show where a low patch size is not a virtue. On Codeforces every system's patches inflate, and Refactory's \RefacRPSCF{} looks competitive against \textsc{CoEP}\textsubscript{LF}'s \HybridRPSCF{} --- but it is averaged over the \RefacRRCF\% of submissions it accepts, where \textsc{CoEP}\textsubscript{LF} repairs \HybridRRCF\%. A tool measured only on the cases it accepts is not measured on the same problem. We report both columns rather than choosing the framing that flatters us.

\noindent\fbox{\parbox{0.965\columnwidth}{\textbf{RQ1.} \textsc{CoEP}'s local repair reaches \LocalRR\% RR at \LocalRPS{} mean RPS on the Refactory corpus, beating the classical non-LLM tool (\RefacRR\%, \RefacRPS) on both coverage and patch size at zero marginal LLM cost. Against per-submission LLM repair, coverage is at parity ($p{=}0.78$) and patch size is a third smaller; escalation adds \HybridRRAll\% coverage, ahead of PyDex at $p{<}10^{-3}$.}}

\subsubsection{RQ2: Cost Effectiveness and Break-Even}

\begin{figure*}[t]
\centering
\includegraphics[width=0.92\textwidth]{figures/fig_cost.pdf}
\caption{Cost, and where amortization overtakes per-submission inference. Total
spend is for all \NumEval{} submissions and includes \textsc{CoEP}'s one-off
build; the local search runs on a CPU, so its turnaround carries no network
dependency, rate limit, or nondeterminism.}
\label{fig:cost}
\end{figure*}

The systems differ in \emph{cost structure}, not just constant. A per-submission LLM arm pays an inference on every submission, so its cost grows linearly with enrollment and recurs every term. \textsc{CoEP} pays a one-off synthesis cost $C_{\text{build}}$ per assignment, then repairs the covered fraction at \emph{zero} marginal LLM cost locally and pays a per-submission inference only on the escalating tail. Over the whole benchmark that is \$\HybridUsd{} against PyDex's \$\PydexUsd{} at the frontier tier, a factor of \CostRatio, and \$\HybridUsdMini{} against \$\PydexUsdMini{} at the cheap tier, a factor of \CostRatioMini. Of \textsc{CoEP}'s total, \$\BuildUsdSonnet{} is the one-off build and \$\GateUsd{} the entire deployment spend across \NumEval{} submissions.

Fig.~\ref{fig:cost}(b) turns that into the quantity a department actually decides on. With $\Delta$ the marginal per-submission saving and $f$ the escalation rate, synthesis wins past $N^{*}=C_{\text{build}}/(\Delta(1-f))$, which our measured build cost and escalation tail put at \textbf{11 submissions per assignment} against PyDex and 13 against PyDex\textsubscript{PC}. Ten of our eleven assignments exceed that, most by an order of magnitude; the rug on the axis marks their actual sizes. Below $N^{*}$ a per-query repairer is the right tool, and the paper claims nothing else.

\textbf{Caching and cheaper tiers do not close it.} The standard remedies for per-submission cost are provider prompt caching and cheaper model tiers, and the design measures both. PyDex\textsubscript{PC} re-prices every PyDex query under the provider's documented caching rules, as an upper bound that assumes a cache hit wherever one is allowed; every LLM arm already runs at the cheapest tier at which caching functions. The discount is \CacheSavingFrac\% (\$\PydexUsd{} to \$\PydexPCUsd), and the measurement exposes why it is small: caching pays for a shared leading \emph{prefix}, but the shared material in these prompts is not a prefix. The variable buggy program and retrieved exemplars come first, leaving an identical prefix of about ten tokens; what remains cacheable is the reuse within one submission across its $K$ sampled candidates, and that is what PyDex\textsubscript{PC} realizes. The break-even bound makes the same point analytically: $N^{*}$ is invariant to token price under the stated assumption that build and per-query tokens are billed on the same schedule, since $C_{\text{build}}$ and $\Delta$ scale together. The claim is about how many model calls per specification are made, not the price of a call --- and because every arm runs at the cheapest tier, the measured dollar gaps are a \emph{floor} on the effect rather than its size.

\textbf{Turnaround is a trade, not a sweep.} At the frontier tier \textsc{CoEP}\textsubscript{LF} answers in \HybridATT\,s against PyDex's \PydexATT\,s, and the split is the whole story: \textsc{CoEP} spends \LocalATT\,s on local CPU search and \GateUsd{}-worth of API on a tenth of submissions, while PyDex spends 0.66\,s locally and 13.97\,s waiting on the network. At the cheap tier the ordering reverses --- PyDex answers in \PydexATTMini\,s against our \HybridATTMini\,s --- because a small model returns a single completion faster than our search enumerates and re-executes candidates. We report it rather than quoting only the tier that flatters us. The trade is what the two seconds buy: the local answer is deterministic, has no rate limit, and never leaves the institution, and it is unaffected by the deadline-night spikes that make a hosted queue slowest exactly when a class needs it most.

\smallskip
\noindent\fbox{\parbox{0.965\columnwidth}{\textbf{RQ2.} \textsc{CoEP} replaces a per-submission inference with a one-off \$\BuildUsdSonnet{} synthesis plus a \$\GateUsd{} escalation tail, \CostRatio$\times$ cheaper than per-submission repair over \NumEval{} submissions and breaking even at $N^{*}{=}11$ per assignment. Caching recovers only \CacheSavingFrac\% and $N^{*}$ is price-invariant, so the gap is structural rather than a matter of tier.}}

\textbf{Two complementary local mechanisms.} \textsc{CoEP}'s local repair combines named rules (problem-specific plus the shared generic library) with reference-guided transplant, and the two carry different loads. The rules make small, labelled edits for the common misconceptions --- a relaxed comparison, an off-by-one bound --- and they are surgical: \RuleShare\% of repaired submissions at mean RPS \RuleRPS, with the always-on generic library alone at 0.025. Most student bugs are not single-token slips, though; they need a medium, structural edit no token-level rule expresses, and the transplant supplies it by adopting the smallest set of differing hunks from a structurally-matched correct program, variable-renamed to fit. It carries \RefShare\% of repairs at \RefRPS, five and a half times more of the student's program disturbed. The transplant is what lifts a rule-only tool to competitive coverage; the rules keep the common cases at near-minimal patch size and are the only layer that leaves a diagnosis behind.

Fig.~\ref{fig:source} shows the division is not uniform. Where the correct pool is deep and the assignment small, the transplant dominates and the authored rules take a fifth of the work; where one misconception dominates a class the authored layer takes it over: on C4 a single rule, \texttt{carry\_fix\_two\_value\_print}, repairs 27 of the assignment's 38 submissions, and the authored layer accounts for 78.9\% of them. That is the shape the once-per-assignment build is meant to exploit: the LLM's contribution is largest exactly where the class shares one mistake.

\textbf{What the LLM layer buys.} A \emph{framework-only} ablation, the identical tool with the LLM-authored rules removed and the generic library and transplant left in place, isolates it. \emph{[Ablation cells from the running pass.]} The provenance logs say what to expect and why. The builder authored 91 rules that fired at all, against the generic library's 5, and they fired 789 times against the library's 293 --- but only one authored rule fired on more than one assignment, while \texttt{generic\_flip\_compare} alone fired 198 times across 8 of the 11. The authored layer is assignment-specific by construction, which is the point: it is bought once per assignment and encodes what \emph{this} class got wrong.

\textbf{Escalation as a fourth source.} \textsc{CoEP}\textsubscript{LF} adds one more producer. The threshold fires on \GateFired{} submissions, \GateRate\% of those repaired locally, and the model returns the smaller patch on \GateWon{} of them (\GateWinFrac\%), for \$\GateUsd{} across the benchmark. Those are the cases where no reference aligned hunk-wise and the transplant fell back on rewriting; the escalation is what stops a rewrite from being reported as a repair.

\textbf{Diagnosis for free.} Every rule-produced patch carries the ordered rule names that produced it, so aggregated over a class the tool yields a misconception profile: how often each named mistake occurred, and on which programs. The names are legible as misconceptions rather than as patches --- \texttt{append\_missing\_return\_len\_after\_loop}, \texttt{count\_compare\_relax}, \texttt{slice\_case\_check\_to\_equality} --- and an instructor gets the report at no extra cost, from an artifact that can be read and edited. Diagnosis coverage, the fraction of local repairs carrying such a label, is \RuleShare\% (Table~\ref{tab:source}); a per-submission API emits none of it at any price.

\smallskip
\noindent\fbox{\parbox{0.965\columnwidth}{\textbf{RQ3.} Named rules produce \RuleShare\% of local repairs at mean RPS \RuleRPS, five times smaller than the transplant's \RefRPS{} and each carrying a misconception label; the transplant produces \RefShare\% and is what carries coverage. Authored rules are assignment-specific (one of 91 recurs across problems) while the generic library recurs everywhere, which is why the build is priced per assignment.}}

\textbf{Difficulty.} The six Codeforces problems climb from rating 800 to 2000, and the deep solution pools of the CS1 assignments give way to sparser, more diverse ones as difficulty rises. One pattern is already visible in the completed arms: the symbolic baseline loses ground on Codeforces overall, repairing 78.6\% against the 90.8\% it reports on its own corpus, and its per-problem rate swings between 40.3\% and 100\% with no clean monotone trend in rating. What predicts the collapse is not difficulty itself but whether the correct pool holds a structurally matching reference, since block-level reuse starves when solution strategies diverge. \textsc{CoEP}'s hunk-level transplant faces the same pool sparsity, which is precisely where the authored rules and the fallback tail must carry weight. \emph{[Per-band decomposition from the canonical run; cf\_10C's three submissions are folded into the 1200--2000 band rather than reported alone.]}

\textbf{Provider.} Every LLM arm runs identically on GPT-5.4-mini and Claude Sonnet 5, so a conclusion that held for one provider only would surface here. \emph{[Per-provider deltas from the canonical run.]}

\textbf{Threshold.} The local tool accepts whatever passes the tests, so its patch-size distribution has a tail the acceptance rule does nothing about: the largest local patches exceed the size of the programs they repair. Escalating that tail is what \textsc{CoEP}\textsubscript{LF} spends on, and the question is how much the choice of where to cut matters. We swept 38 settings spanning relative rules (median or mean anchored, with MAD, standard-deviation or interquartile spread), bare quantiles, multiples of the assignment's median, corpus-wide variants of each, and fixed constants. Three things hold across all of them. Repair rate is \emph{identical} to four decimals, because the threshold only re-examines patches the tests already passed and the smaller of the two is kept --- the gate can cost a call but cannot lose a repair. Mean RPS falls monotonically with the escalation rate, with no interior optimum, so the setting is a budget choice rather than a discoverable value. And the total spend across the entire family stays within a band whose width is a rounding error beside the baselines it is compared to \emph{[band from the sweep]}, so every one of the 38 settings beats all three baselines on repair rate, patch size, turnaround and dollars at once (Fig.~\ref{fig:gate}).

Two findings inside the sweep are worth stating because they are negative. Making the threshold \emph{relative to the assignment} does not pay: a single corpus-wide cutoff sits on the same frontier or better, since RPS is already normalized by program size and a second per-assignment normalization directs calls toward assignments where the tool is already doing well. And the median-plus-MAD family we began with is Pareto-dominated inside the sweep --- it buys the same patch-size reduction for more calls. The rule we ship is therefore the one whose value is a definition rather than a fitted constant, and the honest cost of that choice is that it is nearly inert on the three assignments whose local patches are uniformly small \emph{[per-assignment gate rates]}.

\section{Related Work}
\label{sec:related}

\textbf{APR for programming assignments.} The pre-LLM systems surveyed in the introduction \citep{itsp2017,clara2018,sarfgen2018,refactory2019,verifix2022} exploit per-assignment structure, and the reference-reuse ones among them depend on finding a structurally matching correct solution; our transplant stage stands openly in their reference-reuse lineage, at hunk rather than block granularity, and our head-to-head run shows the composed artifact exceeding the strongest of them on both coverage and patch size. Closest to our synthesis layer, Refazer learns per-assignment syntactic transformations from (buggy, fixed) student pairs with PROSE \citep{refazer2017}; \textsc{CoEP} replaces the example-driven synthesizer with a cheapest-tier LLM that \emph{names} the misconception behind each rule, and surrounds the learned layer with generic search, reference transplant, and harness-gated escalation. At AAAI the setting stays active from the per-submission side: counterexample-guided and preference-tuned minimal repair at AAAI-25 \citep{orvalho2025,adapr2025}, and AAAI-26's learner-tailored repair, which retrieves per-assignment example fixes to guide each query \citep{lsgen2026}, amortizing \emph{data} into a retrieval index while every repair still pays for an LLM call (our PyDex arm bounds this design's economics). \textsc{CoEP} instead removes the per-submission call for everything its artifact covers and pays only on escalation.

\textbf{LLM-based repair.} AlphaRepair recast repair as generation \citep{alpharepair2022}; ChatRepair adds conversational test feedback and per-bug cost accounting \citep{chatrepair2024}; PyDex/MMAPR target student programs \citep{pydex2024,mmapr2022}; FastFixer accelerates per-query inference \citep{fastfixer2024}; CREF adds a tutor in the loop \citep{cref2024}. All are per-submission; \textsc{CoEP} is complementary (any can serve as its fallback) but shifts the primary cost to the assignment.

\textbf{Templates, cost-efficient inference, and tool synthesis.} PAR and TBar showed a fixed library of human-curated fix templates repairs a surprising share of real bugs \citep{par2013,tbar2019}; \textsc{CoEP}'s generic layer is a mutation-inversion instance \citep{mutants2014}, and its novelty is the \emph{synthesized, assignment-specific} template layer, authored per specification by an LLM. FrugalGPT cascades, SRepair's cheap pipelines, and provider caching \citep{frugalgpt2024,srepair2024,anthropiccaching,openaicaching} all optimize \emph{within} the pay-per-query paradigm and compose with \textsc{CoEP}, which instead removes queries. Voyager and LLMs-as-tool-makers amortize agent-written code across episodes \citep{voyager2024,toolmakers2024}, self-refinement improving one-shot generations \citep{selfrefine2023,reflexion2023}; \textsc{CoEP} adds what education forces: verifiability (never-trust-self-reports) and minimal, measured patches, because its output is feedback to a learner.

\section*{Ethical Statement}
\textsc{CoEP} automates feedback, not grading, under instructor oversight; unhandled students get full-LLM treatment; repairs are auditable; data are public.
