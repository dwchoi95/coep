\title{\textsc{CoEP}: LLM-Synthesized Repair Tools with Amplified Oracles for Programming Assignments}

\author{Anonymous Author(s)}

% [번역] 우리는 대형 언어 모델(LLM)이 제출물마다 패치를 쓰는 대신 과제마다 한 번 합성한 수리 도구로 학생의 프로그래밍 과제를 수리하는 CoEP를 제시한다. 최근 LLM 기반 프로그램 수리는 자동으로 수리할 수 있는 학생 제출물의 비율을 크게 높였다. 그러나 이 기법들은 버기 제출물마다 모델에 한 번씩 질의하므로, 많은 제출물이 "반복 수리"—같은 과제의 다른 제출물도 필요로 하는 편집—를 필요로 함에도 지출이 수강 인원과 함께 늘며, 강사의 적은 테스트 케이스를 통과하는 패치는 무엇이든 받아들인다. 이 논문은 커버리지와 정확성을 희생하지 않고 모델의 노력을 제출물에서 과제로 옮기는 것을 목표로 한다. 주요 도전과제는 LLM이 합성한 것을 LLM을 믿지 않고 신뢰해야 하며, 강사의 테스트가 많은 후보를 탐색하는 수리기를 판정하기에는 너무 빈약하다는 점이다. 이를 해결하기 위해 CoEP는 학급의 편집 스크립트를 군집화해 작업 쌍을 고르고, 반례 유도 루프로 오개념 이름 재작성 규칙을 합성하며, 합성된 생성기의 입력을 학급의 정답 프로그램으로 라벨링해 강사의 테스트를 증폭하고, 규칙의 조합과 참조 hunk 이식으로 모든 제출물을 로컬에서 수리하며, 제출물당 질의로 넘긴 소수의 제출물에서 새 규칙을 학습한다. CoEP가 반환하는 모든 수리는 LLM이 무엇을 쓰든 증폭된 테스트를 통과하고, 규칙 적용 j번으로 이루어진 수리는 학생 프로그램의 위치를 최대 j곳만 바꾸며, 탐색이 입력의 ε 비율에서 학급과 어긋나는 패치를 받아들일 확률은 증폭 테스트 수에 대해 지수적으로 줄어든다. 11개 과제의 버기 프로그램 2,970개에 대한 실험 결과, CoEP는 그중 99.4%를 수리해 제출물당 LLM 수리의 98.9%와 참조 유도 수리의 85.9%와 대등하거나 앞섰고, 두 LLM에서 모델 지출은 21.2배와 27.3배 적었다. ablation은 그 절약을 local-first 구조에, held-out 테스트에서의 정확성(1학년 과제에서 90.1%와 88.6%에서 98.5%와 98.3%로)을 합성된 오라클에, 더 작은 패치를 합성된 규칙에 귀속시킨다.
\begin{abstract}
We present \tool, which repairs students' programming assignments with a repair tool that a large language model (LLM) synthesizes once per assignment, rather than with a patch the LLM writes for every submission. Recently, LLM-based program repair has substantially improved the share of student submissions that can be repaired automatically. However, these techniques query the model once per buggy submission, so their spending grows with enrollment even though many submissions need ``recurring repairs''---edits that other submissions to the same assignment also need---and they accept any patch that passes the instructor's few test cases. This paper aims to move the model's effort from the submission to the assignment without sacrificing coverage or correctness. One major challenge is that whatever the LLM synthesizes must be trusted without trusting the LLM, and the instructor's tests are too thin to arbitrate a repairer that searches many candidates. To address this, \tool selects worked pairs by clustering the class's edit scripts, synthesizes misconception-named rewrite rules in a counterexample-guided loop, amplifies the instructor's tests with inputs from a synthesized generator labelled by the class's correct programs, repairs every submission locally by composing the rules and transplanting reference hunks, and learns new rules from the few submissions it escalates to a per-submission query. Every repair \tool returns passes the amplified tests, whatever the LLM writes; a repair composed of $j$ rule applications changes at most $j$ positions of the student's program; and the chance that its search accepts a patch departing from the class on a fraction $\varepsilon$ of inputs decays exponentially in the number of amplified tests. Experimental results on 2{,}970 buggy programs from 11 assignments show that \tool repairs 99.4\% of them, compared with 98.9\% for per-submission LLM repair and 85.9\% for reference-guided repair, at 21.2 and 27.3 times lower model spend on two LLMs. An ablation attributes the saving to the local-first architecture, correctness on held-out tests (from 90.1\% and 88.6\% to 98.5\% and 98.3\% on a first-year course) to the synthesized oracle, and smaller patches to the synthesized rules.
\end{abstract}

\section{Introduction}
%=============================================================================

% [번역] 프로그래밍 과제를 위한 자동 프로그램 수리(APR)는 학생의 잘못된 제출물을 자동으로 고쳐 강의의 모든 학생이 즉각적이고 개인화된 피드백을 받게 한다. 과제의 문제 설명, 테스트 케이스, 버기 제출물이 주어지면 이 기법은 모든 테스트 케이스를 통과하는 수정 프로그램을 만들고, 그로부터 힌트나 패치를 학생에게 제시한다. 실제로 한 강의에서는 수백 명의 학생이 같은 과제를 풀고, 온라인 저지에는 같은 문제에 대한 제출물이 수천 건씩 쌓인다. 특히 이미 모든 테스트 케이스를 통과한 제출물은 수리가 활용할 수 있는 참조 프로그램 풀을 이룬다.
Automated program repair (APR) for programming assignments~\cite{gulwani2018automated,wang2018search,hu2019re,ahmed2022verifix,zhang2024pydex} automatically fixes students' incorrect submissions, so that every student in a course receives immediate and personalized feedback~\cite{yi2017feasibility}. Given an assignment's problem description, its test cases, and a buggy submission, the technique produces a fixed program that passes every test case, from which a hint or a patch is presented to the student. In practice, hundreds of students attempt the same assignment in a course, and online judges accumulate thousands of submissions to the same problem~\cite{penedo2025codeforces}. In particular, the submissions that already pass every test case form a pool of reference programs on which repair can draw.

% [번역] 이 과제를 위해 두 계열의 기법이 개발되어 왔다. 참조 유도 기법은 버기 프로그램을 구조적으로 맞는 참조 프로그램에 정렬하고 어긋나는 영역을 옮겨 심는다. 이 기법은 모델이 필요 없고 제출물당 추가 비용 없이 수리한다. LLM 기반 기법은 대신 버기 프로그램으로 대형 언어 모델(LLM)에 질의하므로, 맞는 참조가 필요 없고 더 어려운 문제까지 수리를 넓힌다. 그 결과 자동으로 수리할 수 있는 제출물의 비율이 눈에 띄게 향상되었다.
Two lines of techniques have been developed for this task. Reference-guided techniques~\cite{gulwani2018automated,wang2018search,hu2019re,ahmed2022verifix} align a buggy program with a structurally matching reference program and transplant the regions in which they differ; they need no model and repair each submission at no marginal cost. LLM-based techniques~\cite{zhang2024pydex,xia2024automated,yang2024cref,liu2024fastfixer,orvalho2025counterexample,orvalho2025mentor,yang2026morepair,dai2026learner} instead query a large language model (LLM) with the buggy program, which removes the need for a matching reference and extends repair to harder problems. As a result, the share of submissions that can be repaired automatically has seen marked improvement~\cite{zhang2024pydex,orvalho2025mentor}.

% [번역] 그러나 우리의 관찰은 제출물당 수리가 같은 수리를 거듭 다시 유도한다는 것이다. 이 연구에서 우리는 같은 과제의 다른 버기 제출물이 가장 가까운 참조 프로그램에 이르기 위해 동일한 편집을 필요로 하면 그 수리를 반복 수리라고 정의한다. 3.2절에서 보이듯 11개 과제의 버기 프로그램 2,970개 중 36.6%가 반복 수리를 필요로 하고, 1학년 강의 과제에서는 49.9%에 이른다. 하나의 오개념을 공유하는 두 제출물이 편집 전체까지 공유하는 일은 드물므로 이는 하한이다. 그런데도 LLM 기반 수리기 PyDex는 제출물마다 질의 하나를 지불해 claude-sonnet-5에서 이 프로그램들에 292.77달러를 쓰며, 프롬프트 캐싱은 그 지출의 10.2%만 덜어 준다. 참조 유도 수리는 그 지출을 피하지만, Refactory는 풀에 구조적으로 맞는 프로그램이 없는 1200 이상 등급 온라인 저지 문제에서 버기 프로그램의 54.5%만 수리한다. 결국 강의는 커버리지와, 수강 인원과 함께 늘고 매 학기 되풀이되는 모델 지출 사이에서 선택해야 한다.
However, our observation is that per-submission repair re-derives the same repairs over and over. In this work, we define a repair as \emph{recurring} if another buggy submission to the same assignment needs the identical edit to reach its nearest reference program. As shown in Section~\ref{sec:limit}, 36.6\% of 2{,}970 buggy programs from 11 assignments need a recurring repair, and 49.9\% on first-year course assignments; this is a lower bound, since two submissions that share one misconception rarely share an entire edit. Yet the LLM-based repairer PyDex~\cite{zhang2024pydex} pays one query for every submission, \$292.77 over these programs on \cs, and prompt caching removes only 10.2\% of that spend. Reference-guided repair avoids the spend, but Refactory~\cite{hu2019re} repairs only 54.5\% of the buggy programs on online-judge problems rated 1200 and above, where the pool seldom holds a structurally matching program. Consequently, a course must choose between coverage and a model spend that grows with enrollment and recurs every term.

% [번역] 이 논문에서 우리는 LLM이 제출물마다 패치를 한 번씩 만드는 대신 과제마다 과제 전용 수리 도구를 한 번 합성하게 하는 CoEP(Cost-Effective Program repair)를 제시한다. 출발점은 학급이 저지르는 실수를 담은 재작성 규칙 집합, 즉 작은 error model이 과제의 잘못된 시도 대부분을 고친다는 Singh 등의 관찰이다. 다만 그 error model은 과제마다 손으로 써야 한다. CoEP의 핵심 통찰은 수리 도구에서 과제에 따라 달라지는 부분은 합성할 수 있고, 그것을 쓰는 탐색은 고정해 둘 수 있다는 것이다. 반복 수리는 자신이 고치는 오개념의 이름을 단 AST 재작성 규칙으로 한 번 적어 둘 수 있는 변환이며, 무엇이 올바른 수리인지는 학급의 정답 프로그램이 라벨링하는 테스트 입력 생성기로 과제마다 한 번 날카롭게 할 수 있다. 빌더 LLM은 문제 설명과 소수의 (버기, 참조) 작업 쌍으로부터 둘 다 쓴다. 그러면 배포된 도구는 대부분의 제출물을 모델 없이 수리하고, 고치지 못한 것만 관례적인 제출물당 질의로 넘긴다.
In this paper, we present \tool (\underline{Co}st-\underline{E}ffective \underline{P}rogram repair), which has an LLM synthesize an assignment-specific repair tool once per assignment, rather than a patch once per submission. Our starting point is the observation of Singh et al.~\cite{singh2013automated} that a small \emph{error model}---a set of rewrite rules capturing the mistakes a class makes---corrects most incorrect attempts at an assignment; their error models, however, are written by hand for each assignment. The key insight of \tool is that the assignment-specific parts of a repair tool can themselves be synthesized, while the search that uses them stays fixed. A recurring repair is a transformation that can be written down once as an abstract syntax tree (AST) rewrite rule named after the misconception it repairs, and what counts as a correct repair can be sharpened once per assignment by a generator of test inputs that the class's correct programs label. A builder LLM writes both from the problem description and a handful of worked (buggy, reference) pairs. The deployed tool then repairs most submissions with no model at all, and only what it cannot repair is sent to a conventional per-submission query.

% [번역] 그러나 핵심 도전과제는 반복 수리가 글자 그대로 반복되는 일이 드물다는 점이다. 3.2절에서 보고하듯 버기 프로그램 2,970개는 서로 다른 편집 스크립트 2,228개를 필요로 한다. 규칙 하나가 버기 프로그램 560개 중 105개를 수리하는 cAPS lOCK에서조차, 동일한 편집 스크립트를 공유하는 가장 큰 프로그램 묶음은 31개뿐이다. 따라서 빌더는 각 수리를 자신이 본 프로그램 너머로 일반화해야 하고, 빌더가 쓴 코드는 그 코드에 대한 빌더 자신의 주장을 믿지 않고도 신뢰할 수 있어야 한다. 두 번째 장애물은 강사의 테스트가 빈약하다는 것이다. 1학년 강의에서 과제당 7.4개이므로 이를 통과한 후보도 틀릴 수 있으며, 많은 후보를 탐색하는 도구일수록 문제가 아니라 테스트에 맞는 후보를 찾기 쉽다.
However, a key challenge is that recurring repairs rarely recur verbatim. As reported in Section~\ref{sec:limit}, the 2{,}970 buggy programs need 2{,}228 distinct edit scripts. Even on cAPS lOCK, where a single rule repairs 105 of the 560 buggy programs, the largest group of programs sharing an identical edit script holds only 31. Thus, a builder must generalize each repair beyond the program it was shown, and the code it writes must be trusted without trusting its own claims about that code. A second obstacle is that the instructor's tests are thin, 7.4 per assignment on the first-year course, so a candidate that passes them may still be wrong, and a tool that searches many candidates is precisely the repairer most likely to find one that fits the tests rather than the problem.

% [번역] 이 도전과제들을 해결하기 위해 CoEP는 LLM을 신뢰하지 않는 합성기로 다루고 그것이 만드는 모든 것을 실행으로 검증한다. CoEP는 네 단계를 수행한다. (1) Select는 각 버기 프로그램을 최소 편집 참조 프로그램과 짝짓고 그 결과 편집 스크립트로 학급을 군집화해 군집마다 작업 쌍 하나를 고른다. (2) Synthesize는 빌더가 오개념 이름 재작성 규칙을 쓰고 규칙이 아직 수리하지 못한 작업 쌍을 돌려받는 반례 유도 루프이며, 빌더는 입력 생성기도 써서 학급의 정답 프로그램이 다수결로 라벨링한 입력으로 강사의 테스트 T를 T⁺로 증폭한다. (3) Repair는 프리즈된 규칙 조합에 대한 너비 우선 탐색과 hunk 단위 참조 이식으로 모든 제출물을 수리하고, 기권과 과대 패치에서만 제출물당 질의로 에스컬레이션한다. (4) Learn은 에스컬레이션된 수리를 새 규칙으로 증류한다. 우리는 CoEP가 반환하는 모든 수리가 빌더가 무엇을 쓰든 T⁺를 통과하고, CoEP가 모든 규칙에 단일 지점 계약을 강제하므로 규칙 적용 j번으로 이루어진 규칙 수리는 프로그램의 위치를 최대 j곳만 바꾸며, 후보 N개에 대한 로컬 탐색이 생성된 입력의 ε 비율 넘게에서 학급과 어긋나는 패치를 받아들일 확률이 증폭 테스트 n개에 대해 N(1−ε)ⁿ 이하임을 증명한다. 즉 탐색이 넓을수록 오라클이 중요하다. 또한 규칙 탐색이 가장 얕은 조합을 반환하고, 에스컬레이션이 커버리지를 잃거나 패치를 키우지 않으며, 수리가 종료함을 보인다(4.7절).
To address these challenges, \tool treats the LLM as an untrusted synthesizer and validates everything it produces by execution. It performs four stages: (1) \emph{Select}, which pairs each buggy program with its minimum-edit reference program and clusters the class by the resulting edit scripts, choosing one worked pair per cluster; (2) \emph{Synthesize}, a counterexample-guided loop in which the builder writes misconception-named rewrite rules and is shown the worked pairs they still fail to repair, and in which it also writes an input generator whose inputs the class's correct programs label by majority vote, amplifying the instructor's tests $T$ into a suite $T^{+}$; (3) \emph{Repair}, which repairs every submission by a breadth-first search over compositions of the frozen rules and a hunk-level reference transplant, escalating to a per-submission query only on abstentions and oversized patches; and (4) \emph{Learn}, which distills the escalated repairs into new rules. We prove that every repair \tool returns passes $T^{+}$ whatever the builder writes, that a rule repair composed of $j$ rule applications changes at most $j$ positions of the program, since \tool enforces a single-site contract on every rule, and that a local search over $N$ candidates accepts a patch departing from the class on more than a fraction $\varepsilon$ of generated inputs with probability at most $N(1 - \varepsilon)^{n}$ for $n$ amplified tests, so the broader the search, the more the oracle matters; we also show that the rule search returns a shallowest composition, that escalation never loses coverage or enlarges a patch, and that repair terminates (Section~\ref{sec:props}).

% [번역] 실험 결과는 CoEP가 커버리지와 정확성을 희생하지 않고 LLM 기반 수리의 비용을 크게 줄임을 보여 준다. 우리는 두 빌더 claude-sonnet-5와 gpt-5.4-mini로 11개 과제(1학년 강의 다섯, 800~2000 등급의 Codeforces 문제 여섯)의 버기 프로그램 2,970개에서 CoEP를 Refactory 및 PyDex와 비교했다. CoEP는 프로그램의 99.4%를 수리했으며 Refactory는 85.9%, PyDex는 98.9%였고, 패치는 PyDex보다 31% 작았으며, 지출은 13.83달러와 1.04달러로 PyDex보다 21.2배와 27.3배 적었다. ablation은 이 결과를 귀속시킨다. 합성된 규칙이 없어도 CoEP는 PyDex보다 79~173배 적게 쓰므로 절약은 local-first 구조에서 나오고, 합성된 오라클이 없으면 1학년 과제의 held-out 수리율이 98.5%와 98.3%에서 90.1%와 88.6%로 떨어지며, 합성된 규칙은 RPS 0.25 이하의 패치로 수리한 프로그램의 비율을 5.7포인트와 1.8포인트 올린다. 학급의 처음 10%로 만든 도구는 마지막 4분의 1의 버기 프로그램 중 99.3%와 98.9%를 수리했다.
Experimental results demonstrate that \tool markedly reduces the cost of LLM-based repair without sacrificing coverage or correctness. We evaluated \tool with two builders, \cs and \gm, on 2{,}970 buggy programs from 11 assignments, five from a first-year course~\cite{hu2019re} and six Codeforces problems rated 800 to 2000~\cite{penedo2025codeforces}, against Refactory~\cite{hu2019re} and PyDex~\cite{zhang2024pydex}. \tool repaired 99.4\% of the programs, where Refactory repaired 85.9\% and PyDex 98.9\%, with patches 31\% smaller than PyDex's, and spent \$13.83 and \$1.04 on the two models, 21.2 and 27.3 times less than PyDex. An ablation attributes these results: without the synthesized rules, \tool still spends 79 to 173 times less than PyDex, so the saving comes from the local-first architecture; without the synthesized oracle, its held-out repair rate on the first-year course falls from 98.5\% and 98.3\% to 90.1\% and 88.6\%; and the synthesized rules raise the share of programs repaired with a patch of RPS at most 0.25 by 5.7 and 1.8 points. A tool built from the first 10\% of a class repaired 99.3\% and 98.9\% of the last quarter's buggy programs on the two corpora.

% [번역] - 정식화: 프로그래밍 과제의 수리를 수리 도구에서 과제에 따라 달라지는 두 부분, 즉 AST 재작성 규칙 집합과 입력 생성기로 증폭한 수용 테스트 집합의 합성으로 정식화한다. LLM은 둘 모두의 신뢰하지 않는 합성기이고, 둘을 참조 이식과 결합하는 탐색은 고정된다. 이는 선행 연구가 손으로 쓴 error model을 일반화한다(3–4장).
% [번역] - 기법과 보장: 편집 스크립트 군집화로 작업 쌍을 고르고, 반례 유도 루프로 오개념 이름 규칙을 합성하고, 차분 테스트로 테스트를 증폭하고, 규칙 조합 탐색과 hunk 단위 이식 및 관문을 둔 fallback으로 모든 제출물을 로컬에서 수리하며, 에스컬레이션된 수리에서 새 규칙을 학습하는 알고리즘 CoEP를 제시하고, 합성된 규칙에 단일 지점 계약을 강제하고 규칙 수리의 크기를 묶는 지역성 정리를 증명하며, T⁺ 기준의 건전성, 증폭된 오라클의 레이블 건전성, 탐색이 과적합 패치를 받아들일 확률의 상한과 그 밖의 세 성질을 증명한다(4장).
% [번역] - 평가: 11개 과제의 버기 프로그램 2,970개에서 참조 유도 및 LLM 기반 수리와 비교해 CoEP를 평가한다. 반복 수리의 규모 측정, 비용·정확성·패치 크기를 구조·오라클·규칙에 귀속시키는 ablation, held-out 테스트, 제출 순서 분할을 포함한다. CoEP, 합성된 도구 22개, 입력 생성기 10개, 모든 프롬프트, 제출물별 로그 전체를 공개한다(데이터 가용성 진술).
\textbf{Contributions.} We summarize our contributions below:
\begin{itemize}
  \item \textbf{Formulation:} We formulate repair for programming assignments as the synthesis of the two assignment-specific parts of a repair tool---a set of AST rewrite rules, and an acceptance suite amplified by an input generator---with an LLM as an untrusted synthesizer of both and a fixed search that combines them with a reference transplant, generalizing the hand-written error models of prior work~\cite{singh2013automated} (Sections~\ref{sec:prelim} and~\ref{sec:approach}).
  \item \textbf{Technique and guarantees:} We present \tool, an algorithm that selects worked pairs by clustering edit scripts, synthesizes misconception-named rules in a counterexample-guided loop, amplifies the tests by differential testing, repairs every submission locally by searching rule compositions and transplanting reference hunks behind a gated fallback, and learns new rules from escalated repairs; we enforce a single-site contract on the synthesized rules and prove a locality theorem that bounds the size of rule repairs, along with soundness relative to $T^{+}$, the label soundness of the amplified oracle, a bound on the probability that its search accepts an overfitted patch, and three further properties (Section~\ref{sec:approach}).
  \item \textbf{Evaluation:} We evaluate \tool against reference-guided and LLM-based repair on 2{,}970 buggy programs from 11 assignments, including the prevalence of recurring repairs, an ablation that attributes cost, correctness, and patch size to the architecture, the oracle, and the rules, held-out test cases, and splits by submission order. We make \tool, the 22 synthesized tools, the 10 input generators, every prompt, and every per-submission log publicly available (Data-Availability Statement).
\end{itemize}

    """slice.isupper()/islower() fails on an empty slice; the
    equality form also fixes the isupper/islower mix-up."""
    tree = ast.parse(source)
    out = []
    for node in ast.walk(tree):
        if (isinstance(node, ast.Call) and not node.args
                and not node.keywords
                and isinstance(node.func, ast.Attribute)
                and node.func.attr in ("isupper", "islower")

            candidate = _splice(source, node, new_text)
            if candidate != source:
                out.append(candidate)
    return out

\textbf{A recurring misconception.} cAPS lOCK (Codeforces 131A) asks whether a word was typed with the caps lock on, i.e., whether all its letters, or all but the first, are uppercase. Suppose a student tests the tail of the word with \texttt{s[1:].isupper()} at line~4 of Figure~\ref{fig:example}-(a). The program then fails on a one-letter word such as \texttt{"z"}, since the tail is empty and an empty string is not uppercase in Python. 105 of the 560 buggy programs submitted to this problem share this misconception. Per-submission LLM repair queries the model 105 times to rediscover the same fix, and a reference transplant must import a length guard together with the structure around it. Nor do the 108 programs share one edit: they differ elsewhere, so their edits to the nearest correct program differ too.

% [번역] 도구 합성. CoEP는 첫 수리 전에 도구를 만든다. Select는 버기 프로그램 560개 각각을 편집이 가장 적게 드는 정답 프로그램과 짝짓고 그 편집 스크립트로 프로그램을 군집화해 작업 쌍 353개를 고른다. Synthesize는 이를 빌더 LLM에 보여 주고, 빌더는 재작성 규칙의 Python 모듈로 답한다. CoEP는 규칙을 작업 쌍에 실행해 아직 수리하지 못한 쌍을 돌려주며 이를 세 라운드 반복한다. cAPS lOCK에서 claude-sonnet-5는 1.23달러로 규칙 10개를 썼다. Figure 1-(b)가 그중 하나인 slice_case_check_to_equality다. 이 규칙은 슬라이스에 대한 대소문자 검사를 찾아 빈 슬라이스에서도 성립하는 등식으로 바꿔 끼운다. 규칙은 작업 쌍 하나에서 쓰였지만 AST 위에서 진술되므로 그 패턴이 나타나는 곳이면 어디든 적용된다.
\textbf{Synthesizing the tool.} \tool builds the tool before the first repair. Select pairs each of the 560 buggy programs with the correct program it is fewest edits from and clusters the programs by these edit scripts, yielding 353 worked pairs. Synthesize shows them to a builder LLM, which answers with a Python module of rewrite rules; \tool runs the rules on the worked pairs and returns the pairs they still fail to repair, for three rounds. On cAPS lOCK, \cs wrote 10 rules for \$1.23. Figure~\ref{fig:example}-(b) shows one, \rn{slice_case_check_to_equality}: it locates a case test on a slice and splices in an equality that also holds for the empty slice. The rule was written from one worked pair but is stated over the AST, so it applies wherever the pattern occurs.

% [번역] 로컬 수리. 프리즈된 도구는 규칙 조합에 대한 너비 우선 탐색으로 각 제출물을 수리하며 모든 후보를 테스트 실행으로 검증하고, 통과하는 규칙 조합이 없으면 참조 프로그램에서 줄 hunk를 이식한다. cAPS lOCK에서 slice_case_check_to_equality는 프로그램 105개를, 도구의 규칙들은 모두 147개를, 이식은 나머지 413개를 모델 호출 없이 수리했다. Figure 1-(a)의 수리는 한 줄을 바꾸며 RPS는 0.118이다.
\textbf{Repairing locally.} The frozen tool repairs each submission by a breadth-first search over compositions of its rules, validating every candidate by running the tests, and transplants line hunks from the reference programs when no composition passes. On cAPS lOCK, \rn{slice_case_check_to_equality} repaired 105 programs, the tool's rules 147 in all, and the transplant the remaining 413, without a model call; the repair of Figure~\ref{fig:example}-(a) changes one line, at a relative patch size (RPS) of 0.118.

\textbf{When the tests are thin.} Sequential search (R1) asks for the position at which $x$ would be inserted into a sorted sequence, and its instructor ships 11 test cases, none with a one-element sequence. For the buggy program of Figure~\ref{fig:thin}-(a), the transplant finds the patch of Figure~\ref{fig:thin}-(b), which passes all 11 tests but returns 1 for \texttt{search(-15, [-6])}: its guard \texttt{x <= seq[0]} sits inside a loop that never runs on a one-element sequence. The builder's input generator draws sorted sequences, one-element ones included, and the class's correct programs label each input by majority. 100 such inputs join the 11 tests in $T^{+}$, and the patch of Figure~\ref{fig:thin}-(b) fails 10 of them. The search therefore continues and accepts the patch of Figure~\ref{fig:thin}-(c), transplanted from a reference program with an explicit guard, which also passes the held-out tests of Section~\ref{sec:rq-heldout}. \textbf{Escalation and learning.} When both local strategies abstain, or the local patch is at least as large as the program, \tool issues one query that attaches the minimum-edit reference program (12.6\% of the submissions), and the Learn stage generalizes such repairs into new rules. Whichever path a repair takes, it passes $T^{+}$ (Section~\ref{sec:props}).

\subsection{Program Repair for Programming Assignments}
\label{sec:prelim-apr}

% [번역] 프로그래밍 과제 수리의 주된 목적은 각 버기 제출물을 과제의 테스트 케이스를 통과하는 수정 프로그램으로 바꾸는 것이다. 이를 위해 수리기는 모든 제출물에 대해 후보 프로그램을 반복적으로 생성하고, 검증하고, 선택한다. 우리는 과제를 사중쌍 (d, T, B, R)로 정의하며, d는 자연어 문제 설명, T = {t_1, ..., t_n}는 교수자의 테스트 케이스, B는 버기 프로그램, R은 참조 프로그램을 나타낸다. 프로그램 p가 T의 모든 테스트 케이스를 통과할 때 p ⊨ T로 쓰면 제출물은 B = {p | p ⊭ T}와 R = {p | p ⊨ T}로 나뉜다. b ∈ B를 수리한다는 것은 f ⊨ T인 수정 프로그램 f를 만드는 것이며, 테스트 케이스 일부만 통과하는 후보는 수리가 아니다.
The main aim of program repair for programming assignments is to turn each buggy submission into a fixed program that passes the assignment's test cases. To do so, a repairer iteratively generates, validates, and selects candidate programs for every submission. We define an assignment as a quadruple $(d, T, B, R)$, where $d$ represents the natural-language problem description, $T = \{t_1, \dots, t_n\}$ denotes the instructor's test cases, $B$ indicates the buggy programs, and $R$ the reference programs. Writing $p \models T$ when a program $p$ passes every test case in $T$, the submissions divide into $B = \{p \mid p \not\models T\}$ and $R = \{p \mid p \models T\}$. To repair $b \in B$ is to produce a fixed program $f$ with $f \models T$; a candidate that passes only some test cases is not a repair.

\begin{algorithm}[t]
\caption{Repairing an Assignment}\label{alg:generic}
\footnotesize
\begin{algorithmic}
\Require Description ($d$), tests ($T$), buggy programs ($B$), reference programs ($R$), local repair tool ($L$).
\Ensure Fixed programs ($F$).
\end{algorithmic}
\begin{minipage}[t]{0.42\textwidth}
\begin{algorithmic}[1]
\Procedure{RepairAssignment}{$d, T, B, R, L$}
  \State $F \gets \emptyset$
  \For{\textbf{each} $b \in B$}
    \State $f \gets \V{fail}$
    \If{$L \neq \emptyset$}
      \State $f \gets \Fn{LocalRepair}(L, b, R, T)$
    \EndIf
\algstore{generic}
\end{algorithmic}
\end{minipage}\hfill
\begin{minipage}[t]{0.56\textwidth}
\begin{algorithmic}[1]
\algrestore{generic}
    \If{$f = \V{fail}$ \textbf{or} $\RPS(b, f) > \eta_{\V{rps}}$}
      \For{\textbf{each} $c \in \Fn{Generate}(d, T, b, R)$}
        \State \textbf{if} $c \models T \wedge \RPS(b, c) < \RPS(b, f)$ \textbf{then} $f \gets c$
      \EndFor
    \EndIf
    \State $F \gets F \cup \{(b, f)\}$
  \EndFor
  \State \Return $F$
\EndProcedure
\end{algorithmic}
\end{minipage}
\end{algorithm}

% [번역] Algorithm 1은 과제를 수리하는 일반 알고리즘을 기술한다. 이 알고리즘은 다섯 입력, 즉 설명(d), 테스트 케이스(T), 버기 프로그램(B), 참조 프로그램(R), 로컬 수리 도구(L)를 받는다. 지금은 마지막 입력 L과 관련 함수 LocalRepair를 잠시 미뤄 두자. 그 역할은 4장에서 설명한다. 기존 기법은 도구 없이(즉 L = ∅) Algorithm 1을 실행한다. 2행에서 알고리즘은 수정 프로그램 집합 F를 공집합으로 초기화한다. 그런 다음 각 버기 프로그램 b에 대해 3–10행의 루프를 반복한다. 8행에서 Generate 함수가 b로부터 후보 프로그램을 만들고, 9행은 모든 테스트 케이스를 통과하면서 현재 패치보다 작은 후보 c를 남기므로(RPS(b, fail) = ∞) PyDex처럼 통과하는 후보 중 가장 작은 것이 남는다. 7행은 지나치게 큰 로컬 패치, 즉 RPS(b, f) > η_rps인 경우에도 에스컬레이션하며 그 이유는 4.5절에서 설명한다. 마지막으로 Algorithm 1은 버기 프로그램과 그 수정 프로그램의 쌍 집합 F를 반환하며, f = fail은 수리되지 않은 프로그램을 표시한다.
Algorithm~\ref{alg:generic} describes a generic algorithm that repairs an assignment. It takes five inputs: the description ($d$), the test cases ($T$), the buggy programs ($B$), the reference programs ($R$), and a local repair tool ($L$). For now, let us set aside the last input, $L$, and the associated function, \Fn{LocalRepair}; their roles will be explained in Section~\ref{sec:approach}. Existing techniques run Algorithm~\ref{alg:generic} without a tool (i.e., $L = \emptyset$). At line 2, the algorithm initializes the set $F$ of fixed programs as an empty set. It then repeats the loop at lines 3--10 for each buggy program $b$. At line 8, the \Fn{Generate} function produces candidate programs from $b$, and line 9 keeps a candidate $c$ that passes every test case and is smaller than the current patch, with $\RPS(b, \V{fail}) = \infty$, so the smallest passing candidate survives, as in PyDex~\cite{zhang2024pydex}. Line 7 also escalates an oversized local patch, $\RPS(b, f) > \eta_{\V{rps}}$, for reasons Section~\ref{sec:repair} gives. Finally, Algorithm~\ref{alg:generic} returns the set $F$ of pairs of a buggy program and its fixed program, where $f = \V{fail}$ marks a program that was not repaired.

% [번역] 프로그래밍 과제를 위한 기존 기법은 8행의 Generate 함수를 구현하는 방식에서 갈린다. 참조 유도 기법은 b를 구조적으로 맞는 참조 프로그램 r ∈ R에 정렬하고 둘이 어긋나는 영역을 옮겨 심는다. CLARA와 Sarfgen은 b를 가장 가까운 참조 프로그램에 정렬하고, Verifix는 그 정렬을 형식 검증으로 뒷받침하며, Refactory는 참조 프로그램을 리팩터링해 정렬 가능한 범위를 넓힌다. 이들은 추가 비용 없이 오프라인으로 돌지만, R에 b와 구조가 맞는 프로그램이 없으면 Generate는 후보를 내지 못한다. LLM 기반 기법은 Generate를 모델 질의로 구현한다. PyDex는 d, b, 그리고 학급에서 검색한 (버기, 정답) 예시 세 쌍으로 모델에 프롬프트하고 후보 열 개를 샘플링하며, 다른 기법들은 대화, 튜터링, 미세조정, 결함 위치 추정을 더한다. 이 기법들은 어떤 참조와도 맞지 않는 제출물을 수리하지만, 3행 루프의 매 반복이 자기 질의를 발행하므로 질의 수가 |B|와 함께 늘어난다.
Existing techniques for programming assignments differ in how they implement the \Fn{Generate} function at line 8. Reference-guided techniques align $b$ with a structurally matching reference program $r \in R$ and transplant the regions in which they differ: CLARA~\cite{gulwani2018automated} and Sarfgen~\cite{wang2018search} align $b$ with its nearest reference program, Verifix~\cite{ahmed2022verifix} backs the alignment with formal verification, and Refactory~\cite{hu2019re} refactors the reference programs to widen the range of alignable programs. They run offline at no marginal cost, but \Fn{Generate} returns no candidate when $R$ holds no program whose structure matches $b$. LLM-based techniques implement \Fn{Generate} as a model query: PyDex~\cite{zhang2024pydex} prompts the model with $d$, $b$, and three (buggy, correct) exemplars retrieved from the class and samples ten candidates, while others add conversation~\cite{xia2024automated}, tutoring~\cite{yang2024cref}, fine-tuning~\cite{liu2024fastfixer,yang2026morepair}, or fault localization~\cite{orvalho2025counterexample,orvalho2025mentor}. These techniques repair submissions that no reference matches, but each iteration of the loop at line 3 issues its own query, so the number of queries grows with $|B|$.

\subsection{Limitation of Per-Submission Repair}
\label{sec:limit}

% [번역] 우리의 핵심 관찰은 한 과제의 많은 제출물이 같은 수리를 필요로 하는데도 Algorithm 1은 그 각각을 독립적으로 유도한다는 것이다. 이 연구에서 우리는 같은 과제의 다른 버기 제출물도 필요로 하는 편집을 가진 수리를 반복 수리로 새로 정의한다. 더 정확히는, π(b)를 b로부터 AST 편집 연산이 가장 적게 드는 참조 프로그램, ε(b)를 b를 π(b)로 옮기는 편집 연산의 다중집합이라 하자(둘 다 4.3절에서 정의한다). 다른 b' ∈ B에 대해 ε(b) = ε(b')이면 b의 수리는 반복 수리다.
Our key observation is that many submissions to one assignment need the same repair, yet Algorithm~\ref{alg:generic} derives each of them independently. In this work, we newly define a \emph{recurring repair} as a repair whose edit another buggy submission to the same assignment also needs. More precisely, let $\pi(b)$ be the reference program that takes the fewest AST edit operations from $b$, and $\varepsilon(b)$ the multiset of edit operations that takes $b$ to $\pi(b)$ (both defined in Section~\ref{sec:select}); the repair of $b$ is recurring if $\varepsilon(b) = \varepsilon(b')$ for some other $b' \in B$.

Table~\ref{tab:limit} shows that 1{,}087 of the 2{,}970 buggy programs (36.6\%) across the 11 assignments of our benchmark (Section~\ref{sec:settings}) need a recurring repair, and 49.9\% on the five first-year assignments. Nevertheless, the per-submission repairer PyDex~\cite{zhang2024pydex} spent \$292.77 on \cs querying for each of them, so that a single misconception is paid for once per student who makes it. Surprisingly, the share of recurring repairs falls to 2.7\% on Codeforces problems rated 1200 to 2000, precisely where the reference-guided Refactory~\cite{hu2019re} repairs only 54.5\% of the programs. This might stem from the larger number of solution strategies that harder problems admit: each buggy program needs an edit of its own, and the pool seldom holds a program of the same structure.

% [번역] 질의를 더 싸게 만드는 것으로는 충분하지 않다. 프롬프트 캐싱은 출력 토큰이 지출을 지배하므로 PyDex의 지출을 10.2%와 17.3%만 줄였고(5.3절), 버기 프로그램의 8.6%만 다른 프로그램과 텍스트가 같아 제출물 텍스트로 패치를 메모이즈하는 것은 더 도움이 안 된다.
Making each query cheaper does not suffice: prompt caching~\cite{anthropiccaching,openaicaching} removed only 10.2\% and 17.3\% of PyDex's spend, since output tokens dominate it (Section~\ref{sec:rq-cost}), and memoizing patches by submission text helps even less, as only 8.6\% of the buggy programs are textual duplicates of another.

\subsection{Goal}
\label{sec:goal}

% [번역] 이 논문의 목표는 모델 질의를 제출물이 아니라 과제 단위로 쓰면서 과제의 모든 버기 프로그램을 수리하는 것이다. 형식적으로, 우리는 빌더 질의 수가 |B|와 함께 늘지 않는 방식으로 로컬 수리 도구 L을 합성해 아래 집합을 최대화하는 것을 목표로 한다. 여기서 LocalRepair는 Algorithm 1의 6행에 있는 훅이고, 모든 수리는 그것을 찾은 탐색에 충분할 만큼 강한 수용 테스트 집합 T⁺ ⊇ T를 통과해야 하며, 나머지 프로그램은 8행의 Generate로 넘어간다. 이는 결코 간단하지 않다. 반복 수리로 범위를 좁혀도 편집 스크립트 하나를 공유하는 가장 큰 묶음은 프로그램 48개(R4)에 그친다. 따라서 우리 연구는 세 가지 핵심 도전과제를 다룬다. (1) 수천 개의 서로 다른 편집 중에서, 빌더가 자신이 본 프로그램 너머로 수리를 일반화할 수 있는 작업 예시를 고르는 것, (2) 빌더가 쓴 코드를 그 코드에 대한 빌더의 주장을 믿지 않고 신뢰하는 것, (3) 수리를 찾은 탐색의 폭에 충분할 만큼 강한 테스트로만 수리를 받아들이는 것.
The goal of this paper is to repair every buggy program of an assignment while spending model queries per assignment rather than per submission. Formally, we aim to synthesize a local repair tool $L$, with a number of builder queries that does not grow with $|B|$, such that the set
\[
\{\, b \in B \mid \Fn{LocalRepair}(L, b, R, T) \neq \V{fail} \,\}
\]
is maximized, where \Fn{LocalRepair} is the hook at line 6 of Algorithm~\ref{alg:generic}, and every repair passes an acceptance suite $T^{+} \supseteq T$ strong enough for the search that found it; the remaining programs fall through to \Fn{Generate} at line 8. This is far from straightforward: even among recurring repairs, the largest group sharing one edit script holds only 48 programs (R4). Our work thus tackles three key challenges: (1) selecting, from thousands of distinct edits, the worked examples from which a builder can generalize a repair beyond the program it saw, (2) trusting the code a builder writes without trusting its claims about that code, and (3) accepting a repair only against tests strong enough for the breadth of the search that found it.

Synthesize에서 빌더 LLM은 작업 쌍을 오개념 이름 AST 재작성 규칙의 Python 모듈로 바꾸고, CoEP는 테스트 케이스를 실행해 규칙이 여전히 실패하는 쌍을 돌려주며 라운드 예산까지 반복한다. 빌더는 입력 생성기도 쓰며, CoEP는 그 입력을 참조 프로그램들의 다수결로 라벨링해 T를 T⁺로 증폭한다. 뒤의 두 단계는 모든 제출물에서 돈다. Repair에서 프리즈된 도구는 규칙과 hunk 단위 이식을 시도하고 T⁺를 통과하는 후보만 받아들이며, 둘 다 기권하거나 로컬 패치가 프로그램보다 클 때만 제출물당 질의를 발행한다. Learn에서 모델은 그런 질의의 수리를 새 이름 붙은 규칙으로 일반화하고, 도구는 그 규칙이 수리를 재현할 때만 유지한다.
Figure~\ref{fig:overview} illustrates how \tool synthesizes and deploys an assignment-specific repair tool while interacting with an LLM. The first two stages run once per assignment and build the tool. Select pairs each buggy program with its minimum-edit reference program and chooses one worked pair per cluster of edit scripts, without querying a model. In Synthesize, a builder LLM turns the worked pairs into a Python module of AST rewrite rules, each named after the misconception it repairs, and \tool executes the test cases to return the pairs on which the rules still fail, up to a round budget. The builder also writes a generator of test inputs, which \tool labels by the majority output of the reference programs to amplify $T$ into $T^{+}$. The last two stages run on every submission. In Repair, the frozen tool tries its rules and then a hunk-level transplant, accepting a candidate only if it passes $T^{+}$, and issues a per-submission query only when both abstain or the local patch is larger than the program it repairs. In Learn, the model generalizes each repair obtained from such a query into a new named rule, which the tool keeps only if the rule reproduces the repair.

% [번역] CoEP의 핵심 신규성은 모델을 각 제출물의 수리에서, 수리 도구에서 과제에 따라 달라지는 두 부분, 즉 규칙과 오라클 뒤의 생성기의 구축으로 옮기는 데 있다. 둘 다 오프라인으로 돌고 감사할 수 있는 평범한 코드이며, 둘을 참조 이식과 결합하는 탐색은 고정된다. 5.4절은 각 부분이 무엇을 사는지 측정한다. 제출물당 수리 대비 절약은 local-first 구조가, 강사 테스트 너머의 정확성은 오라클이, 작은 패치는 규칙이 맡는다.
The key novelty of \tool lies in moving the model from the repair of each submission to the construction of the two assignment-specific parts of a repair tool, its rules and the generator behind its oracle, both ordinary code that runs offline and can be audited, while the search that combines them with the reference transplant stays fixed. Section~\ref{sec:rq-stage} measures what each part buys: the local-first architecture accounts for the saving over per-submission repair, the oracle for correctness beyond the instructor's tests, and the rules for small patches.

\subsection{\textsc{CoEP}}

\begin{algorithm}[t]
\caption{\textsc{CoEP}}\label{alg:coep}
\footnotesize
\begin{algorithmic}
\Require Description ($d$), tests ($T$), buggy programs ($B$), reference programs ($R$), builder LLM ($M$).
\Ensure Fixed programs ($F$), repair tool ($L'$).
\end{algorithmic}
\begin{minipage}[t]{0.5\textwidth}
\begin{algorithmic}[1]
\Procedure{CoEP}{$d, T, B, R, M$}
  \State \textbf{/* Step 1. Select */}
  \State $S \gets \aux{Select}(B, R)$ \Comment{$(b^{\star}, \pi(b^{\star})) \in S$}
  \State \textbf{/* Step 2. Synthesize */}
  \State $\langle U, j \rangle \gets \langle S, 0 \rangle$ \Comment{$\eta_{\V{round}} = 3$}
  \Repeat
    \State $j \gets j + 1$
    \State $L_j \gets \aux{Synthesize}(M, d, T, S, U)$
    \State $U \gets \{(b, \WC) \in S \mid \aux{Search}(L_j, b, T) = \V{fail}\}$
  \Until{$U = \emptyset$ \textbf{or} $j = \eta_{\V{round}}$}
\algstore{coep}
\end{algorithmic}
\end{minipage}\hfill
\begin{minipage}[t]{0.48\textwidth}
\begin{algorithmic}[1]
\algrestore{coep}
  \State $L \gets \argmax_{i \le j} \aux{cov}(L_i)$
  \State $T^{+} \gets T \cup \aux{Amplify}(M, d, T, R)$
  \State \textbf{/* Step 3. Repair */}
  \State $F \gets \Fn{RepairAssignment}(d, T^{+}, B, R, L)$
  \State \textbf{/* Step 4. Learn */}
  \State $L' \gets L$
  \For{\textbf{each} $(b, f) \in F$ repaired by \Fn{Generate}}
    \State $\rho' \gets \aux{Learn}(M, b, f)$
    \State \textbf{if} $\aux{Search}(L \cup \{\rho'\}, b, T^{+}) \neq \V{fail}$ \textbf{then} $L' \gets L' \cup \{\rho'\}$
  \EndFor
  \State \Return $F, L'$
\EndProcedure
\end{algorithmic}
\end{minipage}
\end{algorithm}

% [번역] Algorithm 2는 CoEP가 과제의 수리 도구를 합성하고 제출물을 수리하는 방법을 자세히 보여 준다. CoEP는 과제 (d, T, B, R)와 빌더 LLM(M)을 받아 수정 프로그램(F)과 도구를 반환한다. 3행에서 Select 함수가 빌드 집합 S를 고른다(4.3절). 5–11행에서 CoEP는 최대 η_round 라운드로 도구를 합성한다. 각 라운드는 빌더에게 모듈 L_j를 요청하고(8행) 그 모듈이 여전히 수리하지 못하는 작업 쌍 U를 모아(9행) 다음 라운드에 돌려주며, 커버리지가 가장 높은 라운드를 남긴다(11행). 12행에서 Amplify 함수는 수용 테스트 집합 T⁺를 만든다(4.4절). 14행에서 CoEP는 프리즈된 도구 L과 T⁺로 Algorithm 1을 호출해 모든 버기 프로그램을 수리하고, 16–19행에서 모델 질의로 얻은 수리로부터 새 규칙을 학습한다. 실험에서 η_round는 3으로 두었고, 아래의 다른 모든 상수도 모든 과제에 걸쳐 고정했다.
Algorithm~\ref{alg:coep} details how \tool synthesizes a repair tool for an assignment and repairs its submissions. \tool accepts the assignment $(d, T, B, R)$ and a builder LLM ($M$), and returns the fixed programs ($F$) together with the tool. At line 3, the \aux{Select} function chooses the build set $S$ (Section~\ref{sec:select}). At lines 5--11, \tool synthesizes the tool in at most $\eta_{\V{round}}$ rounds: each round asks the builder for a module $L_j$ (line 8), collects the worked pairs $U$ it still fails to repair (line 9) for the next round, and the round with the highest coverage is kept (line 11). At line 12, the \aux{Amplify} function builds the acceptance suite $T^{+}$ (Section~\ref{sec:synth}). At line 14, \tool repairs every buggy program by calling Algorithm~\ref{alg:generic} with the frozen tool $L$ and $T^{+}$, and at lines 16--19, it learns new rules from the repairs obtained from a model query. In our experiments, $\eta_{\V{round}}$ was set to 3, and every other constant below is fixed across all assignments.

\subsection{Select}
\label{sec:select}

% [번역] Select 단계의 목표는 빌더가 학급의 반복 수리를 일반화할 수 있는 작업 쌍 집합을 고르는 것이다(3행). 이 단계는 로컬이며 모델 질의를 하지 않는다. 프로그램을 짝짓기 위해 CoEP는 AST를 비교한다. σ(p)를 p의 AST 노드 타입을 너비 우선으로 읽은 수열로 두되 최상위 문장마다 수열 σ_i(p) 하나로 나눈다. lev를 두 수열 사이 레벤슈타인 거리라 할 때, 버기 프로그램 b와 참조 프로그램 r 사이 거리를 두 수열들 사이의 가장 싼 일대일 대응 M의 비용으로 정의한다.
The goal of the Select stage is to choose a set of worked pairs from which the builder can generalize the recurring repairs of the class (line 3). This stage is local and issues no model query. To pair programs, \tool compares their ASTs. Let $\sigma(p)$ be the sequence of node types of $p$'s AST read in breadth-first order, split into one sequence $\sigma_i(p)$ per top-level statement. With $\mathrm{lev}$ the Levenshtein distance between two such sequences, we define the distance between a buggy program $b$ and a reference program $r$ as the cost of the cheapest one-to-one matching $\mathcal{M}$ between their sequences:
\[
\delta(b, r) = \min_{\mathcal{M}} \Big[ \sum_{(i, j) \in \mathcal{M}} \mathrm{lev}(\sigma_i(b), \sigma_j(r)) + \sum_{i \notin \mathcal{M}} |\sigma_i(b)| + \sum_{j \notin \mathcal{M}} |\sigma_j(r)| \Big]
\]
% [번역] 여기서 대응되지 않은 수열은 길이 전체를 비용으로 치르므로 빠지거나 남는 정의는 제값을 낸다. 그런 다음 각 버기 프로그램은 편집이 가장 적게 드는 참조 프로그램 π(b) = argmin_{r∈R} δ(b, r)을 짝으로 삼고, ε(b)는 b를 π(b)로 옮기는 편집 연산의 다중집합이다. 직관적으로 π(b)는 그저 가장 비슷해 보이는 프로그램이 아니라 b가 시도한 방식대로 문제를 푸는 참조 프로그램이다. 노드 타입 정렬이 편집을 내지 못하면 ε(b)는 식별자와 리터럴 수준의 정렬로 세분화되는데, 잘못된 변수나 상수는 노드 타입만으로는 보이지 않기 때문이다.
where an unmatched sequence costs its full length, so a missing or surplus definition costs what it is. Each buggy program then takes as partner the reference program it is fewest edits from, $\pi(b) = \argmin_{r \in R} \delta(b, r)$, and $\varepsilon(b)$ denotes the multiset of edit operations that takes $b$ to $\pi(b)$. Intuitively, $\pi(b)$ is the reference program that solves the problem the way $b$ tries to, rather than the one that merely looks closest. When the node-type alignment yields no edit, $\varepsilon(b)$ is refined to an alignment over identifiers and literals, since a wrong variable or constant is invisible to node types alone.

% [번역] 다음으로 CoEP는 편집 스크립트 ε(b)의 TF-IDF 벡터 사이 코사인 거리에 대한 평균 연결 응집 군집화로 B를 군집 C_1 ⊎ ... ⊎ C_k로 나누며, k는 평균 실루엣 계수를 최대화하도록 고른다. 군집화 특징으로 편집 스크립트를 선택한 이유는 한 원소에서 쓴 규칙이 같은 편집을 필요로 하는 원소들에서만 값어치를 하기 때문이다. 프로그램 자신의 AST 경로로 군집화하면 가장 큰 군집이 서로 닮았을 뿐인 프로그램들로 채워졌다. SemCluster는 문법이 프로그램을 과분할한다며 의미 특징으로 군집화하지만, 그 논거는 편집에는 이어지지 않는다. 편집 스크립트는 b가 π(b)와 공유하는 문법을 상쇄하고, 군집을 소비하는 재작성 규칙은 문법에 매칭되기 때문이다. 각 군집은 군집이 가장 많이 동의하는 편집을 가진 최빈 원소 b*_i를 내놓는다. 대개 여러 결함이 뒤엉킨 메도이드는 편집이 한 번도 반복되지 않는 군집에만 쓴다. 빌드 집합은 δ가 증가하는 순서로 놓인 S = {(b*_i, π(b*_i))}이므로, 약한 빌더도 각 버기 프로그램을 그것을 수리하는 참조 프로그램과 함께 보고 변환을 일반화하기만 하면 된다. 실험적으로 Select는 11개 과제에서 작업 쌍 1,524개를 골랐으며 과제당 2개에서 353개다.
\tool then partitions $B$ into clusters $C_1 \uplus \dots \uplus C_k$ by average-linkage agglomerative clustering over the cosine distance between TF-IDF vectors of the edit scripts $\varepsilon(b)$, choosing $k$ to maximize the mean silhouette coefficient~\cite{rousseeuw1987silhouettes}. We selected edit scripts as the clustering feature because a rule written from one member pays off only on the members needing the same edit; clustering on the programs' own AST paths instead filled the largest clusters with programs that merely look alike. SemCluster~\cite{perry2019semcluster} clusters programs by semantic features because syntax over-partitions them, but the argument does not carry over to edits: an edit script cancels the syntax $b$ shares with $\pi(b)$, and the consumer of a cluster, a rewrite rule, matches syntax. Each cluster contributes its modal member,
\[
b^{\star}_i = \argmax_{b \in C_i} \big|\{ b' \in C_i \mid \varepsilon(b') = \varepsilon(b) \}\big|,
\]
whose edit the cluster most agrees on. The medoid, usually a tangle of several faults, serves only for a cluster whose edits never repeat. The build set is $S = \{(b^{\star}_i, \pi(b^{\star}_i))\}_{i=1}^{k}$, ordered by increasing $\delta$, so a weak builder is shown each buggy program with a reference program that repairs it and need only generalize the transformation. Empirically, Select chose 1{,}524 worked pairs over our 11 assignments, from 2 to 353 per assignment.

\subsection{Synthesize}
\label{sec:synth}

% [번역] Synthesize 단계의 목표는 빌드 집합을 과제 전용 수리 도구와 그 수용 테스트 집합으로 바꾸는 것이다(5–12행). 8행에서 Synthesize 함수는 설명 d, 예시로 쓰는 T의 테스트 케이스 최대 η_test = 8개, S의 작업 쌍으로 빌더 M에 프롬프트한다. 빌더는 AST 재작성 규칙들로 된 Python 모듈 L_j로 답하며, 각 규칙은 자신이 겨냥하는 오개념의 이름을 달고 자신이 다루는 실패 증상(예: 오답, TypeError)으로 태그된다. 형식적으로 규칙은 프로그램 p를 후보 프로그램 집합 ρ(p)로 보내는 후보 생성기 ρ다. Figure 1-(b)가 그런 규칙 하나를 보여 준다. 규칙의 계약은 엄격하다. 규칙은 AST에서 편집 위치를 찾아 소스 구간 치환으로 이어 붙이며, 손대지 않은 줄까지 다시 서식화하는 모듈 재렌더링을 하지 않는다. 함수 전체를 다시 쓰지 않으며, 수정을 주장하지 않고 후보를 제안한다. 표적 편집을 표현할 수 없거나, 예외를 던지거나, η_alarm = 2초 알람을 넘기는 규칙은 ρ(p) = ∅을 내므로 그 제출물은 다음 전략으로 넘어간다. CoEP는 이 계약을 강제한다. 각 후보 c ∈ ρ(p)는 p의 단일 지점 재작성, 즉 구멍이 하위 트리 하나이거나 문장·식 목록의 연속 구간 하나인 한 구멍 문맥 C에 대해 p = C[t], c = C[t']이어야 한다. 규칙은 ast 모듈 위의 Python이므로 이 조항은 정적으로 검사할 수 없고, CoEP는 이를 동적으로 검사해 p와 최대 AST 위치 둘 이상에서 다른 후보를 검증 전에 버린다. 강제하기 전에는 빌더가 만든 규칙 수리의 9.8%가 이를 어겼다.
The goal of the Synthesize stage is to turn the build set into an assignment-specific repair tool and the suite that accepts its repairs (lines 5--12). At line 8, the \aux{Synthesize} function prompts the builder $M$ with the description $d$, up to $\eta_{\V{test}} = 8$ test cases of $T$ as examples, and the worked pairs of $S$. The builder answers with a Python module $L_j$ of AST rewrite rules, each named after the misconception it targets and tagged with the failure symptoms it addresses (e.g., a wrong answer or a \texttt{TypeError}). Formally, a rule is a candidate generator $\rho$ that maps a program $p$ to a set $\rho(p)$ of candidate programs. Figure~\ref{fig:example}-(b) shows one such rule. The contract on a rule is strict, and \tool enforces it. A rule locates its edit on the AST and splices it in as a source-span replacement, rather than re-rendering the module; it proposes candidates rather than claiming a fix; and each candidate $c \in \rho(p)$ is a \emph{single-site} rewrite of $p$: $p = C[t]$ and $c = C[t']$ for a one-hole context $C$ whose hole is one subtree, or one run of a statement or expression list. Since rules are Python over the \texttt{ast} module, the last clause cannot be checked statically, so \tool checks it dynamically, discarding before validation every candidate that differs from $p$ at more than one maximal AST position; before we enforced it, 9.8\% of the builders' rule repairs broke it. A rule that cannot express a targeted edit, raises an exception, or runs beyond an $\eta_{\V{alarm}} = 2$-second alarm yields $\rho(p) = \emptyset$, so its submission falls through to the next strategy.

% [번역] 한 번에 쓴 모듈은 자체 결함을 가질 수 있으므로, CoEP는 반례 유도 귀납 합성과 실행 피드백 기반 자기 정제의 방식으로 빌드 집합 자체에서 루프를 닫는다. 규칙이 아직 실패하는 작업 쌍이 반례다. 우리는 모듈의 커버리지를 그 규칙이 버기 쪽을 수리하는 빌드 집합의 비율로 정의한다. 여기서 Search는 4.5절의 규칙 탐색이다. 커버리지는 모듈 자신의 주장이 아니라 T를 실행해 측정하며, 참조 이식을 제외하므로 각 라운드는 그 아래 기반이 아니라 빌더가 쓴 규칙으로 채점된다. cov(L_j) < 1인 동안 9행은 여전히 실패하는 쌍 U를 수정용으로 빌더에게 돌려준다. 프리즈된 도구 L은 커버리지가 가장 높은 라운드이며(11행) 동점이면 가장 이른 라운드를 택한다. 직관적으로 정제는 빌더가 구체적 실패로부터 자기 규칙을 고치게 하고, argmax는 수정본이 더 나은 모듈을 대체하는 일이 없게 한다.
Since a module written in one shot can contain its own defects, \tool closes the loop on the build set itself, in the manner of counterexample-guided inductive synthesis~\cite{solar2006combinatorial} and of self-refinement from execution feedback~\cite{madaan2023self,shinn2023reflexion}: the worked pairs the rules still fail are the counterexamples. We define the coverage of a module as the fraction of the build set whose buggy half its rules repair:
\[
\aux{cov}(L_j) = \frac{|\{ (b, \WC) \in S \mid \aux{Search}(L_j, b, T) \neq \V{fail} \}|}{|S|}
\]
where \aux{Search} is the rule search of Section~\ref{sec:repair}. Coverage is measured by executing $T$, never from the module's own claim, and it excludes the reference transplant, so a round is scored on the rules the builder wrote rather than on the substrate beneath them. While $\aux{cov}(L_j) < 1$, line 9 returns the still-failing pairs $U$ to the builder for revision. The frozen tool $L$ is the round with the highest coverage (line 11), ties going to the earliest. Intuitively, the refinement lets a builder repair its own rules from concrete failures, while the $\argmax$ ensures that a revision never replaces a better module.

% [번역] 증폭된 수용 테스트. 강사의 테스트 케이스는 적다. R1–R5는 과제당 평균 7.4개이며, Repair 단계의 모든 전략은 c ⊨ T인 후보를 받아들이므로 빈약한 T는 테스트에만 맞춘 패치를 통과시킨다. 그래서 12행의 Amplify 함수는 과제당 한 번, 참조 프로그램과의 차분 테스트로 수용 테스트 집합을 키운다. 빌더 M은 d, T, 강사의 참조 해답을 받아 유효한 무작위 입력의 생성기를 작성하고, CoEP는 규칙을 검증하듯 생성기를 검증한다. 생성기가 예외를 던지거나, 형식이 틀린 입력을 내거나, 참조 해답이 입력의 10% 넘게를 거부하면 그 라운드는 실패하며, 실패 이유가 최대 η_round 라운드 동안 빌더에게 돌아간다. 그런 다음 CoEP는 새 입력 η_draw = 300개를 뽑아, R에서 표본으로 뽑은 프로그램 η_vote = 40개와 참조 해답의 다수 출력으로 각 입력을 라벨링하고, 그중 θ = 90% 이상이 일치하는 입력만 남긴다. 따라서 명세 밖에서처럼 정답 프로그램끼리 엇갈리는 입력은 테스트가 되지 않는다. V를 이 투표자 |V| = 41개, y_x를 x에 대한 그 다수 출력이라 하면, 남은 처음 η_amp = 100개 입력이 T_amp = {(x, y_x) | |{v ∈ V | v(x) = y_x}| ≥ θ|V|}를 이루고 T⁺ = T ∪ T_amp이다. Amplify는 규칙이 프리즈된 뒤에 돌므로 어떤 규칙도 T_amp에 의존하지 않으며, 정리 4.3은 이 사실에 기댄다. Repair와 Learn 단계의 모든 수용 검사에서 T⁺가 T를 대신하며, 규칙의 커버리지는 계속 T로 잰다. 이는 학급을 오라클로 삼은 차분 테스트이며, 과적합된 패치에 맞선 테스트 생성의 취지를 따른다. 증폭은 과제당 빌더 질의를 하나 더할 뿐 제출물당 질의는 더하지 않는다.
\textbf{Amplified acceptance.} The instructor's test cases are few, 7.4 per assignment on R1--R5, and every strategy of the Repair stage accepts any candidate $c \models T$, so a thin $T$ admits patches that fit the tests rather than the problem. At line 12, the \aux{Amplify} function therefore enlarges the acceptance suite once per assignment, by differential testing against the reference programs. The builder $M$ is prompted with $d$, $T$, and the instructor's reference solution, and writes a generator of random valid inputs, which \tool validates as it validates rules: a round fails if the generator raises, returns a malformed input, or yields inputs of which the reference solution rejects more than 10\%, and the failure is returned to the builder for at most $\eta_{\V{round}}$ rounds. \tool then draws $\eta_{\V{draw}} = 300$ fresh inputs and labels each with the majority output of $\eta_{\V{vote}} = 40$ programs sampled from $R$ together with the reference solution, keeping an input only if at least $\theta = 90\%$ of them agree, so an input on which correct programs disagree, as they may outside the specification, never becomes a test. With $V$ these $|V| = 41$ voters and $y_x$ their majority output on $x$, the first $\eta_{\V{amp}} = 100$ kept inputs form
\[
T_{\V{amp}} = \{\, (x, y_x) \mid \lvert\{ v \in V \mid v(x) = y_x \}\rvert \ge \theta\,\lvert V\rvert \,\},
\]
and $T^{+} = T \cup T_{\V{amp}}$. Since \aux{Amplify} runs once the rules are frozen, no rule depends on $T_{\V{amp}}$, which Theorem~\ref{thm:overfit} relies on. $T^{+}$ replaces $T$ in every acceptance check of the Repair and Learn stages, whereas the coverage of the rules is still measured on $T$. This is differential testing~\cite{mckeeman1998differential} with the class as the oracle, in the spirit of test generation against overfitted patches~\cite{smith2015cure,xin2017identifying}; it adds one builder query per assignment and none per submission.

\subsection{Repair}
\label{sec:repair}

% [번역] Repair 단계의 목표는 프리즈된 도구로 각 버기 프로그램 b를 수리하고, 도구가 못 하는 곳에서만 모델 질의를 쓰는 것이다(14행). CoEP는 Algorithm 1의 LocalRepair 훅(6행)을 비용이 낮은 순서의 두 전략으로, Generate 함수(8행)를 관례적인 모델 질의로 구현한다. c ⊨ T⁺인 후보를 먼저 내놓는 쪽이 f를 공급한다.
The goal of the Repair stage is to repair each buggy program $b$ with the frozen tool, and to spend a model query only where the tool cannot (line 14). \tool implements the \Fn{LocalRepair} hook of Algorithm~\ref{alg:generic} (line 6) with two strategies in increasing order of cost, and the \Fn{Generate} function (line 8) with a conventional model query; whichever first yields a candidate $c$ with $c \models T^{+}$ supplies $f$.

% [번역] 규칙 기반 수리. Search 함수는 재작성된 프로그램 층에 대한 너비 우선 탐색으로 규칙을 조합한다. Λ_0 = {b}이고 Λ_{j+1}은 Λ_j의 각 프로그램에 모든 규칙을 적용한 결과에서 이전 층을 뺀 것이며, b의 실패 테스트 서명이 선언 증상이 일치하는 규칙들의 순서를 정한다. Λ_{j+2}를 열거하기 전에 Λ_{j+1}의 모든 후보를 검증하므로 반환되는 수리는 c ⊨ T⁺인 가장 얕은 후보다. Figure 1-(a)의 프로그램에서는 Λ_1에 이미 Figure 1-(b)의 4행 치환이 있고 이것이 통과하므로 탐색은 깊이 1에서 이를 반환한다. 탐색은 η_search = 3초가 지나면 더 깊은 층을 열거하지 않는다. 빌더의 규칙과 나란히, 모든 도구는 어느 학급이든 범하는 실수, 예컨대 비교 연산 뒤집기와 range·인덱스의 하나 차이 이동을 위한 항상 켜진 규칙 몇 개를 지니며, 이는 고전적 변이 연산자를 거꾸로 한 것이다. 규칙이 만든 모든 수리는 그 뒤에 있는 규칙들의 이름을 순서대로 지닌다.
\textbf{Rule-based repair.} The \aux{Search} function composes the rules by a breadth-first search over layers of rewritten programs, $\Lambda_0 = \{b\}$ and $\Lambda_{j+1} = (\bigcup_{p \in \Lambda_j} \bigcup_{\rho \in L} \rho(p)) \setminus \bigcup_{i \le j} \Lambda_i$, where the failing-test signature of $b$ orders the rules whose declared symptoms match it. Every candidate in $\Lambda_{j+1}$ is validated before $\Lambda_{j+2}$ is enumerated, so the returned repair is the shallowest candidate $c$ with $c \models T^{+}$. For the program of Figure~\ref{fig:example}-(a), $\Lambda_1$ already holds the splice of Figure~\ref{fig:example}-(b) at line~4, which passes, so the search returns it at depth 1. The search enumerates no further layer once $\eta_{\V{search}} = 3$ seconds have elapsed. Alongside the builder's rules, every tool carries a handful of always-on rules for the slips any class makes, such as flipped comparisons and off-by-one range and index shifts, which invert classical mutation operators~\cite{just2014mutants,kim2013automatic,liu2019tbar}. Every repair the rules produce carries the ordered names of the rules behind it.

% [번역] 참조 기반 수리. 대부분의 학생 버그는 토큰 수준 규칙이 표현하지 못하는 구조적 편집을 필요로 하며 R이 그것을 공급한다. δ로 b에 가장 가까운 참조 프로그램 η_ref = 8개 각각에 대해 CoEP는 b와 r이 어긋나는 줄 hunk의 집합 H(b, r)를 계산하며, r 그대로와 r의 변수를 b의 것으로 바꾼 사본(매개변수는 위치로, 지역 변수는 첫 바인딩 순서로) 양쪽에 대해 계산한다. b ⊕ h를 hunk h ⊆ H(b, r)를 적용한 b라 하자. CoEP는 참조들을 통틀어 1 ≤ |h| ≤ 3이면서 바뀌는 줄 수가 가장 적은 부분집합 η_cand = 300개를 검증하고, 처음 통과하는 부분집합 η_pass = 5개 P에 대해 RPS를 최소화하는 것을 반환하며, 하나도 통과하지 않으면 기권한다. 여기서 상대 패치 크기 RPS(b, f)는 b와 f의 AST 사이 트리 편집 거리를 b의 AST 크기로 나눈 값이다. 이는 CLARA, Sarfgen, Refactory 계보의 참조 재사용이지만 블록 전체가 아니라 줄 hunk 입도이므로, 학생의 전략이 다른 곳에서 참조 프로그램과 달라도 hunk는 여전히 적용 가능하다.
\textbf{Reference-based repair.} Most student bugs need a structural edit that no token-level rule expresses, and $R$ supplies it. For each of the $\eta_{\V{ref}} = 8$ reference programs nearest to $b$ under $\delta$, \tool computes the set $H(b, r)$ of line hunks in which $b$ and $r$ differ, both for $r$ as written and for $r$ with its variables renamed to $b$'s (parameters by position, locals by first binding). Let $b \oplus h$ denote $b$ with the hunks $h \subseteq H(b, r)$ applied. \tool validates, across them, the $\eta_{\V{cand}} = 300$ subsets $h$ with $1 \le |h| \le 3$ that change the fewest lines, and returns $\argmin_{h \in P} \RPS(b, b \oplus h)$ over the first $\eta_{\V{pass}} = 5$ passing subsets $P$, abstaining when none passes. Here, the relative patch size $\RPS(b, f)$ is the tree-edit distance~\cite{zhang1989simple} between the ASTs of $b$ and $f$ divided by the size of $b$'s AST~\cite{hu2019re}. This is reference reuse in the lineage of CLARA, Sarfgen, and Refactory~\cite{gulwani2018automated,wang2018search,hu2019re}, but at the granularity of line hunks rather than whole blocks: a hunk remains applicable when the student's strategy differs from the reference program's elsewhere.

% [번역] LLM 기반 수리. 두 로컬 전략이 모두 기권하면 CoEP는 Select 단계의 최소 편집 참조 프로그램을 붙인 질의 LLM(d, T, b, π(b)) 하나를 발행해, 모델이 학생 자신의 전략 쪽으로 b를 수리하게 한다. CoEP는 또한 로컬 전략이 RPS(b, f_loc) > η_rps = 1로 성공할 때, 즉 통과 패치가 고치려는 프로그램만큼 클 때도 에스컬레이션한다. 그 이유는 수용 검사 c ⊨ T⁺가 패치 크기에 대해 아무 말도 하지 않기 때문이다. 이식은 학생 프로그램의 대부분을 대체해서도 T⁺를 통과할 수 있는 반면, 규칙은 표적 편집을 표현할 수 없으면 언제나 기권해야 한다. CoEP는 둘 중 T⁺를 통과하면서 RPS가 가장 작은 것을 남기므로, 에스컬레이션은 질의 하나를 쓸 수는 있어도 커버리지나 패치 크기를 잃을 수는 없다. 임계값은 적합된 값이 아니라 정의다.
\textbf{LLM-based repair.} When both local strategies abstain, \tool attaches the minimum-edit reference program from the Select stage and issues a single query $\mathrm{LLM}(d, T, b, \pi(b))$, so that the model repairs $b$ toward the student's own strategy. \tool also escalates when the local strategies succeed with $\RPS(b, f_{\V{loc}}) > \eta_{\V{rps}} = 1$, i.e., with a passing patch at least as large as the program it repairs. The reason is that the acceptance test, $c \models T^{+}$, says nothing about patch size: a transplant can pass $T^{+}$ by replacing most of a student's program, whereas a rule must abstain whenever it cannot express a targeted edit. \tool keeps
\[
\argmin_{f \in \{f_{\V{loc}},\, \mathrm{LLM}(d, T, b, \pi(b))\},\ f \models T^{+}} \RPS(b, f),
\]
so an escalation can cost a query but never coverage or patch size. The threshold is a definition rather than a fitted value.

\subsection{Learn}
\label{sec:learn}

% [번역] Learn 단계의 목표는 도구가 하지 못한 수리를 도구 자체에 흡수하는 것이다(16–19행). Algorithm 1이 모델 질의로 수리한 각 쌍 (b, f)에 대해 Learn 함수는 M에게 b에서 f로의 편집을 새 이름 붙은 규칙 ρ'으로 일반화하게 한다. CoEP는 ρ'으로 확장한 도구가 b를 스스로 수리할 때, 즉 Search(L ∪ {ρ'}, b, T⁺) ≠ fail일 때만 ρ'을 유지한다. 학습된 규칙은 현재 패스가 참조하지 않는 스테이징 사본 L'에 기록되므로 어떤 제출물의 결과도 그 앞의 제출물에 의존하지 않으며, L'은 도구가 다시 프리즈될 때에만 L을 대체한다. Learn은 이미 에스컬레이션된 제출물에서만 모델에 질의하므로, 도구가 수리하는 제출물에는 질의를 더하지 않는다.
The goal of the Learn stage is to absorb the repairs the tool could not make into the tool itself (lines 16--19). For each pair $(b, f)$ that Algorithm~\ref{alg:generic} repaired with a model query, the \aux{Learn} function asks $M$ to generalize the edit from $b$ to $f$ into a new named rule $\rho'$. \tool keeps $\rho'$ only if the tool extended with it repairs $b$ by itself, i.e., $\aux{Search}(L \cup \{\rho'\}, b, T^{+}) \neq \V{fail}$. Learned rules are written to a staging copy $L'$ that the current pass never consults, so no submission's outcome depends on which submissions preceded it, and $L'$ replaces $L$ only when the tool is frozen again. Since Learn queries the model only for submissions that already escalated, it adds no query for a submission the tool repairs.

% [번역] 배포된 도구 자체는 모델에 질의하지 않는다. 로컬 전략은 제출물당 2~3초 안에 CPU에서 돌므로(5.3절) 도구를 만든 뒤에는 학생 코드가 에스컬레이션될 때만 기관을 떠나며, 모든 후보가 반환되기 전에 T⁺로 검증되므로 결함 있는 규칙은 실패하는 수리가 아니라 기권으로 퇴화한다.
The deployed tool itself never queries a model. Its local strategies run on a CPU in about three seconds per submission (Section~\ref{sec:rq-cost}), so once the tool is built, student code leaves the institution only on escalation, and a defective rule degrades into abstention rather than a failing repair, because every candidate is validated against $T^{+}$ before it is returned.

\subsection{Properties}
\label{sec:props}

% [번역] 성질. 이 절은 빌더가 무엇을 쓰든 CoEP가 보장하는 것을 진술한다. 이하에서 c ⊨ T는 후보 c가 T의 모든 테스트 케이스를 시간 제한 안에 통과한다는 뜻이므로, 충돌하거나 시간을 넘긴 후보는 통과하지 않는다. CoEP_L은 Algorithm 1을 Generate 없이(에스컬레이션 없이) 돌린 것이고 CoEP_LF는 Generate와 관문을 포함한 것이다.
We now state what \tool guarantees whatever the builder writes. Throughout, $c \models T$ means that the candidate $c$ passes every test case of $T$ within its time limit, so a candidate that crashes or times out does not pass; \coepL runs Algorithm~\ref{alg:generic} without \Fn{Generate}, and \coepLF with \Fn{Generate} and the gate of Section~\ref{sec:repair}.

% [번역] 신뢰 경계. 빌더의 규칙과 생성기는 신뢰하지 않는 코드다. 규칙은 탐색 프로세스 안에서 η_alarm 알람 아래 돌며, 예외를 던지거나 시간을 넘기면 그 출력은 버려진다. 모든 후보와 생성된 입력은 테스트마다 시간 제한이 있는 새 서브프로세스에서 돌고, fallback 질의는 최대 다섯 번 재시도되며 각 시도는 클라이언트의 요청 타임아웃 아래 놓인다. 우리는 규칙이 탐색 프로세스 자체를, 예컨대 테스트 실행기를 바꿔치기해 수정하지 않고 후보를 계산한다고 가정한다. 빌더는 올바르다고 신뢰되지 않을 뿐 적대적이라고 가정되지는 않는다. 규칙도 서브프로세스로 격리하면 규칙 호출마다 프로세스 하나를 대가로 이 가정을 없앨 수 있다.
\textbf{Trust boundary.} The builder's rules and generator are untrusted code. A rule runs in the search process under the $\eta_{\V{alarm}}$ alarm, which discards its output if it raises or runs over; every candidate and every generated input runs in a fresh subprocess under a per-test time limit; and the fallback query is retried at most five times, each under the client's request timeout. We assume that a rule computes its candidates without modifying the search process itself, e.g., by patching the test runner: the builder is untrusted to be correct, not assumed to be adversarial. Isolating rules in subprocesses as well would discharge this assumption at the cost of one process per rule call.

% [번역] 명제 1(T⁺ 기준 건전성). 모든 빌더 M과 모든 b ∈ B에 대해, CoEP가 b에 대해 f ≠ fail을 반환하면 f ⊨ T⁺이고, 따라서 f ⊨ T이다.
\begin{proposition}[Soundness relative to $T^{+}$]\label{prop:sound}
For every builder $M$ and every $b \in B$, if \tool returns $f \neq \V{fail}$ for $b$, then $f \models T^{+}$, and hence $f \models T$.
\end{proposition}
% [번역] 증명. F로 들어가는 각 경로는 후보를 반환하기 전에 T⁺에 대해 검증한다. Search와 이식은 통과하는 후보만 반환하고, Generate의 후보는 c ⊨ T⁺일 때만 남으며(T⁺로 호출한 Algorithm 1의 9행), 관문은 통과하는 후보에 대한 argmin을 남기고, 학습된 규칙은 Search를 통해서만 들어온다. 빌더와 모델이 쓴 것은 후보와 테스트를 제안할 뿐이다. 마지막으로 T ⊆ T⁺이다.
\begin{proof}
Each path into $F$ validates its candidate against $T^{+}$ before returning it: \aux{Search} and the transplant return only passing candidates, a candidate of \Fn{Generate} is kept only if $c \models T^{+}$ (line~9 of Algorithm~\ref{alg:generic}, called with $T^{+}$), the gate keeps an $\argmin$ over passing candidates, and learned rules enter only through \aux{Search}. What the builder and the model write only proposes candidates and tests. Finally, $T \subseteq T^{+}$.
\end{proof}

% [번역] 명제 1은 증폭이 수락 집합을 줄일 수만 있음을 함의하며, 5.6절은 그 교환의 값을 T에서의 수리율 0.3–0.5포인트 대 held-out 테스트에서의 8.5–9.7포인트로 측정한다. 증폭된 테스트의 값은 그 레이블에 달려 있으며, 다음 명제가 이를 묶는다.
Proposition~\ref{prop:sound} implies that amplification can only shrink the set of accepted candidates; Section~\ref{sec:rq-heldout} measures the exchange at 0.3 to 0.5 points of repair rate on $T$ for 8.5 to 9.7 points on held-out tests. What the amplified tests are worth depends on their labels, which the next proposition bounds.

% [번역] 명제 2(레이블 건전성). V를 Amplify의 투표자, θ를 일치 임계값, (x, y) ∈ T_amp라 하자. 같은 틀린 출력을 내는 투표자가 ⌈θ|V|⌉개보다 적으면, y는 x에 대한 올바른 출력이다.
\begin{proposition}[Label soundness]\label{prop:label}
Let $(x, y) \in T_{\V{amp}}$. If fewer than $\lceil \theta |V| \rceil$ voters produce one and the same incorrect output on $x$, then $y$ is the correct output on $x$.
\end{proposition}
% [번역] 증명. 구성상 y는 적어도 ⌈θ|V|⌉개 투표자의 출력이다. y가 틀렸다면 이 투표자들은 x에서 같은 틀린 출력을 내게 되어 가정에 모순된다.
\begin{proof}
By construction, $y$ is the output of at least $\lceil \theta |V| \rceil$ voters. If $y$ were incorrect, these voters would produce one and the same incorrect output on $x$, contrary to the hypothesis.
\end{proof}
% [번역] |V| = 41이므로 틀린 레이블에는 T를 통과한 프로그램에서 뽑은 투표자 37개가 같은 입력에서 같은 실수를 저질러야 한다. 이는 학급 대부분이 공유하는 오개념이며, 학급이 라벨링한 어떤 테스트도 바로 그것을 드러낼 수 없다(5.7절). 우리의 증폭 집합 열 개에서 모든 레이블은 41표 중 최소 38표를 받았고, 1,000개 중 708개는 만장일치였으며, 강사의 참조 해답은 모든 레이블과 일치했다.
With $|V| = 41$, a wrong label therefore needs 37 voters, sampled from programs that pass $T$, to make the same mistake on the same input: a misconception shared by most of the class, which is precisely what no test labelled by the class can expose (Section~\ref{sec:threats}). In our ten amplified suites, every label had at least 38 of the 41 votes, 708 of the 1{,}000 were unanimous, and the instructor's reference solution agreed with every label.

% [번역] 정리 4.3(과적합 상한). D를 Amplify가 남기는 입력의 분포라 하고, 프로그램 c에 대해 err(c) = Pr_{x∼D}[c(x) ≠ y_x]를 c가 학급의 레이블에서 벗어날 확률이라 하자. C_k(b)를 b에 대한 이식의 후보와 규칙 층 Λ_1, …, Λ_k의 후보를 합친 집합이라 하자. T_amp의 입력 n개가 D에서 독립으로 뽑힌다고 하면, 모든 b, k, ε > 0에 대해 로컬 전략이 C_k(b)에서 err(c) > ε인 수리 c를 반환할 확률은 |C_k(b)|(1−ε)ⁿ 이하다.
Let $D$ be the distribution of the inputs that \aux{Amplify} keeps, and for a program $c$, let $\mathrm{err}(c) = \Pr_{x \sim D}[c(x) \neq y_x]$ be the probability that $c$ departs from the class's label. Let $C_k(b)$ be the candidates of the transplant for $b$ together with those of the rule layers $\Lambda_1, \dots, \Lambda_k$.
\begin{theorem}[Overfitting bound]\label{thm:overfit}
Suppose the $n$ inputs of $T_{\V{amp}}$ are drawn independently from $D$. For every $b$, every $k$, and every $\varepsilon > 0$, the probability that the local strategies return a repair $c \in C_k(b)$ with $\mathrm{err}(c) > \varepsilon$ is at most $|C_k(b)|\,(1 - \varepsilon)^{n}$.
\end{theorem}
% [번역] 증명. C_k(b)는 T_amp에 의존하지 않는다. 규칙은 Amplify가 돌기 전에 프리즈되고, 규칙은 테스트를 보지 않고 프로그램을 후보로 보내며, 이식은 R에서만 hunk를 가져온다. 테스트는 열거된 것의 순서를 정하고 거를 뿐이다. err(c) > ε인 c ∈ C_k(b)를 고정하면, T_amp의 각 입력은 독립으로 확률 err(c)로 c를 드러내므로 c가 n개를 모두 통과할 확률은 (1−err(c))ⁿ < (1−ε)ⁿ이다. 반환된 수리는 T⁺ ⊇ T_amp를 통과하므로(명제 1), 그런 후보 최대 |C_k(b)|개에 대한 합집합 상한이 주장을 준다.
\begin{proof}
$C_k(b)$ does not depend on $T_{\V{amp}}$: the rules are frozen before \aux{Amplify} runs, a rule maps a program to candidates without seeing the tests, and the transplant draws its hunks from $R$ alone; the tests only order and filter what is enumerated. Fix $c \in C_k(b)$ with $\mathrm{err}(c) > \varepsilon$. Each input of $T_{\V{amp}}$ exposes $c$ independently with probability $\mathrm{err}(c)$, so $c$ passes all $n$ of them with probability $(1 - \mathrm{err}(c))^{n} < (1 - \varepsilon)^{n}$. A returned repair passes $T^{+} \supseteq T_{\V{amp}}$ (Proposition~\ref{prop:sound}), and a union bound over the at most $|C_k(b)|$ such candidates gives the claim.
\end{proof}
% [번역] 이 상한은 탐색이 넓을수록 오라클이 중요하다는 것을 정량화한다. n ≥ (ln|C_k(b)| + ln(1/δ))/ε이면 확률이 δ 아래로 유지된다. n = 100이면, 최대 η_cand = 300개 후보를 검증하는 이식이 생성된 입력의 10% 넘게에서 학급과 어긋나는 패치를 받아들일 확률은 0.8% 미만이다. 같은 오라클은 후보가 하나뿐인 질의에는 훨씬 덜 필요하다. 예컨대 Figure 2-(b)의 패치는 R1의 증폭 입력 100개 중 10개에서 실패하며, D의 10%에서 어긋나는 패치가 독립 추출 100개를 모두 통과할 확률은 0.9¹⁰⁰ < 3·10⁻⁵이다. 5.6절은 상한이 예측하는 상호작용을 관찰한다. 증폭은 CoEP의 held-out 수리율을 8.5와 9.7포인트 올렸지만 LLM_Direct에는 도움이 되지 않았고, PyDex에 준 이득은 PyDex가 뽑은 표본 수와 함께 커졌다. fallback의 후보는 실패한 테스트를 프롬프트에서 보므로 C_k(b)에 들지 않으며 명제 1로만 다뤄진다.
The bound quantifies why the broader the search, the more the oracle matters: $n \ge (\ln |C_k(b)| + \ln(1/\delta))/\varepsilon$ keeps it below $\delta$. With $n = 100$, the transplant, which validates at most $\eta_{\V{cand}} = 300$ candidates, accepts a patch departing from the class on more than 10\% of generated inputs with probability below 0.8\%, whereas a single query needs the oracle far less. The patch of Figure~\ref{fig:thin}-(b), for instance, fails 10 of R1's 100 amplified inputs, and a patch departing on 10\% of $D$ passes 100 independent draws with probability $0.9^{100} < 3 \cdot 10^{-5}$. Section~\ref{sec:rq-heldout} observes the interaction the bound predicts: amplification raised \tool's held-out repair rate by 8.5 and 9.7 points but did not help \direct, and what it gave PyDex grew with the number of samples PyDex drew. The fallback's candidate sees failing tests in its prompt, so it lies outside $C_k(b)$ and is covered by Proposition~\ref{prop:sound} alone.

% [번역] 명제 4(가장 얕은 규칙 조합). Search가 층 Λ_j에서 후보 c를 반환하면, Λ_0 ∪ … ∪ Λ_{j−1}의 모든 후보는 T⁺를 통과하지 못한다. 즉 c는 열거된 층 중에서 통과하는 가장 적은 규칙 적용의 조합이다.
\begin{proposition}[Shallowest composition]\label{prop:shallow}
If \aux{Search} returns a candidate $c \in \Lambda_j$ for $b$, then no candidate in $\Lambda_0 \cup \dots \cup \Lambda_{j-1}$ passes $T^{+}$; that is, $c$ composes the fewest rule applications among the passing candidates of the enumerated layers.
\end{proposition}
% [번역] 증명. Search는 Λ_{j+1}을 열거하기 전에 Λ_j의 모든 후보를 검증하고 통과하는 첫 후보에서 멈춘다. 따라서 c가 Λ_j에서 반환되었다면 Λ_0, …, Λ_{j−1}은 모두 끝까지 검증되었고 통과한 후보가 없었다. 층은 이전 층에 나온 프로그램을 빼므로 Λ_i의 원소는 정확히 i번의 규칙 적용으로 처음 도달한 프로그램이다.
\begin{proof}
\aux{Search} validates every candidate of $\Lambda_j$ before it enumerates $\Lambda_{j+1}$, and stops at the first passing candidate. If $c$ is returned from $\Lambda_j$, the layers $\Lambda_0, \dots, \Lambda_{j-1}$ were therefore validated completely and held no passing candidate. Since each layer excludes the programs of earlier layers, an element of $\Lambda_i$ is a program first reached by exactly $i$ rule applications.
\end{proof}
% [번역] 가장 얕다는 것은 패치 크기가 가장 작다는 것과 같지 않다. 규칙 적용 하나가 큰 편집일 수 있기 때문이다. 강제된 계약이 그 크기를 묶는다. 조각 t의 AST 노드 수를 |t|로 쓴다.
Shallowest is not smallest, since one rule application may be a large edit; the enforced contract bounds how large. Write $|t|$ for the number of AST nodes in a fragment $t$.

% [번역] 정리 4.5(지역성). Search가 b에 대해 c ∈ Λ_j를 반환하면, c는 b와 최대 j곳에서만 다르고 TED(b, c) ≤ Σ_{i=1}^{j} (|t_i| + |t'_i|)이다. 여기서 t_i와 t'_i는 i번째 규칙 적용이 바꾸는 조각과 넣는 조각이다.
\begin{theorem}[Locality]\label{thm:local}
If \aux{Search} returns $c \in \Lambda_j$ for $b$, then $c$ differs from $b$ at no more than $j$ positions, and $\mathrm{TED}(b, c) \le \sum_{i=1}^{j} (|t_i| + |t'_i|)$, where $t_i$ and $t'_i$ are the fragments the $i$-th rule application replaces and inserts.
\end{theorem}
% [번역] 증명. j에 대한 귀납. Λ_j의 원소는 Λ_{j−1}의 원소에 규칙을 한 번 적용해 얻으며, 계약은 그 적용을 한 위치, 즉 C[t]를 C[t']로 바꾸는 것으로 제한한다. 그런 재작성은 이전 위치들과 떨어져 있거나 그 구멍 안의 위치들을 흡수하므로 b와 다른 위치를 최대 하나 늘리며, t의 노드를 지우고 t'의 노드를 넣는 것으로 트리 편집 거리에서 최대 |t| + |t'|가 든다. 트리 편집 거리는 삼각 부등식을 만족하므로 j번 적용의 비용이 더해진다.
\begin{proof}
By induction on $j$. An element of $\Lambda_j$ is obtained from one of $\Lambda_{j-1}$ by one rule application, which the contract confines to one position, rewriting $C[t]$ to $C[t']$. Such a rewrite either lies apart from the earlier positions or absorbs those inside its hole, so it adds at most one position at which the program differs from $b$, and it costs at most $|t| + |t'|$ in tree edit distance, by deleting $t$'s nodes and inserting $t'$'s. Tree edit distance satisfies the triangle inequality, so the costs of the $j$ applications add up.
\end{proof}
% [번역] 따라서 RPS(b, c) ≤ Σ(|t_i| + |t'_i|)/|b|다. 규칙 수리는 그 규칙들이 다시 쓰는 조각만큼만 크고, 명제 4.4는 그런 조각이 가장 적은 조합을 반환한다. 이식은 그런 상한을 따르지 않으며, 5.4절에서 규칙 수리가 이식보다 훨씬 작은 이유가 이것이다.
Hence $\RPS(b, c) \le \sum_{i} (|t_i| + |t'_i|) / |b|$: a rule repair is as small as the fragments its rules rewrite, and Proposition~\ref{prop:shallow} returns the fewest of them. The transplant obeys no such bound, which is why rule repairs are far smaller than transplanted ones (Section~\ref{sec:rq-stage}).

% [번역] 명제 4.6(에스컬레이션의 단조성). 모든 b에 대해, CoEP_L이 b를 f_L로 수리하면 CoEP_LF도 b를 RPS(b, f_LF) ≤ RPS(b, f_L)인 f_LF로 수리한다.
\begin{proposition}[Monotone escalation]\label{prop:gate}
For every $b$, if \coepL repairs $b$ with $f_L$, then \coepLF repairs $b$ with some $f_{LF}$ such that $\RPS(b, f_{LF}) \le \RPS(b, f_L)$.
\end{proposition}
% [번역] 증명. CoEP_LF는 같은 로컬 수리 f_loc = f_L을 계산한다. RPS(b, f_L) ≤ η_rps이면 에스컬레이션하지 않으므로 f_LF = f_L이다. 그렇지 않으면 f_LF는 {f_L, LLM(d, T, b, π(b))} 중 T⁺를 통과하는 것들에 대한 RPS의 argmin이며, 명제 1에 의해 f_L ⊨ T⁺이므로 이 집합은 f_L을 포함하고 공집합이 아니다.
\begin{proof}
\coepLF computes the same local repair $f_{\V{loc}} = f_L$. If $\RPS(b, f_L) \le \eta_{\V{rps}}$, it does not escalate and $f_{LF} = f_L$. Otherwise, $f_{LF}$ is the $\argmin$ of $\RPS(b, \cdot)$ over the candidates in $\{f_L, \mathrm{LLM}(d, T, b, \pi(b))\}$ that pass $T^{+}$, a set that contains $f_L$ by Proposition~\ref{prop:sound} and is therefore nonempty.
\end{proof}

% [번역] 명제 4.7(종료). 모든 b에 대해 Repair 단계는 종료한다.
\begin{proposition}[Termination]\label{prop:term}
For every $b$, the Repair stage terminates.
\end{proposition}
% [번역] 증명. 규칙 호출 하나는 η_alarm에서 끊기고, 후보 검증 하나는 테스트마다 시간 제한이 있으며, 규칙 집합과 각 층은 유한하다. Search는 η_search가 지나면 더 깊은 층을 열거하지 않으므로 유한한 수의 층에서 멈춘다. 이식은 η_ref개 참조에서 모두 합쳐 최대 η_cand개 부분집합을 검증한다. 마지막으로 Generate는 질의 하나를 발행하며, 이는 클라이언트의 요청 타임아웃 아래 최대 다섯 번 재시도된다.
\begin{proof}
Each rule call is cut off after $\eta_{\V{alarm}}$, each validation runs under a per-test time limit, and the rule set and every layer are finite. \aux{Search} enumerates no further layer once $\eta_{\V{search}}$ has elapsed, so it stops after finitely many layers. The transplant validates at most $\eta_{\V{cand}}$ subsets in all, drawn from the $\eta_{\V{ref}}$ reference programs, and \Fn{Generate} issues one query, retried at most five times under the client's request timeout.
\end{proof}
% [번역] 탐색 예산이 벽시계 시간이므로 어떤 층이 열거되는지, 따라서 반환되는 수리는 기계의 부하에 따라 달라질 수 있다. 실제로 빌더마다 프로그램 203개 표본에서 프리즈된 도구를 한 번에 하나씩 다시 실행했을 때 패치 406개가 모두 그대로 재현되었다.
Because the search budget is wall-clock time, which layers are enumerated, and hence which repair is returned, can depend on machine load; in practice, re-running the frozen tools one program at a time, on a sample of 203 programs per builder, reproduced all 406 of their patches.

% [번역] 보장하지 않는 것. CoEP는 완전하지 않다. 이식은 최대 300개 부분집합에서 hunk를 최대 세 개까지 시도하고 탐색은 예산에서 멈추므로, 수리 가능한 프로그램도 에스컬레이션으로 넘어가거나 수리되지 않은 채 남을 수 있다. 또한 수리는 T⁺ 너머에서 올바르다고 보장되지 않는다. 명제 1은 CoEP가 받아들이는 것을 명세가 아니라 T⁺로 묶고, 정리 4.3은 모든 입력이 아니라 생성기의 분포에서 학급 레이블로부터의 이탈을 묶으며, 5.6절은 독립된 생성기에서 뽑은 held-out 테스트로 그 간극을 측정한다.
\textbf{What is not guaranteed.} \tool is not complete: the transplant tries at most three hunks over at most 300 subsets and the search stops at its budget, so a repairable program may fall through to escalation or remain unrepaired. Nor is a repair correct beyond $T^{+}$: Proposition~\ref{prop:sound} bounds what \tool accepts by $T^{+}$, not by the specification, Theorem~\ref{thm:overfit} bounds departures from the class's labels under the generator's distribution, not under every input, and Section~\ref{sec:rq-heldout} measures the gap on held-out tests drawn from an independent generator.

\section{Experiments}
\label{sec:exp}

% [번역] 이 장에서는 다음 연구 질문에 답하기 위해 CoEP를 평가한다.
% [번역] (1) 효과: CoEP는 수리율과 패치 크기 측면에서 참조 유도 및 LLM 기반 수리와 비교해 버기 프로그램을 얼마나 효과적으로 수리하는가?
% [번역] (2) 효율: 과제당 한 번 도구를 합성하는 것은 제출물마다 LLM에 질의하는 것에 비해 모델 지출과 소요 시간을 얼마나 절약하는가?
% [번역] (3) 각 부분의 효능: 합성된 규칙, 합성된 오라클, local-first 구조는 각각 무엇을 기여하는가?
% [번역] (4) 일반성: 학급의 앞선 제출물로 만든 도구가 뒤의 제출물을 수리하는가, 그리고 빌드는 학급 규모에 따라 어떻게 늘어나는가?
% [번역] (5) 테스트 너머의 정확성: 수리 결과는 어떤 팔도 탐색에 쓰지 않은 테스트 케이스에서도 올바른가?
In this section, we evaluate \tool to answer the following research questions:
\begin{enumerate}
  \item[(1)] \textbf{Effectiveness:} How effectively does \tool repair buggy programs compared to reference-guided and LLM-based repair, in terms of repair rate and patch size?
  \item[(2)] \textbf{Efficiency:} How much model spend and turnaround does synthesizing a tool once per assignment save, compared to querying an LLM per submission?
  \item[(3)] \textbf{Efficacy of Each Part:} What do the synthesized rules, the synthesized oracle, and the local-first architecture each contribute?
  \item[(4)] \textbf{Generality:} Does a tool built from a class's earlier submissions repair its later ones, and how does its build scale with the class?
  \item[(5)] \textbf{Correctness beyond the Tests:} Do the repairs remain correct on test cases that no arm searched against?
\end{enumerate}
% [번역] 우리는 CoEP를 Python의 표준 ast 모듈 위에 Python으로 구현했으며, 합성된 각 도구는 오프라인으로 도는 평범한 Python 모듈로 출력된다. 트리 편집 거리는 Zhang–Shasha 알고리즘으로, 군집화는 scikit-learn으로 계산한다. 모든 로컬 계산은 Mac Studio(Apple M1 Ultra, 20코어, 64 GB RAM, macOS 26.7)에서 수행했다.
We implemented \tool in Python on top of the standard \texttt{ast} module, and each synthesized tool is emitted as an ordinary Python module that runs offline. Tree-edit distance is computed with the Zhang--Shasha algorithm~\cite{zhang1989simple} and clustering with scikit-learn. All local computation ran on a Mac Studio (Apple M1 Ultra, 20 cores, 64 GB RAM, macOS 26.7).

\subsection{Experimental Settings}
\label{sec:settings}

% [번역] 베이스라인. 우리는 CoEP를 프로그래밍 과제 수리의 두 주류 계열과 비교했다. 우리의 Python 코퍼스에서 도는 가장 강한 참조 유도 수리기인 Refactory와 LLM 기반 PyDex이며, 다른 기법이 베이스라인이 될 수 없었던 이유는 부록 A에서 설명한다. PyDex는 버기 프로그램과 학급에서 검색한 비슷한 (버기, 정답) 예시 세 쌍으로 모델에 프롬프트하고, 후보 열 개를 샘플링해 T로 거른 뒤 학생 프로그램에 가장 가까운 생존자를 반환한다. 우리는 그 few-shot 의미 수리 단계를 재구현해 열 개의 샘플 모두에 비용을 청구했고, 동일한 프롬프트 열 개 중 아홉 개를 공급자의 캐시 읽기 요율로 매긴 프롬프트 캐싱 하의 가격(PyDex_PC)도 매겼다. CoEP는 수리 시점에 모델 없이 프리즈된 도구만 돌리는 CoEP_L과 에스컬레이션 시 질의를 더하는 CoEP_LF로 돌렸다. LLM_Direct는 CoEP_LF의 질의 LLM(d, T, b, π(b))를 모든 버기 프로그램에 보내므로, 도구가 처리하지 못하는 곳에서만 질의한다는 점 하나만 CoEP_LF와 다르다. 각 부분의 효능을 위해, CoEP_LF−Rules는 빌더의 규칙을 빼되 항상 켜진 규칙, 이식, T⁺, 관문을 둔 질의를 유지하고, CoEP_LF−Amp는 T만으로 받아들인다. CoEP_L−Syn은 빌더의 규칙을 뺀 CoEP_L이고, CoEP_L+Learn은 학습된 규칙으로 CoEP_L을 다시 돌린다. 오라클과 수리기를 분리하기 위해 T⁺로 받아들이는 PyDex도 돌렸다(5.6절). 질의는 도구에 의존하지 않고 LLM_Direct가 모든 프로그램에 그 질의를 보냈으므로, CoEP_LF와 그 변형들은 에스컬레이션에 대한 답을 CoEP_LF의 관문 아래에서 LLM_Direct의 로그에서 가져온다. 그러면 두 팔은 모델의 답을 고정한 채 구조 하나만 다르며, 실제로 돌린 CoEP_LF를 이렇게 구성하면 쌍의 99.93%에서 그 결과를 재현한다.
\textbf{Baselines.} We compared \tool with the two mainstream lines of repair for programming assignments: the reference-guided Refactory~\cite{hu2019re}, the strongest such repairer that runs on our Python corpora, and the LLM-based PyDex~\cite{zhang2024pydex}; Appendix~\ref{app:baselines} explains why other techniques could not serve. PyDex prompts a model with the buggy program and three similar (buggy, correct) exemplars retrieved from the class, samples ten candidates, filters them with $T$, and returns the survivor closest to the student's program; we re-implemented its few-shot semantic phase, billed all ten samples, and also priced it under prompt caching (\pydexPC), with nine of its ten identical prompts at the providers' cache-read rate~\cite{anthropiccaching,openaicaching}. We ran \tool as \coepL, the frozen tool with no model at repair time, and as \coepLF, which adds the query on escalation. \direct issues \coepLF's query $\mathrm{LLM}(d, T, b, \pi(b))$ for every buggy program, so it differs from \coepLF only in not reserving the query for what the tool cannot serve. For the efficacy of each part, \coepLF$-$Rules drops the builder's rules but keeps the always-on rules, the transplant, $T^{+}$, and the gated query, and \coepLF$-$Amp accepts against $T$ alone; \coepNS is \coepL without the builder's rules, and \coepLL re-runs \coepL with the learned rules. To separate the oracle from the repairer, we also ran PyDex accepting against $T^{+}$ (Section~\ref{sec:rq-heldout}). Since the query does not depend on the tool and \direct issued it for every program, \coepLF and its variants take the answers to their escalations from \direct's log, under \coepLF's gate: the two arms then differ in the architecture alone, with the model's answers held fixed, and composing a live \coepLF run this way reproduces its outcome on 99.93\% of the pairs.

% [번역] 벤치마크. 우리는 Table 2에 요약한 두 코퍼스의 11개 과제에서 버기 프로그램 2,970개를 사용했다. 처음 다섯 과제(R1–R5)는 대학 1학년 프로그래밍 강의의 과제로, 학생들이 쓴 모든 제출물을 담고 있으며 Refactory의 저자들이 공개했다. 나머지 여섯(C1–C6)은 open-r1 릴리스가 제출물을 반영하는 Codeforces 문제로, 난이도가 입문 연습 이상으로 오르도록 800, 1000, 1200, 1400, 1600, 2000 등급에서 한 문제씩 골랐으며 Newbie부터 Candidate Master까지 다섯 공식 등급 밴드를 포괄한다. 각 코퍼스의 레이블을 그대로 유지했으므로 모든 팔의 분모는 같은 프로그램 2,970개다.
\textbf{Benchmarks.} We used 2{,}970 buggy programs from 11 assignments in two corpora, summarized in Table~\ref{tab:effect}. The first five assignments (R1--R5) are those of a first-year university programming course, with every submission its students wrote, released by the authors of Refactory~\cite{hu2019re}. The other six (C1--C6) are Codeforces problems whose submissions the open-r1 release mirrors~\cite{penedo2025codeforces}, one at each of the ratings 800, 1000, 1200, 1400, 1600, and 2000, so that difficulty spans five official rating bands from Newbie to Candidate Master~\cite{cfratings}. We kept each corpus's own labels, so the denominator of every arm is the same 2{,}970 programs.

% [번역] 기타 설정. 모든 LLM 팔은 gpt-5.4-mini(입력/출력 백만 토큰당 0.75/4.50달러)와 claude-sonnet-5(2/10달러)에서 돌았으며, 각 공급자에서 이 프롬프트들에 캐싱이 동작하는 가장 값싼 티어다. 각 모델은 CoEP의 빌더이자 fallback이면서 PyDex의 수리 모델로 쓰였다. CoEP는 R1–R5에서 T⁺로 수리를 받아들였고, 테스트 케이스가 채점기의 공식 전체 테스트 집합(문제당 22–56개)인 C1–C6에서는 T⁺ = T다. 수리율(RR)은 수정 프로그램이 T를 모두 통과할 때만 수리로 센다. 상대 패치 크기(RPS, 4.5절)는 수리된 프로그램에 대해 평균하며, RR_τ는 5.6절의 held-out 집합(C1–C6에서는 공식 테스트)을 통과하면서 RPS ≤ τ인 패치로 수리된 프로그램의 비율이다. 소요 시간(ATT)은 제출물당 평균 벽시계 초로 로컬 계산(ATT_cpu, CoEP는 과제당 프로그램 20개를 다른 작업 없는 기계에서 하나씩 재고 과제 크기로 가중)과 모델 지연(ATT_api)의 합이고, 모델 비용 C_tot = C_build + C_api는 정확한 토큰 수로 매긴 벤치마크 전체의 미국 달러이며 빌드는 증폭을 포함한다. R1–R5의 Refactory는 저자들이 발표한 수리율과 패치 크기를 보고하고, 짝지은 검정에는 저자들이 배포한 실행의 프로그램별 결과를 쓴다. 이 결과는 발표된 수리율을 0.05포인트 이내로 재현한다. C1–C6에서는 공개 도구를 직접 돌렸다. 두 빌더에 걸친 결과를 보고하되 각 빌더를 따로 검정하며, 짝지은 수리 결과는 정확 McNemar 검정, 패치 크기는 Wilcoxon 부호 순위 검정으로 비교했고 기준은 p < 0.05다.
\textbf{Other Settings.} Every LLM arm ran on \gm (\$0.75/\$4.50 per million input/output tokens) and \cs (\$2/\$10), each provider's cheapest tier at which prompt caching works on these prompts; each model served as \tool's builder and fallback and as PyDex's repairer. On R1--R5, \tool accepted repairs against $T^{+}$; on C1--C6, whose test cases are the judge's full official sets (22 to 56 per problem), $T^{+} = T$. The \emph{repair rate} (RR) counts a repair only when the fixed program passes all of $T$. The \emph{relative patch size} (RPS, Section~\ref{sec:repair}) is averaged over the repaired programs, and $\mathrm{RR}_{\tau}$ is the share of programs repaired by a patch with $\RPS \le \tau$ that passes the held-out suite of Section~\ref{sec:rq-heldout} (on C1--C6, the official tests). The \emph{turnaround} (ATT) is the mean wall-clock seconds per submission, local computation ($\mathrm{ATT}_{\V{cpu}}$, for \tool timed one program at a time on an otherwise idle machine over 20 programs per assignment, weighted by its size) plus model latency ($\mathrm{ATT}_{\V{api}}$), and the \emph{model cost} $C_{\V{tot}} = C_{\V{build}} + C_{\V{api}}$ is the US dollars spent over the benchmark, priced from exact token counts, with amplification in the build. For Refactory on R1--R5, we report the repair rates and patch sizes its authors published, and pair against the per-program results of the run they released, which reproduces those rates to within 0.05 points; on C1--C6, we ran the released tool. We report results over both builders but test each builder separately, with the exact McNemar test on paired repair outcomes and the Wilcoxon signed-rank test on patch sizes, at $p < 0.05$.

Table~\ref{tab:effect} shows that \coepLF repaired as many programs as the strongest baseline while making the smallest patches. Overall, \coepLF repaired 99.4\% of the 2{,}970 programs, against 85.9\% for Refactory and 98.9\% for PyDex, and reached 100\% on eight of the eleven assignments. Its mean RPS of 0.435 is 31.3\% smaller than PyDex's 0.634 and smaller than Refactory's 0.500, and on the 5{,}025 pairs all three arms repaired, it was 0.420 against 0.479 and 0.626 (Figure~\ref{fig:effect}-(b), where a curve further to the left means smaller patches). PyDex's large patches are often rewrites: 17.8\% and 17.1\% of its repairs have $\RPS \ge 1$, against 6.0\% and 6.8\% of \coepLF's.

% [번역] 특히 난이도가 오를수록 Refactory와의 격차가 벌어진다. CS1 과제, Codeforces 800–1000, Codeforces 1200–2000으로 묶으면 Refactory의 수리율은 90.8%에서 83.1%, 54.5%로 떨어지는 반면 CoEP_LF는 99.0%, 100.0%, 100.0%를 유지한다(Figure 4-(a)). 빈약한 풀만으로는 이 붕괴가 설명되지 않는다. C5와 C6는 모든 팔에 참조 프로그램 두 개만 주지만 두 CoEP 팔은 모두 완전히 수리하기 때문이다. 차이는 재사용의 입도에 있다. Refactory는 어긋나는 블록을 채택하므로 다른 방식으로 문제를 푸는 풀에서는 채택할 것이 남지 않지만, CoEP는 이름을 바꾼 뒤 줄 hunk를 채택한다.
Notably, the gap to Refactory widens with difficulty. Grouped into the CS1 assignments, Codeforces 800--1000, and Codeforces 1200--2000, Refactory's repair rate falls from 90.8\% to 83.1\% and 54.5\%, whereas \coepLF holds 99.0\%, 100.0\%, and 100.0\% (Figure~\ref{fig:effect}-(a)). Thin pools alone do not explain this collapse, since C5 and C6 give every arm only two reference programs and both \tool arms repair them completely. The difference lies in the granularity of reuse: Refactory adopts divergent blocks, so a pool that solves the problem another way leaves nothing to adopt, whereas \tool adopts line hunks after renaming.

% [번역] 프리즈된 도구만 쓰는 CoEP_L은 모델 호출 없이 98.4%를 수리해 PyDex의 98.9%보다 조금 적었다. 차이는 대부분 후보가 증폭된 테스트 케이스 100개도 통과해야 하는 R2와 R3에 있으며, CoEP_LF의 에스컬레이션이 그 대부분을 되살렸다. 통계적으로 CoEP_LF는 두 빌더 모두에서 Refactory보다 많은 프로그램을 수리했다(정확 McNemar, p < 0.001). PyDex 대비로 CoEP_LF는 gpt-5.4-mini에서 더 많은 프로그램을 수리했지만(p = 0.029) claude-sonnet-5에서는 유의하지 않았고(p = 0.14), CoEP_L의 차이는 유의하지 않았다(p = 0.091과 0.075). 두 팔 모두 공통 쌍에서 두 베이스라인보다 작은 패치를 만들었다(빌더별 Wilcoxon, p < 0.01). 과제당 한 번 합성한 도구는 제출물마다 질의하는 모델만큼 많은 프로그램을 3분의 1 작은 패치로 수리한다.
The frozen tool alone, \coepL, repaired 98.4\% without a single model call, slightly fewer than PyDex's 98.9\%; most of the gap lies on R2 and R3, where a candidate must also pass the 100 amplified test cases, and the escalation of \coepLF recovered most of it. Statistically, \coepLF repaired more programs than Refactory on both builders (exact McNemar, $p < 0.001$). Against PyDex, \coepLF repaired more programs on \gm ($p = 0.029$) but not significantly on \cs ($p = 0.14$), and \coepL's difference was not significant ($p = 0.091$ and $0.075$); both made smaller patches than both baselines on the common pairs (Wilcoxon signed-rank, $p < 0.01$ per builder). A tool synthesized once per assignment thus repairs as many programs as a model queried per submission, with patches a third smaller.

% [번역] 제출물당 팔은 모든 제출물에 질의 하나의 값을 치르는 반면, CoEP_LF는 과제당 한 번 빌드 비용을 치르고 에스컬레이션된 제출물에서만 질의한다. 두 비용은 과제당 N* = C̄_build / Δ 제출물에서 같아지며, C̄_build는 과제의 평균 빌드 비용, Δ는 제출물당 절약이다. 부록 B의 Figure 8은 두 비용을 로그 축에 그리며, 원은 N*를, 눈금은 우리 과제 11개의 크기를 표시한다.
A per-submission arm pays for a query on every submission, whereas \coepLF pays its build once per assignment and queries only on escalation; the two break even at $N^{*} = \bar{C}_{\V{build}} / \Delta$ submissions per assignment, with $\bar{C}_{\V{build}}$ the mean build cost of an assignment and $\Delta$ the saving per submission. Figure~\ref{fig:cost} in Appendix~\ref{app:cost} plots both costs on log scales, with circles at $N^{*}$ and ticks at the sizes of our 11 assignments.

% [번역] Table 3은 CoEP_LF가 벤치마크 전체에서 claude-sonnet-5로 13.83달러, gpt-5.4-mini로 1.04달러를 쓴 반면 PyDex는 292.77달러와 28.42달러로 21.2배와 27.3배를 더 썼음을 보여 준다. 출력 토큰이 지출을 지배하므로 프롬프트 캐싱을 적용한 PyDex_PC도 19.0배와 22.6배 더 들었고, 모든 입력 토큰을 캐시 읽기 요율로 청구해도 16.7배와 12.6배 더 든다. 과제 하나는 PyDex 대비 claude-sonnet-5에서 N* = 11개, gpt-5.4-mini에서 7개 제출물 이후 빌드 비용을 회수했고, 11개 과제 중 10개가 이 지점을 넘었으며 대부분은 한 자릿수 이상 넘었다. 예시 없이 질의 하나만 보내는 LLM_Direct에 대해서도 CoEP_LF는 1.2배와 2.6배 덜 들었으며, 손익분기점은 220개와 80개 제출물로 늦지만 LLM_Direct가 수리한 프로그램은 82.5%뿐이었다. CoEP는 제출물의 12.6%(5,940쌍 중 751쌍)에서 모델에 질의했다. 소요 시간에서 CoEP_LF는 claude-sonnet-5로 제출물당 3.02초가 걸려 PyDex의 14.64초보다 빨랐지만, gpt-5.4-mini에서는 3.21초로 PyDex의 2.14초보다 느렸다. 제출물당 팔의 소요 시간은 거의 모두 모델 지연이고 CoEP의 소요 시간은 거의 모두 로컬 탐색이기 때문이다. CoEP가 대신 치르는 것은 첫 제출물 전에 한 번 치르는 과제당 22.2분과 15.3분의 빌드다.
Table~\ref{tab:cost} shows that \coepLF spent \$13.83 over the benchmark on \cs and \$1.04 on \gm, whereas PyDex spent \$292.77 and \$28.42, 21.2 and 27.3 times more. Since output tokens dominate the spend, \pydexPC still cost 19.0 and 22.6 times more, and billing every input token at the cache-read rate would leave it 16.7 and 12.6 times more. An assignment repaid its build after $N^{*} = 11$ submissions against PyDex on \cs and 7 on \gm, and ten of the eleven assignments exceeded these points, most by an order of magnitude. Even against \direct, which sends a single query without exemplars, \coepLF cost 1.2 and 2.6 times less; it breaks even later, at 220 and 80 submissions, but \direct repaired only 82.5\% of the programs. \tool queried the model on 12.6\% of the submissions (751 of 5{,}940 pairs). Regarding turnaround, \coepLF took 3.02 seconds per submission against PyDex's 14.64 on \cs, but 3.21 against 2.14 on \gm, since a per-submission arm's turnaround is almost all model latency and \tool's almost all local search; what \tool pays instead is a build of 22.2 and 15.3 minutes per assignment, once before the first submission.

% [번역] 구조가 절약을 산다. 빌더의 규칙이 없어도 CoEP의 수리율과 held-out 수리율은 거의 움직이지 않았고(5,940쌍 중 2쌍만 달라졌다), 비용은 1.69달러와 0.36달러로 떨어져 PyDex보다 173배와 79배 적었다. 절약은 local-first 구조, 즉 대부분의 제출물을 수리하고 나머지만 에스컬레이션하는 프리즈된 탐색에서 나온다. 그 폭은 참조 이식이 맡아 CoEP_L의 수리 5,845개 중 80.4%를 평균 RPS 0.582로 만들었다. 이식은 버기 프로그램과 제어 흐름이 같은 정답 프로그램을 요구하지 않는데, CLARA는 그 요구를 자기 접근의 유일한 근본적 문제라 했고 Sarfgen은 정확한 일치를 요구한다. CoEP_LF가 수리한 5,904쌍 중 154개(2.6%)는 학급의 어떤 정답 프로그램과도 루프 구조가 다르고 1,448개(24.5%)는 루프와 조건문 중첩이 다르며, 도구는 후자 중 1,258개를 질의 없이 수리했다. 같은 질의를 모든 프로그램에 보내는 LLM_Direct는 82.5%만 수리했다(정확 McNemar, 빌더별 p < 0.001). 질의 하나는 패치가 실패하면 두 번째 후보가 없기 때문이다. 다만 둘 다 수리한 4,899쌍에서는 LLM_Direct의 패치가 더 작았으며(RPS 0.330 대 0.393), 이는 두 팔이 모두 붙이는 최소 편집 참조 프로그램 π(b) 덕분이다.
\textbf{The architecture buys the saving.} Without the builder's rules, \tool's repair rate and held-out repair rate barely moved (2 of the 5{,}940 pairs changed), and its cost fell to \$1.69 and \$0.36, 173 and 79 times less than PyDex: the saving comes from the local-first architecture, a frozen search that repairs most submissions and escalates the rest. The reference transplant carries its breadth, producing 80.4\% of \coepL's 5{,}845 repairs at mean RPS 0.582. It needs no correct program with the buggy program's control flow, the requirement CLARA calls the only fundamental problem of its approach~\cite{gulwani2018automated} and Sarfgen imposes exactly~\cite{wang2018search}: of the 5{,}904 pairs \coepLF repaired, 154 (2.6\%) have a loop structure and 1{,}448 (24.5\%) a nesting of loops and conditionals that no correct program of the class shares, and the tool repaired 1{,}258 of the latter without a query. Sending the same query for every program instead, \direct repaired only 82.5\% (exact McNemar, $p < 0.001$ per builder), since a single query has no second candidate when its patch fails; on the 4{,}899 pairs both repaired, though, its patches were smaller (RPS 0.330 against 0.393), which credits the minimum-edit reference program $\pi(b)$ that both attach.

% [번역] 오라클이 정확성을 산다. 증폭이 없으면 CoEP는 T에서 조금 더 많은 프로그램을 수리했지만 버티는 수리는 더 적었다. held-out 수리율이 99.1%와 99.0%에서 94.0%와 93.1%로 떨어졌으며(정확 McNemar, 빌더별 p < 0.001, 154개와 175개 대 3개와 2개), 아낀 빌드 비용은 생성기의 값인 0.02달러와 0.01달러였다. 5.6절은 이것이 정리 4.3이 예측하는 상호작용임을 보인다.
\textbf{The oracle buys correctness.} Without amplification, \tool repaired slightly more programs on $T$ but fewer that hold: its held-out repair rate fell from 99.1\% and 99.0\% to 94.0\% and 93.1\% (exact McNemar, $p < 0.001$ per builder; 154 and 175 programs against 3 and 2), while the build it saved was the generator's price, \$0.02 and \$0.01. Section~\ref{sec:rq-heldout} shows that this is the interaction Theorem~\ref{thm:overfit} predicts.

% [번역] 규칙이 작은 패치를 산다. 합성된 규칙은 커버리지가 아니라 패치 크기와 빈약한 풀에서 중요하다. 규칙이 있으면 CoEP는 held-out을 통과하는 RPS 0.25 이하 패치로 5.7포인트와 1.8포인트 더 많은 프로그램을 수리했고(규칙이 있어야만 그런 패치가 되는 경우 173개와 53개, 반대 경우 4개와 1개, 정확 McNemar, 빌더별 p < 0.001), 둘 다 수리한 프로그램에서 패치가 더 작았다(RPS 0.422 대 0.448, 0.450 대 0.458, Wilcoxon p < 0.001). 합성된 규칙은 규칙 수리 1,147개 중 837개에 관여했으며, 규칙 수리는 정리 4.5가 예상하게 하듯 이식의 0.582에 대해 시스템에서 가장 작은 평균 RPS 0.109의 패치를 만들었고, 405개(35.3%)는 규칙 적용 둘에서 다섯을 조합해 더 얕은 조합이 모두 실패한 뒤에야 도달했다(Figure 5-(b), 명제 4). 맞는 풀이 있으면 이식이 규칙이 수리하는 거의 모든 것(99.2%)을 수리하므로 커버리지 이득은 작지만, 풀이 빈약하면 규칙이 중요하다. 빌더가 보지 않은 프로그램 146개에서 참조 프로그램이 하나도 없으면 규칙은 CoEP_L의 수리율을 8.2%에서 28.8%로 올렸고, 참조가 하나나 둘이면 RPS를 0.09–0.14 줄였다. 규칙은 무엇을 고치는지 이름도 단다. 세 평가자가 규칙 191개를 코드와 그 규칙이 만든 수리 하나에 비추어 판정했으며(Fleiss' κ = 0.890), 규칙이 만든 수리의 99.2%가 규칙이 한 일과 일치하는 이름을 지녔다.
\textbf{The rules buy small patches.} The synthesized rules matter for patch size and thin pools rather than coverage. With them, \tool repaired 5.7 and 1.8 points more programs with a held-out-passing patch of RPS at most 0.25 (173 and 53 programs against 4 and 1; exact McNemar, $p < 0.001$ per builder), and on the programs both arms repaired, its patches were smaller (RPS 0.422 against 0.448 and 0.450 against 0.458; Wilcoxon, $p < 0.001$). Synthesized rules took part in 837 of the 1{,}147 rule repairs, which make the smallest patches in the system at mean RPS 0.109 against 0.582 for the transplant, as Theorem~\ref{thm:local} leads one to expect, and 405 of those repairs (35.3\%) composed two to five rule applications (Figure~\ref{fig:source}-(b)), reached only after every shallower composition had failed (Proposition~\ref{prop:shallow}). The coverage gain is small because the transplant repairs nearly everything a rule repairs when a matching pool exists (99.2\%), but when the pool is thin the rules matter: on 146 programs the builder never saw, they raised \coepL's repair rate from 8.2\% to 28.8\% with no reference program, and cut RPS by 0.09 to 0.14 with one or two. The rules also name what they repair: three raters judged 191 rules against their code and a repair each produced (Fleiss' $\kappa = 0.890$), and 99.2\% of the rule-produced repairs carry a name consistent with what the rule did.

% [번역] Learn. Learn 단계는 도구가 실패하는 곳에서만 동작한다. CoEP_L은 95쌍에 실패했고 fallback이 그중 59쌍을 수리했으며, Learn 단계는 이 수리를 0.89달러(Table 3에는 포함되지 않음)에 규칙 11개로 일반화했다. CoEP_L+Learn은 이 규칙들로 회귀 없이 프로그램 15개를 되살렸으며(claude-sonnet-5에서 14개, 정확 McNemar p < 0.001, gpt-5.4-mini에서 1개), 계약을 강제하기 전에는 LLM 패치가 여러 위치를 고치는 경우가 많아 32개였다. 이는 과제 안에서의 재사용이며 과제 간 전이는 아니다. CoEP_LF가 수리하지 못한 36쌍은 모두 fallback까지 갔다. 그중 18쌍은 T만으로 받아들이면 수리되고, 나머지 18쌍(모두 R2)은 T를 통과하는 후보가 없었다.
\textbf{Learn.} The Learn stage fires only where the tool fails: \coepL failed on 95 pairs, the fallback repaired 59, and the Learn stage generalized these repairs into 11 rules for \$0.89, not included in Table~\ref{tab:cost}, with which \coepLL recovered 15 programs without a regression (14 on \cs, exact McNemar $p < 0.001$; one on \gm), against 32 before the contract was enforced, since an LLM patch often edits several positions. This is reuse within an assignment, not transfer across assignments. The 36 pairs \coepLF left unrepaired all reached the fallback: 18 are repaired when accepting against $T$ alone, and for the other 18, all on R2, no candidate passed $T$.

\subsection{Generality}
\label{sec:rq-general}

% [번역] 우리는 학급의 앞선 제출물로 만든 도구가 뒤의 제출물을 수리하는지 살폈다. 제출 id가 제출 시간을 따르는 C1–C5의 제출물은 id 순으로, 시간도 학생도 기록하지 않는 CS1의 제출물은 시드를 고정한 무작위 순서 세 개로 놓았다(C6는 제출물이 다섯 개다). 각 순서의 처음 f ∈ {10, 25, 50, 75}%로 도구를 만들고(버기 프로그램은 Select에, 정답 프로그램은 R에) 마지막 4분의 1의 버기 프로그램(CS1은 순서마다 439개, Codeforces는 313개)을 수리했으며, 기준으로 학급 전체로 만든 5.2절의 도구로도 수리했다(부록 C Figure 8-(a)의 all).
We examined whether a tool built from a class's earlier submissions repairs its later ones. We ordered the submissions of C1--C5 by id, which follows submission time, and those of CS1, which records neither time nor student, in three seeded random orders (C6 has five submissions). We built a tool from the first $f \in \{10, 25, 50, 75\}\%$ of each order, its buggy programs feeding Select and its correct programs forming $R$, and repaired the buggy programs of the last quarter, 439 per order on CS1 and 313 on Codeforces, also with the tools of Section~\ref{sec:rq-effect}, built from the whole class (``all'' in Figure~\ref{fig:general}-(a), Appendix~\ref{app:general}).

% [번역] 학급의 처음 10%로 만든 도구는 전체 학급으로 만든 도구만큼 뒤의 제출물을 잘 수리했다(부록 C의 Figure 8-(a)). CoEP_LF는 10% 빌드로 CS1에서 99.3%(전체 도구는 99.1%), Codeforces에서 98.9%(100.0%)를 수리했고 Codeforces는 학급 절반부터 99.5%로 올랐다. 프리즈된 도구만으로는 Codeforces에서 이식할 참조가 적어 더 많은 이력이 필요했으며(10%에서 93.9%, 50%에서 98.4%), fallback이 그 차이 대부분을 되살렸다. CS1에서 10%에서 75%로 가는 동안 작업 쌍은 9.2배 늘었지만 빌드 비용은 1.9배만 늘었으므로(부록 C), 새 과제를 맡은 강사는 첫 제출물 몇십 개로 도구를 만들고 학기가 진행되며 다시 만들 수 있다.
A tool built from the first 10\% of a class repaired its later submissions about as well as one built from the whole class (Figure~\ref{fig:general}-(a)): \coepLF repaired 99.3\% on CS1 (against 99.1\% for the whole-class tool) and 98.9\% on Codeforces (against 100.0\%), rising to 99.5\% from half the class. The frozen tool alone needed more history on Codeforces, where a thin pool offers fewer reference programs to transplant from (93.9\% from 10\% and 98.4\% from 50\%), and the fallback recovered most of the difference. From 10\% to 75\% of CS1, the worked pairs grew 9.2-fold but the build cost only 1.9-fold (Appendix~\ref{app:general}), so an instructor facing a new assignment can build a tool from its first few dozen submissions and rebuild it as the term proceeds.

\subsection{Correctness beyond the Tests}
\label{sec:rq-heldout}

\begin{figure}[t]
\centering
\includegraphics[width=\textwidth]{figures/fig_heldout}
\caption{Held-out repair rate on R1--R5 of each arm and of PyDex against its number of samples. Accepting $T$ or $T^{+}$: accepting a candidate against $T$ alone or against \tool's amplified suite.}
\label{fig:heldout}
\end{figure}

% [번역] R1–R5는 과제당 강사 테스트 케이스 7.4개를 제공하며, 5.2절에서 모든 팔은 이 테스트로 탐색하고 이 테스트로 채점받았다. 우리는 어떤 팔도 탐색에 쓰지 않은 held-out 테스트 집합을 과제마다 만들었다. 빌더의 생성기와 독립적으로 우리가 손으로 쓴 생성기에서 다른 시드로 뽑은 입력 100개이며, 각 입력은 정답 프로그램의 다른 표본 40개와 참조 해답의 다수 출력으로 90% 일치에서 라벨링했고 T⁺와 겹치지 않는다. 그런 다음 모든 팔의 수리를 T와 held-out 집합에서 다시 실행했다. C1–C6는 이미 채점기의 공식 전체 테스트 집합을 쓴다.
R1--R5 ship 7.4 instructor test cases per assignment, and in Section~\ref{sec:rq-effect} every arm both searched against them and was judged by them. To check whether the repairs remain correct beyond them, we built a held-out suite per assignment that no arm searched against: 100 inputs drawn with a different seed from a generator we wrote by hand, independently of the builders' generators, each labelled by the majority output of a different sample of 40 correct programs and the reference solution at 90\% agreement, and none in $T^{+}$. We then re-ran every arm's repairs on $T$ and the held-out suite; C1--C6 already use the judge's full official test sets.

% [번역] Figure 6-(a)는 각자의 수용 기준으로 돌린 베이스라인보다 CoEP의 수리가 더 자주 버텼음을 보여 준다. CoEP_LF가 수리한 프로그램의 99.7%와 99.2%가 held-out 집합도 통과했으며 PyDex는 97.8%와 98.0%였고, 그 결과 held-out 집합에서 CoEP_LF는 98.5%와 98.3%를, PyDex는 96.4%와 97.2%를 수리했다(정확 McNemar, p < 0.001과 p = 0.042). T만으로 받아들인 같은 도구는 90.1%와 88.6%를 수리했으므로, 증폭은 T에서의 수리율 0.5와 0.3포인트를 held-out 집합에서의 8.5와 9.7포인트와 맞바꾼 것이다.
Figure~\ref{fig:heldout}-(a) shows that \tool's repairs held more often than those of the baselines run with their own acceptance. Of the programs \coepLF repaired, 99.7\% and 99.2\% also passed the held-out suite, against 97.8\% and 98.0\% for PyDex, so on the held-out suite \coepLF repaired 98.5\% and 98.3\% of the programs against PyDex's 96.4\% and 97.2\% (exact McNemar, $p < 0.001$ and $p = 0.042$). Accepting against $T$ alone, the same tool repaired 90.1\% and 88.6\%: amplification traded 0.5 and 0.3 points of repair rate on $T$ for 8.5 and 9.7 points on the held-out suite.

% [번역] 이 정확성은 CoEP의 탐색이 아니라 오라클의 몫이며 다른 수리기로 옮겨 간다. 같은 T⁺를 주자 PyDex의 held-out 수리율은 0.9포인트와 1.8포인트 올라 97.3%와 99.0%가 되었다. 오라클을 같게 하면 CoEP는 claude-sonnet-5에서 여전히 앞섰고(98.5% 대 97.3%, 정확 McNemar p = 0.010) gpt-5.4-mini에서는 뒤졌다(98.3% 대 99.0%, p = 0.054). CoEP는 둘 다 수리한 프로그램에서 패치를 21%와 35% 작게 유지했고(RPS 0.307 대 0.389, 0.323 대 0.497, Wilcoxon p < 0.001) 비용은 19배와 30배 적었다. T⁺를 통과하는 후보가 나올 때까지만 샘플링하면 gpt-5.4-mini에서 PyDex의 비용은 2.28달러로 줄지만 여전히 CoEP의 0.59달러의 3.9배이고 패치는 RPS 0.596이다. 우리는 gpt-5.4-mini에서 후보 열 개를 모두 남기며 PyDex를 다시 질의했고, claude-sonnet-5에서는 더 엄격한 오라클이 바꿀 수 있는 유일한 프로그램, 즉 고른 패치가 T⁺에서 실패하는 69개를 다시 질의했다.
\textbf{The oracle, not the search, buys correctness, and it transfers.} Given the same $T^{+}$, PyDex's held-out repair rate rose by 0.9 and 1.8 points, to 97.3\% and 99.0\%; with equal oracles, \tool remained ahead on \cs (98.5\% against 97.3\%, exact McNemar $p = 0.010$) and trailed on \gm (98.3\% against 99.0\%, $p = 0.054$). \tool kept its patches 21\% and 35\% smaller on the programs both repaired (RPS 0.307 against 0.389 and 0.323 against 0.497; Wilcoxon, $p < 0.001$) at 19 and 30 times lower cost; sampling only until a candidate passes $T^{+}$ cuts PyDex's cost on \gm to \$2.28, still 3.9 times \tool's \$0.59, with patches at RPS 0.596. We re-queried PyDex on \gm keeping all ten candidates, and on \cs for the 69 programs whose pick fails $T^{+}$, the only ones a stricter oracle can change.

% [번역] Figure 6-(b)는 정리 4.3이 예측하는 폭의 효과를 한 수리기 안에서 보여 준다. PyDex가 뽑는 표본이 늘수록, T 대신 T⁺로 받아들이는 것은 k = 1에서 held-out 수리율 0.4포인트를 잃고(92.4% 대 92.8%) k = 10에서 1.8포인트를 얻는다(99.0% 대 97.3%). 후보가 하나뿐이면 더 엄격한 오라클은 거부만 할 수 있으며, 질의 하나를 보내는 LLM_Direct는 실제로 T⁺ 아래에서 held-out 수리를 잃었다(87.8%와 82.1%, T 아래에서는 90.2%와 83.8%). CoEP든 PyDex든 탐색은 통과하는 다른 후보를 찾는다. 나머지는 설명 가능하다. R5의 여섯 개는 모두 유일한 빈 입력 top_k([], 0)에서 실패하는데 두 집합을 겹치지 않게 하면서 이 입력이 T⁺에서 빠졌고, gpt-5.4-mini의 R3 생성기는 −2에서 3 사이 값만 뽑아 더 큰 값에서만 실패하는 패치 아홉 개를 놓쳤다.
Figure~\ref{fig:heldout}-(b) shows the breadth effect Theorem~\ref{thm:overfit} predicts, within one repairer: as PyDex draws more samples, accepting against $T^{+}$ instead of $T$ costs 0.4 points of held-out repair rate at $k = 1$ (92.4\% against 92.8\%) and gains 1.8 at $k = 10$ (99.0\% against 97.3\%). With a single candidate, a stricter oracle can only reject, and \direct, which sends one query, indeed lost held-out repairs under $T^{+}$ (87.8\% and 82.1\%, against 90.2\% and 83.8\% under $T$), whereas a search, \tool's or PyDex's, finds another candidate that passes. The rest are explicable: all six on R5 fail \texttt{top\_k([], 0)}, the only empty input, which keeping the suites disjoint removed from $T^{+}$, and \gm's R3 generator drew values only from $-2$ to $3$, missing nine patches that fail on larger ones.

\subsection{Threats to Validity}
\label{sec:threats}

% [번역] (1) 학급 분할: 5.5절의 CS1 분할은 무작위 순서이며, 학기 단위로 나누면 수리율이 낮을 수 있다. (2) 빌드와 평가의 겹침: 5.2–5.4절과 5.6절의 도구는 그것이 수리하는 학급으로 만들었으며 버기 프로그램 2,970개 중 1,524개가 작업 쌍에 들었다. 5.5절은 빌더가 보지 않은 제출물에서 평가한다. (3) 테스트 적정성: 수리는 T를 통과할 때 센다. R1–R5에서 CoEP는 T⁺도 요구하고 5.6절은 held-out 테스트로 검사하지만, 두 집합 모두 학급의 정답 프로그램으로 라벨링되므로 학급 대부분이 똑같이 틀리는 동작은 드러나지 않으며(명제 2), C1–C6에서는 채점기의 공식 테스트에 의존한다. (4) 빌더: 두 빌더 모두 닫힌 상용 모델이므로 다시 빌드하면 같은 규칙이 나오지 않을 수 있다. 우리는 오프라인으로 도는 도구 22개와 생성기 10개를 공개한다. (5) 벤치마크: 과제 11개는 Python 문제이고 C6는 버기 프로그램 세 개만 기여하므로 다른 언어나 큰 프로젝트로 이어지지 않을 수 있다.
(1) \textbf{Class splits:} The CS1 splits of Section~\ref{sec:rq-general} are random orders; a split by term may yield lower rates. (2) \textbf{Build and evaluation overlap:} The tools of Sections~\ref{sec:rq-effect}--\ref{sec:rq-stage} and~\ref{sec:rq-heldout} were built from the class they repair, with 1{,}524 of the 2{,}970 buggy programs among the worked pairs; Section~\ref{sec:rq-general} evaluates on submissions the builder never saw. (3) \textbf{Test adequacy:} A repair counts when it passes $T$. On R1--R5, \tool also requires $T^{+}$ and Section~\ref{sec:rq-heldout} checks held-out tests, but both suites are labelled by the class's correct programs, so a behavior most of the class gets wrong goes undetected (Proposition~\ref{prop:label}); on C1--C6, we rely on the judge's official tests. (4) \textbf{Builders:} Both builders are closed commodity models, so a rebuild may not reproduce the same rules; we release the 22 tools and 10 input generators, which run offline. (5) \textbf{Benchmarks:} Our 11 assignments are in Python, and C6 contributes three buggy programs; the results may not transfer to other languages or large projects.

\section{Related Work}
\label{sec:related}
%=============================================================================

% [번역] 프로그래밍 과제 수리. Singh 등은 강사가 쓴 error model, 즉 Sketch 기반 탐색이 최소 수정을 찾아 조합하는 재작성 규칙 집합으로 시도를 수리하며, CoEP는 그 error model을 과제마다 합성하고 T⁺로 검증하는 열거로 탐색한다. 참조 유도 기법은 학급의 정답 프로그램을 재사용한다. CLARA와 Sarfgen은 버기 프로그램을 루프 구조나 제어문 순서가 같은 정답 프로그램에 정렬하는데 우리 수리의 4분의 1은 그런 프로그램이 없으며(5.4절), Verifix는 정렬을 형식 검증으로 뒷받침하고, Refactory는 풀을 리팩터링해 정렬 범위를 넓히며, MENTORED는 정답과 오답 프로그램을 유전 프로그래밍으로 재조합한다. LLM 기반 기법은 검색한 예시, 튜터링 대화, 미세 조정, 결함 위치 추정, 다른 학생의 수정 쌍 검색과 함께 제출물마다 모델에 질의한다. 이들과 달리 CoEP는 모델 노력을 과제당 한 번 만드는 도구에 쓰며, 이들 중 어느 것이든 그 도구 뒤의 Generate 함수가 될 수 있다.
\textbf{Program Repair for Programming Assignments.} Singh et al.~\cite{singh2013automated} repair an attempt with an instructor-written \emph{error model}, a set of rewrite rules whose combinations a Sketch-based search explores for a minimal correction; \tool synthesizes that error model per assignment and searches it by enumeration validated against $T^{+}$. Reference-guided techniques reuse the class's correct programs: CLARA~\cite{gulwani2018automated} and Sarfgen~\cite{wang2018search} align a buggy program with a correct one of the same loop structure or sequence of control statements, which a quarter of our repairs lack (Section~\ref{sec:rq-stage}), Verifix~\cite{ahmed2022verifix} backs the alignment with formal verification, Refactory~\cite{hu2019re} refactors the pool to widen what aligns, and MENTORED~\cite{choi2025automated} recombines correct and incorrect programs by genetic programming. LLM-based techniques query a model per submission, with retrieved exemplars~\cite{zhang2024pydex}, tutoring~\cite{yang2024cref}, fine-tuning~\cite{liu2024fastfixer,yang2026morepair}, fault localization~\cite{dai2025less,orvalho2025counterexample,orvalho2025mentor}, or other students' fixes~\cite{dai2026learner}. Unlike these techniques, \tool spends its model effort on a tool built once per assignment; any of them can serve as the \Fn{Generate} function behind it.

% [번역] 제출물의 군집화와 변환. OverCode, CLARA, SemCluster, InvAASTCluster는 정규화한 문장, 제어 흐름과 변수 추적, 경로별 의미 특징, 불변식과 익명화한 AST가 맞는 프로그램을 묶어 수리기가 정렬할 참조 프로그램을 고르는 데 쓴다. CoEP는 대신 버기 프로그램을 그것을 수리하는 편집으로 묶는데, 군집이 빌더가 일반화할 수리를 정하기 때문이다. Head 등은 오답을 그것을 고치는 변환으로 묶어 강사가 묶음마다 피드백을 한 번 쓰게 한다. CoEP처럼 Refazer도 (전, 후) 쌍에서 과제 전용 재작성 규칙을 유도하지만, 학생 자신의 수정으로부터 DSL에서 예제 기반 프로그래밍으로 합성한다. CoEP의 빌더는 각 쌍과 함께 문제 설명과 테스트를 보므로 규칙이 수정 하나의 문법이 아니라 오개념을 담을 수 있고, CoEP는 규칙을 검증하는 오라클도 합성한다. 템플릿 기반 수리와 Reyes 등은 마이닝하거나 LLM이 만든 AST 변환을 학급이 아닌 소프트웨어 프로젝트에 적용한다.
\textbf{Clustering and Transforming Submissions.} OverCode~\cite{glassman2015overcode}, CLARA~\cite{gulwani2018automated}, SemCluster~\cite{perry2019semcluster}, and InvAASTCluster~\cite{orvalho2025invaastcluster} group programs whose normalized statements, control flow and variable traces, per-path semantic features, or invariants and anonymized ASTs coincide, to choose the reference program a repairer aligns with. \tool instead clusters buggy programs by the edit that repairs them, since its clusters decide which repairs a builder generalizes. Head et al.~\cite{head2017writing} group incorrect submissions by the transformations that fix them, so that a teacher writes feedback once per group. Like \tool, Refazer~\cite{rolim2017learning} induces assignment-specific rewrite rules from (before, after) pairs, by programming-by-example in a domain-specific language from students' own fixes; \tool's builder instead sees the problem description and tests with each pair, so a rule can encode the misconception rather than the syntax of one fix, and \tool synthesizes the oracle that validates the rules as well. Template-based repair~\cite{kim2013automatic,liu2019tbar} and Reyes et al.~\cite{reyes2026agentic} apply mined or LLM-generated AST transformations to software projects rather than to a class.

% [번역] 도구 제작자로서의 LLM. 한 연구 흐름에서 LLM은 과제를 직접 풀지 않고 재사용 가능한 도구를 쓴다: LATM, CRAFT, TroVE, ReGAL, Voyager, FunSearch, ReaComp. 그러나 이들 대부분은 추론 시 도구를 부르는 모델을 루프에 남기는 반면, CoEP는 뒤에 모델이 없는 도구를 배포하며, 프로그램 수리는 도구 자체에 대한 실행 가능한 오라클을 더한다. PL에 더 가까운 연구로, 타입 제약 디코딩은 각 접두사를 타입 시스템에 비추어 검사함으로써 LLM 출력이 타입 검사를 통과함을 보장하는 반면, CoEP는 대신 LLM이 쓴 모든 것을 T⁺에 대해 실행하며(명제 4.1) 그 오라클도 합성한다.
\textbf{LLMs as Tool Makers.} In a line of research LLMs write reusable tools instead of solving each task directly: LATM~\cite{cai2024large}, CRAFT~\cite{yuan2024craft}, TroVE~\cite{wang2024trove}, ReGAL~\cite{stengel2024regal}, Voyager~\cite{wang2023voyager}, FunSearch~\cite{romera2024mathematical}, ReaComp~\cite{naik2026reacomp}. Most of them keep a model in the loop that calls the tools at inference, whereas \tool deploys its tool with no model behind it, and program repair adds an executable oracle for the tool itself. Closer to programming languages, type-constrained decoding guarantees well-typed LLM output by checking each prefix against the type system~\cite{mundler2025type}; \tool instead executes everything the LLM writes against $T^{+}$ (Proposition~\ref{prop:sound}), an oracle it also synthesizes.

\section{Conclusion}
%=============================================================================

% [번역] 최근 LLM 기반 프로그램 수리는 자동으로 수리할 수 있는 학생 제출물의 비율을 크게 높였다. 그러나 이 기법들은 버기 제출물마다 모델에 한 번씩 질의하므로 학급은 반복 수리마다 값을 다시 치르며, 강사의 적은 테스트를 통과하는 패치는 무엇이든 받아들인다. 이 논문은 LLM이 제출물마다 패치를 쓰는 대신 과제마다 수리 도구에서 과제에 따라 달라지는 부분, 즉 재작성 규칙과 오라클의 입력 생성기를 한 번 합성하게 하는 CoEP를 제시한다. CoEP는 학급의 편집 스크립트를 군집화해 작업 쌍을 고르고, 오개념 이름 재작성 규칙을 합성하고, 학급의 정답 프로그램과의 차분 테스트로 테스트 케이스를 증폭하고, 모든 제출물을 로컬에서 수리하며, 에스컬레이션한 소수에서 새 규칙을 학습한다. 실험 결과는 CoEP가 수리율에서 제출물당 LLM 수리와 대등하면서 모델 지출은 그 일부에 그침을 보여 주며, 그 절약은 local-first 구조에서, 강사 테스트 너머의 정확성은 합성된 오라클에서, 더 작은 패치는 합성된 규칙에서 나온다. 우리는 탐색이 넓어질수록 그 오라클도 강해져야 한다는 원리가 과제 수리 너머의 LLM 합성 도구에도 적용되리라 기대한다.
Recently, LLM-based program repair has substantially improved the share of student submissions that can be repaired automatically. However, these techniques query the model once per buggy submission, so a class pays again for every recurring repair, and they accept any patch that passes the instructor's few tests. This paper presents \tool, which has an LLM synthesize, once per assignment, the assignment-specific parts of a repair tool, its rewrite rules and the input generator behind its oracle, rather than a patch for every submission. \tool selects worked pairs by clustering the class's edit scripts, synthesizes misconception-named rewrite rules, amplifies the test cases by differential testing against the class's correct programs, repairs every submission locally, and learns new rules from the few it escalates. Experimental results demonstrate that \tool matches per-submission LLM repair in repair rate at a fraction of the model spend, with the saving owed to its local-first architecture, correctness beyond the instructor's tests to its synthesized oracle, and smaller patches to its synthesized rules. We expect the principle that a broader search needs a stronger oracle to carry over to LLM-synthesized tools beyond the repair of assignments.

\section{Selection of Baselines}
\label{app:baselines}

% [번역] 우리는 위 기법들 중에서 기법이 (1) 군집이나 다른 과제용 도구가 아니라 수리를 내놓고, (2) Python 프로그램을 수리하며, (3) 학생의 연속된 시도 사이의 연결, 루프 안의 튜터, 이 과제를 위해 학습한 모델처럼 우리 벤치마크에 없는 입력을 요구하지 않고, (4) CS1 코퍼스에서 자기 계열을 대표한다는 네 기준으로 베이스라인을 골랐다. Refactory와 PyDex만 네 기준을 모두 만족한다. 군집화, 강사가 개입하는 피드백, 도구 제작 접근은 기준 (1)을, Verifix, SemCluster, InvAASTCluster, 반례 유도 수리기(C), Sarfgen(C#), 템플릿·변환 기반 수리(소프트웨어 프로젝트)는 (2)를, 학생의 연속된 시도에서 배우거나 검색하는 Refazer와 LSGen, 과제마다 강사가 쓴 error model이 필요한 Singh 등, 튜터를 두는 CREF, 모델을 미세 조정하는 FastFixer, AdaPatcher, MORepair는 (3)을 만족하지 못한다. 남은 CLARA와 MENTORED는 Refactory처럼 학급의 제출물을 재사용하며, 우리는 CS1 코퍼스를 공개하고 그 위에서 CLARA와 비교한 Refactory를 이 계열의 대표로 삼는다. PyDex는 ChatRepair 같은 범용 수리기와 달리 입문 Python 과제를 위해 설계되었고 프롬프트를 전부 공개한다.
We selected the baselines of Section~\ref{sec:settings} by four criteria: a technique must (1) produce repairs rather than clusters or tools for other tasks, (2) repair Python programs, (3) require no input our benchmark lacks, such as the link between a student's successive attempts, a tutor in the loop, or a model trained for the task, and (4) represent its line of repair on the CS1 corpus. Only Refactory and PyDex satisfy all four. Clustering, teacher-in-the-loop feedback, and tool-making approaches~\cite{glassman2015overcode,perry2019semcluster,orvalho2025invaastcluster,head2017writing,cai2024large,yuan2024craft,wang2024trove,stengel2024regal} fail (1); Verifix~\cite{ahmed2022verifix}, SemCluster, InvAASTCluster, and the counterexample-guided repairers~\cite{orvalho2025counterexample,orvalho2025mentor} (C), Sarfgen~\cite{wang2018search} (C\#), and template- and transformation-based repair~\cite{kim2013automatic,liu2019tbar,reyes2026agentic} (software projects) fail (2); and Refazer~\cite{rolim2017learning} and LSGen~\cite{dai2026learner}, which learn from or retrieve a student's successive attempts, Singh et al.~\cite{singh2013automated}, which needs an instructor-written error model per assignment, CREF~\cite{yang2024cref}, which keeps a tutor in the loop, and FastFixer~\cite{liu2024fastfixer}, AdaPatcher~\cite{dai2025less}, and MORepair~\cite{yang2026morepair}, which fine-tune a model, fail (3). Of the remaining techniques, CLARA~\cite{gulwani2018automated} and MENTORED~\cite{choi2025automated} reuse the class's submissions as Refactory does, and we take Refactory, whose authors released the CS1 corpus and evaluated it against CLARA there~\cite{hu2019re}, as the representative of that line; PyDex, unlike general-purpose repairers such as ChatRepair~\cite{xia2024automated}, is designed for introductory Python assignments and publishes its prompts in full~\cite{zhang2024pydex}.
