\begin{abstract}
% [번역] 프로그래밍 과제에 대한 자동 프로그램 수리는 두 계열로 갈린다. 참조 유도 방식은 학급이 이미 제출한 정답 프로그램에서 이식하므로 제출물당 비용이 없지만, 풀에 구조적으로 맞는 프로그램이 없으면 실패한다. LLM 기반 방식은 그런 제약이 없지만 제출물마다 모델에 질의하므로 지출이 수강 인원과 함께 늘고 매 학기 되풀이되며, 한 과제에 대한 질의들이 같은 명세와 같은 소수의 오개념을 수백 번 다시 읽는다. 우리는 모델이 패치가 아니라 수리 도구를 작성하는 CoEP를 제시한다. 과제당 한 번, 빌더 LLM이 학급 자신의 제출물에서 뽑은 작업 쌍을 오개념 이름을 단 AST 재작성 규칙 모듈로 바꾸고, 그 모듈은 참조 유도 이식 위에서 돈다. 프로즌 도구는 모델 없이 제출물을 수리하며 기권한 것만 관례적인 호출을 탄다. 실제 학생 제출물 2,970건과 과제 11개에서 CoEP는 참조 유도 도구를 커버리지와 패치 크기 양쪽에서 이기고(99.1% 대 85.9%), 제출물당 LLM 수리와 커버리지에서 대등하면서 학생 프로그램을 27% 덜 건드리며 비용은 21.6배 낮고, 일회성 빌드를 과제당 11건 안에 회수한다. 배포되는 것은 모델이 아니라 읽고 감사할 수 있으며 각 수리를 오개념으로 이름 붙이는 코드다.
Automated program repair can give every student in a programming course immediate feedback, and it is pursued along two lines. Reference-guided repair transplants from the correct programs a class has already submitted and costs nothing per submission, but it fails where the pool holds no structurally matching program. LLM-based repair has no such limit, yet it issues one model query per submission, so spending grows with enrollment and recurs every term while the queries to a single assignment re-read one specification and re-derive a few recurring misconceptions hundreds of times. We present \textsc{CoEP}, in which the model writes the repair \emph{tool} rather than the patch. Once per assignment, a builder LLM turns worked pairs drawn from the class's own submissions into a module of misconception-named AST rewrite rules that runs atop a reference-guided transplant; the frozen tool then repairs submissions with no model at all, and only what it abstains on takes a conventional call. Over 2{,}970 real student submissions across 11 assignments, \textsc{CoEP} beats a reference-guided repairer on both coverage and patch size (99.1\% against 85.9\%), matches per-submission LLM repair on coverage while editing 27\% less of the student's program at 21.6 times lower cost, and repays its one-off build within 11 submissions per assignment. What is deployed is not a model but code that can be read, audited, and that names the misconception behind every repair.
\end{abstract}

\section{Introduction}

% [번역] 매년 수천 명의 학생이 프로그래밍 과목을 수강하고, 온라인 저지에는 같은 문제에 대한 제출물이 수백만 건씩 쌓인다. 수강 인원이 빠르게 늘면서 프로그래밍 과제에 대해 개인화되고 시의적절한 피드백을 주는 일은 교수진에게 상당한 시간과 노력을 요구하는 중대한 과제가 되었다.
Every year, thousands of students enroll in programming courses, and online judges accumulate millions of submissions to the same set of problems. With the rapid growth of Computer Science enrollment, providing personalized and timely feedback on programming assignments has become a significant challenge, requiring substantial time and effort from faculty \citep{itsp2017,refactory2019}.

% [번역] 자동 프로그램 수리(APR)는 학생의 오류에 대해 자동화되고 개인화된 피드백을 주려는 유망한 해법으로 등장했다. 참조 유도 APR은 같은 문제에 대한 정답 프로그램에 버기 프로그램을 정렬한 뒤 어긋나는 영역을 옮겨 심는다. 배포 시점에 모델을 쓰지 않으므로 오프라인에서 결정적으로 돌고 제출물당 추가 비용이 없다. 이 방식의 적용 범위는 정답 프로그램 풀에 구조적으로 맞는 정답 프로그램이 있는지에 달려 있다. 정렬이 불가능하면 도구는 구조 불일치를 보고하고 프로그램은 수리되지 않은 채 반환된다.
Automated Program Repair (APR) has emerged as a promising solution to this challenge, aiming to deliver automated and personalized feedback to students about their programming errors \citep{clara2018,sarfgen2018,refactory2019,verifix2022}. Reference-guided APR aligns a buggy program with a correct program for the same problem and transplants the differing region. It uses no model at deployment, so it runs offline and deterministically at no marginal cost per submission. Its applicability depends on the pool of correct programs containing a structurally matching correct program: when the alignment is not possible, the tool reports a structural mismatch and the program is returned unrepaired \citep{orvalho2025}.

% [번역] 최근에는 코드로 학습된 대형 언어 모델(LLM)이 프로그램 수정 생성에서 큰 가능성을 보였다. LLM 기반 APR은 맞는 참조를 요구하지 않으므로 구조 불일치가 일어나는 곳에서도 동작하며, 입문 과제를 넘어 난이도가 높은 문제까지 다룰 수 있다. 우리가 주목하는 것은 그 배포 방식이다. 기본값은 버기한 제출물 하나마다 모델 질의 하나이므로 지출과 지연, 외부 서비스 의존이 제출물 수에 비례해 늘고 학기마다 다시 발생한다. 게다가 같은 과제에 대한 질의들은 내용의 대부분을 공유한다. 수백 명이 한 문제를 풀고 그 실패는 몇 개의 되풀이되는 오개념으로 뭉치므로, 모델은 같은 명세와 같은 종류의 실수를 반복해서 다시 읽는다. gpt-5.4-mini와 프롬프트 캐싱은 호출 하나의 값을 낮추지만 호출 횟수는 그대로다.
More recently, Large Language Models (LLMs) trained on code have shown great potential in repairing programs \citep{alpharepair2022,chatrepair2024,pydex2024,fastfixer2024,cref2024}. LLM-based APR does not require a matching reference, so it applies where a structural mismatch would otherwise arise, and it extends beyond introductory exercises to harder problems. What concerns us is how it is deployed. The default is one model query per buggy program, so spending, latency, and dependence on an external service all scale with the number of submissions and recur every term. Queries to the same assignment also share most of their content: hundreds of students attempt one problem and their failures cluster into a few recurring misconceptions \citep{clara2018,refactory2019}, so the model re-reads one specification and re-derives one mistake many times over. Cheaper tiers and prompt caching lower the price of a call \citep{anthropiccaching,openaicaching} but leave the number of calls unchanged.

% [번역] 이 논문에서 우리는 모델에게 패치가 아니라 수리 도구를 쓰게 하는 CoEP(Cost-Effective Program repair)를 제안한다. 모델은 제출물마다가 아니라 문제마다 한 번 호출되며, 그 호출의 산출물은 하나의 수리가 아니라 그 문제에 대한 모든 제출물을 처리하는 실행 가능한 프로그램이다. LLM 에이전트가 문제 설명, 테스트 케이스, 그리고 학급의 버기 프로그램에서 군집화로 뽑은 (버기, 수정) 프로그램 쌍을 받아, 자기가 고치는 오개념의 이름을 딴 AST 재작성 규칙들을 작성한다. 이 규칙들은 제네릭 편집 라이브러리와 정답 프로그램 풀로부터의 참조 유도 최소 hunk 이식으로 이루어진 공용 심볼릭 기반 위에서 실행된다. Figure 1이 그런 규칙 하나를 보여준다. cAPS lOCK에서 buggy program 560개 중 108개가 a[1:].isupper()로 단어의 꼬리를 검사하는데, 이는 "Z" 같은 입력의 빈 꼬리에 False가 된다. 이를 제출물 단위로 수리하면 같은 수정을 108번 다시 유도하게 되고, 이식은 길이 가드를 그 주변 구조와 함께 풀에서 들여와야 한다. 대신 규칙 하나가 그 검사식을 제자리에서 다시 써서 108개를 모두 수리하며, 그중 어느 것도 모델은 보지 않았고 배포 시 비용은 들지 않는다. 모든 후보 수정 프로그램은 채택되기 전에 교수자의 테스트 케이스로 검증되므로 도구는 스스로 성공을 보고할 수 없고, 결함이 있는 도구는 잘못된 수리가 아니라 기권으로 퇴화한다. 도구가 기권한 소수만 관례적인 제출물당 호출로 넘어가므로 커버리지는 잃지 않는다. 모델 지출은 제출물 수에 비례하는 한계비용에서 문제 수에 비례하는 고정비용으로 옮겨 가고, 배포된 시스템에는 모델이 남지 않는다. 학생의 제출물이 만나는 것은 읽고 감사할 수 있으며 기관 안에서 오프라인으로 도는 코드다.
In this paper, we propose \textsc{CoEP} (\underline{Co}st-\underline{E}ffective \underline{P}rogram repair), in which the model writes the repair \emph{tool} rather than the patch generation. The model is invoked once per problem instead of once per submission, and the product of that invocation is not a single repair but an executable program that handles every submission to the problem. An LLM agent receives the problem description, its test cases, and a clustered sample of (buggy, fixed) program pairs drawn from the class, and authors AST rewrite rules named after the misconceptions they repair. These rules run atop a shared symbolic substrate of a generic edit library and reference-guided minimal-hunk transplant from the pool of correct programs. Figure~\ref{fig:example} shows one such rule. On cAPS lOCK, 108 of 560 buggy programs test a word's tail with \texttt{a[1:].isupper()}, which is \texttt{False} on the empty tail of an input like \texttt{"Z"}. Repairing them one submission at a time re-derives the same fix 108 times, and a transplant has to bring in a length guard from the pool together with the structure around it. One rule instead rewrites that test in place, repairs all 108, none of which the model saw, and costs nothing at deployment. Every candidate fixed program is validated against the instructor's test cases before it is kept, so the tool can never self-report success, and a defective tool degrades into abstention rather than into a wrong repair. Only the few submissions the tool abstains on escalate to a conventional per-submission call, so coverage is never sacrificed. Model spend therefore moves from a marginal cost that scales with submissions to a fixed cost that scales with problems, and the deployed system retains no model: what a student's submission meets is code that can be read and audited, and that runs offline inside the institution.

% [번역] 실제 학생 제출물 2,970건과 11개 문제로 수행한 실험은 다음을 보인다. 합성된 도구는 최신 심볼릭 수리 도구를 그 도구 자신의 코퍼스와 지표에서 능가해 더 많은 프로그램을 더 작은 패치로 고친다. 제출물당 LLM 수리와 비교하면 커버리지는 대등하면서 학생 프로그램을 더 적게 수정하고, 모델 지출은 그 일부에 그치며, 일회성 빌드 비용은 문제당 수십 건 안에서 회수된다. 절제 실험은 각 층이 무엇을 기여하는지 분리해 보여준다. 도달 범위는 대부분 심볼릭 기반이 만들고, 모델이 작성한 층이 더하는 것은 더 작은 패치와 각 수리가 어떤 오개념에서 비롯됐는지에 대한 이름 붙은 설명이다. 이 둘은 제출물당 호출이 상각할 수 없는 것인데, 호출은 패치를 낳지만 다시 쓸 수 있는 결과물을 남기지 않기 때문이다.
Our experiments with 2{,}970 buggy programs across 11 problems from two corpora, one of course assignments and one of online judge problems, reveal that the synthesized tool outperforms state-of-the-art symbolic repair tools on their own corpus and metric, repairing more programs with smaller patches. Against per-submission LLM repair it matches coverage while modifying less of the student's program, for a fraction of the model spend, and it recovers its one-off build cost within tens of submissions per problem. An ablation separates what each layer contributes: most of the reach comes from the symbolic substrate, and what the authored layer adds is smaller patches and a labelled account of which misconception produced each repair. Those two are what a per-submission call cannot amortize, since a call yields a patch but leaves no reusable artifact behind.

% [번역] 요약하면 이 논문의 기여는 다음과 같다. 모델이 제출물마다 패치를 쓰는 대신 과제당 한 번 수리 도구를 작성하도록 APR을 재정식화하며, 배포된 시스템에는 모델을 남기지 않는다. 오개념 이름 재작성 규칙을 참조 유도 이식 위에 합성하고, 스스로 만들지 못한 수리를 새 규칙으로 증류해 도구를 계속 발전시키는 CoEP를 제시한다. 실제 학생 제출물에 대한 실험은 CoEP가 참조 유도 도구보다 더 많은 프로그램을 더 작은 패치로 수리하고, 제출물당 LLM 수리와 대등하되 비용은 한 자릿수 낮음을 보인다.
In summary, this paper makes the following contributions:
\begin{itemize}
  \item We reformulate APR for programming assignments so that the model authors a repair tool once per assignment rather than a patch per submission, leaving no model in the deployed system;
  \item We present \textsc{CoEP}, which synthesizes misconception-named rewrite rules atop a reference-guided transplant, and keeps developing the tool by distilling the repairs it could not make into new rules;
  \item Experiments on real student submissions show that \textsc{CoEP} repairs more programs with smaller patches than a reference-guided tool, and matches per-submission LLM repair at an order of magnitude lower cost.
\end{itemize}

\section{Related Work}
\label{sec:related}

% [번역] 프로그래밍 과제에 대한 APR. 초기 연구는 학급이 이미 제출한 정답 프로그램을 재사용한다. CLARA와 Sarfgen은 버기 프로그램을 구조적으로 가장 가까운 정답 프로그램에 정렬하고 어긋나는 블록을 옮겨 심으며, Verifix는 그 정렬을 형식 검증으로 뒷받침하고, Refactory는 풀을 버기 프로그램의 구조에 맞게 리팩터링해 정렬 가능한 범위를 넓힌다. 두 번째 계열은 수리 함수를 데이터에서 학습한다. 구문 오류에 대한 시퀀스 모델, 편집 행동에 대한 강화학습, 그리고 (버기, 수정) 프로그램 쌍에서 과제별 변환을 PROSE로 귀납하는 방식이 있다. 최근에는 코드로 학습된 LLM이 이 문제를 직접 다룬다. PyDex는 학생 프로그램을 대상으로 테스트 케이스 거동으로 검색한 유사 정답 프로그램을 few-shot 예시로 붙이고, ChatRepair는 다중 턴 대화를, CREF는 튜터를 루프에 넣으며, FastFixer는 파인튜닝으로 질의당 추론을 가속하고, 최근 연구는 반례 유도 최소 수리와 학습자 맞춤 검색으로 확장한다. 수리 자체와 나란히, OverCode는 학급의 프로그램을 군집화해 어떤 실수가 반복됐는지를 교수자에게 보여준다. 우리 규칙 출처가 수리의 부산물로 내놓는 것과 같은 교수자용 관점이다. 기존 접근들은 심볼릭이든 LLM 기반이든 수리 절차를 사람이 미리 고정하거나 제출물마다 모델이 다시 유도하며, 과제 하나에 대해 다시 쓸 수 있는 결과물을 남기지 않는다. 이 공백을 메우기 위해 우리는 모델이 과제당 한 번 그 결과물을 작성하게 하고, 이후의 모든 제출물을 모델 없이 그것으로 수리한다.
\textbf{APR for programming assignments.} Early work reuses the correct programs a class has already submitted. CLARA and Sarfgen align a buggy program with its structurally nearest correct program and transplant the differing blocks \citep{clara2018,sarfgen2018}, Verifix backs that alignment with formal verification \citep{verifix2022}, and Refactory widens the range of alignable programs by refactoring the pool to match the buggy program's structure \citep{refactory2019}. A second line learns the repair function from data, with sequence models for syntactic errors \citep{deepfix2017}, reinforcement learning over edit actions \citep{rlassist2019}, and PROSE-based induction of per-assignment transformations from (buggy, fixed) program pairs \citep{refazer2017}. Most recently, LLMs trained on code address the problem directly: PyDex targets student programs and prepends similar correct programs retrieved by test-case behaviour as few-shot examples \citep{pydex2024}, ChatRepair adds multi-turn conversation \citep{chatrepair2024}, CREF places a tutor in the loop \citep{cref2024}, FastFixer fine-tunes for faster per-query inference \citep{fastfixer2024}, and recent work extends to counterexample-guided minimal repair \citep{orvalho2025} and learner-tailored retrieval \citep{lsgen2026}. Alongside repair itself, OverCode clusters a class's programs to show an instructor which mistakes recurred \citep{overcode2015}, the same instructor-facing view our rule provenance yields as a by-product of repairing. Existing approaches, symbolic and LLM-based alike, either fix the repair procedure by hand in advance or re-derive it from the model on every submission; neither leaves behind a reusable artifact for the assignment. To remedy this gap, we have the model author that artifact once per assignment, and repair every later submission with it and no model at all.

\section{Approach}
\label{sec:approach}

\subsection{Task Definition}
% [번역] 과제는 자연어 설명 d, 테스트 케이스 집합 T = {t_1, ..., t_n}, 제출물은 테스트 케이스를 하나라도 통과하지 못하는 버기 프로그램 집합 B와 전부 통과하는 정답 프로그램 집합 R로 나뉜다. 버기 프로그램을 수리하는 데 쓰이는 정답 프로그램이 참조 프로그램이므로 R은 참조 프로그램 풀이기도 하다. 버기 프로그램을 수리하면 수정 프로그램 집합 F가 나온다. 개별 원소는 b, r, f로 쓴다. 버기 프로그램 b를 수리한다는 것은 수정 프로그램 f를 만드는 것이고, 그 수리는 f가 T의 모든 테스트 케이스를 통과할 때만 성공으로 친다. 일부만 통과하는 것은 수리가 아니다.
A programming assignment provides a problem description $d$, a set of test cases $T = \{t_1, \dots, t_n\}$, and a set of submissions. Writing $p \models T$ when a program $p$ passes every test case in $T$, the submissions divide into the buggy programs $B = \{p : p \not\models T\}$ and the correct programs $R = \{p : p \models T\}$. Since the correct program used to repair a buggy program is a reference program, $R$ is also the pool of reference programs. Repairing the buggy programs produces a set of fixed programs $F$, with individual members denoted $b$, $r$, and $f$. To repair $b$ is to produce an $f$ with $f \models T$, and nothing weaker counts: an $f$ passing only some test cases is not a repair.

\subsection{Overview}

% [번역] CoEP는 수리 시스템이 하는 두 가지 일을 분리한다(Figure 2). 빌드는 과제당 한 번 일어난다. 모델을 쓰지 않는 로컬 단계가 학급 자신의 제출물을 소수의 작업 쌍으로 바꾸고, 빌더 LLM이 그 쌍들을 d, T, R에서 뽑은 참조 프로그램과 함께 받아 로컬 수리 도구 T를 작성한다. T는 모델 접근이 없는 평범한 파이썬 모듈이다. 수리는 제출물마다 일어나며 언제나 T를 먼저 부른다. 버기 프로그램 b가 주어지면 도구는 비용이 낮은 순서로 세 전략을 시도한다. 자신의 재작성 규칙, 참조 프로그램으로부터의 이식, 그리고 둘 다 기권했거나 로컬 패치가 고치려는 프로그램보다 클 때만 관례적인 모델 호출 한 번이다. T의 모든 테스트 케이스를 통과하는 후보를 처음 내놓은 전략이 수정 프로그램 f를 공급하며, 모델이 개입하는 것은 세 번째뿐이다.
\textsc{CoEP} separates the two things a repair system does (Figure~\ref{fig:arch}). The \emph{build} happens once per assignment. A local step that costs no model call turns the class's own submissions into a small set of worked pairs, and a builder LLM turns those, together with $d$ and $T$, into a \emph{local repair tool} $\mathcal{L}$: an ordinary Python module with no model access. \emph{Repair} happens on every submission and consults $\mathcal{L}$ first. Given a buggy program $b$, the tool tries three strategies in increasing order of cost: its own rewrite rules, a transplant from a reference program, and, only if both abstain or the local patch is larger than the program it repairs, a single conventional model call. Whichever strategy first produces a candidate that passes every test case in $T$ supplies the fixed program $f$, so a model is involved in the third alone.

% [번역] 어디서 멈추는가에 따라 세 구성이 나온다. CoEP_L은 도구만 사용하며 제출물당 CPU 시간 외에는 아무것도 쓰지 않는다. CoEP_LF는 도구가 감당하지 못한 제출물에 대해 모델 호출을 더한다. CoEP_L+SL은 자기 학습을 더한다. fallback이 도구가 놓친 제출물을 수리할 때마다 모델이 그 수리를 이름 붙은 새 규칙으로 일반화하고 도구가 이를 흡수하므로, 과제의 도구는 한 번의 빌드 세션이 만든 상태에 머무르지 않고 학기 동안 나아진다.
Three configurations follow from where we stop. \textsc{CoEP}\textsubscript{L} uses the tool alone and spends nothing per submission beyond CPU time. \textsc{CoEP}\textsubscript{LF} adds the model call for the submissions the tool cannot serve. \textsc{CoEP}\textsubscript{L+SL} adds self-learning: whenever the fallback repairs a submission the tool missed, the model generalizes that repair into a new named rule and the tool absorbs it, so an assignment's tool improves over a semester rather than staying frozen at whatever one build session produced.

\subsection{Build: Local Repair Tool}

% [번역] 작업 쌍. 이 단계는 로컬이며 모델 호출이 없다. 빌더는 B 전체가 아니라 고른 표본을 본다. 프로그램 p의 최상위 문장마다 하나씩, 노드 타입을 너비 우선으로 읽은 수열 σ_i(p)들을 σ(p)라 하고, 두 프로그램 사이 수열들의 일대일 대응 M에 대해 lev를 두 수열 사이 레벤슈타인 거리라 할 때 δ(b,r)를 M에 대한 최소 비용, 즉 min_M [Σ_{(i,j)∈M} lev(σ_i(b),σ_j(r)) + Σ_{i∉M}|σ_i(b)| + Σ_{j∉M}|σ_j(r)|]로 둔다. 대응되지 않은 수열은 길이 전체를 물리므로 빠지거나 남는 정의가 제값을 낸다. 각 버기 프로그램의 짝은 π(b) = argmin_{r∈R} δ(b,r)로, 겉보기에 가장 비슷한 프로그램이 아니라 편집 연산이 가장 적게 드는 참조 프로그램이다. b를 π(b)로 옮기는 편집 연산들의 다중집합을 ε(b)라 쓰며, 노드 타입 수준의 편집이 비면 값 수준 정렬로 대체한다. 잘못된 식별자나 리터럴은 노드 타입만으로는 보이지 않기 때문이다.
\textbf{Worked pairs.} This step is local and costs no model call: the builder sees a \emph{chosen} sample of $B$ rather than all of it. Let $\sigma(p)$ collect the node types of $p$'s AST read in breadth-first order, one sequence $\sigma_i(p)$ per top-level statement, and, with $\mathrm{lev}$ the Levenshtein distance between two such sequences, let $\delta(b,r)$ be the cost of the cheapest one-to-one matching $M$ of $b$'s sequences to $r$'s, $\min_{M} [\sum_{(i,j) \in M} \mathrm{lev}(\sigma_i(b), \sigma_j(r)) + \sum_{i \notin M} |\sigma_i(b)| + \sum_{j \notin M} |\sigma_j(r)|]$, so a missing or surplus definition costs what it is. Every buggy program takes as partner the reference program it is fewest edits from, $\pi(b) = \argmin_{r \in R} \delta(b, r)$, rather than the one that merely looks closest, and $\varepsilon(b)$ is the multiset of edit operations taking $b$ to $\pi(b)$, refined to a value-level alignment when the node-type one comes out empty, since a wrong identifier or literal is invisible to node types alone.

% [번역] 다음으로 ε(b)의 TF-IDF 벡터들 사이 코사인 거리에 대한 평균 연결로 B를 C_1 ⊎ ... ⊎ C_k로 분할하며, k는 평균 실루엣을 최대화하는 값으로 데이터가 정한다. 두 선택 모두 가정이 아니라 측정에서 나왔다. 프로그램 자신의 AST 경로 n-그램이 아니라 ε(b) 위에서 묶는 이유는, 대표로부터 유도한 규칙이 같은 편집을 필요로 하는 원소들에서만 값어치를 하기 때문이다. 모양으로 묶으면 가장 큰 군집이 서로 닮았을 뿐인 프로그램들로 채워진다. k를 고정하지 않는 이유는 고정된 절단 높이가 고정된 k보다 작은 가정이 아니며 우리 과제들 사이에서 여섯 배까지 다른 입도를 낳기 때문이다. 각 군집은 최빈 수리 b*_i = argmax_{b∈C_i} |{b'∈C_i : ε(b')=ε(b)}|, 즉 군집이 가장 많이 동의하는 편집을 가진 원소를 내놓는다. 나머지 두 후보는 편집이 한 번도 반복되지 않는 군집에서만 대비책으로 쓰이며, 그때 b*_i는 메도이드로 퇴화한다. 메도이드는 가장 전형적인 프로그램이지만 대개 여러 결함이 뒤엉킨 것이고, 편집이 가장 작은 원소는 정답에 가장 가까웠던 제출물이라 대변자가 아니라 이상치다. 빌드 집합은 S = {(b*_i, π(b*_i))}이며 δ가 작은 것부터 제시되므로, 약한 빌더도 보여준 변환을 일반화하기만 하면 된다.
We then partition $B = C_1 \uplus \dots \uplus C_k$ by average linkage over cosine distance between TF-IDF vectors of the $\varepsilon(b)$, with $k$ chosen to maximize mean silhouette. Both choices were measured rather than assumed. Clustering on $\varepsilon(b)$ and not on the program's own AST-path $n$-grams, because a rule induced from a representative pays off on the members needing the \emph{same edit}, whereas grouping by shape reliably fills the largest clusters with programs that merely look alike; and $k$ from the data, because a fixed cut height is not a smaller assumption than a fixed $k$ and one constant produced six-fold different granularity across our assignments. Each cluster contributes its \emph{modal} repair, $b^{\star}_i = \argmax_{b \in C_i} |\{b' \in C_i : \varepsilon(b') = \varepsilon(b)\}|$, the member whose edit the cluster most agrees on. The two obvious alternatives survive only as the fallback for a cluster whose edits never repeat, where $b^{\star}_i$ degenerates to the medoid: the medoid is the most typical \emph{program} and is usually a multi-issue tangle, while the smallest edit is the submission that came closest to correct, an outlier rather than a spokesman. The build set is $S = \{(b^{\star}_i, \pi(b^{\star}_i))\}_{i=1}^{k}$, ordered by increasing $\delta$, so a weak builder is shown each buggy program \emph{with} a reference program that repairs it and need only generalize the transformation.

% [번역] 규칙 작성. 빌더 LLM은 (d, T, S)를 과제 전용 도구 L_0으로 바꾼다. T는 예시 8개까지로 제시된다. L_0은 오개념 이름을 달고 실패 증상을 태그한 AST 재작성 규칙들의 모듈이다. 규칙은 후보 생성기, 즉 프로그램 하나를 후보 프로그램 집합으로 보내는 사상 ρ이며 계약은 엄격하다. AST에서 편집 위치를 찾아 소스 구간 치환으로 이어붙이고 모듈 전체를 다시 렌더링하지 않으며, 수정을 주장하는 대신 제안한다. 함수 전체를 다시 쓰지 않으며, 표적 편집을 표현할 수 없거나, 예외를 던지거나, 2초 알람을 넘기면 ρ(p) = ∅이 되어 제출물이 에스컬레이션되게 한다.
\textbf{Rule authoring.} The builder LLM turns $(d, T, S)$, with $T$ shown as up to eight example cases, into the assignment-specific tool $\mathcal{L}_0$: a module of AST rewrite rules, each named after the misconception it targets and tagged with the failure symptoms it addresses. A rule is a \emph{candidate generator}, a map $\rho$ from a program to a set of candidate programs, and the contract is strict. It locates its edit on the AST and splices it as a source-span replacement, never re-rendering the module, which would reformat untouched lines. It proposes rather than claims, and it never rewrites a whole function: a rule that cannot express a targeted edit, that raises, or that runs past a two-second alarm yields $\rho(p) = \emptyset$ and the submission escalates.

% [번역] 생성-검증-정제. 단발 모듈은 자체 결함을 담을 수 있으므로 하네스는 실행 피드백에 기반한 자기 정제 방식으로 빌드 집합 위에서 루프를 닫는다. cov(L)을 아래의 규칙 탐색이 수리하는 S의 비율 |{(b,r) ∈ S : ∃c ∈ L*(b), c ⊨ T}| / |S|로 두며 L*(b)는 그 탐색이 열거하는 후보 집합이다. 이식은 의도적으로 그 바깥에 두어, 각 라운드가 아래의 기반이 아니라 빌더가 쓴 규칙으로 채점되게 한다. 커버리지는 모듈 자신의 주장이 아니라 T를 실제로 실행해 측정한다. cov(L_j) < 1인 동안 하네스는 여전히 실패하는 소스를 돌려주어 L_{j+1}을 얻으며 최대 r_max=3회 빌더 호출까지 반복한다. 프로즌 도구는 L = argmax_{j≤r_max} cov(L_j)이며 동점은 가장 이른 라운드로 간다. 빌드 비용은 이 교환의 토큰 수를 원문자열에서 센 값이다.
\textbf{Generate--validate--refine.} A single-shot module can contain its own defects, so the harness closes the loop on the build set itself, in the manner of self-refinement from execution feedback \citep{selfrefine2023,reflexion2023}. Write $\mathrm{cov}(\mathcal{L})$ for the fraction of $S$ whose buggy half the rule search below repairs, $|\{(b, \cdot) \in S : \exists\, c \in \mathcal{L}^{*}(b),\, c \models T\}| / |S|$, with $\mathcal{L}^{*}(b)$ the candidate set that search enumerates; the transplant sits deliberately outside it, so a round is scored on the rules the builder wrote and not on the substrate underneath them. Coverage is measured by \emph{executing} $T$, never from the module's own claim. While $\mathrm{cov}(\mathcal{L}_j) < 1$ the harness returns the still-failing sources for revision, giving $\mathcal{L}_{j+1}$, for up to $r_{\max}{=}3$ builder calls; the frozen tool is $\mathcal{L} = \argmax_{j \le r_{\max}} \mathrm{cov}(\mathcal{L}_j)$, ties going to the earliest round. Build cost is exactly the token count of these exchanges, measured from the raw strings.

\subsection{Repair: Rules, Reference, LLM}

% [번역] b가 주어지면 프로즌 도구 L은 비용이 낮은 순서로 세 전략을 시도하고 c ⊨ T로 검증되는 첫 후보 c를 반환한다. 이미 b ⊨ T인 제출물은 수정 없이 그대로 반환하며, 이는 벤치마크 자신의 라벨링이 허용하는 경우로 조용히 빼는 대신 크기 0의 수리로 센다. 앞의 두 전략은 모델을 쓰지 않고, 세 번째만 호출을 소비한다.
Given $b$, the frozen tool $\mathcal{L}$ tries three strategies in increasing order of cost and returns the first candidate $c$ it can verify with $c \models T$. A submission that already satisfies $b \models T$ is returned unedited, which the benchmark's own labelling makes possible and which we count as a repair of size zero rather than silently dropping it. The first two use no model; only the third spends a call.

% [번역] 규칙 기반 수리. 규칙들은 층 단위 증상 순서 탐색으로 조합된다. Λ_0 = {b}이고 Λ_{j+1} = (∪_{p∈Λ_j} ∪_{ρ∈L} ρ(p)) \ ∪_{i≤j} Λ_i이며, b의 실패 테스트 서명이 선언 증상이 일치하는 ρ들의 순서를 정한다. Λ_{j+1}의 모든 후보를 Λ_{j+2}를 열거하기 전에 검증하므로 반환되는 수리는 구성상 c ⊨ T를 만족하는 가장 얕은 c이며, L*(b) = ∪_j Λ_j다. 비교 뒤집기와 오프바이원 range·인덱스 이동처럼 어느 학급에나 나오는 실수를 위한 항상 켜진 규칙 몇 개가 빌더가 쓰는 것과 나란히 놓이며, 이는 고전적 변이 연산자 공간의 역산이다. 살아남은 모든 패치는 그것을 만든 규칙 이름 순서를 지니며, 이 출처가 학급 단위 오개념 프로파일로 집계된다.
\textbf{Rule-based repair.} The rules are composed by a symptom-ordered search over layers: $\Lambda_0 = \{b\}$ and $\Lambda_{j+1} = (\bigcup_{p \in \Lambda_j} \bigcup_{\rho \in \mathcal{L}} \rho(p)) \setminus \bigcup_{i \le j} \Lambda_i$, with $b$'s failing-test signature ordering the $\rho$ whose declared symptoms match. Every candidate in $\Lambda_{j+1}$ is validated before $\Lambda_{j+2}$ is enumerated, so the returned repair is by construction the shallowest $c$ with $c \models T$, and $\mathcal{L}^{*}(b) = \bigcup_j \Lambda_j$. A handful of always-on rules for the slips every class makes, comparison flips and off-by-one range and index shifts, sit alongside whatever the builder writes; they invert the classical mutation-operator space \citep{mutants2014,par2013,tbar2019}. Every surviving patch carries the ordered rule names behind it, provenance that aggregates into a per-class \emph{misconception profile}.

% [번역] 참조 기반 수리. 대부분의 학생 버그는 토큰 수준 규칙이 표현하지 못하는 구조적 편집을 필요로 하며 R이 그것을 공급한다. 참조의 변수명을 학생의 것으로 바꾼 뒤(매개변수는 위치로, 지역변수는 첫 등장 순서로) 구조적으로 가장 가까운 참조 8개 각각에 대해, 원본과 변수명을 바꾼 사본 양쪽에서 b와의 차이 hunk를 H(b,r)이라 하고(매개변수는 위치로, 지역변수는 첫 바인딩 순서로), h ⊆ H(b,r)을 적용한 결과를 b ⊕ h라 하자. 1 ≤ |h| ≤ 3인 h 중 바뀐 줄 수가 적은 300개를 검증하고, b ⊕ h ⊨ T를 만족하는 앞의 다섯에 대해 argmin_h RPS(b, b⊕h)를 반환하며 하나도 없으면 기권한다. RPS는 b에서 b⊕h까지의 거리를 b의 크기로 정규화한 값으로 나머지 지표와 함께 Experimental Setup에서 정의하며, 정확한 트리 편집 점수는 통과한 소수에게만 지불된다. 이는 CLARA·Sarfgen·Refactory 계보의 참조 재사용이되 블록이 아닌 hunk 입도이며, 그것이 패치를 손으로 만든 도구보다 작게 유지한다.
\textbf{Reference-based repair.} Most student bugs need a structural edit no token-level rule expresses; $R$ supplies it. Let $H(b, r)$ be the differing line-hunks between $b$ and one of the eight structurally nearest reference programs $r$, taken both raw and with $r$'s variables renamed to the student's, parameters by position and locals by first binding, and let $b \oplus h$ be $b$ with the hunks $h \subseteq H(b,r)$ applied. We validate the 300 smallest $h$ with $1 \le |h| \le 3$ in increasing order of lines changed and return $\argmin_{h} \mathrm{RPS}(b, b \oplus h)$ over the first five satisfying $b \oplus h \models T$, abstaining when none does, so the exact tree-edit score, the distance from $b$ to $b \oplus h$ normalized by the size of $b$ and defined with the other metrics in the Experimental Setup, is paid only on the handful that pass. This is reference reuse in the lineage of CLARA, Sarfgen, and Refactory \citep{clara2018,sarfgen2018,refactory2019}, at hunk granularity rather than the block granularity those systems use.

% [번역] LLM 기반 수리. 관례적 LLM 기반 APR은 각 버기 프로그램 b를 질의 LLM(d,T,b)로 사상한다. CoEP는 그 호출을 로컬 전략이 감당하지 못한 제출물에 남겨두며, 그 비용은 모든 비교에서 CoEP에 청구된다. 로컬 결과를 f_loc이라 하면 호출은 f_loc = fail이거나 RPS(b, f_loc) > 1일 때 발화한다. 기권만이 유일한 트리거가 아닌 이유는 수용 검사가 교수자의 테스트 케이스여서 패치 크기에 대해 아무 말도 하지 않기 때문이다. 이식은 학생 프로그램 전체보다 큰 패치로도 ⊨ T를 만족시킬 수 있는 반면 규칙 층은 표적 편집을 표현할 수 없으면 ∅을 반환해야 한다. 임계값이 이식에 같은 계약을 부과한다. 자기가 고치는 프로그램만큼 큰 패치는 어떤 과제의 기준으로도 수리가 아니라 재작성이기 때문이다. 호출은 빌드와 같은 짝짓기가 주는 최소 편집 참조 프로그램 r = π(b)를 붙여 학생의 전략에 맞춰 강화하며, argmin_{f ∈ {f_loc, LLM(d,T,b,r)}, f ⊨ T} RPS(b,f)를 남기고 둘 다 실패하면 기권하므로 에스컬레이션은 호출을 쓸 수는 있어도 커버리지나 패치 크기를 잃을 수는 없다.
\textbf{LLM-based repair.} Conventional LLM-based APR maps every buggy program to a query $\mathrm{LLM}(d, T, b)$. \textsc{CoEP} keeps that call for the submissions the local strategies cannot serve, and its cost is counted against \textsc{CoEP} in every comparison. Writing $f_{\mathrm{loc}}$ for the local result, it fires when $f_{\mathrm{loc}} = \mathrm{fail}$ or $\mathrm{RPS}(b, f_{\mathrm{loc}}) > 1$, Abstention is not the only trigger because the acceptance test is the instructor's suite, which says nothing about patch size: the transplant can return a $c \models T$ larger than the student's whole program, while the rule layer must return $\emptyset$ whenever it cannot express a targeted edit. The threshold gives the transplant the same contract, since a patch at least as large as the program it repairs is a rewrite, not a repair, under any assignment's standards. The call is strengthened to match the student's strategy by attaching the minimum-edit reference program $r = \pi(b)$, the same pairing the build uses, and we keep $\argmin_{f \in \{f_{\mathrm{loc}},\, \mathrm{LLM}(d,T,b,r)\},\ f \models T} \mathrm{RPS}(b, f)$, abstaining when neither passes, so escalating can cost a call but never coverage or patch size.

% [번역] 임계값은 과제별로 캘리브레이션한 양이 아니라 상수다. 그 값이 적합된 수치가 아니라 정의이기 때문에 그렇게 정했고, 그 선택이 결과를 바꾸는지는 보충 자료가 38개 후보 규칙에 대한 스윕으로 보고하며, 그 전 범위에서 수리율은 움직이지 않는다.
The threshold is a constant rather than a quantity calibrated per assignment. We chose it that way because its value is a definition and not a fitted number; the supplementary material reports a sweep over 38 candidate rules, across which the repair rate does not move.

% [번역] 자기 학습. 에스컬레이션된 쌍 (b, f)에서 LLM이 새 이름 붙은 규칙 ρ'을 쓰고, ∃c ∈ (L ∪ {ρ'})*(b)이 c ⊨ T를 만족할 때만 유지해 L ← L ∪ {ρ'}로 병합한다. 흡수는 평가 패스가 결코 참조하지 않는 스테이징 사본에 기록되므로 어떤 제출물의 결과도 그 앞의 제출물에 의존하지 않으며, 축적된 규칙은 두 번째 프로즌 패스로 평가되고 자기 자신에게 가격이 매겨지는 별도 아티팩트다. 이미 에스컬레이션된 제출물에만 호출을 쓰므로 빌드 주장도 건드리지 않는다.
\textbf{Self-learning.} From an escalated pair $(b, f)$ the LLM writes a new named rule $\rho'$, kept only if $\exists\, c \in (\mathcal{L} \cup \{\rho'\})^{*}(b)$ with $c \models T$, in which case $\mathcal{L} \leftarrow \mathcal{L} \cup \{\rho'\}$. Absorption writes to a staging copy the evaluated pass never consults, so no submission's outcome depends on which preceded it, and the accumulated rules are a separate artifact, evaluated by a second frozen pass and priced to themselves. This is the \textsc{CoEP}\textsubscript{L+SL} configuration; it spends calls only on submissions that already escalated, so it too leaves the build claim untouched.

% [번역] 로컬 경로는 제출물당 약 1~2초에 CPU에서 오프라인으로 돌므로 학생 코드가 기관을 떠나지 않는다. 규칙 적용과 이식 자체는 결정적이지만 그것들에 후보를 공급하는 열거는 벽시계로 제한되므로, 부하가 크면 더 적은 후보만 검토되어 원래라면 고쳤을 것을 기권할 수 있다. 결함 있는 도구는 잘못된 수리를 내놓는 대신 실패하는데, 하네스가 학생이 보기 전에 모든 패치를 재검증하기 때문이다.
The first two strategies run on a CPU in ${\sim}1$--$2$\,s per submission and offline, so no student code leaves the institution. Rule application and transplant are themselves deterministic; the enumeration that feeds them is bounded by a wall clock, so under heavy load fewer candidates are examined and the tool may abstain where it would otherwise repair. A defective tool fails, never returning a wrong repair, because the harness re-validates every patch before a student sees it.

\section{Experiments}

\subsubsection{Research Questions.}

% [번역] RQ1: 수리 도구를 과제당 한 번 합성하는 것이 제출물마다 LLM에 질의하는 것과 비교해 비용에 어떤 영향을 주는가? RQ2: CoEP는 최신 참조 유도 및 LLM 기반 수리 방식과 비교해 프로그래밍 과제를 얼마나 효과적으로 수리하는가? RQ3: LLM이 작성한 규칙 층은 CoEP의 성능에 어떤 영향을 주는가? RQ4: 에스컬레이션된 제출물의 수리를 새 규칙으로 도구에 흡수하는 것은 얼마나 유용한가?
\begin{itemize}
  \item \textbf{RQ1}: What is the cost impact of synthesizing a repair tool once per assignment, compared to querying an LLM once per submission?
  \item \textbf{RQ2}: How effective is \textsc{CoEP} in repairing programming assignments compared to state-of-the-art reference-guided and LLM-based repair approaches?
  \item \textbf{RQ3}: How does the LLM-authored rule layer impact the performance of \textsc{CoEP}?
  \item \textbf{RQ4}: How helpful is it to absorb the repairs of escalated submissions back into the tool as new rules?
\end{itemize}

\subsubsection{Baselines.}
\label{sec:setup}
% [번역] 베이스라인. 프로그래밍 과제 수리의 두 주류 계열과 비교한다. (1) Refactory는 학급의 정답 프로그램을 각 버기 프로그램의 구조에 맞게 리팩터링한 뒤 어긋나는 블록을 옮겨 심는다. 자기 코퍼스에서는 발표된 결과를 인용하고 Codeforces에서는 공개된 도구를 직접 돌린다. (2) PyDex는 각 버기 프로그램을 few-shot 레이아웃으로 모델에 보내고 학급 풀에서 검색한 가장 유사한 (버기, 정답) 예시 셋을 앞에 붙이며, 표본 후보를 테스트 오라클로 거른 뒤 학생 프로그램에 가장 가까운 것을 반환한다. (3) PyDex_PC는 같은 질의를 프롬프트 캐싱으로 다시 매긴다. 공급자는 이전 질의와 선두 접두사가 동일하면 그때 계산한 키·값 텐서를 재사용하게 해주므로, 캐시된 접두사는 입력 요율의 약 10분의 1로 청구되고 다시 인코딩되지도 않는다. CoEP 자체는 세 구성으로 평가한다. CoEP_L은 프로즌 로컬 도구만 쓰고 배포 시 LLM을 쓰지 않으며 테스트 오라클이 통과시키는 패치를 받아들인다. 이는 Refactory와 같은 수용 규칙이다. CoEP_LF는 기권과 RPS가 1을 넘는 로컬 패치에 제출물당 fallback을 더한다. CoEP_L+SL은 자기 학습 규칙을 미리 병합·프리즈한 뒤 CoEP_L을 다시 돌린 것이다.
We compare \textsc{CoEP} against the two mainstream lines of program repair for programming assignments: (1) \textbf{Refactory} \citep{refactory2019}, which refactors the class's correct programs to match each buggy program's structure and transplants the divergent blocks;  (2) \textbf{PyDex} \citep{pydex2024}, which sends each buggy program to the model in its few-shot layout with the three most similar (buggy, correct) exemplars retrieved from the class pool, filters sampled candidates by the test oracle, and returns the survivor closest to the student's program. (3) \textbf{PyDex\textsubscript{PC}} re-prices the same queries under \emph{prompt caching}. Providers let a query reuse the key--value tensors computed for an identical leading prefix of an earlier one, so the cached prefix is billed at roughly a tenth of the input rate and need not be re-encoded \citep{anthropiccaching,openaicaching}. \textsc{CoEP} itself is evaluated in three configurations. \textbf{\textsc{CoEP}\textsubscript{L}} runs the frozen local tool alone with no deployment LLM use, accepting any patch the test oracle passes, which is the acceptance rule Refactory uses. \textbf{\textsc{CoEP}\textsubscript{LF}} adds the per-submission fallback on abstentions and on passing local patches above $\mathrm{RPS}=1$. \textbf{\textsc{CoEP}\textsubscript{L+SL}} re-runs \textsc{CoEP}\textsubscript{L} with the self-learned rules merged and frozen beforehand, so the arm is order-independent; its induction calls are priced to it.

Table~\ref{tab:data}에 나오는 두 개의 실제 학생 코퍼스에서 가져온 11개 문제와 2{,}970개의 버기 프로그램에서 평가한다. 다섯 개 CS1 과제는 1{,}783개의 버기와 2{,}442개의 정답 프로그램을 7.4개의 테스트 케이스로 기여하며, 여섯 개 Codeforces 문제는 1{,}187개의 버기와 698개의 정답을 35.5개의 테스트 케이스로 기여한다. 처음 다섯 개는 Refactory \citep{refactory2019}의 저자들이 발표한 첫해 대학 프로그래밍 과제 제출물이며, 이후 이 문헌의 표준 코퍼스로 채택되었다 \citep{verifix2022,pydex2024,orvalho2025}. 나머지 여섯 개는 Codeforces의 문제로, 공개 온라인 저지 중 하나이며, open-r1 릴리스가 그 제출물을 반영한다 \citep{penedo2025codeforces}; 난이도 등급별로 샘플링하여 Newbie부터 Candidate Master까지 다섯 공식 등급 밴드를 포괄하는 800에서 2000까지 한 단계씩 문제를 선택한다 \citep{cfratings}.
We evaluate on 11 problems and 2{,}970 buggy programs drawn from two real-student corpora (Table~\ref{tab:data}): five CS1 assignments contributing 1{,}783 buggy and 2{,}442 correct programs at 7.4 test cases per assignment, and six Codeforces problems contributing 1{,}187 buggy and 698 correct at 35.5 test cases. The first five are the assignments of a first-year university programming course, with every submission its students actually wrote, released by the authors of Refactory \citep{refactory2019} and since adopted as the standard corpus of this literature \citep{verifix2022,pydex2024,orvalho2025}. The other six are problems from Codeforces, one of the largest public online judges, whose submissions the open-r1 release mirrors \citep{penedo2025codeforces}; we sample them by the difficulty rating, one problem per step from 800 to 2000, covering five official rating bands from Newbie to Candidate Master \citep{cfratings}.

\subsubsection{LLM Configuration.}
% [번역] LLM 설정. 모든 LLM 팔은 공급자당 하나씩 두 모델에서 돈다. 각 공급자에서 프롬프트 캐싱이 동작하는 가장 값싼 티어를 고르는데, 캐싱 베이스라인에 대한 공정성 때문이다. PyDex_PC는 캐싱이 작동해야 경쟁이 되고, 절대 최gpt-5.4-mini는 그것을 배제한다는 것을 실측으로 확인했다.
Every LLM arm runs on two models, one per provider: \textbf{gpt-5.4-mini} (\$0.75/\$4.50 per Mtok) and \textbf{claude-sonnet-5} (\$2/\$10 per Mtok). We select each provider's cheapest tier at which prompt caching is functional, in fairness to the caching baseline: PyDex\textsubscript{PC} only competes if caching can engage, and we verified that the absolute cheapest tiers rule it out: Haiku 4.5 refuses to cache below its 4{,}096-token minimum, above these prompts, and GPT-5.4-nano's automatic caching did not engage on identical 1{,}200-token prompts, whereas both selected models cache at their documented 1{,}024-token minimums.

\subsubsection{Evaluation Metrics.}
% [번역] 평가 지표. 수리율(RR)은 시스템이 수리하는 버기 프로그램의 비율이다. 수정 프로그램이 과제의 모든 테스트 케이스를 통과할 때만 수리로 치며, 일부만 통과하는 수정 프로그램은 수리가 아니다. 상대 패치 크기(RPS)는 버기 AST와 수정 AST 사이의 트리 편집 거리를 버기 프로그램 크기로 나눈 값으로 Refactory의 정의를 다시 구현한 것이며, 각 팔이 수리한 것들에 대해 평균 낸다. 평균 소요 시간 ATT_tot = ATT_cpu + ATT_api는 제출물당 평균 벽시계 초로 로컬 탐색과 모델 지연의 합이다. LLM 비용 C_tot = C_build + C_api는 벤치마크 전체에 대한 미국 달러로 일회성 합성과 제출물당 추론의 합이며 위의 티어 요율로 정확한 토큰 수에서 산정한다. 빌드 국면이 없는 시스템은 C_build = 0이다. 에스컬레이션율 e는 모델 호출을 타는 제출물의 비율이다.
\textbf{Repair rate (RR)} is the percentage of buggy programs a system repairs. A repair counts only when the fixed program passes \emph{all} of the assignment's test cases; a fixed program that passes some of them is not a repair. \textbf{Relative patch size (RPS)} is the tree-edit distance between the buggy and fixed ASTs normalized by buggy program size, reimplemented from Refactory's definition \citep{refactory2019}, and is averaged over what an arm repairs. \textbf{Average time taken} $\mathrm{ATT}_{\mathrm{tot}} = \mathrm{ATT}_{\mathrm{cpu}} + \mathrm{ATT}_{\mathrm{api}}$ is mean wall-clock seconds per submission, local search plus model latency. \textbf{LLM Cost} $C_{\mathrm{tot}} = C_{\mathrm{build}} + C_{\mathrm{api}}$ is US dollars over the whole benchmark, the one-off synthesis plus the per-submission inference, priced at the tiers above from exact token counts; a system with no build phase has $C_{\mathrm{build}} = 0$. The \textbf{escalation rate} $e$ is the fraction of submissions taking a model call.

\subsection{Results}
\label{sec:results}

\subsubsection{RQ1: Cost Effectiveness.}

% [번역] 제출물당 수리에 대한 우리의 문제 제기는 구조적인 것이었다. 지출이 수강 인원과 함께 늘고 매 학기 되풀이되며, 더 값싼 티어나 캐시는 호출 하나의 가격을 낮출 뿐 호출 횟수를 바꾸지 못한다. 이 질문은 호출을 과제당 한 번으로 옮기면 비용이 얼마가 되는지, 일회성 빌드를 회수하려면 제출물이 몇 건 필요한지, 그 배치가 턴어라운드로 무엇을 지불하는지에 답한다. Figure 3은 한 과제가 받는 제출물 수에 대해 그 과제가 쓴 누적 C_tot를 모델마다 그린다. 제출물당 팔은 원점을 지나는 직선이고 기울기는 질의 하나의 가격인 반면 CoEP는 C_build에서 시작해 에스컬레이션하는 비율 e에 대해서만 올라가므로, Δ를 제출물당 한계 절감이라 할 때 두 선은 N* = C_build/(Δ(1−e))에서 만난다. Table 2는 턴어라운드를 로컬 탐색과 그 뒤의 모델 대기로 분해한다.
Our objection to per-submission repair was structural: spending scales with enrollment and recurs every term, and a cheaper tier or a cache lowers the price of a call without changing how many calls are made. This question answers what moving the call to once per assignment costs, how many submissions repay the one-off build, and what the arrangement costs in turnaround. Figure~\ref{fig:cost} plots the cumulative $C_{\mathrm{tot}}$ one assignment spends against the submissions it receives, once per model: a per-submission arm is a line through the origin whose slope is the price of one query, while \textsc{CoEP} starts at $C_{\mathrm{build}}$ and rises only on the fraction $e$ that escalates, so with $\Delta$ the marginal per-submission saving the two cross at $N^{*}=C_{\mathrm{build}}/(\Delta(1-e))$. Table~\ref{tab:att} splits turnaround into local search and the model wait behind it.

(1) 비용에서 CoEP_LF는 벤치마크 전체에 claude-sonnet-5에서 C_tot = $13.58, gpt-5.4-mini에서 $1.00을 쓰는 반면 PyDex는 $292.77과 $28.42로 21.6배와 28.4배다. 프롬프트 캐싱을 적용해도 PyDex_PC는 $263.05와 $23.50에 머물러 여전히 19.4배와 23.5배인데, 캐싱은 공유된 선두 접두사에 값을 매기지만 가변적인 버기 프로그램과 예시가 먼저 와서 동일 접두사가 열 토큰 남짓이기 때문이다. (2) 손익분기에서 한 과제는 PyDex 상대로 제출물 11건, PyDex_PC 상대로 13건에서 빌드를 회수하며 11개 과제 중 10개가 그 지점을 대부분 자릿수만큼 넘었다. N*는 C_build와 Δ가 함께 비례하므로 토큰 가격에 불변이고, 따라서 값싼 모델은 두 팔을 함께 내릴 뿐 교차점을 옮기지 못한다. (3) 턴어라운드에서 ATT_tot는 claude-sonnet-5에서 3.06초 대 14.64초지만 gpt-5.4-mini에서는 3.22초 대 2.14초로, 제출물당 팔이 이길 수 있는 유일한 지표다. 작은 모델이 완성 하나를 돌려주는 것이 우리 탐색이 후보를 열거하고 재실행하는 것보다 빠르기 때문이다. PyDex_PC가 Table 2에 없는 것은 이미 발행된 질의를 다시 보내지 않고 가격만 다시 매긴 팔이어서 턴어라운드가 PyDex와 정확히 같기 때문이다. 앞의 둘을 위해 우리가 지불하는 것은 과제당 평균 22분(5.9~40.0분)의 빌드 시간이며 한 번, 오프라인으로 지불한다. N* 아래에서는 제출물당 수리기가 옳은 도구이고, 모든 팔이 캐싱이 동작하는 최저가 티어에서 돌므로 측정된 격차는 하한이다. 종합하면 호출을 제출물에서 과제로 옮기는 것은 두 모델 모두에서 지출을 한 자릿수 이상 줄이고 열두 건 안에 스스로를 회수하며, 그 대가는 값싼 모델에서의 몇 초다.
Three findings follow. \textbf{(1) In dollars}, \textsc{CoEP}\textsubscript{LF} spends $C_{\mathrm{tot}} = \$13.58$ over the whole benchmark on claude-sonnet-5 and \$1.00 on gpt-5.4-mini, against PyDex's \$292.77 and \$28.42, \textbf{21.6 and 28.4 times} ours; prompt caching leaves PyDex\textsubscript{PC} at \$263.05 and \$23.50, \textbf{still 19.4 and 23.5 times}, because caching pays for a shared leading \emph{prefix} and the variable buggy program and its exemplars come first, leaving an identical prefix of about ten tokens. \textbf{(2) In break-even}, an assignment repays its build after $N^{*}=\textbf{11}$ submissions against PyDex and 13 against PyDex\textsubscript{PC}, and ten of the eleven assignments are past that point, most by an order of magnitude; $N^{*}$ is invariant to token price, since $C_{\mathrm{build}}$ and $\Delta$ scale together, so a cheaper model lowers both arms without moving the crossing. \textbf{(3) In turnaround}, $\mathrm{ATT}_{\mathrm{tot}}$ is 3.06\,s against 14.64\,s on claude-sonnet-5 but 3.22\,s against 2.14\,s on gpt-5.4-mini, the one measure on which a per-submission arm can win, because a small model returns one completion faster than our search enumerates and re-executes candidates. PyDex\textsubscript{PC} is absent from Table~\ref{tab:att}: it re-prices queries PyDex already issued rather than re-issuing them, so its turnaround is PyDex's exactly. What we pay for the first two is 22 minutes of build wall clock per assignment (5.9--40.0), once and offline; below $N^{*}$ a per-query repairer is the right tool, and since every arm runs at the cheapest tier where caching functions the measured gaps are a \emph{floor}. Overall, moving the call from the submission to the assignment cuts spend by more than an order of magnitude on both models and repays itself within a dozen submissions, at a cost of seconds on the cheaper one.

\subsubsection{RQ2: Repair Effectiveness.}

% [번역] 수리기는 두 가지로 판정된다. 몇 건을 고치는가, 그리고 고치면서 학생의 프로그램을 얼마나 건드리는가다. 이 질문은 과제당 한 번 합성된 도구가 두 기준 모두에서 어디에 서는지, 그리고 그 답이 과제마다 어떻게 달라지는지에 답한다. Table 3은 과제별 RR과 RPS를 두 빌더를 합쳐 보고한다. Refactory의 CS1 행은 발표된 수치이고 Codeforces 행은 우리가 공개 도구를 직접 돌린 것이며, RPS는 각 팔이 수리한 것들에 대해 평균 낸 값이므로 수리율이 낮은 팔의 낮은 RPS는 더 쉬운 부분집합을 뜻한다.
A repairer is judged on two things: how many submissions it fixes, and how much of the student's program it disturbs while fixing them. This question answers where a tool synthesized once per assignment stands on both, and how that varies across assignments. Table~\ref{tab:effect} reports per-assignment RR and RPS with the two builders pooled; RPS is averaged over what each arm repairs, so a low RPS beside a low repair rate means an easier subset rather than a better patch.

% [번역] 세 가지 발견이 따라 나온다. (1) 심볼릭 베이스라인 대비, 로컬 도구만으로 도는 CoEP_L이 99.1%를 평균 RPS 0.463에 수리하는 데 반해 Refactory는 85.9%를 0.500에 수리하며, 11개 과제 전부에서 우리 수리율이 그들 이상이다. Refactory 자신의 코퍼스에서도 98.5% 대 90.8%, RPS 0.306 대 0.397로 패치가 4분의 1 작다. 이는 배포 시 모델 호출이 0인 상태에서 얻은 값이다. (2) 제출물당 LLM 수리 대비, 커버리지는 사실상 같은 자리에 있다. CoEP_L 99.1%, PyDex 98.9%이고 에스컬레이션을 더한 CoEP_LF가 99.7%로 11개 중 10개 과제에서 100%에 도달한다. 갈라지는 것은 패치 크기로 0.463 대 0.634, 즉 27% 작으며 CoEP_LF는 0.410으로 35% 작다. 과제별로 보면 CoEP_L이 11개 중 10개에서, CoEP_LF는 11개 전부에서 PyDex보다 작은 패치를 낸다. (3) 과제별 행은 코퍼스 평균이 감추는 것과 그것을 예측하는 것을 함께 보여준다. Refactory의 수리율은 40.3%에서 100%까지 흔들리는 반면 어떤 LLM 팔도 93.8% 아래로 내려가지 않으며, 그 진폭은 문제의 난이도가 아니라 참조 풀의 깊이를 따라간다. 난이도 대역으로 묶으면 Refactory는 CS1의 90.8%에서 Codeforces 800~1000의 83.1%, 1200~2000의 54.5%로 떨어지는데 그 구간에서 풀이 정답 몇 개 수준으로 얇아지기 때문이며, CoEP_LF는 99.5/100.0/100.0을 유지한다. 전략이 갈라지면 블록 수준 재사용이 굶고, C5의 77건은 정답 2개짜리 풀에 의존한다. 낮은 RPS가 늘 미덕인 것도 아니다. Codeforces에서 Refactory의 0.679는 CoEP_LF의 0.597에 견줄 만해 보이지만 그것은 자신이 수용한 78.6%에 대해 평균 낸 값이고 그 위에서 CoEP_LF는 100%를 수리한다. 두 빌더를 합친 것이 무엇을 감추지도 않는다. 따로 보면 99.66%/0.404와 99.73%/0.417로 빌드 가격 18배 차이에 패치 크기는 3% 차이다. 종합하면 합성된 도구는 심볼릭 도구를 커버리지와 패치 크기 양쪽에서 이기고, 제출물당 LLM 수리와는 커버리지에서 대등하되 학생 프로그램을 3분의 1 덜 건드리며, 어느 빌더가 쓰든 그렇다.
Three findings follow. \textbf{(1) Against the symbolic baseline}, the local tool alone repairs \textbf{99.1\%} at mean RPS \textbf{0.463} where Refactory repairs 85.9\% at 0.500, and its repair rate is at least Refactory's on every one of the eleven assignments. On Refactory's own corpus the same holds, 98.5\% against its published 90.8\% at 0.306 against 0.397, a patch a quarter smaller, and all of it at zero marginal LLM cost. \textbf{(2) Against per-submission LLM repair}, coverage is level: \textsc{CoEP}\textsubscript{L} reaches 99.1\% and PyDex 98.9\%, and adding the escalation tail takes \textsc{CoEP}\textsubscript{LF} to \textbf{99.7\%}, at 100\% on ten of the eleven assignments. What separates the arms is patch size, \textbf{0.463} against \textbf{0.634}, 27\% smaller, and 0.410 for \textsc{CoEP}\textsubscript{LF}, 35\% smaller; per assignment, \textsc{CoEP}\textsubscript{L} leaves the smaller patch on ten of eleven and \textsc{CoEP}\textsubscript{LF} on all eleven. \textbf{(3) The per-assignment rows} show what a corpus mean hides, and what predicts it. Refactory's rate swings from 40.3\% to 100\% while no LLM arm drops below 93.8\%, and the swing tracks the depth of the reference pool rather than the difficulty of the problem: grouped into bands, Refactory falls 90.8\% on CS1 to 83.1\% on Codeforces 800--1000 to \textbf{54.5\%} on 1200--2000, where the pools thin to a handful of correct programs, while \textsc{CoEP}\textsubscript{LF} holds 99.5/100.0/100.0. Block-level reuse starves when strategies diverge, and C5's 77 submissions draw on a pool of two. A low RPS is not always a virtue either: Refactory's 0.679 on Codeforces looks competitive against \textsc{CoEP}\textsubscript{LF}'s 0.597, but it is averaged over the 78.6\% it accepts, where \textsc{CoEP}\textsubscript{LF} repairs 100\%. Pooling the two builders hides nothing, finally: separately they reach 99.66\% at 0.404 RPS and 99.73\% at 0.417, three per cent apart in patch size for an eighteen-fold difference in build price. Overall, the synthesized tool beats the symbolic one on both coverage and patch size, matches per-submission LLM repair on coverage while disturbing a third less of the student's program, and does so on whichever builder writes it.

\subsubsection{RQ3: Ablation Study.}

% [번역] 앞의 두 질문은 도구를 하나의 덩어리로 다뤘다. 이 질문은 그것을 열어, 모델이 작성한 규칙이 그 아래의 심볼릭 기반 위에 실제로 무엇을 더하는지 묻는다. framework-only 절제가 그것을 격리한다. 작성 규칙만 제거하고 항상 켜진 규칙과 이식은 그대로 둔 동일한 도구이며, 빌더와 무관하게 정확히 같은 아티팩트인데 남는 층에 모델이 쓴 것이 하나도 없기 때문이다. Figure 4는 절제가 작용하는 그 분해를 보여준다. 어느 전략이 각 수리를 만들었는지를 과제별로 그린 것이다.

A \emph{framework-only} ablation isolates that: the identical tool with the builder's rules removed and the always-on ones and the transplant left in place, which is the same artifact under either builder because nothing the model wrote survives in it. % [번역] 세 가지 발견이 따라 나온다. (1) 작성 층이 사는 것은 도달 범위가 아니라 패치 품질이다. 제거하면 수리율은 99.06%에서 98.69%로 0.37포인트만 떨어지지만 평균 패치는 0.463에서 0.492로 6% 커진다. 대가가 떨어지는 자리는 규칙이 실제로 일하던 곳이다. C6에서 패치가 0.125, C2에서 0.079 커지고 커버리지를 잃는 유일한 과제는 R2로 2.53포인트다. C4는 반대로 움직여 규칙이 없을 때 0.040 작아지는데 거기서는 이식이 발화하는 규칙보다 작은 편집을 찾는다. (2) 커버리지가 거의 움직이지 않는 이유는 층들의 분담에 있다. 이식이 수리된 제출물의 75.4%를 평균 RPS 0.581에 처리하는 반면 규칙은 24.6%를 0.100에, 즉 여섯 배 가까이 작은 패치로 처리한다. 작성 규칙을 빼면 이식이 그 일을 흡수하지만 표적 편집이 아니라 구조적 편집으로 흡수하므로 패치가 커지고, 오개념 라벨도 함께 사라진다. 규칙 층이 진단을 남기는 유일한 층이므로, 그것을 빼면 진단 커버리지가 수리의 24.6%에서 0이 된다. (3) 분담은 균일하지 않고 출처 로그가 그 이유를 말한다. 빌더가 쓴 규칙 중 발화한 것은 127개로 도합 1,216회 발화했지만, 그중 두 과제 이상에서 발화한 것은 단 하나다. 작성 층은 구성상 과제 전용이며 이 학급이 무엇을 틀렸는지를 부호화한다. 풀이 깊은 곳에서는 이식이 지배하지만 한 오개념이 학급을 지배하는 곳에서는 작성 층이 넘겨받아, C4에서는 claude-sonnet-5가 쓴 규칙 하나가 38건 중 27건을 수리한다. 종합하면 도달 범위는 심볼릭 기반이 만들고, 모델이 사는 것은 더 작은 패치와 각 수리가 어떤 오개념에서 비롯됐는지에 대한 이름 붙은 설명이다. 이 둘은 제출물당 호출이 상각할 수 없는 것인데, 호출은 패치를 낳지만 다시 쓸 수 있는 결과물을 남기지 않기 때문이다.
Three findings follow. \textbf{(1) What the authored layer buys is patch quality, not reach.} Removing it costs \textbf{0.37} points of repair rate, 99.06\% to 98.69\%, and inflates the mean patch \textbf{6\%}, 0.463 to 0.492. The cost lands where the rules were doing real work: C6's patches grow 0.125 and C2's 0.079, and R2 is the only assignment that loses coverage, by 2.53 points. C4 moves the other way, 0.040 smaller without the rules, because there the transplant finds a smaller edit than the rule that fires. \textbf{(2) Coverage barely moves because of how the layers divide the work.} The transplant produces \textbf{75.4\%} of repaired submissions at mean RPS 0.581, while the rules produce \textbf{24.6\%} at \textbf{0.100}, a patch nearly six times smaller. Take the authored rules away and the transplant absorbs their share, but with a structural edit rather than a targeted one, which is why the patch grows; the misconception label goes with them: the rule layer is the only one that leaves a diagnosis behind, so removing it takes diagnostic coverage from 24.6\% of repairs to none. \textbf{(3) The division is not uniform, and the provenance logs say why.} The builders wrote 127 rules that fired, 1{,}216 times between them, but only one of those ever fired on more than one assignment. The layer is assignment-specific by construction: it encodes what \emph{this} class got wrong. Where the pool is deep the transplant dominates, and where one misconception dominates a class the authored layer takes over, as on C4, where a single rule claude-sonnet-5 wrote repairs 27 of 38 submissions. Overall, the reach comes from the symbolic substrate and what the model buys is smaller patches and a labelled account of which misconception produced each repair, neither of which a per-submission call can amortize, since a call yields a patch but leaves no reusable artifact behind.

% [번역] 프로즌 도구는 자신이 고치지 못한 것을 기록으로 남긴다. 그 놓친 건을 fallback이 고쳐 주면 모델이 그 수정을 이름 붙은 규칙으로 일반화하고, 증강된 도구가 그 건을 스스로 다시 고칠 때만 규칙을 유지한다. 이 질문은 그렇게 얻은 규칙이 자신이 유도된 제출물 밖에서도 통하는지에 답한다. 흡수는 평가 패스가 참조하지 않는 스테이징 사본에 기록되고 증강된 도구는 이 팔이 돌기 전에 프리즈되므로 비교는 순서와 무관하다. 같은 제출물, 같은 수용 규칙, 두 개의 규칙 집합이다. Figure 5가 그 건들이 어떻게 되는지를 보여준다.
The frozen tool leaves a record of what it could not repair. When the fallback then repairs one of those misses, the model generalizes that fix into a named rule, and the rule is kept only if the augmented tool repairs the miss on its own. This question answers whether such a rule holds outside the submission it was induced from. Absorption writes to a staging copy the evaluated pass never consults and the augmented tool is frozen before this arm runs, so the comparison is order-independent: the same submissions, the same acceptance rule, two rule sets. Figure~\ref{fig:learn} follows what becomes of them.

% [번역] 두 가지 발견이 따라 나온다. (1) 재료가 드물고 문턱이 높다. 두 빌더의 패스를 합쳐 CoEP_L이 못 고친 것은 5,940건 중 56건뿐이며, 그중 fallback이 고쳐 주어 규칙 생성을 시도한 것이 38건이다. 그 38번의 시도에서 살아남은 규칙은 8개인데, 증강된 도구가 그 놓친 건을 스스로 다시 고쳐야만 유지하기 때문이다. 이는 기전의 실패가 아니라 99.06% 로컬 수리율이 의미하는 바다. (2) 살아남은 규칙은 유도된 건 너머로 일반화된다. 8개 전부가 이후 실제 수리에 쓰였고 합쳐서 21건을 되찾았는데, 그것들을 유도한 것은 8건뿐이므로 13건은 그 규칙이 한 번도 본 적 없는 프로그램이다. 퇴행은 1건으로 순증은 20건이며, 유도 비용은 결과물에 가격 매겨진 $0.76이다. 값싼 빌더가 더 많이 얻는다는 점은 말할 가치가 있다. 재료는 어느 쪽이든 R2의 같은 27건 기권이고 다른 것은 모델이 수정 하나에서 얼마나 일반적인 규칙을 쓰느냐다. 종합하면 자기 학습은 도구가 실패한 곳에서만 발화하고 그런 곳이 드물지만, 발화하면 유도된 건 너머로 일반화되며 그 비용은 과제당 1달러 미만이다.
Two findings follow. \textbf{(1) The material is scarce and the bar is high.} Over both builders' passes \textsc{CoEP}\textsubscript{L} fails on \textbf{56} of 5{,}940 submissions, and the fallback repairs \textbf{38} of those, which are the misses induction is attempted on. Those 38 attempts leave \textbf{8} rules, because a rule survives only if the augmented tool then repairs the miss on its own. That scarcity is not a failure of the mechanism but what a 99.06\% local repair rate means. \textbf{(2) The rules that survive generalize past the submissions that induced them.} All eight went on to repair, recovering \textbf{21} submissions between them, and since eight submissions induced them, \textbf{13} of those 21 are programs the rules had never seen. One submission regressed, so the net is 20, and the induction cost \$0.76 priced to the artifact. The cheaper builder gains more, on the same 27 abstentions on R2, which says the gain depends on how general a rule the model writes from one fix rather than on how much material it is given. Overall, self-learning fires only where the tool failed and such places are rare, but where it fires the rules carry past their own examples, for under a dollar per assignment.

\section{Discussion}

% [번역] 규칙은 세 층위로 나뉜다. 빌더가 무엇을 쓰는지 보면 규칙이 하나의 종류가 아니라 일반성의 세 층위로 갈리고, 그 층위가 재사용 범위를 결정한다. 가장 일반적인 층은 언어 차원의 실수를 잡는다. add_missing_call_parens는 스스로를 "x.pop이나 x.reverse가 괄호 없이 문장이나 반환값으로 쓰였다"고 설명하는데, 이는 어떤 과제에도 없는 파이썬 자체의 함정이다. 빌더가 쓴 128개 규칙 중 두 과제 이상에서 발화한 유일한 규칙이 이것이고 R3과 C2에서 10건을 수리했다. 중간 층은 그 문제의 오개념을 잡는다. slice_case_check_to_equality는 "slice.isupper()가 한 글자 단어의 빈 슬라이스에서 실패한다"고 설명하며 C2에서 115건, 즉 그 과제 규칙 수리의 대부분을 처리한다. 다른 과제로 옮길 수는 없지만 이 과제를 낸 어느 학급에서나 통한다. 가장 특화된 층은 문제 서술 자체에 묶인다. carry_fix_two_value_print는 "인치가 12가 될 수 있는 '피트를 먼저 계산하고 나머지를 나중에 반올림하는' 오개념"을 고치려 최종 출력 앞에 인치→피트 올림 검사를 넣으며, C4의 38건 중 27건을 혼자 수리한다. 이 규칙은 다른 과제에서 의미가 없다. 따라서 작성 층이 과제 전용이라는 것은 결함이 아니라 층위의 함수다. 학급을 덮는 규칙은 그 학급의 오개념 수준에서 쓰이기 때문에 과제를 넘지 못하고, 과제를 넘는 규칙은 애초에 과제에 대해 아무것도 모르기 때문에 넘는다.
\textbf{Rules come at three levels of generality.} What the builder writes is not one kind of thing, and the level predicts how far a rule travels. The most general level catches a language slip. \texttt{add\_missing\_call\_parens} describes itself as ``\texttt{x.pop} / \texttt{x.reverse} used as a statement or return value without \texttt{()}'', a Python trap that belongs to no assignment; it is the only one of the builders' 128 rules that ever fired on two assignments, repairing 10 submissions across R3 and C2. The middle level catches the misconception of one problem. \texttt{slice\_case\_check\_to\_equality} explains that ``\texttt{slice.isupper()} fails on empty slices (single char words)'' and repairs 115 submissions on C2, most of that assignment's rule-produced repairs; it cannot move to another problem but it would work for any class given this one. The most specific level is tied to the problem statement itself: \texttt{carry\_fix\_two\_value\_print} inserts an inch-to-foot carry check before the final print, fixing what it calls the ``compute feet first, round remainder second'' misconception, and repairs 27 of C4's 38 submissions on its own. That the authored layer is assignment-specific is therefore not a defect but a consequence of level. A rule that covers a class is written at the level of that class's misconception and so cannot cross assignments; a rule that crosses assignments does so because it knows nothing about the assignment.

% [번역] 부산물로 얻는 오개념 프로파일. 규칙이 만든 모든 패치는 그것을 만든 규칙 이름을 지니므로, 학급 단위로 집계하면 교수자가 읽을 수 있는 보고서가 된다. R2에서 규칙이 수리한 145건은 다음과 같이 갈린다. count_compare_relax 112건, undefined_domain_var_rename 28건, missing_return_false_append 22건, month_day_index_fix 7건이다. 이는 패치 목록이 아니라 이름 붙은 실수의 도수분포이며, 학급의 3분의 2가 같은 비교 오류를 냈다는 사실을 교수자에게 곧바로 말해 준다. 이 보고서는 수리의 부산물로 추가 비용 없이 나오고, 제출물당 API는 어떤 가격으로도 이를 방출하지 않는다. 호출은 패치를 낳지만 이름을 남기지 않기 때문이다.
\textbf{A misconception profile falls out of repairing.} Every rule-produced patch carries the name of the rule that produced it, so aggregating over a class yields a report an instructor can read. On R2 the 145 rule-produced repairs divide as \texttt{count\_compare\_relax} 112, \texttt{undefined\_domain\_var\_rename} 28, \texttt{missing\_return\_false\_append} 22, and \texttt{month\_day\_index\_fix} 7. That is not a list of patches but a frequency table of named mistakes, and it says at once that two thirds of the class made the same comparison error. The report costs nothing beyond the repairing, and a per-submission API emits none of it at any price, because a call yields a patch but leaves no name behind.


\section{Conclusion}

% [번역] 우리는 프로그래밍 과제에 대한 APR에서 모델 호출의 단위를 제출물에서 과제로 옮겼다. 모델은 패치를 쓰는 대신 수리 도구를 한 번 작성하고, 그 도구는 오개념 이름을 단 재작성 규칙을 참조 유도 이식 위에서 실행하며 모든 패치를 교수자의 테스트로 검증한다. 배포된 것은 모델이 아니라 읽고 감사할 수 있는 코드이고 기관 안에서 오프라인으로 돈다. 실제 학생 제출물 2,970건과 과제 11개에서 이 도구는 참조 유도 도구를 커버리지와 패치 크기 양쪽에서 이기고, 제출물당 LLM 수리와 커버리지에서 대등하면서 학생 프로그램을 27% 덜 건드리며 비용은 21.6배 낮고, 일회성 빌드를 과제당 11건 안에 회수한다. 절제는 우리가 예상하지 못한 답을 준다. 도달 범위의 대부분은 심볼릭 기반이 만들고 모델이 사는 것은 더 작은 패치와 각 수리가 어떤 오개념에서 비롯됐는지에 대한 이름 붙은 설명이다. 그리고 그 둘이야말로 제출물당 호출이 상각할 수 없는 것인데, 호출은 패치를 낳지만 다시 쓸 수 있는 결과물을 남기지 않기 때문이다. 도구는 빌드 시점에 고정되지도 않는다. 스스로 만들지 못한 수리는 새 규칙으로 증류되어 남으므로 아티팩트는 자신이 담당하는 과제와 함께 발전한다. 같은 처방은 하나의 명세를 많은 제출물이 공유하는 곳이라면 어디에나 적용된다.
We moved the unit of model invocation in APR for programming assignments from the submission to the assignment: rather than write a patch, the model writes a repair tool once, and that tool runs misconception-named rewrite rules over a reference-guided transplant, validating every patch against the instructor's test cases. What is deployed is not a model but code that can be read and audited, and that runs offline inside the institution. Over 2{,}970 real student submissions across 11 assignments the tool beats a reference-guided repairer on both coverage and patch size, matches per-submission LLM repair on coverage while editing 27\% less of the student's program at 21.6 times lower cost, and repays its one-off build within 11 submissions per assignment. The ablation gives an answer we did not expect: most of the reach comes from the symbolic substrate, and what the model buys is smaller patches and a labelled account of which misconception produced each repair. Those two are exactly what a per-submission call cannot amortize, since a call yields a patch but leaves no reusable artifact behind. Nor is the tool fixed at its build, since the repairs it could not make are distilled into new rules it keeps, so the artifact develops alongside the assignment it serves. The same recipe applies wherever many submissions share one specification.
